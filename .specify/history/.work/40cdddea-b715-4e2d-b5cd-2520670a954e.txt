## Integration 架构详解

### 核心设计思想

Integration 架构解决的核心问题是：**Spec Kit 需要为 30+ 种不同的 AI coding assistant 生成各自格式的命令文件**。每个 AI 工具有自己的文件格式、目录结构和调用约定。旧架构用大量 `if/else` 和硬编码配置处理，新架构用 OOP 插件化彻底重构。

### 整体架构图

```
IntegrationBase (ABC)                     ← 抽象基类，定义所有契约
├── MarkdownIntegration                   ← 标准 Markdown 命令格式 (~20个 agent)
│   ├── WindsurfIntegration               ←   3 行代码定义一个集成
│   ├── RooIntegration
│   ├── CursorAgentIntegration
│   └── ... (约20个)
├── TomlIntegration                       ← TOML 命令格式
│   ├── GeminiIntegration
│   └── TabnineIntegration
├── YamlIntegration                       ← YAML recipe 格式
│   └── GooseIntegration
└── SkillsIntegration                     ← Skills (SKILL.md) 格式
    ├── ClaudeIntegration                 ←   带 argument-hint 等特化逻辑
    ├── CodexIntegration
    ├── KimiIntegration
    └── ... (约8个)

INTEGRATION_REGISTRY: dict[str, IntegrationBase]   ← 全局注册表
IntegrationManifest                                 ← 哈希追踪安装清单
IntegrationCatalog                                  ← 发现/搜索/版本管理
IntegrationDescriptor                               ← integration.yml 描述符
```

### 1. 基类层次 (`base.py`)

**`IntegrationBase`** — 抽象基类，每个集成必须实现：

| 属性 | 用途 |
|------|------|
| `key` | 唯一标识符，匹配 CLI 工具名（如 `"claude"`, `"windsurf"`) |
| `config` | 元数据字典：名称、输出目录、子目录、是否需要 CLI |
| `registrar_config` | 命令注册配置：目录、格式、参数占位符、文件扩展名 |
| `context_file` | agent context 文件路径（如 `CLAUDE.md`、`.github/copilot-instructions.md`） |

核心方法：

- **`setup()`** — 安装命令文件到项目，写入 agent context section
- **`teardown()`** — 卸载命令文件，移除 context section
- **`process_template()`** — 模板处理管线：提取 script → 替换 `{SCRIPT}`/`{ARGS}`/`__AGENT__`/`__CONTEXT_FILE__` → 路径重写 → 命令引用替换
- **`build_exec_args()`** — 构建非交互式 CLI 执行参数
- **`dispatch_command()`** — 通过 CLI 分发 Spec Kit 命令
- **`upsert_context_section()`** — 在 context 文件中用 marker 管理 managed section

四个具体基类处理不同输出格式：

```python
# MarkdownIntegration — 最常见，~20个agent用这个
# 输出: .md 文件，YAML frontmatter + markdown body

# TomlIntegration — Gemini, Tabnine
# 输出: .toml 文件，description + prompt 键

# YamlIntegration — Goose
# 输出: .yaml recipe，带 version/title/description/prompt block scalar

# SkillsIntegration — Claude, Codex, Kimi 等
# 输出: speckit-<name>/SKILL.md 目录结构 (agentskills.io 规范)
```

### 2. 定义新集成有多简单

以 Windsurf 为例（`windsurf/__init__.py`），**仅需 12 行**：

```python
class WindsurfIntegration(MarkdownIntegration):
    key = "windsurf"
    config = {
        "name": "Windsurf",
        "folder": ".windsurf/",
        "commands_subdir": "workflows",
    }

        "dir": ".windsurf/workflows",
        "format": "markdown",
        "args": "$ARGUMENTS",
        "extension": ".md",
    }
    context_file = ".windsurf/rules/specify-rules.md"
    multi_install_safe = True
```

设三个类属性，继承 `MarkdownIntegration`，完成。`setup()`、`teardown()`、模板处理、manifest 追踪全部自动继承。

### 3. 全局注册表 (`__init__.py`)

```python
INTEGRATION_REGISTRY: dict[str, IntegrationBase] = {}

def _register(integration: IntegrationBase) -> None:
    INTEGRATION_REGISTRY[integration.key] = integration

def get_integration(key: str) -> IntegrationBase | None:
    return INTEGRATION_REGISTRY.get(key)
```

`_register_builtins()` 在模块加载时注册所有 33 个内置集成。CLI 通过 `get_integration("claude")` 获取实例。

### 4. Manifest 系统 (`manifest.py`)

**`IntegrationManifest`** 用 SHA-256 哈希追踪安装的每个文件：

```
.specify/integrations/claude.manifest.json
{
  "integration": "claude",
  "version": "0.11.1",
  "installed_at": "2026-06-17T...",
  "files": {
    ".claude/skills/speckit-plan/SKILL.md": "a1b2c3...",
    ".claude/skills/speckit-specify/SKILL.md": "d4e5f6...",
    ...
  }
}
```

关键行为：
- **安装时** — `record_existing()` / `record_file()` 记录文件路径 + SHA-256
- **卸载时** — 只删除哈希未变的文件（用户修改过的跳过并报告）
- **升级时** — 与前次 manifest 对比，旧有但新无的文件视为 stale 删除
- **`recovered_files`** — 标记安装时已存在的文件（观察到的，非产生的），防止覆盖用户自定义

安全防护：
- 路径遍历检查（阻止 `..` 和绝对路径）
- 符号链接检查（拒绝跟随 symlink 写入/删除）
- 原子写入（tempfile → `os.replace`）

### 5. Catalog 系统 (`catalog.py`)

支持集成的发现、搜索和版本管理：

```python
class IntegrationCatalog:
    DEFAULT_CATALOG_URL = ".../integrations/catalog.json"       # 官方
    COMMUNITY_CATALOG_URL = ".../integrations/catalog.community.json"  # 社区

    def remove_catalog(index)                         # 移除源
```

Catalog 解析顺序：
1. `SPECKIT_INTEGRATION_CATALOG_URL` 环境变量

## Workflow Engine 详解

### 架构概览

Workflow Engine 是一个 **YAML-driven 的流程编排引擎**，允许用户定义多步骤、带控制流的自动化工作流。

```
src/specify_cli/workflows/
├── engine.py          ← 核心引擎：加载、验证、执行
├── base.py            ← 基类：StepBase, StepContext, StepResult, 枚举
├── expressions.py     ← 沙箱表达式求值器 ({{ }} 模板)
├── catalog.py         ← Workflow catalog 发现/安装
└── steps/             ← 步骤类型（插件化）
    ├── command/       ← 调用 AI agent 执行 speckit 命令
    ├── shell/         ← 执行本地 shell 命令
    ├── prompt/        ← 交互式用户输入
    ├── gate/          ← 人工审批门控
    ├── if_then/       ← 条件分支
    ├── switch/        ← 多路分支
    ├── while_loop/    ← while 循环
    ├── do_while/      ← do-while 循环
    ├── fan_out/       ← 批量展开（遍历集合）
    ├── fan_in/        ← 汇聚结果
    └── init/          ← 项目初始化步骤
```

### 核心数据模型

```python
class StepContext:
    inputs: dict          # 工作流输入参数
    steps: dict           # 已执行步骤的结果 (key=step_id)
    item: Any             # fan-out 迭代时当前项
    run_id: str           # 运行 ID

class StepResult:
    status: StepStatus    # completed/failed/paused/skipped
    output: dict          # 步骤输出数据
    next_steps: list      # 控制流产生的后续步骤（if/while）
    error: str | None

class RunState:            # 持久化到 .specify/workflows/runs/<run_id>/
    run_id: str
    status: RunStatus     # created/running/paused/completed/failed/aborted
    step_results: dict
    inputs: dict
```

### Workflow YAML 示例

```yaml
schema_version: "1.0"
workflow:
  id: spec-to-tasks
  name: Spec to Tasks
  version: "1.0.0"
  integration: auto        # 从项目配置读取

inputs:
  feature:
    type: string
    required: true
  model:
    type: string
    default: "claude-sonnet-4-6"

steps:
  - id: specify
    type: command
    command: specify
    input: "{{ inputs.feature }}"

  - id: check-spec
    type: shell
    run: "cat specs/{{ inputs.feature }}/spec.md | wc -l"
    output_format: json     # stdout 解析为 JSON → output.data

  - id: gate-review
    type: gate
    message: "Review the spec at specs/{{ inputs.feature }}/spec.md"
    show_file: "specs/{{ inputs.feature }}/spec.md"

  - id: plan
    type: command
    command: plan
    continue_on_error: true  # 失败不中断

  - id: generate-tasks
    type: fan-out
    items: "{{ steps.plan.output.data | from_json }}"
    step:
      id: task
      type: command
      command: implement
      input: "{{ item.description }}"
```

### 表达式系统 (`expressions.py`)

沙箱 Jinja2 子集，**无文件 I/O 和代码执行能力**：

```
{{ inputs.feature }}                    ← 输入引用
{{ steps.plan.output.task_count }}      ← 步骤输出引用
{{ steps.shell.output.stdout | from_json }}   ← JSON 解析 filter
{{ items | map('name') | join(', ') }}  ← 链式 filter
{{ context.run_id }}                    ← 运行时元数据
```

支持的 filter: `default`, `join`, `map`, `contains`, `from_json`
支持的操作: `==`, `!=`, `>`, `<`, `and`, `or`, `not`, `in`, `not in`

### 关键执行机制

1. **状态持久化 + 断点恢复**: 每步执行后写入 `state.json`，`Ctrl+C` 暂停后可 `workflow resume` 继续
2. **控制流**: `if`/`switch`/`while`/`do-while` 通过 `next_steps` 递归执行嵌套步骤
3. **Fan-out**: 对集合中每个 item 执行模板步骤，生成带索引的唯一 ID
4. **`continue_on_error`**: 步骤失败时不中断，允许下游 `if` 分支处理
5. **`integration: auto`**: 从 `.specify/integration.json` 读取项目实际使用的 AI agent

### 对你的价值评估

如果你的自定义版本需要：
- **自动化多步骤 spec → plan → implement 流程** → 非常有价值
- **CI/CD 集成**（workflow 非零退出码、JSON 输出）→ 有价值
- **人工审批门控**（gate step）→ 有价值
- **仅手动逐步操作** → 价值有限，可能不需要

## 安全修复详解

### 1. 目录遍历攻击防护 (`569d18a`)

**问题**: 命令注册时，命令名/别名直接拼接成文件路径。攻击者可以通过恶意命令名（如 `../../etc/passwd`）写入项目目录外的任意位置。

**修复**: 新增 `_ensure_inside()` 共享检查方法：
```python
@staticmethod
def _ensure_inside(candidate: Path, base: Path) -> None:
    normalized = Path(os.path.normpath(candidate))
    base_normalized = Path(os.path.normpath(base))
    if not normalized.is_relative_to(base_normalized):
        raise ValueError(f"Output path {candidate!r} escapes directory {base!r}")
```
应用到 3 个写入路径：主命令、别名、Copilot companion prompt。

**影响范围**: 任何接受外部命令名输入的路径（extension install、preset install）。

### 2. URL 重定向安全加固 (`36ad3cd`)

**问题**: Preset URL 下载验证了源 URL 是 HTTPS，但 `open_url()` 会跟随重定向。攻击者可以设置 HTTPS → HTTP 重定向，绕过传输安全验证，甚至可能在重定向中保留 Authorization header 导致凭据泄露。

**修复**: 三层防护：
1. **`redirect_validator` 回调** — 在 `open_url()` 跟随重定向前验证目标 URL
2. **最终 URL 验证** — 重定向完成后再次验证 `response.geturl()`
3. **凭据降级保护** — HTTPS → HTTP 重定向不传递 Authorization header

```python
def _validate_download_redirect(old_url, new_url):
    if not _is_allowed_download_url(_urlparse(new_url)):
        raise urllib.error.URLError("redirect target must use HTTPS...")
```

### 3. URL scheme 验证 (`30e6fa9`)

**问题**: `build_github_request()` 没验证 URL 格式，可能接受 `file://`、`ftp://` 或空 URL。

**修复**: 
```python
if parsed.scheme not in {"http", "https"}:
    raise ValueError(f"url must start with http:// or https://")
if not parsed.hostname:
    raise ValueError(f"url must include a hostname")
```

### 4. Catalog payload 验证 (`de88c23`)

**问题**: Extension/preset catalog JSON 没有验证顶层结构。恶意 catalog 可以返回非 dict 格式导致未预期行为。

**修复**: 验证 response 是 `dict`，包含 `schema_version` 和 `extensions`/`presets` key，且列表类型正确。

### 5. Config-driven 认证注册表 (`f099834`)

**新能力**: 统一的认证框架，支持 GitHub Token 和 Azure DevOps PAT：
- Provider 注册表按优先级尝试
- 401/403 自动 fallback 到下一个 provider
- 认证信息不泄露给非授权域名
- 所有 catalog 和下载操作统一走认证链路

### 6. Run ID 路径遍历防护 (`bb2b49d`)

**问题**: `RunState.load(run_id)` 将 `run_id` 直接插入路径。`../escape` 类型的 run_id 可读取项目外任意文件。

**修复**: 在构造路径前验证 `run_id` 格式：
```python
_RUN_ID_PATTERN = re.compile(r"^[a-zA-Z0-9][a-zA-Z0-9_-]*$")
```

## 关键 Bug 修复详解

### 1. While/do-while 循环读取过期数据 (`616eba6`)

**问题**: 循环中每次迭代的步骤结果用带索引的 ID（如 `loop:step:1`）存储，但循环条件表达式引用的是原始 ID（如 `step`）。第二次迭代仍然读取到第一次的结果，导致循环条件永远不变化。

**修复**: 每次迭代后将结果 copy-back 到无前缀的 key：
```python
if orig and ns_copy["id"] in context.steps:
    context.steps[orig] = context.steps[ns_copy["id"]]
    state.step_results[orig] = context.steps[ns_copy["id"]]
```

### 2. Non-ASCII 字符被转义 (`811a3aa`)

**问题**: `yaml.safe_dump()` 默认 `allow_unicode=False`，中文/日文等字符在 SKILL.md frontmatter 中被转为 `\uXXXX`。

**修复**: 在 7 处 `safe_dump` 调用加上 `allow_unicode=True`，并抽取 `dump_frontmatter()` 共享 helper。

### 3. Fan-out items 非 list 时静默失败 (`36fd5f6`)

**问题**: 表达式解析后如果不是 list（如 `None`、`dict`），fan-out 静默跳过，用户难以诊断。

**修复**: 返回 `StepStatus.FAILED` 并明确报告表达式和实际类型。

### 4. Workflow 失败时退出码为 0 (`1ee2b62`)

**问题**: `workflow run` 命令在 workflow 失败/中止时仍返回 exit code 0，CI 无法检测失败。

**修复**: `failed|aborted → exit(1)`, `completed|paused → exit(0)`。

### 5. .vscode/settings.json 被升级删除 (`84db931`)

**问题**: Copilot integration 在文件已存在时只 merge 不 track。升级时新 manifest 不含该文件，旧 manifest 包含，触发 stale-cleanup 删除。

**修复**: 新增 `stale_cleanup_exclusions()` hook，Copilot 返回 `{".vscode/settings.json"}`，升级时跳过这些路径。

### 6. Extension self-install 删除源目录 (`de18d21`)

**问题**: `extension add --dev` 从本地路径安装时，清理逻辑误删了源目录本身。

### 7. Windows PS 5.1 挂起 (`75aee19`)

**问题**: Rich Live 的 transient mode 在 PowerShell 5.1 上输出 ANSI 序列导致进程挂起。

**修复**: Windows 上禁用 transient mode。
