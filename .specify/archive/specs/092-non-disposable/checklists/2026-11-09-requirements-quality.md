# Requirements Quality Checklist: Non-Disposable（不可一次性处置）

**Purpose**: Validate the quality, clarity and **decidability** of the 092 requirements before implementation — across
the seven focus faces the driver named: the mechanism-not-slogan face, the four-stage `/speckit.history` contract, the
closed-set carrier of the ten-directory review surface, the supersede/renumber protocols, the machine-readable status
contract, the A–H tier split, and the team/concurrency reuse boundary.
**Created**: 2026-11-09
**Feature (Requirement Scope)**: `.specify/features/092-non-disposable.md` (created in implement package P1; `feature-ref.md` is the interim pointer)
**Requirements (What)**: [`../requirements.md`](../requirements.md)
**Specifications (How, context only)**: [`../plan.md`](../plan.md), [`../tasks.md`](../tasks.md), [`../contracts/`](../contracts/),
[`../notes/input-review-080-090.md`](../notes/input-review-080-090.md)

**Readers**: the driver that owns the 092 loop, plus an independent verifier who did not write the spec; it decides
whether the requirement text is answerable or must go back to a prior stage.
**Reading scenario**: before the implement stage, walk every category and answer each item **by reading
`requirements.md`**; an item answerable only by opening a contract or running code is itself the finding.

**Note**: generated by the `/speckit.checklist` skill to validate the quality of **Requirements (What)**.
`plan.md` / `tasks.md` / `contracts/` are read **only** to surface gaps, ambiguities, conflicts and traceability breaks
in the requirements — never to grade the plan or the tasks, and never to test implementation behaviour.

**Method record** — Depth: Standard · Audience: verifier · Focus: the seven faces above · Item count: 40 (soft cap 40)
· Traceability: 40/40 items carry a `[Req §…]` anchor, a named artifact path, or an explicit
`[Gap]`/`[Ambiguity]`/`[Conflict]`/`[Assumption]`/`[Dependency]` marker (target ≥80%) · Severity: deliberately absent —
this checklist's analogue of a propagation cap is the traceability anchor, so an item guarding nothing shows up as
untraceable rather than as "low".

## 1. "Non-Disposable" as a decidable mechanism, not a slogan

- [ ] CHK001 Does the requirement text state each of the three state classes (过期 / 无用 / 延期) as a **reading a program or a cited semantic judgement can take**, rather than as an adjective the author may apply? [Clarity, Req §FR-002, Req §FR-003]
- [ ] CHK002 Is the **judge** of the "expired" predicate named — the owner page holds the criteria, but does any requirement say who answers "this carrier's count no longer matches the tree" at review time? [Gap, Req §FR-002, Req §FR-003]
- [ ] CHK003 Is "对当前任何消费者都无输入作用" (useless) operationalised into a closed reading — is an explicit consumer set defined (registry rows, engine reads, index membership), or is "consumer" itself the vague term? [Ambiguity, Req §FR-003]
- [ ] CHK004 Is "载体上存在一处未附到期条件的留存声明" (deferred) given a **detectable shape** — which spellings, block positions or marker forms count as a retention declaration, and are near-miss wordings excluded? [Clarity, Req §FR-002, Req §FR-003]
- [ ] CHK005 Is the "延期" class's proof settled — the two-way check admits no A–H row represents it, so is its proof-by-construction criterion written in the requirements, or only in a contract clause? [Conflict, Req §A–H Corpus Mapping, Req §FR-003]
- [ ] CHK006 Is the relationship between the three **states** and the eight **detection classes** stated (class per state, or a declared many-to-one), so a reader can tell which class fires for which state? [Clarity, Req §Key Entities, Req §FR-003]
- [ ] CHK007 Is "closed" for a dispositioned entry given a recomputable predicate **in the requirements**, not only in a report-schema clause, and is "无静默留存" given a residual definition — are carriers no entry mentions (neither disposed nor exempt nor reported) a stated non-finding? [Gap, Req §FR-009, Req §Edge Cases]
- [ ] CHK008 Is "no silent retention" bounded against the review surface itself — after a review round, is the set of carriers the report did **not** mention stated as reportable, so "nothing found" and "nothing looked at" stay different conclusions? [Coverage, Req §FR-011, Req §SC-014]

## 2. Exemption (`exempt`) — the anti-permanent escape hatch

- [ ] CHK009 Are the four required `exempt` fields and the three-value `expiry_kind` domain stated once, with the requirement text (not only a contract) naming what happens when each is absent? [Completeness, Req §FR-006, Req §FR-007]
- [ ] CHK010 Is the "constant-true condition" prohibition expressed as a **decidable test** (which predicates count as trivially true), or does `condition: true` remain the only named instance? [Clarity, Req §FR-006]
- [ ] CHK011 Is the upper bound on `expiry_recheck` traceable to a single owner the requirement points at, given the requirement itself defers the number to "the owner page"? [Dependency, Req §FR-006]
- [ ] CHK012 Is `on-condition` bounded — who guarantees the named predicate is expressible in the engine's evaluation language, and what is the disposition when it evaluates but is false? [Clarity, Req §FR-006, Req §FR-007]
- [ ] CHK013 Is exemption accumulation given a stated ceiling, warning or metric, or is the Edge-Cases concern ("exempt becomes the new garbage") recorded without a requirement behind it? [Coverage, Req §Edge Cases, Req §FR-007]
- [ ] CHK014 Is re-entry after expiry stated symmetrically for all three `expiry_kind` values, including exactly when an expired entry is re-evaluated (next run only, or any run), so no reader can infer a grace period? [Clarity, Req §FR-007, Req §SC-017]

## 3. The four-stage `/speckit.history` contract

- [ ] CHK015 Are the four stage names fixed in the requirement text itself (not only "as the skill names them"), so a second reader cannot re-name a stage without breaking traceability? [Clarity, Req §FR-029, Req §FR-043]
- [ ] CHK016 Is the zero-write obligation decidable as written — are the two snapshot points, the snapshot content, and the "managed path set" whose hashes are taken all defined by the requirements, or is the last one left to a contract? [Measurability, Req §FR-031, Req §SC-004]
- [ ] CHK017 Is the distinction between "a temporary plan may be written" and "review and design write nothing" stated as one rule, with the cleanup obligation stated for the abort path (the user never confirms)? [Edge Case, Req §FR-031, Req §Edge Cases]
- [ ] CHK018 Is the `group` default stated together with the reason full execution is unreachable, and is "confirm every group" distinguishable from one blanket confirmation? [Clarity, Req §FR-032]
- [ ] CHK019 Is `unconfirmed` defined with respect to the **next** round — "not retried automatically" plus "still visible" leaves open whether it re-appears as a fresh proposal; is that stated? [Ambiguity, Req §FR-033, Req §SC-019]
- [ ] CHK020 Is reversibility stated per disposition as a **decidable property** (a named git operation per class), or does "可逆 or 明示不可逆" leave the reader to decide which dispositions are which? [Measurability, Req §FR-034, Req §SC-019]
- [ ] CHK021 Are the evidence sink's four segments and "one file per run" stated together with the group-boundary evidence rule, so that per-group and per-run evidence cannot be read as two stores? [Consistency, Req §FR-035, Req §FR-042]
- [ ] CHK022 Is the conflict between "the review and design segments write nothing" and "the design segment produces a report the user confirms" resolved for both the abort and the confirm paths (where does the proposal live on disk)? [Conflict, Req §FR-029, Req §FR-031, Req §FR-042]
- [ ] CHK023 Is the preserved pre-existing capability (session distillation + incremental manifest) stated as an obligation with a decidable reading, rather than as "must not be removed"? [Coverage, Req §FR-043, Req §FR-044]

## 4. The review surface and its closed-set carrier

- [ ] CHK024 Is the ten-directory root set expressed in the requirements **only by pointer** to the declared fact file, with the requirement text carrying neither a second list nor a second count? [Consistency, Req §FR-036, Req §FR-037, Req §FR-038]
- [ ] CHK025 Does the requirement set name every value domain the declaration takes from the existing contract (`kind` from the closed `fact_kinds`, the required fact keys) instead of implying them? [Completeness, Req §FR-037]
- [ ] CHK026 Are the four declaration failure faces (missing file / bad `kind` / bad required key / degraded read) each mapped to one exit code and one named label, with no second label set invented in the requirement text? [Consistency, Req §FR-039, Req §FR-010]
- [ ] CHK027 Are "declared but absent" and "present but empty" stated as distinguishable in the coverage declaration, and does the requirement say which of the two counts as a candidate? [Clarity, Req §FR-040, Req §Edge Cases]
- [ ] CHK028 Is "unregistered sibling directory" decidable — what exactly makes a directory "历史目录-shaped", and is that shape a closed criterion or the heuristic the requirement forbids elsewhere? [Ambiguity, Req §FR-041]
- [ ] CHK029 Is the empty-surface exit code a requirements-level obligation or only a contract one — FR-010's three-way exit domain and the Edge-Cases rule ("no candidates is not clean") do not state which code an empty surface yields? [Conflict, Req §Edge Cases, Req §FR-010, Req §FR-011]
- [ ] CHK030 Is the review surface's relation to `.specify/history/`'s own distillation output stated (it is one reviewed carrier among the ten roots), so "history" cannot be misread as the git history the requirement forbids? [Clarity, Req §FR-030, Req §FR-044, Req §Assumptions A4]

## 5. Supersede and renumber protocols — mechanical detectability

- [ ] CHK031 Is the "superseded marker + pointer to the new carrier" given a detectable form (which marker, where it sits relative to the retained old text), or may each superseding feature invent its own spelling? [Clarity, Req §FR-015, Req §FR-017]
- [ ] CHK032 Is "the old guard must no longer demand the old behaviour" decidable — how does a check tell a replaced guard from a guard that was merely renamed or moved? [Ambiguity, Req §FR-016, Req §SC-005]
- [ ] CHK033 Are the live-binding shapes and the history-record predicate face each closed enumerations owned by one page, with the requirements declaring that closure (by path and by section position)? [Completeness, Req §FR-022, Req §FR-024]
- [ ] CHK034 Is "a history record was rewritten" stated as decidable — against which baseline is a rewrite detected, given the corpus holds no instance and git history is explicitly out of scope? [Gap, Req §FR-023, Req §FR-030, Req §SC-007]
- [ ] CHK035 Is the tier tally's count coherence assigned to one surface — the requirements' group table, the per-entry expansion (35 entries) and the corpus form three counting points; does the requirement text say which one owns the number? [Consistency, Req §A–H Corpus Mapping, Req §FR-057]
