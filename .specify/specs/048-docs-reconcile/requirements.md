# Requirements Specification: /speckit.docs 三段式调协编排(目标结构驱动)

**Requirement Branch**: `048-docs-reconcile`  
**Created**: 2026-09-01  
**Status**: Draft  
**Input**: User description: "需要针对templates/commands/docs.md命令进行优化,它应该遵循shared/patterns/reconcile-pattern.md这个模式,先设定一个规范化的文档结构,然后每次执行都是将当前的文档现状向这个设定的目标格式进行调协. 因此这个命令主要包含三大部分:1)根据项目特点和内容设计一个最佳的文档结构作为目标;2)基于现状和目标的差异分解具体的执行动作;3)使用create-docs和improve-docs 技能完成对应的操作. 这个命令在执行的时候如果用户传入了额外的信息,那么在进行调协之外还需要根据用户的描述额外分解用户的要求作为额外的动作,比如用户执行'/speckit.docs \"创建一个描述登录流程的文档\"' ,除了进行文档的调协还需要创建一个新的文档."

## Related Feature *(mandatory)*

**Feature ID**: 037  
**Feature Name**: Docs Command

绑定依据(clarify 2026-09-01):037 的契约 `contracts/docs-command-template.md` C-18 已治理 create-docs(创建与基础结构)/ improve-docs(既有文档内容)的配对边界,而 improve-docs 技能自身从未注册任何 Feature;037 亦已历经三次 follow-up 演进(2026-08-10 薄分发层重构、08-20 呈现层解耦、08-24 主题化导航)。本需求是同一命令与同一技能对的第四次演进,故作为 037 的 follow-up 而非新 Feature——与 Feature 041 Goal Registry 吸收需求 038-goal-target 的先例同构。

## Overview

把 `/speckit.docs` 从"单技能委托的薄分发层"升级为**目标结构驱动的三段式调协编排**:①根据项目特点与内容设计最佳文档结构并**持久化为目标结构声明**——此后各次执行都向这份既定目标收敛,而不是每次重设;②对比现状与目标的差异(容忍带先行),把实质性偏差分解为**分型执行动作**;③把动作**分发到 owning 技能**执行——结构类动作交 create-docs,内容类动作交 improve-docs。用户附加输入不取代基线调协,而是分解为**额外动作**并入同一次运行(如"创建一个描述登录流程的文档" → 既有调协 + 新建文档动作)。

### 现状锚点(以源码实测为准)

- `templates/commands/docs.md`(72 行)为薄分发层,委托对象**仅 create-docs**;全文 improve-docs 出现 **0 次**——内容质量半边不在命令分发链路里。
- create-docs 技能(170 行)承载**静态** Desired-State Baseline(保留根文件名 + 六类 docs/ 分类 + notes 生命周期)、五类作用域判定(全量/单目标/写作/扇出/Bootstrap)与 R0–R6 调谐环;improve-docs 在其资源表中仅作 hand-off 提及(4 处),不进入任何执行路径。
- improve-docs 技能(150 行)为内容质量半边:单文档/次(或单维度有界批)、证据驱动("无发现即停")、section-level 编辑、禁止建/移/归档。
- `shared/patterns/reconcile-pattern.md`(135 行)已是调谐语义唯一真源:R0–R6、容忍带、只归档不删除、单引擎坍缩、薄分发层纪律——本需求**复用**该模式,不新模式。
- 用户参考文档 `docs/reference/commands/docs.md` 已存在;命令模板的各工具镜像经 `regen-command-copies.py` 再生。

**与现状的差异(本需求要闭合的缺口)**:

| 缺口 | 现状 | 目标 |
|------|------|------|
| 目标态 | 框架级静态基线,无项目专属结构 | 项目专属**目标结构声明**,设计一次、持久收敛 |
| 差异处理 | create-docs 内部一次性 diff | 命令层显式分解为**分型执行动作** |
| 执行通道 | 仅 create-docs | create-docs(结构)+ improve-docs(内容)双技能分发 |
| 用户带参 | 按作用域走单一流程(写作委托只走 Authoring Flow,不叠加调协) | 基线调协 + 用户要求分解的**额外动作**同次运行交付 |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 目标结构设定与持久化 (Priority: P1)

用户在一个项目上首次运行 `/speckit.docs`(或显式要求重新设计结构)时,命令依据项目特点与内容——项目形态(库/CLI/应用/框架)、现有文档清单与内容主题盘点、目标读者、框架静态基线(保留根文件名 + 六类分类 + notes 生命周期)——设计一份最佳文档结构,作为**持久化的目标结构声明**呈现给用户确认。此后的每一次执行都向这份既定目标收敛,而不是每次重新发明目标。

**Why this priority**: 三段式的第一段,是后两段的地基——没有既定的目标,"差异分解"无从谈起,每次运行的目标都会漂移。仅这一段落地,项目就获得一份稳定、可回查的文档结构契约。

**Independent Test**: 在一个无目标结构声明的项目上运行一次,验证:(a) 产出的目标声明持久落盘,可在后续会话中被引用;(b) 声明内容反映该项目实际特点(而非通用模板的复述);(c) 声明以引用方式继承静态基线,不复制基线事实;(d) 用户确认之前,声明不作为收敛依据。

**Acceptance Scenarios**:

1. **Given** 无 `docs/` 结构的新项目,**When** 用户运行 `/speckit.docs`,**Then** 命令先设计目标结构(含 Bootstrap 骨架)并经用户确认后持久化,再以此为目标执行收敛
2. **Given** 项目已有大量杂乱文档但从未设定目标,**When** 首次运行,**Then** 目标设计建立在对现有内容的盘点(主题聚类、读者路径)之上,而非空模板套用
3. **Given** 目标声明已存在且用户未要求重设,**When** 再次运行,**Then** 命令复用该既定目标,不重新设计(防抖)
4. **Given** 设计所需信息不足,**When** 进入设计阶段,**Then** 提出必要问题(≤3)而不是虚构目标

---

### User Story 2 - 差异分解与双技能分发 (Priority: P1)

目标既定后,每次运行把文档空间现状与目标对比:先过容忍带(带内偏差标记"已一致(容忍)",不进收敛计划),再把实质性偏差分解为**分型执行动作**——结构类动作(归位/命名/新建/搬迁/归档/索引/frontmatter/链接)分发 create-docs 执行;内容类动作(已正确就位的既有文档的准确性/过时/完整性/可读性修复)分发 improve-docs 执行,并遵守其"单文档/次"约束(多文档内容发现分解为逐文档顺序分发)。执行沿用既有分级确认门禁与只归档不删除;运行结束的残差报告按动作路由分别汇报——哪个技能执行了什么、容忍了什么、待人工决策什么。

**Why this priority**: 三段式的第二、三段合起来才是引擎本体——差异看得见、动作有归属。improve-docs 进入分发链路是本需求的关键增量:此前结构收敛与内容质量修复是两条互不知晓的通道,用户需要分别触发。

**Independent Test**: 在一个同时存在结构漂移(文档放错位置)与内容漂移(就位文档含失效路径)的空间上全量运行一次,验证:(a) 两类偏差都进入动作清单并被分别路由到正确技能;(b) 结构修复由 create-docs 语义完成、内容修复由 improve-docs 语义完成(可从审计日志/残差报告回查);(c) 无证据指瑕的文档零改动(反 churn)。

**Acceptance Scenarios**:

1. **Given** 文档 A 放错分类目录、文档 B 就位但含过时事实,**When** 全量运行,**Then** 动作清单同时含 A 的结构动作(create-docs)与 B 的内容动作(improve-docs),两者都执行并在残差报告中分列
2. **Given** 三份就位文档各有内容问题,**When** 运行,**Then** improve-docs 侧分解为逐文档顺序分发(或显式给出顺序计划),不合并为一次批量改写
3. **Given** 空间与目标完全一致,**When** 运行,**Then** 零收敛,审计日志照写,残差报告如实报告"全维度在容忍带内"
4. **Given** 某结构动作属搬迁/归档类,**When** 执行,**Then** 走干跑计划 + 逐项确认的门禁(既有纪律不放松)

---

### User Story 3 - 用户附加输入的额外动作分解 (Priority: P2)

用户带参调用(如 `/speckit.docs "创建一个描述登录流程的文档"`)时,基线调协照常进行;同时命令把用户描述分解为**额外动作**并入同一次运行——该例中新文档创建(经 create-docs 写作流程按分类落位)成为调协之外的附加收敛项。用户输入亦可为方向性指示(如"整理 README"、"激进重组"),作用于动作分解的方向与优先级。当用户输入隐含目标结构变更(如"把 reference/ 拆成两部分")时,变更经确认后写回目标声明,使后续运行向更新后的目标收敛。

**Why this priority**: 它是编排表达力的扩展,建立在故事 1/2 的地基上;且当前命令已有写作委托的单通道路由,本故事的新颖点在"叠加而非取代"与"输入可回写目标"。

**Independent Test**: 在一个已收敛的空间上执行 `/speckit.docs "创建一个描述登录流程的文档"`,验证:(a) 调协侧如实报告零收敛;(b) 新文档按分类学落位创建并完成索引;(c) 一次运行同时交付两个结果,互不挤占。

**Acceptance Scenarios**:

1. **Given** 已收敛空间,**When** 用户带写作委托运行,**Then** 一次运行既完成基线调协(零收敛照实报告)又创建合规新文档
2. **Given** 用户输入为方向性指示("激进重组"/"整理 README"),**When** 分解动作,**Then** 指示作用于对应动作的方向与优先级,不改变目标声明本身
3. **Given** 用户输入隐含结构变更("把 reference/ 拆成两部分"),**When** 运行,**Then** 变更作为待确认项呈现,确认后写回目标声明,下次运行向新目标收敛
4. **Given** 用户输入是站点请求(生成/发布站点),**When** 运行,**Then** 仍按既有纪律移交给 create-pages,不被吸收为本命令动作

### Edge Cases

- **目标声明与项目实态脱节**(新增子系统/重大特性落地后):运行检测到实质性不匹配时**提议**重新设计目标,经用户确认后重设;绝不在每次运行中静默重设(防抖反模式)。
- **用户输入与目标声明冲突**:本次运行中用户输入优先级最高(沿用期望态来源优先序:模板 < 规则 < 原则 < 外部权威事实 < 本地既成约定 < 本次用户输入);但其持久影响必须经确认写回目标,不留一次性覆盖。
- **内容维度无证据**:全量调协不做"无证据全文重读找茬"——内容动作仅由具体证据(确定性 validate 发现、feedback 条目、用户陈述、已核实过时信号)触发;无证据即标记容忍(反 churn + token 效率)。
- **improve-docs 证据不足("无发现即停")**:分发后技能可能报告"无可改进",该结果如实进入残差报告,不视为运行失败。
- **大规模内容扇出(已接受的代价)**:全量运行可能扇出数十次 improve-docs 分发(不设上限,FR-008)。分发前先告知计划文档数,用户可在启动前中止;若在扇出中途中止,已完成的逐文档结果保留(不回滚),未开始项以 pending 进入残差报告,由后续运行继续收敛。
- **搬迁失败**:沿用 R5 中止纪律——停止剩余项、保留已成功项、记录、请求人工复查。
- **无 `.specify/` 的独立技能模式、站点工具目录(C 区)跳过、镜像文件不可手改**等既有边界全部不变。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: `/speckit.docs` MUST 在首次执行(或用户显式要求重设)时,基于项目特点与内容设计最佳文档结构并持久化为**目标结构声明**;设计依据至少包含项目形态、现有文档内容盘点、目标读者、框架静态基线四类信息。声明落在**运行工作区 `.specify/docs/`**(clarify 2026-09-01 裁定;该目录已入库受版本控制,可承载跨运行契约)。
- **FR-002**: 目标结构声明 MUST 以**引用**方式继承 create-docs 拥有的静态基线(保留文件名/六类分类/notes 生命周期),只声明项目专属扩展;MUST NOT 复制基线事实(单一事实源纪律)。
- **FR-002a**: 目标结构声明是**跨运行长期契约**,与同一工作区内的按次运行痕迹(干跑计划、审计日志)生命周期不同频;实现 MUST 使其在该工作区内可区分(独立子路径/命名),且 MUST NOT 随按次产物一同轮转、清理或被当作可丢弃的运行痕迹。
- **FR-003**: 目标结构声明 MUST 经用户确认后方可作为收敛依据;设计信息不足时提出必要问题(≤3),MUST NOT 虚构目标。
- **FR-004**: 目标声明已存在且用户未要求重设时,每次执行 MUST 向该既定目标收敛;对未变化空间的重复执行 MUST 零收敛(容忍带/防抖)。
- **FR-005**: 命令 MUST 将现状-目标差异(容忍带先行)分解为**分型执行动作**,每个动作至少携带:类型(结构/内容/用户委托)、目标对象、所属技能、确认层级。
- **FR-006**: 结构类动作(归位/命名/新建/搬迁/归档/索引/frontmatter/链接修复)MUST 分发 create-docs 执行。
- **FR-007**: 内容类动作(就位文档的准确性/过时/完整性/可读性修复)MUST 分发 improve-docs 执行,且 MUST 有具体证据支撑;无证据指瑕的文档 MUST 标记为容忍,MUST NOT 改写。
- **FR-008**: 多文档内容动作 MUST 按 improve-docs 的"单文档/次(或单维度有界批)"约束分解为顺序分发,MUST NOT 合并为批量改写。单次运行的内容动作量**不设上限**——本次运行检出的全部有证据支撑的内容动作都在本次分发完毕(clarify 2026-09-01 裁定:取单次最大收敛,接受大空间上运行成本不可预期的代价);下游设计 MUST NOT 擅自引入隐式上限或静默截断。为使该代价可控,分发开始前 MUST 先告知计划分发的文档数,使用户可在扇出启动前中止。
- **FR-009**: 用户传入附加信息时,命令 MUST 在基线调协之外把用户描述分解为**额外动作**并入同一次运行;用户输入 MUST NOT 取代基线调协。调协的作用域沿用既有作用域判定(无参=全量;目标路径=该目标的定向调协;委托/方向性输入=全量)。
- **FR-010**: 隐含目标结构变更的用户输入 MUST 经确认后写回目标声明;未经确认 MUST NOT 改变持久目标。
- **FR-011**: 既有分级确认门禁 MUST 原样保留:安全本地写自动执行;搬迁/归档/重组经干跑计划逐项确认;正式区只归档不删除。
- **FR-012**: 命令 MUST 保持薄编排层定位——引擎语义(基线/作用域/调谐环/门禁/写作规范)留在两个技能内;MUST NOT 新增顶层模式(单引擎坍缩纪律)。
- **FR-013**: 运行结束的残差报告 MUST 按动作路由区分汇报:各技能执行了什么、容忍了什么、待人工决策什么;审计日志在零收敛时也 MUST 照写。
- **FR-014**: 命令 MUST 维持既有移交边界:站点请求 → create-pages;技能本体改进 → improve-skills。
- **FR-015**: 运行检测到目标声明与项目实态实质性脱节时,MUST 提议(而非直接执行)目标重设计,经用户确认后重设。

### Key Entities *(include if requirement involves data)*

- **目标结构声明 (Target Structure Declaration)**: 项目专属文档结构的持久化契约,是每次调协的期望态锚点;由"对静态基线的引用 + 项目专属扩展"构成;生命周期为设计 → 确认 →(实质性修订)。**归属运行工作区 `.specify/docs/`**(已入库),与同目录按次产物(plans/audit)同址但不同频——它跨运行长存,按次产物随运行累积。与 Goal Target(目标切片)无关——那是 goal 域的 run 级指派范围概念。
- **调协动作 (Reconcile Action)**: 一次运行中分解出的最小执行单元;属性包括类型(结构/内容/用户委托)、目标对象、owning 技能、确认层级、执行结果;动作聚合为干跑计划,执行后进入审计日志与残差报告。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新项目首次运行一次即产出经确认的持久目标结构声明;随后在零变更空间上的第二次运行,收敛动作数为 0(防抖证据)。
- **SC-002**: 在含 1 处结构漂移与 1 处内容漂移的空间上,单次全量运行同时修复两类漂移,且残差报告可回查每个动作的执行技能归属,路由正确率 100%。
- **SC-003**: 在已收敛空间执行带写作委托的调用(如"创建一个描述登录流程的文档"),一次运行交付两个结果:调协侧零收敛如实报告 + 新文档按分类落位;两者缺一即不达标。
- **SC-004**: 无证据指瑕的文档在连续两次全量运行中被改写的次数为 0(反 churn)。
- **SC-005**: 目标结构声明中可机检的基线事实(保留文件名清单、分类目录名等由 create-docs 拥有的枚举)的复制数为 0——均以引用表达(单一事实源合规)。
- **SC-006**: 命令模板保持薄编排层:不内联调谐环步骤展开、门禁表复制等引擎语义(结构契约可检)。

### Measurement Sources & Collection Methods

- **SC-001 Source**: 本仓 dogfooding 实测运行记录——`/speckit.docs` 在本仓自身 docs/ 空间上的连续两次运行,取自 `.specify/docs/audit/` 审计日志与残差报告,按运行编号回查。
- **SC-002 Source**: dogfooding 运行(构造或自然存在双类漂移的空间)的审计日志条目 + 残差报告的动作-技能归属清单,人工核对每个动作的语义类别与执行技能一致性。
- **SC-003 Source**: dogfooding 运行的一次带参调用实测:残差报告(调协侧)+ 新文档落位结果(git 状态/docs 树)。
