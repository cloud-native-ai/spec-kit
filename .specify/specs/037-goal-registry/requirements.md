# Requirements Specification: Goal 作为项目级一等概念(goal 定义归档 + 团队引用 + 单一撰写入口 + 多团队协调)

**Requirement Branch**: `037-goal-registry`  
**Created**: 2026-08-04  
**Status**: Planned  
**Input**: User description: "添加一个独立的概念“goal”，当前在team相关的技能和命令中会配置goal,但是这些goal都是分散的,需要使用spec-kit框架建立项目级别的goal(.specify/goal目录归档).一个goal可以由多个team来实现,另外code cli程序内置的/goal命令也可以通过这个goal的描述文件来指定."

## Related Feature *(mandatory)*

**Feature ID**: 041  
**Feature Name**: Goal Registry

**绑定理由**:goal 是**项目级**概念,其消费方包含团队域之外的对象(宿主 CLI 的 goal 机制、以及任何需要"项目当前目标"的读者);而 Feature 027(Team Management)的章程明确限定在"团队多代理配置"。把项目级概念挂进团队域章程会与本需求的核心主张(goal 不是团队属性)直接冲突,故新建 Feature 041 记录 goal 概念本身。

**与 027 的关系**:027 经需求 036 已落地以 goal 为索引的总结聚合。本需求为其提供缺失的**定义源**并收编其交付目录(FR-022),因此 041 与 027 双向交叉引用;036 已确立的聚合语义与身份文法不变(FR-014)。

## Overview

**goal 今天不是一个对象,而是一个字段。** 它只以团队属性的形式存在,且同一个 goal 在多处被重复书写:每个团队的 `team.md` 同时在 frontmatter `goal:` 与正文 `## Goal` 两处写同一个目标(实测 4 个存量团队全部如此,即 4 个 goal 被写成 8 份);团队域另有 12 个以上文件(预设、agent 模板、`references/goal.md`、`references/optimization-goals.md`、`improve-team/references/goal-editing.md`)各自讨论 goal 的写法与改法。

后果有三:

- **同一目标无单一定义**:需求 036 已引入 `goal_slug` 作为"同一个 goal"的连接键,并据此把总结按 goal 聚合;但**被连接的那个 goal 本身没有定义文件**——只有各团队各写一份的描述。多团队共享一个 goal 时,以谁的措辞为准只能靠人裁决。
- **目标漂移无处可查**:goal 的可验证成功判据散落在团队文件里,改一处不影响另一处,没有权威版本可供比对。
- **目标无法被复用**:宿主 CLI 内置的 `/goal` 机制、以及未来任何需要"项目当前目标"的消费者,都无法指向一个稳定的项目级对象。

本需求把 goal 提升为**项目级一等概念**:在 [[STR-001]] 下归档 goal 的**定义**(目标叙述 + 可验证成功判据 + 生命周期状态),由团队以 [[STR-002]] **引用**而非复制,从而为任何需要"项目当前目标"的消费者提供一个稳定的引用点。宿主 CLI 的 goal 机制是这类消费者之一,但**其集成不在本需求范围内**(理由见 Out of Scope)。

边界明确:goal 定义是**被撰写的事实源**(authored),不是派生物;它与需求 036 落地的 goal **总结**(derived)是同一对象的两面,前者是输入、后者是输出,同处 [[STR-001]]`<goal-slug>/` 之下但结构分离(FR-023)。本需求不改变 036 已确立的聚合语义,只为其提供缺失的定义源。

概念以 [[STR-005]] 为准,其中两点决定了本需求的边界:goal 的**作用对象不受限**——它可以指向框架自身、代码规范收敛、能力运行结果等任意维度,不以"本项目源码能实现"为界;goal 与 requirement 分属**不同平面且无必然层级**,互不派生也无结构化字段相连。

**N 团队 : 1 goal 还带来一个今天无人负责的问题:协调。** 多个团队同时推进一个 goal 时,它们的覆盖范围可能重叠——两个团队写同一批文件就从协作退化为竞争,后写的覆盖先写的,而没有任何机制会发现。团队**内部**早已有答案:parallel 模式的 `territory`(Write Scope / Read Scope / Forbidden)以"零写重叠"不变式把成员之间的范围划清。但它只存在于**成员级**且只对 parallel 模式成立;团队**之间**既无范围声明,也无重叠检测。goal 是唯一能看见这件事的层次——"同一个 goal"正是这些团队产生交集的原因。本需求因此把既有的 territory 纪律提升一级:goal 侧派生参与团队名册,团队侧声明团队级范围,机制检测重叠并提议重划,由人裁定(见 US5)。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - goal 有了定义文件:一个目标,一份权威描述 (Priority: P1)

作为项目维护者,我希望能在项目级别创建并归档一个 goal:它有稳定的身份、一段目标叙述、一组**可验证的成功判据**、以及生命周期状态(进行中 / 已达成 / 已放弃)。此后"这个项目当前要达成什么"有唯一可引用的答案,而不必去若干个团队文件里拼凑。

**Why this priority**: 这是整个概念的地基。没有定义文件,后面的引用、聚合与消费方集成都无所指。它也是唯一能独立交付价值的最小切片:哪怕还没有任何团队引用它,项目已经获得了此前不存在的"目标清单"。

**Independent Test**: 创建两个 goal 定义并归档;仅凭归档目录即可列出项目全部 goal 及其状态与成功判据;每个 goal 的身份合法且可作为目录名;重复创建同一身份被拒绝而非静默覆盖。

**Acceptance Scenarios**:

1. **Given** 项目尚无任何 goal 定义, **When** 创建一个 goal, **Then** 在 [[STR-001]] 下产生该 goal 的定义文件,含身份、目标叙述、可验证成功判据与状态。
2. **Given** 一个已存在的 goal 身份, **When** 以同一身份再次创建, **Then** 被拒绝并提示改用修改路径,既有定义不被覆盖。
3. **Given** goal 的成功判据被有意修改, **When** 保存, **Then** 变更被记录(可追溯到修改前的判据),而非静默替换。
4. **Given** 一个 goal 已达成或已放弃, **When** 更新其状态, **Then** 定义仍留在归档中并携带终态,不被删除——历史目标是项目记忆的一部分。
5. **Given** 一段描述里捆绑了多个目标, **When** 试图作为一个 goal 归档, **Then** 被要求拆分为各自独立的身份,而非归档成一份复合定义。

### User Story 2 - 团队引用而不复制:消除同一目标的多份副本 (Priority: P1)

作为团队维护者,我希望团队只需**声明它服务于哪个 goal**,而不必把目标叙述抄进 `team.md` 的两个位置。多个团队服务同一个 goal 时,它们指向同一份定义;我改定义,所有团队看到的目标同时更新。

**Why this priority**: 与 US1 并列 P1。"这些 goal 都是分散的"是用户诉求的原话,去重是本需求的核心价值。它也直接消除一类真实缺陷:同一目标的两份副本可以不一致,而没有任何机制会发现。

**Independent Test**: 让两个团队引用同一个 goal 定义;二者解析出的目标叙述与成功判据逐字相同;修改定义后两个团队再次解析,均反映新内容且无需编辑任何团队文件;未迁移的存量团队仍能正常工作。

**Acceptance Scenarios**:

1. **Given** 一个已归档的 goal 与两个声明引用它的团队, **When** 解析各团队的目标, **Then** 两者得到逐字相同的目标叙述与成功判据,且来源指向同一份定义文件。
2. **Given** 团队引用了一个不存在的 goal 身份, **When** 解析, **Then** 报为断链引用并指明缺失的身份,不静默降级为空目标。
3. **Given** 一个存量团队只有内联的目标而未引用任何 goal 定义, **When** 解析, **Then** 仍以其内联目标正常工作,MUST NOT 要求先迁移(与 036 对未声明 [[STR-002]] 团队的处置一致)。
4. **Given** 团队同时声明了引用与内联目标且两者不一致, **When** 解析, **Then** 以被引用的定义为权威,并把不一致显式报出供人裁决。
5. **Given** goal 定义被修改, **When** 团队下次运行, **Then** 无需编辑任何团队文件即反映新定义。

### User Story 3 - 目标级读者视图:goal 定义与其推进状态对齐 (Priority: P2)

作为关心"目标推进到哪里"的读者,我希望 goal 的**定义**与需求 036 产出的**推进总结**是同一个目标的两面:总结里的项目叙述与里程碑来自 goal 的定义与成功判据,而不是从某个团队的措辞里推断。

**Why this priority**: 这是把新概念接进既有机制的兑现点,依赖 US1/US2 已有定义与引用,故置 P2。它同时修掉 036 的一处现存弱点——目前项目叙述取自"任一团队的 goal 正文",多团队措辞不一致时只能记为待裁决。

**Independent Test**: 对一个被两个团队引用的 goal 产出总结:总结的项目叙述取自 goal 定义(而非任一团队的副本);里程碑逐条来自 goal 的成功判据;两个团队措辞差异不再产生"待裁决"缺口。

**Acceptance Scenarios**:

1. **Given** 一个有定义文件的 goal, **When** 产出其总结, **Then** 项目叙述取自该定义,里程碑逐条取自其成功判据。
2. **Given** 两个团队对同一 goal 的内联措辞不同但都引用了同一定义, **When** 产出总结, **Then** 不再报"goal 正文不一致"待裁决项——定义已是唯一权威。
3. **Given** 一个 goal 尚无任何团队推进, **When** 查看其状态, **Then** 能区分"目标已定义但尚未启动"与"目标在推进中",而不是无从判断。

### User Story 4 - 存量迁移:不要求先改造再使用 (Priority: P3)

作为已有 4 个团队的维护者,我希望新概念上线后不必先做一轮迁移:未引用任何 goal 定义的团队照旧工作;愿意迁移时,能从团队现有的内联目标一键生成一份 goal 定义并把团队改为引用,内联副本的去留由我决定。

**Why this priority**: 存量是常态,但它建立在 US1/US2 之上且不阻塞主路径,故置 P3。其真正价值是把"零改造即可用"钉成验收项——否则新概念会因为迁移成本而无人采用。

**Independent Test**: 4 个存量团队在不做任何编辑的情况下全部照旧工作;对其中一个执行迁移:生成的 goal 定义与该团队原内联目标语义一致、团队改为引用后解析结果不变、其余 3 个团队不受影响。

**Acceptance Scenarios**:

1. **Given** 4 个未声明 [[STR-002]] 的存量团队, **When** 各自运行, **Then** 全部照旧工作,零编辑要求。
2. **Given** 一个存量团队的内联目标, **When** 执行迁移, **Then** 生成一份 goal 定义(目标叙述与成功判据取自该团队现有内容)并把团队改为引用,解析结果与迁移前一致。
3. **Given** 迁移已完成, **When** 检查该团队, **Then** 内联目标是否保留由用户决定,机制 MUST NOT 强制删除(以免破坏其可读性)。

### User Story 5 - 多团队协调:同一目标下是分工,不是抢地盘 (Priority: P2)

> 文档顺序不等于优先级顺序:本故事置 P2,排在 P3 的 US4 之后只是为了避免又一次重编号。

作为同时开了几个团队去推进一个 goal 的维护者,我希望能一眼看到**谁在推进这个 goal**,并且当两个团队的范围压在一起时被明确告知,而不是等到一方的产出被另一方覆盖才发现。我要的是一轮协调:机制把重叠摆出来、给出一份重划提议,我裁定,然后各团队按裁定各守其地。

**Why this priority**: 依赖 US1/US2 已有定义与引用(至少两个团队引用同一 goal 才谈得上协调),故不置 P1;但它是 N 团队 : 1 goal 从"能聚合"走到"能并行工作"的必要条件——没有它,多团队共享一个 goal 在写入面上是不安全的,而这正是用户当前的关切。

**Independent Test**: 让两个团队引用同一 goal 并声明有交集的范围;刷新该 goal 的总结后,名册列出两个团队及其范围,重叠区被指名到具体路径;协调轮给出重划提议且不改动任何文件;裁定后各 `team.md` 的范围更新且两者 Write Scope 交集为空;把其中一个团队的范围改成非路径维度(如"框架自身"),该项被如实并列为待裁定而非判为无重叠。

**Acceptance Scenarios**:

1. **Given** 三个团队声明了同一 [[STR-002]], **When** 刷新该 goal 的总结, **Then** 派生名册列出全部三个团队及各自范围、身份类型与是否在推进,且 goal 定义文件字节未变。
2. **Given** 两个团队的 Write Scope 存在路径交集, **When** 检测运行, **Then** 交集被指名到具体路径并判定为重叠;**And** 仅 Read Scope 相交的团队不被判为重叠。
3. **Given** 已检出重叠, **When** 发起协调轮, **Then** 产出一份重划提议(含提议依据),且此时**尚未**改动任何 `team.md`。
4. **Given** 人已裁定某份重划, **When** 落盘, **Then** 各团队的 `team.md` 范围被更新,协调结果不在 goal 目录内新增被撰写的文件。
5. **Given** 一个团队根本没声明团队级范围, **When** 检测运行, **Then** 报为"范围未声明、无法判定重叠",而不是当作空范围给出"无重叠"。
6. **Given** 两个团队都声称覆盖同一个非路径维度(如"保持框架持续更新"), **When** 检测运行, **Then** 两条声明被如实并列为待裁定项,机制不自行判定二者等价。
7. **Given** 一个争用区两个团队都必须写, **When** 协调, **Then** 它被列为该 goal 的禁写区或归给唯一一个团队,不留在"双方都可写"的状态。

### Edge Cases

- **goal 身份与既有目录名冲突**:归档目录下已有同名条目 → 拒绝创建并提示,不覆盖。
- **两个 goal 的成功判据实质重叠**:机制不做语义去重,只如实并列;是否合并由人裁决。
- **goal 叙述被写成任务清单或实施计划**:违反"结果而非步骤"(FR-027)→ 被指出并要求改写为期望达成的结果,不静默归档。
- **goal 的作用对象超出本项目源码可实现的范围**(例如"让本项目使用的 spec-kit 框架保持持续更新")→ 照常归档并可被团队引用;机制 MUST NOT 因为找不到对应的 FR 而拒绝它(FR-029)。
- **goal 定义被删除而团队仍引用**:报为断链引用,团队回退到内联目标(若有)或明确失败,不静默产出空目标。
- **同一团队声明引用两个 goal**:拒绝——团队在任一时刻只服务一个 goal(与 036 的 GI-2 一致)。
- **goal 只有叙述没有可验证判据**:允许归档,但里程碑组为空,且在消费侧显式声明"该目标未提供可验证判据",不虚构判据。
- **同一 goal 目录内定义与总结混写**:目录既有被撰写的 [[STR-003]] 又有派生的 [[STR-004]] 子树 → 写入面是 [[STR-004]] 白名单(FR-023);若刷新写到了 [[STR-003]],视为写入面违规而非"顺带更新"。
- **派生产物散落在 goal 目录根**:迁移前的产物直接躺在 `<goal-slug>/` 根(036 现状:`data/project-input.yaml` 与被调技能产出的 `project.md` / 图表)→ 视为待迁移状态,MUST 收拢进 [[STR-004]],MUST NOT 与 [[STR-003]] 平级长期共存。
- **迁移期新旧路径并存**:迁移过程中若旧 `.specify/project/goal/` 仍有产物 → 以 [[STR-001]] 为唯一权威,旧位置的产物 MUST 被迁移或删除,MUST NOT 长期并存两份总结。
- **同一 goal 下只有一个团队**:名册照常产出(单行),重叠集为空,协调轮不发起——"无重叠"与"无从判定"MUST 被区分开。
- **两团队的范围写法不同但指向同一路径**(glob 与显式枚举、相对与规范化路径、`{a,b}` 花括号与展开形式)→ MUST 先规范化再求交,MUST NOT 因写法差异漏判重叠(此类漏判在本仓库已有先例:花括号路径曾逃过一次存在性检查)。
- **团队改绑到另一个 goal 后仍与新 goal 的团队重叠**:改绑即视为范围变更,下次刷新按新 goal 重新检测(与 036 的 GI-2 一致);原 goal 的名册记录其已不再参与。
- **争用区无法归给单一团队**(两团队确实都必须写)→ 转为该 goal 的禁写区并显式上报,或由人裁定两团队不并发运行;MUST NOT 静默允许双方并发写。
- **团队级范围与其成员级 territory 不一致**(成员写到了团队声明之外)→ 报为越界,MUST NOT 静默放行;两级 territory 的一致性本身是可检查的。

## Requirements *(mandatory)*

### Functional Requirements

**goal 定义与归档**

- **FR-001**: 系统 MUST 提供项目级 goal 的**定义归档**(见 [[STR-001]]),每个 goal 一份定义,作为该 goal 的单一事实源。
- **FR-002**: goal 定义 MUST 恰由三部分构成:目标叙述、可验证成功判据(零条或多条)、生命周期状态。身份由 [[STR-002]](即归档目录名)承载,MUST NOT 另立身份字段;创建 / 更新时间等元信息服务于 FR-005 的变更追溯,MUST NOT 被计入 goal 的构成部分。
- **FR-003**: goal 的身份 MUST 复用需求 036 已确立的 [[STR-002]] 语义与文法(首字符字母或数字,其余限 `[A-Za-z0-9_.-]`,且为合法路径片段),MUST NOT 引入第二套 goal 标识机制。
- **FR-004**: 以已存在的身份创建 goal MUST 被拒绝并指向修改路径;既有定义 MUST NOT 被静默覆盖。
- **FR-005**: goal 的成功判据被修改时,系统 MUST 记录该变更(保留可追溯的前值),MUST NOT 静默替换。
- **FR-006**: 生命周期状态 MUST 恰为三态:进行中(`active`)、已达成(`achieved`)、已放弃(`abandoned`);终态 goal MUST 保留在归档中而非被删除。
- **FR-007**: goal 定义 MUST 是**被撰写的事实源**,MUST NOT 由任何派生流程改写(与 036 的总结产物形成输入/输出的清晰分工)。

**团队引用**

- **FR-008**: 团队 MUST 能以 [[STR-002]] 声明它服务于哪个 goal,并据此解析出目标叙述与成功判据;同一 [[STR-002]] 值的多个团队 MUST 解析到同一份定义。
- **FR-009**: 一个团队在任一时刻 MUST 只服务一个 goal;声明两个 MUST 被拒绝。
- **FR-010**: 引用了不存在身份的团队 MUST 被报为断链引用并指明缺失身份,MUST NOT 静默降级为空目标。
- **FR-011**: 未声明 [[STR-002]] 的存量团队 MUST 仍能以其内联目标正常工作,MUST NOT 要求先迁移。
- **FR-012**: 团队同时存在引用与内联目标且不一致时,MUST 以被引用的定义为权威,并把不一致显式报出供人裁决。

**消费方集成**

- **FR-013**: 需求 036 的总结机制 MUST 在 goal 定义存在时以其为项目叙述与里程碑的来源,取代当前"取自任一团队 goal 正文"的做法;定义缺失时 MUST 回退到既有行为(不破坏 036 的存量路径)。
- **FR-014**: 本需求 MUST 保留 036 已确立的**聚合语义与身份文法**(N 团队 : 1 goal、`goal_slug` 文法、团队命名空间化 ID、并发串行化);其**交付目录位置**按 FR-022 迁移,聚合行为本身 MUST NOT 改变。
- **FR-015**: 系统 MUST 能区分"目标已定义但尚无团队推进"与"目标在推进中"两种状态。

**迁移与去重**

- **FR-016**: 系统 MUST 提供从团队内联目标生成 goal 定义并将该团队改为引用的迁移路径;迁移前后该团队解析出的目标 MUST 语义一致。
- **FR-017**: 迁移 MUST NOT 强制删除团队的内联目标副本;是否保留由用户决定。
- **FR-018**: 迁移 MUST 逐团队可选,MUST NOT 要求全量迁移才能启用本机制。
- **FR-019**: 团队域中现存的 goal 撰写与修改指引(`create-team/references/goal.md`、`improve-team/references/goal-editing.md`、`optimization-goals.md` 等)MUST 按两级事实源改写,MUST NOT 与任一级并存为第二套说法:关于 goal **概念**的说法(是什么、与 requirement 的分界、单一性、判据权威)MUST 链接到 [[STR-005]];某个具体目标的**内容**MUST 指向该 goal 在 [[STR-001]] 下的实例定义。

**单一 goal 目录(收编 036 的总结交付目录)**

- **FR-020**: [[STR-001]] MUST 是项目中 goal 相关产物的**唯一**归属位置,同时承载该 goal 的**定义**(被撰写)与**总结**(派生);MUST NOT 存在第二个以 goal 为索引的目录。
- **FR-021**: 新增的任何命令行选项 MUST NOT 与既有 `--goal` 语义冲突——该选项已被两支脚本占用且含义不同(见 Assumptions)。
- **FR-022**: 需求 036 落地的总结交付目录 MUST 从 `.specify/project/goal/<goal-slug>/` 迁移到 [[STR-001]]`<goal-slug>/`[[STR-004]] 之下;`.specify/project/` MUST NOT 再存放任何 goal 相关产物。迁移 MUST 覆盖**全部活跃引用面**——计划阶段实测 **24 个源文件**:4 个 canonical 源(`skills/create-team/{SKILL.md,references/summary-mapping.md,scripts/build-summary-input.py}`、`templates/commands/team.md`)、4 个 `.specify/` 镜像、5 份 per-tool 生成副本、9 个测试文件、1 个用户文档(`docs/reference/commands/team.md`)、1 个 Tool 记录。**活跃面**的残留旧路径引用数 MUST 为 0;**历史面** MUST NOT 被改写——036 的既有规格产物、append-only 的反馈记录、以及本规格 `## Clarifications` 中逐字引用旧路径的条目(计划阶段实测 18 个文件)是历史事实,改写它们等于篡改记录。
- **FR-023**: 在 [[STR-001]]`<goal-slug>/` 之内,**被撰写的定义**MUST 落在 [[STR-003]],**派生的总结**MUST 全部落在 [[STR-004]] 子树之内;总结刷新的写入面 MUST 是 [[STR-004]] 的白名单,MUST NOT 写入 [[STR-003]](承接 FR-007 与 036 的写入面纪律)。
- **FR-024**: 迁移 MUST 保持 036 的既有验收能力不回归:其成功判据与测试在迁移后 MUST 仍然成立(仅路径更新),MUST NOT 因迁移而削弱任何既有断言。

**撰写入口**

- **FR-025**: goal 定义的创建、修改、查看与迁移 MUST 由单一入口 `/speckit.goal` 承载(与 Feature 027 以 `/speckit.team` 作为团队域唯一入口同构);MUST NOT 存在第二个撰写入口。
- **FR-026**: `/speckit.goal` MUST 按框架既有的镜像模型交付(canonical `templates/commands/goal.md` → `.specify/` 镜像 + 各受支持工具的命令副本,经 `sync-mirrors.py` 扇出),MUST NOT 手工双写任何副本。

**概念对齐(以 [[STR-005]] 为准)**

- **FR-027**: goal 叙述 MUST 是期望达成的**结果**(北极星),MUST NOT 被写成任务清单或实施计划。
- **FR-028**: 一个 goal MUST 只承载一个目标;复合目标 MUST 被拆分为各自独立的 [[STR-002]],各有自己的目录与生命周期。项目 MAY 同时持有多个 `active` goal。
- **FR-029**: goal 的作用对象 MUST NOT 被限制为"本项目源码可实现的范围"——它可指向框架自身、代码规范收敛、能力运行结果等任意维度;机制 MUST NOT 因某个 goal 找不到对应的 FR 而拒绝归档它。
- **FR-030**: goal 的成功判据 MUST 被视为**按度量推进**的达成条件(进度 / 阈值 / 评分),消费方 MUST NOT 把它们当作逐条 pass/fail 条款;具体进度表示形态由计划阶段裁定。
- **FR-031**: goal 判据与需求规格的 SC-xxx **权威互斥**:SC-xxx 只服务其所属 Feature,goal 判据是跨 Feature 的;两侧判据 MUST NOT 互相复制,跨 Feature 汇总 MUST 只发生在评估 / 总结层并各自引用自身来源。
- **FR-032**: goal 与 requirement 分属**不同平面且无必然层级**:`requirements.md` MUST NOT 携带 goal 字段,goal 定义 MUST NOT 枚举其下的 FR;二者的关联 MUST 只以观察形态出现在评估结果、团队总结与运行报告中。

**多团队协调(N 团队 : 1 goal)**

- **FR-033**: 同一 goal 下的**参与团队名册** MUST 由机制从各团队声明的 [[STR-002]] **派生**得出,并作为派生产物落在 [[STR-004]] 之内;MUST NOT 成为 [[STR-003]] 的字段,MUST NOT 使团队↔goal 的绑定变为双向(承接 FR-007 与单向绑定语义)。
- **FR-034**: 名册 MUST 至少载明每个团队的:团队 slug、其声明的团队级范围、身份类型(显式 / 推断,承接 036 的 GI-1)、以及当前是否在推进(承接 FR-015);已改绑离开的团队 MUST 被标注为不再参与而非从名册消失。
- **FR-035**: 团队 MUST 能声明**团队级范围**(territory),沿用既有的 territory 词汇(Write Scope / Read Scope / Forbidden);声明 MUST 同时支持**路径形**条目(可程序求交)与**类型化非路径**条目(如框架自身、运行环境等,承接 FR-029)。该声明 MUST 对四种协作模式一律适用,MUST NOT 只在 parallel 模式下成立。
- **FR-036**: 机制 MUST 在同一 goal 的团队之间检测范围重叠:路径形条目 MUST 先规范化再求交并给出确定结论(指名到具体路径);非路径条目 MUST 如实并列为待裁定项,机制 MUST NOT 自行判定两条非路径声明等价。
- **FR-037**: 同一 goal 下,任两个团队的 **Write Scope** MUST NOT 重叠——把既有的成员级"零写重叠"不变式提升到团队级;**Read Scope 重叠 MUST 被允许**,且仅 Read Scope 相交 MUST NOT 被判为重叠。
- **FR-038**: 被两个及以上团队写入的**争用区** MUST 在协调中归给**唯一**一个团队,或转为该 goal 的禁写区(此后仅由人处置);MUST NOT 停留在"多方都可写"的状态。
- **FR-039**: 协调轮 MUST 只**检测并提议**新划分(提议 MUST 附依据),MUST 由人裁定后才落盘;机制 MUST NOT 自行改写任何团队的范围。
- **FR-040**: 裁定后的划分 MUST 写回各自的 `team.md`(团队保持唯一声明方),MUST NOT 在 goal 目录内新增被撰写的协调记录——[[STR-003]] 与 [[STR-004]] 的二分(FR-023)保持不变。
- **FR-041**: 重叠检测 MUST 搭载 036 既有的 goal 总结刷新(其刷新范围本就是该 goal 下的全部团队),MUST NOT 引入第二套触发机制;检测结论 MUST 出现在该 goal 的总结中,协调轮本身由人显式发起。
- **FR-042**: 团队未声明团队级范围时,机制 MUST 报为"范围未声明、无法判定重叠",MUST NOT 将其视为空范围而给出"无重叠"的结论;"无重叠"与"无从判定"MUST 是两种可区分的结论。

### Key Entities *(include if requirement involves data)*

- **Goal(目标)**:项目级一等概念,归档于 [[STR-001]]。**恰由三部分构成**——目标叙述、可验证成功判据、生命周期状态;身份由目录名([[STR-002]])承载,时间戳等为变更追溯的元信息。**被撰写的事实源**,非派生物。**作用对象不受限**:可指向框架自身、代码规范收敛、能力运行结果等任意维度,不以"本项目源码可实现"为界。
- **Goal Identity(目标身份)**:认定"同一个 goal"的键,复用 036 的 [[STR-002]];同时是归档目录名,故受路径片段安全约束。
- **Goal Success Criteria(成功判据)**:goal 的达成条件集合,**按度量推进**(进度 / 阈值 / 评分)而非逐条 pass/fail;是消费侧里程碑的唯一来源;可为空,空时消费侧显式声明而不虚构。其权威**跨 Feature**,与任一需求规格的 SC-xxx(只服务其所属 Feature)互斥且不互相复制。
- **Goal–Team Binding(目标—团队绑定)**:团队到 goal 的单向引用(N 团队 : 1 goal);团队侧只存身份,不存副本。
- **Goal Lifecycle(生命周期)**:`active`(进行中)/ `achieved`(已达成)/ `abandoned`(已放弃)三态;终态保留归档,构成项目的目标史。
- **Goal Archive(目标归档)**:[[STR-001]] 下的全部 goal 定义集合,即"项目当前与历史目标清单"的物化形态。
- **Goal 概念事实源**:[[STR-005]] —— goal 概念本身(定义、与 requirement 的平面分界、单一性、判据权威、绑定语义)的单一事实源,对本需求**只读**;本需求负责让实例定义与团队域指引与之一致,不负责修改它。
- **Team Roster(参与团队名册)**:同一 goal 下全部引用团队的**派生**清单(团队 slug + 团队级范围 + 身份类型 + 是否在推进),落在 [[STR-004]] 内。派生物,不是 goal 定义的字段——绑定仍是团队→goal 单向。
- **Team Territory(团队级范围)**:团队声明的 Write Scope / Read Scope / Forbidden,沿用既有成员级 territory 的词汇但抬到团队级,四种协作模式通用。含**路径形**条目(可规范化后求交)与**类型化非路径**条目(框架自身、运行环境等)。由团队侧撰写,是协调裁定的落盘处。
- **Overlap Finding(重叠发现)/ Contested Area(争用区)**:同一 goal 下两团队范围的交集。路径形交集是确定结论并指名到路径;非路径交集只如实并列为待裁定。其中被两个以上团队**写入**的部分即争用区,必须归给唯一团队或转为禁写区。
- **Coordination Round(协调轮)**:针对已检出重叠的一次重划过程——机制提议(附依据),人裁定,裁定结果写回各 `team.md`。机制自身无改写权。

## Out of Scope

- **宿主 CLI 的 goal 集成(2026-08-05 用户裁定)**:不在本需求范围内,留待独立需求。裁定依据是一次官方文档核实(`https://docs.qoder.com/cli/goal.md`):该 CLI 的命令面为 `/goal set <描述> [--turns <n>]` 与 `status` / `pause` / `resume` / `take` / `clear`,其中 **`set` 只接受内联文本**——不存在以文件路径或 goal 身份指定目标的选项;目标达成后被自动清除,且其生命周期由会话持有(`/goal take` 接管)。用户原始描述中"通过这个goal的描述文件来指定"因此**无法由该 CLI 侧直接兑现**,只能在 Spec Kit 侧渲染文本代偿。该代偿属于另一层次的能力(消费方适配),单独立项比夹带进本需求更清晰。本需求仍为其保留了前提:goal 定义已是稳定可引用的项目级对象。

- **goal 之间的语义去重、层级与依赖建模**:判据实质重叠只如实并列(见 Edge Cases),本需求不引入 goal 的父子层级或依赖图。

## Assumptions

- **单一 goal 目录(2026-08-04 用户裁定)**:[[STR-001]] **收编**需求 036 刚落地的 `.specify/project/goal/<goal-slug>/`,`.specify/project/` 不再存放 goal 相关产物。理由是同一个 goal 的定义与总结本就属于同一对象的两面,分置两个高度相似的路径(仅差一层目录)只会持续制造误读。代价已实测(计划阶段复核):**24 个活跃源文件**引用旧路径需一并迁移(FR-022),其中包含 5 份 per-tool 生成副本与 036 的 9 个测试文件;另有 18 个历史面文件同样含该字符串但 MUST NOT 被改写。旧目录 `.specify/project/goal/` 在本仓库尚未实体化,故这是纯代码/文档/测试迁移,无存量数据搬移。这笔返工是有意接受的,换取长期只有一个 goal 索引。目录内部以 [[STR-003]](定义)与 [[STR-004]] 子树(总结)分离(FR-023),使 036 的写入面纪律由"黑名单"变为单一子树白名单,继续可机械校验。
- **身份复用 `goal_slug` 而不新造**:036 已把 [[STR-002]] 确立为"同一个 goal"的连接键并写入团队 frontmatter schema,其文法受被调技能的 DDL 约束(首字符字母或数字,其余限 `[A-Za-z0-9_.-]`)。本需求沿用同一键与同一文法,使定义与聚合天然对齐;新造第二套标识会立刻产生两套身份的交接问题。
- **团队侧改为"引用 + 可选内联"而非强制替换**:团队声明 [[STR-002]] 即视为引用该定义;内联 `goal:` 与 `## Goal` 保留为合法(可读性与存量兼容),但定义存在时以定义为权威(FR-012)。这与 036 对未声明 [[STR-002]] 团队采用推断回退的处置同构,故存量零改造可用。
- **`--goal` 命令行选项已被占用**:`build-summary-input.py --goal` 表示"要聚合的 goal 身份",`match-team-preset.py --goal` 表示"目标文本"。本需求若需新增选项,MUST 避开该名称或明确复用其中一种语义(FR-021);建议用 `--goal-id` 之类无歧义形式。具体命名留待 `/speckit.plan` 裁定——它取决于 `/speckit.goal` 是否需要脚本级选项,而那是设计决定,不是需求歧义。
- **新增命令面的代价已知并接受(2026-08-05 用户裁定)**:goal 定义的撰写入口取"新建 `/speckit.goal` 命令"而非新增技能或扩展 `/speckit.team`,与 goal 作为一等概念对称,并与 Feature 027 以 `/speckit.team` 为团队域唯一入口的既有范式同构。代价是一个新命令面:canonical `templates/commands/goal.md` + `.specify/` 镜像 + 各受支持工具的命令副本(FR-026),须在 `/speckit.plan` 的 Constitution Principle IX(Framework Scope Discipline)检查中显式记录理由。扩展 `/speckit.team` 被否决的原因是它会把项目级概念的撰写绑回团队命令,与本需求"goal 不是团队属性"的核心主张直接冲突。
- **goal 与 requirement 分属不同平面,彼此无必然层级**([[STR-005]] 的裁定):requirement 的作用对象固定——本项目源码 / 配置要实现的 feature;goal 的作用对象不受限。二者互不派生、互不包含、互不校验,也没有结构化字段相连(FR-032);关联只在评估与总结层以观察形态出现。Feature 是项目能力条目,是第三个独立事物。本需求不合并这三者,也不改动 Feature Index 的语义。
- **概念事实源为只读输入(2026-08-05 用户裁定)**:[[STR-005]] 是 goal **概念**的单一事实源,本需求只引用、不修改它(其 `.specify/shared/definitions/` 镜像同理)。因此本轮核对的处置一律是"改规格以对齐定义",而非"改定义以迁就规格"——生命周期由 4 态收敛为 3 态即属此列。若日后确需第四个状态或其他概念变更,应作为对该文件的独立修订提出,不由本需求夹带。
- **目录内布局由本 Feature 拥有**:[[STR-005]] 只固定 goal 的**位置与语义**,并明确"`<goal-slug>/` 之内的文件布局归实现 goal 管理的 Feature 所有"。因此 [[STR-003]] + [[STR-004]] 的划分(含把 036 的派生总结收进同一 goal 目录)不与定义文件冲突,而正是它显式授权的范围;定义文件的存储树只画出 goal 定义本身,并未排除同目录下的派生子树。
- **成功判据可为空**:允许只有叙述的 goal 归档,此时消费侧(如 036 的里程碑)显式声明"未提供可验证判据"而不虚构——与 036 既有的诚实降级纪律一致。
- **协调复用既有 territory 词汇,而非另造"覆盖区域"(2026-08-05 用户裁定)**:团队内部早有答案——`skills/create-team/SKILL.md` 的 Territory Division 以 Write Scope / Read Scope / Forbidden 加"零写重叠"不变式解决成员之间的同一问题,并已有可选的 worktree 物理隔离作后手。本需求把这套词汇与不变式抬到团队级(FR-035 / FR-037),而不是引入第二套范围概念。必须新增**团队级**字段的原因是实测:`territory` 只存在于 parallel 模式的**成员级**,serial / iteration / continuous 三种模式完全没有,故无法只靠"求成员范围的并集"来推导团队范围。路径形与非路径形并存则是 FR-029 的直接后果——goal 的作用对象不受限,团队的覆盖范围因此不一定是文件形状的。
- **协调与 [[STR-005]] 兼容性已核对**:定义文件规定绑定是"单向身份引用,团队侧只存身份"。本需求的名册是**派生**的(FR-033)——由机制扫描各团队声明得出,不写入 goal 定义、不产生 goal→team 的存储字段,故单向绑定不变;裁定后的划分写回 `team.md`(FR-040),团队仍是唯一声明方。定义文件的单一性规则本就写明"项目可并行持有多个 active goal,each advanced by its own **team(s)**",即 N 团队推进一个 goal 是它已经认可的形态,只是未涉及协调。因此协调是**团队域的增量**而非 Goal 概念的变更,上一轮"定义文件为只读输入"的裁定继续成立,本需求不修改它。
