# Requirements Specification: Team Summary 信息管理机制(团队概念 → 项目管理概念映射 + 阶段性总结)

**Requirement Branch**: `036-team-summary`  
**Created**: 2026-08-04  
**Status**: Draft  
**Input**: User description: "需要为"team"增加一个"summary"的信息管理机制.当前创建team的时候都会设置一个goal,作为team的目标,然后team按照拓扑结构创建多个agent进行协作.需要在team的执行的流程中阶段性的调用summarize-project技能进行进行项目状态总结,将team的概念映射到summarize-project技能定义的项目管理概念中."

## Related Feature *(mandatory)*

**Feature ID**: 027  
**Feature Name**: Team Management

**Binding evidence**: Feature 027 owns the team domain(`/speckit.team` create/modify/run、`create-team` + `improve-team` 技能、`.specify/teams/` 持久化),且其 `## Future Evolution Suggestions` 已预告本项——「Team run history/observability under `.specify/teams/` for improve-team evidence」。本规格的全部改动面(团队配置 schema、四种模式执行流触发点、`/speckit.team run` 确认门禁、团队交付目录)均落在团队域内;FR-024 明确禁止改动 `summarize-project`,故不绑定 Feature 013(Skills Command)。

## Overview

团队(team)当前只有两类可读产物:每次运行的 `runs/<ts>-report.md`,以及 continuous 模式的 `STATE.md` + `run-log.jsonl`。它们都是**单次视角**——读者可以知道"上一个 cycle 发生了什么",但无法回答"这个团队相对它的 goal 走到了哪里、谁在做什么、有没有延期"。团队跑得越久,报告越多,这个问题越严重:信息量随运行次数线性增长,可理解度反而下降。

本需求为团队引入 **summary 信息管理机制**:把团队自身当作一个"项目",在团队执行流程的**阶段边界**上调用 `summarize-project` 技能,产出一份**累积式**的团队状态总结(概览 / 需求与特性 / 功能分解 / 里程碑 / 任务进展 五个呈现层面,含四态进度编码与配套图表)。

落地的关键不是"再写一个报告模板",而是**一层概念映射 + 一次表单生成**:

- **概念映射(单一事实源)**:团队词汇(goal、静态结构 Role × Stage × Type 名册、动态结构=协作模式、cycle/generation/stage/territory、STATE 分级、run-log 计数)对齐到 `summarize-project` 定义的七个项目管理实体(`project` / `people` / `phases` / `work_items` / `milestones` / `features` / `sources`),四种协作模式各有自己的"阶段"与"工作项"语义。
- **表单生成(程序优先)**:`summarize-project` 的唯一输入是项目输入表单(见 [[STR-004]]),技能对它只读不改,R 档字段缺失会以退出码 3 阻断。因此团队侧必须**扮演表单作者**,由确定性程序从团队的机器可读工件(`team.md` frontmatter、`run-log.jsonl`、`STATE.md` 分节、子代理结果清单)派生表单,而不是让大模型通读历史运行报告后转写。

边界明确:`summarize-project` 保持不变(仍是只读的呈现工具),团队侧适配它;summary 是**派生物、增量物**,不替代 run report / STATE.md / run-log.jsonl,也不修改 `team.md`。

**双索引**(2026-08-04 范围修订):产物分两侧落地——`.specify/teams/<team-slug>/` 以 **team** 为索引,只保留运行信息(`runs/` / `STATE.md` / `run-log.jsonl` / `items.jsonl`),回答"这个团队在怎么运行";[[STR-001]] 以 **goal** 为索引,承载**唯一的完整总结**(自包含交付目录),聚合所有声明了同一 [[STR-006]] 的团队,回答"这个目标推进到哪里"。goal 身份由 `team.md` frontmatter 显式声明,故 goal 正文改写不会迁移目录。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 概念映射与表单自动生成:让团队的状态能被项目化呈现 (Priority: P1)

作为团队的维护者,我希望团队的既有工件能自动变成 `summarize-project` 认得的项目输入:团队的 goal 成为项目目标、成员名册成为人员表、协作模式对应的阶段单位成为阶段表、团队实际处理的工作单位成为工作项表、goal 里的可验证成功判据成为里程碑。这样我不需要手工填任何表单,就能对任意一个团队产出状态总结。

**Why this priority**: 这是整个机制的地基。没有映射与表单生成,`summarize-project` 在每个团队上都会以退出码 3 阻断并要求人工补填,后续所有触发、累积、纪律都无从谈起。它也是唯一能独立交付价值的最小切片:哪怕只支持"手动对一个团队跑一次总结",读者已经获得了此前不存在的全局视图。

**Independent Test**: 取四个既有团队(四种协作模式各一),仅凭其 tracked 工件生成表单:表单校验退出 0(非 3)、数据装载与一致性校验通过,并产出含五个呈现章节与功能分解图的总结,全程零手工填表。

**Acceptance Scenarios**:

1. **Given** 一个 `pattern: continuous` 的团队(有 `team.md` / `STATE.md` / `run-log.jsonl` / `runs/`), **When** 生成项目输入表单, **Then** 项目名取自团队 `name`、项目目标叙述承载 goal、阶段为各 cycle、工作项为 STATE 中被跟踪的条目、人员为 `members[]`,且 R 档字段齐备。
2. **Given** 一个 `pattern: iteration` 的团队, **When** 生成表单, **Then** 阶段为各 generation(代)、工作项为每代的变体任务与被采纳的改进项、里程碑含收敛阈值达成判据。
3. **Given** 一个 `pattern: serial` 的团队, **When** 生成表单, **Then** 阶段为链上各 stage、工作项为各 stage 的交付物,成员间的阻塞关系映射为工作项依赖。
4. **Given** 一个 `pattern: parallel` 的团队, **When** 生成表单, **Then** 工作项为各 territory(领地),派发批次作为阶段。
5. **Given** 团队 goal 中写有可验证成功判据(阈值 / 达标条件), **When** 生成表单, **Then** 每条判据成为一条里程碑,使"至少一组工作项或里程碑非空"的 R 档约束在**首次总结时即可满足**。
6. **Given** 呈现引擎不读系统时钟, **When** 生成表单, **Then** 基线日期由本次运行/cycle 的时间戳显式写入,而非由被调技能推断。

### User Story 2 - 阶段性触发:总结长在执行流程里,而不是靠人记得跑 (Priority: P1)

作为团队的运营者,我希望总结在团队执行流程的**阶段边界**上自动刷新——serial 在 stage 交接后、parallel 在交叉校验汇总后、iteration 在每代 DECIDE 之后、continuous 每 N 个 cycle——并且这个动作受预算与节奏门控:预算吃紧时它是第一个被跳过的步骤,且跳过这件事本身被明确记录,而不是静默消失。

**Why this priority**: 与 US1 并列 P1。"阶段性"是用户诉求的原话,也是本机制区别于"手动跑一次总结"的核心价值:总结必须是流程的一环。同时它承担唯一的成本风险面——continuous 团队每 2h 一个 cycle,若每 cycle 都做全量出图总结,会直接撞上 token 预算断路器。因此触发与门控必须同批交付。

**Independent Test**: 对一个团队连续运行两次:在声明的阶段边界处总结自动刷新;把预算占用抬到 report-only 档后再运行,总结被跳过、cycle 仍正常完成、且运行报告中出现明确的跳过记录。

**Acceptance Scenarios**:

1. **Given** 一个团队在执行流程中到达其模式声明的阶段边界, **When** 该边界完成, **Then** 总结被刷新,且刷新结果在本次运行报告中以状态行声明(见 [[STR-005]])。
2. **Given** `config.summary` 声明了节奏(如 continuous 每 N cycle), **When** 未到节奏点的 cycle 结束, **Then** 不产出总结,运行报告记录按节奏跳过,不视为失败。
3. **Given** 预算阶梯触发 report-only 档或 kill-switch, **When** 运行走到总结步骤, **Then** 总结被跳过并记为 [[STR-003]],运行正常收尾,预算不因总结而越线。
4. **Given** 团队达成 goal 或运行终止(收敛 / halt / 人工停止), **When** 收尾, **Then** 产出一次终态总结(除非预算已越线)。
5. **Given** `/speckit.team run` 的 preview → confirm 门禁, **When** 展示本次运行计划, **Then** 明确披露本次运行是否会产出总结,使用户在确认前即知晓其成本。

### User Story 3 - 累积式团队总结:一份当前视图,而不是又一堆报告 (Priority: P2)

作为团队成果的外部读者(未读过任何运行报告的人),我希望团队目录下只有**一份当前**的总结:它反映到目前为止所有运行的累积状态——哪些工作项已完成、哪些在进行、哪些延期、里程碑达成到哪一步——并且我上次手工写在总结里的批注,下次刷新后仍然在。

**Why this priority**: 这是读者侧的价值兑现点,但依赖 US1/US2 已能产出总结,故置 P2。累积(而非每次快照)是"项目状态总结"成立的前提:一次性快照与既有运行报告无本质区别。

**Independent Test**: 对同一团队刷新两次总结,在第一次产物中人工加入批注:第二次刷新后,总结中同时体现两次运行的工作项与进度、批注原样保留、交付目录中仍只有一份当前总结(而非两份并列报告)。

**Acceptance Scenarios**:

1. **Given** 团队已有 K 次运行, **When** 刷新总结, **Then** 交付目录中是一份反映全部 K 次累积状态的当前总结,历史运行细节仍留在 `runs/` 中不被搬迁。
2. **Given** 上一版总结中存在人工批注章节, **When** 刷新, **Then** 批注原样保留。
3. **Given** 某工作项在上次总结为进行中、本次运行完成, **When** 刷新, **Then** 其状态推进为已完成,且该变化可追溯到具体的团队工件(见 US4)。
4. **Given** 团队 goal 在生命周期中被有意修改, **When** 刷新总结, **Then** 新 goal 生效、历史工作项保留,goal 变更在元信息中被记录,而非静默改写历史。

### User Story 4 - 只读与出处纪律:总结不许改源,数字不许没出处 (Priority: P2)

作为框架维护者,我要求总结这一步是**纯派生**的:它只写团队自己的交付目录(与反馈存量),绝不修改 `team.md` / `STATE.md` / `run-log.jsonl` / `runs/` 等事实源;并且总结里出现的每一个状态与百分比都能指回一个具体的团队工件路径,没有出处的数字宁可记为"未知",也不许写成 0%。

**Why this priority**: 团队机制已有"子代理不得写 tracked 团队文件""状态不可自标绿"等硬规则,总结是新增的写入面与新增的数字来源面,两处都必须先封住边界再谈内容——否则一个派生报告会污染事实源,或制造出看起来精确的编造进度。

**Independent Test**: 在一次总结刷新前后审计文件变更:变更集仅落在团队交付目录(及反馈存量)内;对总结中每个百分比检查其出处字段,均指向一个 tracked 的团队工件路径;构造一个无进度依据的工作项,确认它呈现为"未知"而非 0%。

**Acceptance Scenarios**:

1. **Given** 一次总结刷新, **When** 审计写入, **Then** 写入仅落在该团队的交付目录与反馈存量,事实源工件字节不变。
2. **Given** 一个工作项带有进度百分比, **When** 校验表单, **Then** 其出处字段非空且指向具体团队工件(运行报告 / run-log 行 / 结果清单),缺出处时装载被拒绝。
3. **Given** 某工作项没有任何状态信号, **When** 呈现, **Then** 状态记为"未知"、进度记为无可计数依据,**不写** 0%、**不判**未开始。
4. **Given** 出处只存在于 git-ignored 位置(运行中间目录、Agent Execution 运行日志), **When** 生成表单, **Then** 该出处不被采用(运行时证据会被清理且不入库),降级为可追溯的 tracked 工件或记为未知。
5. **Given** 一个子代理试图写入 tracked 的总结产物, **When** 该写入发生, **Then** 被拒绝——tracked 总结只由团队主管写入。
6. **Given** 总结面向未读过运行报告的读者, **When** 检查五个呈现章节, **Then** 其中不出现团队内部标识符(代理 id、结果清单路径、运行中间目录路径),这些只出现在元信息与来源声明中。

### User Story 5 - 存量团队回填与材料缺口降级:薄材料也能产出诚实的总结 (Priority: P3)

作为已有团队的维护者,我希望机制上线后不需要重建团队:已跑过多轮的团队在下一次总结时能从既有 tracked 工件回填历史;而对材料本身就薄的团队(只有 `runs/`、没有 `STATE.md` / `run-log.jsonl`,或完全没有日期材料),总结要**如实声明缺口并降级出图**,而不是编造日期与工期把甘特图凑出来。

**Why this priority**: 存量团队与薄材料是常态而非例外,但它建立在 US1 的映射之上,且不阻塞主路径,故置 P3。它的真正价值是把"诚实降级"钉成验收项——薄材料下最容易发生的失败模式正是编造。

**Independent Test**: 对一个只有 `runs/` 的既有 iteration 团队产出总结:历史各代被回填为阶段与工作项;缺少排期材料时不出甘特图,任务进展章节以声明句 + 复用功能分解图降级;缺口在报告中以材料缺口结构列出。

**Acceptance Scenarios**:

1. **Given** 一个先于本机制存在、已有多次 `runs/` 记录的团队, **When** 首次产出总结, **Then** 历史运行被回填为阶段与工作项,不要求团队重建或补写历史格式。
2. **Given** 团队缺少 `STATE.md` / `run-log.jsonl`(如 iteration 模式), **When** 生成表单, **Then** 以 `runs/` 与 `team.md` 为来源,并在报告中声明该来源限制。
3. **Given** 团队工件不含任何排期依据, **When** 呈现任务进展, **Then** 不出甘特图,以声明句 + 复用功能分解图降级,**不虚构**开始/结束日期与工期。
4. **Given** 图表渲染失败, **When** 收尾, **Then** 以既有渲染失败告示形式标注该图,总结其余部分照常交付。
5. **Given** 一个 iteration 团队中被淘汰的变体, **When** 统计进度, **Then** 它计入被排除口径,**不**被算作延期或未完成工作项。

### User Story 6 - goal 索引与跨团队聚合:按目标读进展,而不是按团队 (Priority: P2)

作为关心"目标推进到哪里"的读者(而非关心某个团队怎么运行的人),我希望以 **goal** 为入口拿到一份聚合总结:同一个目标下不管由几个团队、先后还是并行推进,我都能在一处看到这个目标的整体完成度、里程碑达成情况,以及"哪个团队推进了哪一部分";而团队目录仍然按 team 保留各自的运行细节。

**Why this priority**: 与 US3/US4 同级 P2。它是本次范围修订引入的读者侧价值兑现点——team 索引回答不了"跨团队的目标进展",而这恰是目标级读者唯一关心的问题。它依赖 US1 的映射与表单生成已能产出总结,故不置 P1。

**Independent Test**: 构造两个声明同一 `goal_slug` 的团队(模式可不同),各跑一次:两者的工作项都出现在同一个 goal 交付目录的当前总结中、各自可归属到产出团队、里程碑不重复;仅刷新其中一个团队后,另一团队此前的贡献仍在;goal 正文改写后交付目录路径不变。

**Acceptance Scenarios**:

1. **Given** 两个团队在 `team.md` frontmatter 声明了相同的 [[STR-006]], **When** 任一团队触发刷新, **Then** 二者的工作项、阶段与人员在同一个 goal 交付目录中被聚合为一份总结,里程碑取自该 goal 的成功判据而不逐团队重复。
2. **Given** 某工作项由团队 A 产出、另一个由团队 B 产出, **When** 阅读总结, **Then** 每个工作项可归属到其产出团队,且该归属不通过代理 id / 结果清单路径等团队内部标识符呈现。
3. **Given** 同一 goal 下只有团队 A 本次刷新, **When** 刷新完成, **Then** 团队 B 此前贡献的工作项仍完整保留在总结中,不因"本次未参与"而消失。
4. **Given** 一个存量团队未声明 [[STR-006]], **When** 产出总结, **Then** 以其团队 slug 回填推断的 goal 身份并在元信息中标记为推断,不要求先行改造团队。
5. **Given** 该团队其后显式声明了 [[STR-006]], **When** 下次刷新, **Then** 其历史贡献归并进显式 goal 目录,推断目录与显式目录不并列存在。
6. **Given** 团队的 goal 正文被刻意修改(FR-019), **When** 刷新, **Then** 交付目录路径不变、历史工作项保留,goal 变更记入元信息。
7. **Given** 同一 goal 下两个团队在极短时间内各自到达阶段边界, **When** 两次刷新相遇, **Then** 串行化为一次成功刷新、当前总结仍只有一份、无丢失更新,被跳过的那次在其运行报告中留下状态记录。

### Edge Cases

- **尚无任何执行材料就要求总结**:团队刚创建、一个阶段边界都没跨过 → 明确拒绝并声明原因(见 [[STR-005]] 的 `declined(no-material)`),不产出空图表、不用 goal 判据凑出一份看似完整的报告。
- **工作项为空、仅有里程碑**:功能分解图在被调技能中是无条件出图项,与"工作项为空"直接冲突 → 该情形按上一条拒绝处理,而非渲染一张空的分解图。
- **条目跨越 ID 边界**:某条目在推断身份时代已存在,团队开始发 ID 后它获得了显式 ID → MUST 归并为一条(显式 ID 为权威、保留其历史进度),不得在总结中同时出现推断身份与显式身份两条重复记录。
- **推断身份时代发生重命名**:该时代的身份由标题派生,重命名后无法认定为同一条目 → 旧标题条目按"本次未见"处理并在材料缺口中声明,不得静默消失;显式 ID 时代的重命名不受影响(ID 不变)。
- **continuous 团队成熟度中途升降级(L1↔L2)**:此前 report-only 期间的条目不得因升级而被追溯改写为"已行动";状态语义按条目发生时的成熟度锚定。
- **团队监控的是一个外部项目**(如需求实现监控团队):总结呈现的是**团队自身相对其 goal 的执行状态**;被监控目标自己的项目总结是另一次独立调用,不在本机制范围内。
- **同一 cycle 内既到达节奏点又触发预算阶梯**:预算门控优先,记为 [[STR-003]],不因"到点了"而强行出图。
- **团队被删除或改名(team slug 变更)**:交付目录由 [[STR-006]] 决定,**不随 team slug 变动**;需要跟随的是出处路径与归属标签。团队被删除时其历史贡献 MUST 保留在 goal 总结中并标注该团队已不存在,不得留下指向已删除团队的悬空出处。
- **两个阶段边界在极短时间内连续到达**:总结按节奏合并为一次刷新,不为每个边界各出一份。
- **运行中间目录 / Agent Execution 日志已被清理但总结需要其中的数字**:该数字降级为未知,不从缓存或记忆中回填——出处必须可验证。
- **同一 goal 下的团队使用不同协作模式**(如 continuous + iteration):阶段单位不同 → 阶段 MUST 按团队命名空间化,不得把不同模式的阶段混为同一序列;里程碑仍取自 goal 的成功判据,只有一套。
- **团队改绑到另一个 goal**([[STR-006]] 被改写):原 goal 目录 MUST 保留该团队此前的历史贡献并标注其已不再参与,新 goal 目录从改绑时点起接收其新贡献;不得把历史贡献静默搬走或双份呈现。
- **两个团队声明的 [[STR-006]] 相同但 goal 正文实质不同**:以显式声明为准(声明即同一 goal),并把正文差异记入元信息供人裁决——不由机制自行判定"其实不是同一个目标"。
- **`<goal-slug>` 与 `.specify/project/` 下既有条目同名**:`.specify/project/` 已存在历史产物(`project.md` 与 wbs/gantt/milestones 图表),goal 子树 MUST 落在 `goal/` 之下与其平级共存,MUST NOT 覆盖或改动既有产物。

## Requirements *(mandatory)*

### Functional Requirements

**概念映射**

- **FR-001**: 系统 MUST 提供一份团队 → 项目管理概念映射的**单一事实源**,逐项定义团队词汇到七个项目管理实体(`project` / `people` / `phases` / `work_items` / `milestones` / `features` / `sources`)的对应关系与字段级来源。
- **FR-002**: 映射 MUST 覆盖四种协作模式各自的"阶段"与"工作项"语义:serial → stage / stage 交付物;parallel → 派发批次 / territory;iteration → generation / 每代变体任务与采纳改进;continuous → cycle / 被跟踪条目。
- **FR-003**: 映射 MUST 把团队 goal 承载为项目目标叙述,并把 goal 中的可验证成功判据映射为里程碑,使"至少一组工作项或里程碑非空"的 R 档约束在有执行材料时即可满足。
- **FR-004**: 映射 MUST 把团队 `members[]` 承载为人员实体(代理标识 → 人员标识、角色 → 人员角色),并保证人员称名在报告正文与各图表间逐字一致;人员标识与称名 MUST 以名册所引用的 agent 定义(`.specify/agents/{templates,instances}/<slug>.agent.md`,同名时 instance 优先)的 frontmatter `name` 为权威来源。
- **FR-005**: 系统 MUST 显式提供基线日期(取自本次运行/cycle 的时间戳),不依赖被调技能读取系统时钟。
- **FR-006**: 映射 MUST 把团队条目的生命周期状态归一到工作项四态(已完成 / 进行中 / 延期 / 未开始)与降级终态"未知";无状态信号时 MUST 记为未知,MUST NOT 记为未开始或 0%。
- **FR-007**: 七个实体中每一个 MUST 要么有已定义的团队侧来源,要么有显式声明的缺席降级形态;MUST NOT 存在"未映射即静默留空"的实体。
- **FR-026**: 工作项的跨运行身份 MUST 由团队在其机器可读工件中**显式发放的条目 ID** 承载;团队工件 MUST 扩展以携带该 ID(至少覆盖 `STATE.md` 的被跟踪条目与子代理结果清单条目)。条目被重命名时其 ID MUST 保持不变,使重命名不产生新条目。
- **FR-027**: 在团队开始发放显式 ID 之前产生的历史条目,MUST 以「条目标题 + 所属阶段」派生的身份回填,并 MUST 在派生数据中标记为**推断身份**(与既有出处纪律一致,不伪装为精确值)。两套身份机制的交接规则 MUST 定义:同一条目若先以推断身份存在、其后获得显式 ID,MUST 归并为一条记录(以显式 ID 为权威并保留其历史),MUST NOT 同时呈现推断身份与显式身份两条重复记录。

**表单生成与消耗纪律**

- **FR-008**: 项目输入表单 MUST 由确定性程序从团队的机器可读工件(`team.md` frontmatter、`run-log.jsonl`、`STATE.md` 结构化分节、子代理结果清单)派生,MUST NOT 依赖大模型通读运行报告原文后转写。
- **FR-009**: 总结步骤 MUST 以摘要 / 字段投影 / 定向节选方式消费团队工件;注入上下文的内容量 MUST NOT 随团队运行次数线性增长。
- **FR-010**: 表单中每个状态与进度数值 MUST 携带出处,指向一个具体的团队工件路径;无出处的数值 MUST 被拒绝,而非以默认值落库。
- **FR-011**: 出处 MUST 指向 tracked 工件;仅存在于 git-ignored 位置的依据 MUST NOT 作为出处采用——含运行中间目录(`.specify/teams/.work/<slug>/`)与 Agent Execution 运行日志(`.specify/agents/execution/logs/`,含外部派发可见性三元组 `.live.log`/`.jsonl`/`.status`)。

**阶段性触发与门控**

- **FR-012**: 系统 MUST 在四种模式各自的阶段边界处触发总结刷新,边界定义为:serial → 每个 stage 交接完成后;parallel → 交叉校验与汇总完成后;iteration → 每代 DECIDE 相完成后;continuous → 每第 N 个 cycle 收尾时。并 MUST 在团队达成 goal 或运行终止(收敛 / halt / 人工停止)时产出一次终态总结。
- **FR-013**: 总结 MUST 默认启用:团队未声明 `config.summary` 时视为**启用**(opt-out 语义),按已文档化的每模式默认节奏运行。触发节奏 MUST 可通过团队配置调整;continuous 模式的默认节奏 MUST NOT 是"每 cycle 出图"。配置键 MUST 嵌套于 `config` 之下(见 [[STR-002]]),以避免与团队预设文件顶层的一行式 `summary:` 字段混淆。
- **FR-028**: 首次为某团队产出总结(该团队此前从未有过总结产物)时,MUST 在该次运行报告中一次性声明"总结机制本次首度启用"及其生效节奏,使 opt-out 默认对存量团队的行为变化可见而非静默发生。
- **FR-014**: 总结 MUST 受预算阶梯门控:达到 report-only 档或 kill-switch 时跳过总结并记为 [[STR-003]],运行照常收尾;总结自身的消耗 MUST NOT 导致预算越线。
- **FR-015**: 每次运行 MUST 在其运行报告中以状态行(见 [[STR-005]])声明本次总结是产出、按节奏跳过、按预算跳过还是因无材料拒绝,使"未观测"与"观测到无进展"可区分。
- **FR-016**: `/speckit.team run` 的确认门禁 MUST 披露本次运行是否会产出总结。

**产物、累积与边界**

- **FR-017**: 每个 goal MUST 有一个属于该 goal 的总结交付目录(见 [[STR-001]]),其中始终只有**一份当前**总结;历史运行细节 MUST 保留在各团队的 `runs/` 中不被搬迁。团队目录 MUST NOT 承载完整总结产物——它只保留运行信息(`runs/` / `STATE.md` / `run-log.jsonl` / `items.jsonl`)。
- **FR-018**: 刷新 MUST 以累积(逐条更新既有记录)方式演进,逐条更新 MUST 以 FR-026 / FR-027 定义的工作项身份为键,MUST NOT 每次从零重建而丢失此前累积的工作项;上一版总结中的人工批注 MUST 原样保留。
- **FR-029**: 已完成与已归档工作项 MUST 全量保留于派生数据层(不删除、不裁剪);在呈现层它们 MUST 按所属阶段**聚合为计数**展示,仅进行中 / 延期 / 未开始条目逐条展开。该聚合 MUST 使分解图节点数在团队长期运行后仍处于被调技能的节点阈值内,而非依赖无限拆分图集。
- **FR-019**: goal 正文被有意修改时,系统 MUST 记录该变更并保留历史工作项,MUST NOT 静默改写历史状态;goal 正文的修改 MUST NOT 改变 [[STR-006]] 的取值,因而 MUST NOT 导致交付目录迁移或孤立。
- **FR-020**: 总结步骤的写入面 MUST 限于该 goal 的交付目录与反馈存量;在总结步骤执行期间,`.specify/teams/**`(含 `team.md` / `STATE.md` / `run-log.jsonl` / `items.jsonl` / `runs/`)以及任何被监控目标 MUST 保持字节不变。该不变性约束的对象是**总结步骤**;团队主管在其正常 cycle 写入中按 FR-026 向 `STATE.md`、`items.jsonl` 与结果清单发放条目 ID,不受此条限制。
- **FR-021**: tracked 的总结产物 MUST 只由团队主管写入;子代理 MUST NOT 写入 tracked 总结产物。
- **FR-022**: 总结的读者章节 MUST NOT 出现团队内部标识符(代理 id、结果清单路径、运行中间目录路径);此类信息 MUST 仅出现在元信息与来源声明中。
- **FR-023**: 材料不足时 MUST 沿用被调技能既有的降级形态(无排期材料不出甘特、里程碑图按既有判据阶梯、渲染失败以告示标注),MUST NOT 虚构日期、工期或百分比以凑出图表。
- **FR-024**: 本机制 MUST NOT 改变 `summarize-project` 的概念模型、输入契约与只读定位;适配责任在团队侧。
- **FR-025**: 先于本机制存在的团队 MUST 能仅凭其既有 tracked 工件产出总结,MUST NOT 要求重建团队或补写历史格式;其无显式 ID 的历史条目按 FR-027 的推断身份路径回填,其无 [[STR-006]] 的情形按 FR-034 回填。

**双索引:goal 维度的聚合**

- **FR-030**: 系统 MUST 以 **goal** 为索引产出总结交付目录(见 [[STR-001]]),与以 **team** 为索引的运行信息目录(`.specify/teams/<team-slug>/`)构成两个互不替代的索引:team 索引回答"这个团队在怎么运行",goal 索引回答"这个目标推进到哪里"。
- **FR-031**: goal 的身份 MUST 由团队在 `team.md` frontmatter 中**显式声明**的 [[STR-006]] 承载,MUST NOT 从 goal 正文派生。同一 [[STR-006]] 值 MUST 被认定为同一个 goal,无论声明它的是哪个团队。
- **FR-032**: 一个 goal 交付目录 MUST 聚合**所有**声明了该 [[STR-006]] 的团队的状态:工作项、阶段与人员取各团队之并集,里程碑取自该 goal 的可验证成功判据(而非逐团队重复)。某团队本次未参与刷新 MUST NOT 导致其此前贡献的工作项从总结中消失。
- **FR-033**: 聚合后的每个工作项 MUST 可归属到产出它的团队,归属 MUST 由机器可判定(而非仅凭叙述);读者 MUST 能在总结中区分"哪个团队推进了哪一部分",且该归属 MUST NOT 依赖 FR-022 所禁止的团队内部标识符。
- **FR-034**: 未声明 [[STR-006]] 的存量团队 MUST 仍能产出总结:系统 MUST 以该团队自身的 slug 回填一个推断的 goal 身份,并在派生数据与元信息中标记为**推断**(与 FR-027 的推断身份同构)。团队其后显式声明 [[STR-006]] 时,MUST 归并到该显式 goal 目录并保留其历史贡献,MUST NOT 同时留下推断目录与显式目录两份并列总结。
- **FR-035**: 当同一 goal 下多个团队在时间上邻近地各自到达阶段边界时,goal 交付目录的刷新 MUST 串行化为一次成功的刷新,MUST NOT 因并发写入产生互相覆盖(丢失更新)或半写产物;被跳过的那次 MUST 按 FR-015 在其自己的运行报告中留下状态记录。
- **FR-036**: 本机制 MUST NOT 改动 `.specify/project/` 下既有的历史产物(先前由 `manage-project` 建立的项目文档与图表);goal 交付目录 MUST 作为其平级新增子树存在。

### Key Entities *(include if requirement involves data)*

- **Goal Summary(目标总结)**:某 goal 的派生交付目录(见 [[STR-001]])——当前总结正文 + 图表源与渲染物 + 派生数据,按 [[STR-006]] 归属,聚合该 goal 下全部团队,累积演进,纳入版本控制。这是本机制唯一的完整总结产物。
- **Goal Identity(目标身份)**:认定"同一个 goal"的键,由 `team.md` frontmatter 显式声明的 [[STR-006]] 承载(权威形态,goal 正文改写安全);存量团队缺失时以团队 slug 回填并标记为**推断**,其后获得显式值时归并为一条(与 Work Item Identity 同构)。
- **Team Attribution(团队归属)**:聚合后每个工作项到产出它的团队的机器可判定映射,使 goal 视图能回答"哪个团队推进了哪一部分",且不向读者章节泄漏团队内部标识符。
- **Team Run Info(团队运行信息)**:团队目录下以 team 为索引的事实源——`runs/` / `STATE.md` / `run-log.jsonl` / `items.jsonl`;在总结步骤期间只读、字节不变。
- **Concept Mapping(概念映射)**:团队词汇 ↔ 七个项目管理实体的字段级对应关系,含每种协作模式的阶段/工作项语义与缺席降级形态;本需求的单一事实源。
- **Team Project Form(团队项目输入表单)**:由程序从团队工件派生的项目输入表单,是团队侧向被调技能交付的唯一输入面;派生物,非人工维护物。
- **Summary Trigger(总结触发点)**:模式相关的阶段边界 + 节奏配置 + 预算门控三者共同决定的触发决策,其结果以状态行落在运行报告中。
- **Progress Provenance(进度出处)**:每个状态/进度数值背后的 tracked 团队工件路径;缺失时该数值降级为未知。
- **Work Item Identity(工作项身份)**:跨运行认定"同一工作项"的键,决定累积刷新是就地推进还是新增条目。两种形态:团队**显式发放的条目 ID**(权威形态,重命名安全);「标题 + 所属阶段」**派生的推断身份**(仅用于团队开始发 ID 之前的历史条目,在派生数据中显式标记为推断)。同一条目跨越两种形态时以显式 ID 为权威并归并为一条。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 四种协作模式各取一个既有团队,均能仅凭其 tracked 工件产出总结:输入校验通过而非阻断补填、数据装载与一致性校验通过,手工填表工作量为零。
- **SC-002**: 在有执行材料的前提下,首次总结的 R 档必填字段齐备率 100%——无需人工补填即可通过校验。
- **SC-003**: 一次总结刷新的文件变更集 100% 落在该 goal 交付目录与反馈存量内;`.specify/teams/**`、被监控目标、`summarize-project` 技能自身文件、`.specify/agents/**`(三层全部)、以及 `.specify/project/` 下 `goal/` 之外的既有历史产物**五者**均零变更。本条是不变量分组的单一事实源,其它工件引用其分组数而不各自枚举。
- **SC-004**: 总结中出现的状态与进度数值,携带可解析出处者占比 100%;无出处数值出现次数为 0;抽查的出处路径 100% 指向 tracked 且实际存在的工件。
- **SC-005**: 总结步骤注入上下文的团队工件内容量(行/字节代理指标)在团队运行次数从 K 增长到 2K 时**不翻倍**,即不随运行次数线性增长。
- **SC-006**: 预算阶梯触发 report-only 档时,总结跳过率 100%、运行仍正常收尾率 100%、跳过被显式记录率 100%;因总结导致的预算越线次数为 0。
- **SC-007**: 同一 goal 连续刷新两次后,该 goal 交付目录中当前总结份数恒为 1;上一版人工批注保留率 100%;两次运行的工作项均体现在当前总结中。
- **SC-008**: 概念映射对七个实体的覆盖率 100%(每个实体有来源定义或显式缺席降级),对四种协作模式的阶段/工作项语义覆盖率 100%。
- **SC-009**: 材料缺口场景下,虚构日期/工期/百分比的出现次数为 0;应降级而未降级(强行出图)的次数为 0。
- **SC-010**: 一位未读过任何运行报告的读者,仅凭总结即能说出团队的 goal、当前完成度、进行中与延期条目、里程碑达成情况;总结读者章节中团队内部标识符出现次数为 0。
- **SC-011**: 跨刷新身份稳定性:同一工作项在连续刷新中被重复计入的次数为 0、被静默丢失的次数为 0;发放显式 ID 之前的历史条目被标记为推断身份的比例 100%;跨越 ID 边界的条目归并后重复记录数为 0。
- **SC-012**: 长期运行团队(累积工作项数超过分解图节点阈值)的分解图节点数 100% 处于阈值内,且已完成/已归档条目在数据层保留率 100%(呈现层以聚合计数出现,零删除)。
- **SC-013**: goal 身份与目录正确性:声明了同一 [[STR-006]] 的团队 100% 落入同一个 goal 交付目录;goal 正文被修改后交付目录路径变化次数为 0;未声明 [[STR-006]] 的存量团队被标记为推断 goal 身份的比例 100%;由推断转为显式后遗留的并列目录数为 0。

### Measurement Sources & Collection Methods

- **SC-001 Source**: 对四个既有团队分别执行一次总结产出,采集输入校验与数据装载/一致性校验的退出码与输出(退出 0 = 齐备通过,退出 3 = 阻断补填);手工填表工作量以"是否需要人工编辑表单"二值记录。基线:当前四个团队均无法产出总结(0/4)。
- **SC-002 Source**: 校验器针对 R 档字段的输出(缺失清单为空即齐备);每次首轮总结采集一次。
- **SC-003 Source**: 总结刷新前后的版本控制变更集(变更路径清单),以及 SC-003 所列**五组**内容指纹的前后比对;每次总结刷新采集。
- **SC-004 Source**: 派生数据中出处字段的非空率与路径可达性批量检查(程序判定,非人工抽读);每次总结刷新采集,并对随机抽样的出处路径做存在性验证。
- **SC-005 Source**: 总结步骤读入团队工件的行/字节代理计数,在同一团队两个运行次数水位(K 与 2K)各采一次,对比增长倍数。
- **SC-006 Source**: 运行报告中的总结状态行 + continuous 团队运行日志的逐 cycle 机器聚合(不采用叙述式自评);另构造一次预算越线情景做验证。
- **SC-007 Source**: goal 交付目录文件清单(当前总结份数)+ 批注章节内容前后比对 + 工作项集合的前后差集;连续两次刷新后采集。
- **SC-008 Source**: 以映射单一事实源为对象的结构化核对表(七实体 × 四模式矩阵),逐格标记"有来源定义 / 有缺席降级 / 缺失";映射定稿时采集一次,并在其变更时复核。
- **SC-009 Source**: 派生数据中被标记为推断的日期/进度字段计数 + 出图判据与实际出图结果的一致性检查(判据为假却出图 = 违规);在薄材料团队上专项采集。
- **SC-010 Source**: 一次外部读者可读性核查(读者仅获得总结,回答固定五问)+ 对读者章节做内部标识符模式匹配的程序化扫描。
- **SC-011 Source**: 连续两次刷新前后对派生数据中工作项身份键集合做差集比对(新增 / 消失 / 重复三类计数,程序判定);推断身份标记率由派生数据的推断标记字段统计;归并正确性以"同一显式 ID 对应记录数 = 1"断言。
- **SC-012 Source**: 构造或选取一个累积工作项数超阈值的团队,采集分解图各子图的节点计数与数据层工作项总数,核对"节点数 ≤ 阈值"且"数据层总数 = 聚合计数之和 + 逐条展开条目数"两个等式。
- **SC-013 Source**: 以「team → 解析出的 goal 目录」映射表为对象的程序化核对(声明同值者是否同目录、推断标记是否置位);另做一次 goal 正文改写前后的目录路径比对,以及一次"推断 → 显式"迁移后的目录清点(并列目录数应为 0)。
- **SC-014 Source**: 构造一个 goal 下挂两个团队的场景,对派生数据做工作项集合的并集核对(逐团队贡献是否齐全)、归属字段的非空率统计,以及仅刷新其中一个团队后对另一团队历史贡献的存在性断言;读者章节仍走 SC-010 的模式匹配扫描。
- **SC-015 Source**: 在同一 goal 下让两个团队邻近触发刷新,采集交付目录的当前总结份数、刷新前后的内容指纹链(以检出丢失更新)、以及产物完整性检查(半写检测);被跳过那次的状态行由其运行报告采集。

## Assumptions

- **"拓扑结构"的语义对齐**:用户输入中的"拓扑结构"不是本项目的既有词汇;团队的结构词汇是**静态结构**(Role × Stage × Type 名册)与**动态结构**(协作模式:parallel / serial / iteration / continuous)。本规格按"静态结构 + 动态结构"这一对概念理解该表述。
- **"项目"= 团队自身**:总结的对象是团队自身相对其 goal 的执行状态(团队 ≡ 项目),而非团队所监控的外部目标。依据是用户明确要求"将 team 的概念映射到 summarize-project 定义的项目管理概念中"。被监控目标自己的项目总结属于另一次独立调用。
- **适用范围为全部四种协作模式**,各自有不同的阶段边界语义;不限于长运行的 iteration / continuous 模式。
- **总结是累积式单份产物**,而非每次运行各出一份快照;这是"项目状态总结"区别于既有运行报告的前提。
- **交付目录位置**(2026-08-04 范围修订):完整总结落在以 goal 为索引的 [[STR-001]];团队目录只保留运行信息。选择 `.specify/project/goal/` 而非团队目录下的子目录,是为了让"目标"成为可跨团队延续的索引;沿用既有产物(图表源与渲染物一并纳入版本控制)的先例。
- **`goal_slug` 是新增 frontmatter 字段**:现有 4 个团队均未声明它,故 FR-034 提供以团队 slug 回填的推断路径,使本机制对存量团队零改造即可启用;显式声明由 `/speckit.team modify`(improve-team)按需补齐。字段名 `goal_slug` 与既有 `slug`(team slug)并存,二者语义不同,不得混用。
- **`.specify/project/` 已有历史产物**:该目录现存 `project.md` 与 wbs/gantt/milestones 三组图表(2026-07-25 由已重构的 `manage-project` 建立,现作为只读信息源)。本机制在其下新增 `goal/` 子树平级共存,不改动、不迁移、不覆盖既有内容(FR-036)。
- **`summarize-project` 保持不变**:它仍是只读的呈现工具、输入面仍是表单;团队侧承担"表单作者"角色。本需求不修改其概念模型、脚本或写入白名单语义。
- **配置键命名冲突已规避**:团队预设文件顶层已存在一行式 `summary:` 字段(预设摘要)。本机制的配置键嵌套为 `config.summary`(见 [[STR-002]]),不新增顶层 `summary:`;若用户偏好其他命名,可在澄清阶段覆盖。
- **无可执行的团队运行器**:团队执行当前是提示层编排(`/speckit.team run` 的 preview → confirm → execute),故本机制由提示层触发点 + 确定性表单生成步骤共同构成,不假设存在调度守护进程。
