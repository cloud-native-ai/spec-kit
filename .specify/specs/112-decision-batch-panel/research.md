## 2. Resolved design points

Each point below resolves one design question the requirements leave to the plan. All fixed-rule judgements stay in the engine (Program-First); the skill only carries interaction and rendering.

**D-1 — Engine surface.** `scripts/python/decision-batch.py`, stdlib only, closed actions `scan` / `record` / `replay`, flags `--workspace-root`, `--format {text,json}`, `--presentation`, `--reply`, `--authorization {interactive,unattended}`, `--batch`, plus `-h`/`--help`/`--version` and undeclared-option rejection (script-interface contract, pointer). Exit codes: `0` success (including `nothing-pending`), `1` documented refusal, `2` usage/environment error. `scan` and `replay` are strictly read-only; `record` is the only writer and only through the named carriers. Rationale: FR-039 + Constitution XXI; sibling engines (`validate-decisions.py`, `memory-utils.py`) already use this shape.

**D-2 — Batch record carrier mechanics.** The engine composes the record body, derives the title `decision-batch-<batch_id>`, and writes through `memory-utils.py --action record --scope knowledge --source /speckit.decide --title … --tags decision-batch,<batch_id>`; before writing it asserts the target path (stable slug of the title) does not exist and refuses otherwise (M-6: the memory engine is upsert-by-slug, so create-only semantics must be enforced by the caller). Recognition for read-time joins: knowledge entries whose title/slug starts with `decision-batch-` (the spec's edge case); a matching entry that cannot be parsed yields a named refusal, never a guess.

**D-3 — Deterministic ordering.** Presentation order = roster order (`register-open-decision-row` before `authored-pending-item`) → carrier repository-relative path → occurrence position (register row order; block start line). Per-row source references are listed in the same order. Identity comparison: `subject` trimmed, **byte-equal**; same-name family additionally compares `resource_locator` values; no case folding, no Unicode normalisation, no fuzzy matching (FR-009/A-22). Two scans of the same tree differ only in the scan timestamp (SC-010).

**D-4 — Qualification precedence.** A candidate gets exactly one classification. Exclusion first: `not-human-held` (declared `ai-autonomous`, or same-identity class conflict) and `already-resolved`; then presentation status precedence `incomplete` → `source-conflict` → `no-default` → `irreversible-default` → `prior-decision-conflict` → `eligible`. `incomplete` reasons are a closed named set (`authority-unresolved`, `ambiguous-link`, `class-missing`, `malformed-field`, `unknown-field`, `duplicate-field`, `option-count-mismatch`, `missing-field`, `option-element-missing`, `evidence-unresolvable`); the set grows only by owner revision. This precedence is the deterministic reading of the closed state set in § Batch States; it keeps every candidate classified exactly once.

**D-5 — Grounding join.** Closed inputs: (a) the default option's `evidence` pointers that resolve to a prior-experience carrier; (b) prior decision records whose `context` contains the subject string **verbatim**; (c) the `T-NNN` identifiers those records cite. Prior-experience carriers: the four scan roots' decision-record carriers, batch records (knowledge), `T-NNN` tensions, `.specify/history/`, `.specify/feedback/`, `.specify/knowledge/` entries. Any one resolvable prior-experience pointer → `grounded` with the whole resolvable set emitted; otherwise `no-evidence`. Pointer resolution = path exists and, when an anchor is given, the heading/anchor is findable (same reading as M-09). `basis` is text, never evidence. No semantic retrieval at presentation time.

**D-6 — Reply artifact and validation split.** The skill turns the user's reply into a small reply file carrying `reply_verbatim` (the literal text) plus structured entries bound **by item identity** (`subject`, optional `resource_locator`) with `action: alternative|park` and, for alternatives, the full option label. The engine validates structure and membership: identity must match a presented item byte-exactly; the label must be a member of the presented option set (or follow the declared `other` path); duplicates and unknown identities are refused; all validation precedes any write (FR-026). Whether a message constitutes a reply at all (explicit reply vs follow-up question vs abort) is a behaviour-class judgement made by the skill and preserved verbatim in the record; the machine judges structure and membership only (FR-045 honesty boundary).

**D-7 — Record transaction.** `record` re-scans, compares candidate identity set and per-item content fingerprints (subject, option set, default, grounding, qualification, source reference set) against the presentation payload, and refuses on drift with the diff; only after every precondition passes does it mint `B-<YYYYMMDDTHHMMSSZ>-<8 lowercase hex>` and write. Write order: batch record (head → item rows → decision records) → register rows and settled-row status cells → pending-block `resolution` fields. A failure after the batch record lands is disclosed and the read-time join (FR-012) prevents re-presentation. A rejected attempt writes nothing and mints no id (A-24). Concurrency: distinct batch ids produce distinct knowledge paths; register remains the single index; conflicts are repaired by the existing renumber lane, never silently renumbered.

**D-8 — Redecision and supersession.** A matched prior record whose chosen label differs from the new chosen label is superseded: the old record keeps its content byte-for-byte and gains `superseded_by: <D-NNN> (<carrier path>)`; the old carrier being unreadable/unwritable refuses the item's settlement. The new record lives in the batch record (P-13 carrier) and therefore uses a new dense id range there; the cross-carrier pointer carries the carrier path (owner § 编号).

**D-9 — Explicit settlement of ineligible items.** Alternatives are accepted for `no-default`, `irreversible-default`, `source-conflict` and `prior-decision-conflict` items (an explicit choice is exactly what the confirmation-gate obligation requires; the batch row retains the qualification). For `incomplete` items an alternative is accepted only when the presented option set is grammatically complete (declared count, five elements, unique labels) and `subject`/`context` are resolvable — otherwise the engine refuses with a named reason because the resulting 107 record would fail its own grammar (FR-033 + the spec's edge case).

**D-10 — Batch-family field extension.** The owner page's conditional layer gains one family: `batch_id` / `batch_disposition` / `recommendation_grounding`, required exactly when the record was produced by a batch; `batch_disposition` ∈ {`accepted-default`, `objected-alternative`}, `recommendation_grounding` ∈ {`grounded`, `no-evidence`}, `batch_id` = the B-shape. `validate-decisions.py` gains the same three fields in `CONDITIONAL_FIELDS` plus one recorded M rule for their trigger/value rules; existing records are untouched and keep passing (additive closure). The human choice signal is carried by the disposition→signal mapping (M-8), not by decorating `chosen_option` (M-5).

**D-11 — Guard and fixture plan.** New fixtures `tests/fixtures/decision-batch/` (two-source + duplicates + incomplete + `ai-autonomous`; unreadable register; empty project; grounding two sets; prior conflict; drift; four reply shapes; source/class conflict; resolution join; batch-family reverse samples; replay broken pointer; concurrency). Engine unit/contract tests exercise scan/record/replay determinism, bookkeeping, zero-write refusals and the zero-network/zero-feedback-write assertions. The owner's M/B roster grows with the batch rules and `tests/contract/test_decision_governance_guards.py`'s `GUARD_ROSTER` moves in the same change (table–guard parity); the frozen inventory test moves `32→33` commands and `60→61` skills; the probe census pin moves `122→123` with the new skill's probe object.

**D-12 — Feature integration and stale reading.** This plan advances Feature 112 `Draft → Planned` in both carriers and records the key changes. The 112 detail still quotes the requirements-stage baseline "eight open rows"; the clarify ruling (A-21) corrected the baseline to the predicate-derived **17** (M-1). The detail is corrected in the same edit and the correction is disclosed in the stage return.

## 4. Bounds and honest limits

- The first real batch on this tree presents 17 `incomplete` rows and settles none; that is the honest start (A-16), not a defect of the mechanism.
- "Recommendation reasonable", "consequence truthful", "name complete", "basis sufficient" remain behaviour-class judgements on the review surfaces; no guard in this plan claims machine coverage of them (FR-045).
- No new runtime store, no `.specify/.gitignore` change, no network, no feedback-store write, no automatic transmission (FR-004/FR-005); the batch record reuses `.specify/knowledge/`.
