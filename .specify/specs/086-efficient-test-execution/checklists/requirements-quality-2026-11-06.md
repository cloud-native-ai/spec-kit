# Requirements Quality Checklist: 测试高效执行（默认并发）— plan/tasks 后的质量门

**Purpose**: Validate the quality, clarity and completeness of the 086 requirements *after* the plan and tasks artifacts exist — gap-finding against the design artifacts, never grading them.
**Created**: 2026-11-06
**Feature (Requirement Scope)**: `.specify/memory/features/086.md` (bound by `/speckit.clarify` Mode A, 2026-11-06)
**Requirements (What)**: [`../requirements.md`](../requirements.md)
**Specifications (How, context only)**: [`../plan.md`](../plan.md), [`../tasks.md`](../tasks.md), [`../contracts/`](../contracts/), [`../quickstart.md`](../quickstart.md), [`../data-model.md`](../data-model.md)
**Flow Class**: `execution` (`flow-class-check.py --action lookup` → `flow_class: execution`, `source: declaration`, exit 0) — the expression-class gate operator adds nothing here.

**Note**: Every item is a question about the **requirement text**. An item answerable only by running the product is out of scope. `plan.md` / `tasks.md` are read to expose what the requirements *omit*, never to be graded. Rows are `[ ]` — unanswered by design: this gate records gaps, it does not fix them (`create-checklist` § Boundaries).

**Prior checklist**: [`requirements.md`](requirements.md) (2026-11-06, 17 items, pre-plan). This file is a **new dated checklist**; the earlier one is not refreshed in place.

## Requirement Clarity — the decision rule the whole feature rests on

- [ ] CHK001 Is "efficiency is a quality attribute at the same tier as coverage" given a decidable predicate, or does it remain a ranking statement with no failure condition? The three load-bearing propositions are required verbatim by `FR-019`/`C-027`, but neither states what makes a project *violate* the tier claim. [Clarity/Measurability, Req §FR-019, §SC-002]
- [ ] CHK002 Is the discriminating property that selects process parallelism vs async concurrency named at requirement level, or only deferred to the owner guideline? `FR-018` requires the owner to hold "选择规则" but the requirements never state what the rule decides on, so `SC-002` cannot judge whether the rule is *right*, only that it exists. [Clarity/Coverage, Req §FR-018, §A2, `C-022`(3)]
- [ ] CHK003 Is "efficient" itself defined by any threshold or comparative predicate in the requirements? `SC-001` demands a "被记录的下降" and the goal file says "at most 40% of 1031.48 s", but no requirement carries that bound, so the acceptance ceiling lives outside the requirement set. [Measurability/Ambiguity, Req §SC-001; goal `## Success Criteria` 1]
- [ ] CHK004 Is the runner's precedence order stated once for every competing input? `FR-003` gives `--workers` > `SPECKIT_TEST_WORKERS` > auto, but `FR-005` (nested worker env) and `FR-004` (caller-supplied `-n`) enter the same decision without an ordering relative to `--serial` or to each other — a caller passing both `--serial` and `--workers N` has no recorded outcome. [Clarity/Consistency, Req §FR-002–§FR-005]
- [ ] CHK005 Is "既存失败" (pre-existing failure) given a stable definition — the U0 list, the A9 implementation-start slot, or "whatever the serial baseline of that tree is"? `A9` fixes the *slot* but the word is still used in `FR-010` and `SC-001` as if it named a set. [Clarity/Ambiguity, Req §A3, §A9, §FR-010]

## Requirement Completeness — objects named without an owner

- [ ] CHK006 Is the **serial-exception registry** given an owner and a form? The requirements require the exception set to be "可枚举" (`FR-011`) and `C-011` fixes the enumeration command, but no requirement names where the marker vocabulary is *declared* — so a reader cannot tell whether it is pytest's marker registry, a runner-side list, or both. [Completeness/Traceability, Req §FR-011, §A14]
- [ ] CHK007 Is the two-pass execution (parallel pass + serial pass over marked tests) a *requirement*, or only a design decision? `A14` preferences it as a shape and `FR-008` implies one combined list, yet no FR requires the split; the requirement text and `plan.md` T-002 are not aligned on whether the runner MUST two-pass. [Coverage/Gap, Req §A14, §FR-008]
- [ ] CHK008 Is a requirement named for the operator-facing **mode disclosure**? `SC-004` requires "从命令与 stderr 可判定实际走了哪条路径" and `C-002` fixes the exact line, but the requirements contain no FR for the mode/reason line — the obligation exists only in the contract and `tasks.md` T007. [Coverage/Gap, Req §SC-004 vs `C-002`]
- [ ] CHK009 Is the **baseline-slot and closure-slot identification** specified as a requirement — which run counts, at which commit, recorded where — rather than only named as a Key Entity? `Key Entities` names "Baseline / Closure Slot" but no FR fixes the slot boundaries; `A9` and `SC-006` refer to them as settled. [Completeness, Req §Key Entities, §A9, §SC-006]
- [ ] CHK010 Is the **documentation refresh** requirement (`FR-032`) enumerated over a closed surface list? It says "开发文档中关于如何跑套件的说明" without naming the files that carry those instructions, so no reader can decide when the requirement is satisfied. [Clarity/Completeness, Req §FR-032 vs `plan.md` WP-A3 file list]
- [ ] CHK011 Is the rule for **which existing tests may be touched** stated as a requirement? `FR-013` covers shared-mutable-state causes and `C-046` forbids pre-emptive rewrites, but the requirements themselves never say "a test that passes in parallel today MUST NOT be rewritten" — a preservation-of-subject rule that lives only in the contract. [Coverage/Gap, Req §FR-013 vs `C-046`]
- [ ] CHK012 Is there a requirement that the **existing guard suite keeps its own red-first property** while counts move in one batch? `FR-022` demands guard updates land in the same change but does not require each moved pin to be observed red before the edit, which is the anti-pattern `plan.md` R-6 exists to prevent. [Completeness, Req §FR-022 vs `plan.md` R-6]

## Requirement Consistency — two-sided claims that do not meet in the middle

- [ ] CHK013 Do `FR-016` / `A5` ("MUST NOT 引入网络服务、常驻进程或新的外部系统依赖") and the new dev-side dependency (`FR-015`, `STR-005`) agree on which dependency surface is closed and which is merely runtime-closed? The requirements never say that a dev-only package is exempt from the "no new external dependency" wording, and a literal reader fails both. [Consistency, Req §FR-015, §FR-016, §A5]
- [ ] CHK014 Is the **interpreter boundary** consistent across `RS-001`, `RS-002` and `A15`? `RS-001` pins `>=3.8` and `RS-002` says "无声明 pin" with versions recorded at execution time, while `A15` names `pytest 9.2.0` / `xdist 3.8.0` as the "当前实测组合" — the requirements do not say whether that pair is a floor, a ceiling, or a snapshot. [Consistency/Ambiguity, Req §RS-001, §RS-002, §A15]
- [ ] CHK015 Does the version/count ruling in `## Clarifications` agree with the artifacts it will be judged against? The ruling fixes "constitution 模板 XIX / live XX" and "版本 1.16.0 → 1.17.0", but `templates/constitution-template.md` is a downstream-parameterized template whose only version literal is the `[CONSTITUTION_VERSION]` placeholder — the ruling does not say which text a template-side version assertion should read. [Consistency/Ambiguity, Req §Clarifications (2026-11-06, 编号/位置/计数), §FR-019, `C-025`/`C-035`]
- [ ] CHK016 Are `FR-029` ("无新增失败") and `SC-007` ("零新增失败") consistent with `A3`'s "按名称比较" discipline, and do both name the comparison side? Both use the count-free phrase correctly in intent but neither names *which* baseline 085's suites are compared against. [Consistency, Req §A3, §FR-029, §SC-007]
- [ ] CHK017 Do `FR-027` (no 085 path may be modified) and `FR-030` (085 SC-010 status MUST be updated per evidence) describe one mechanism? The status line the requirement orders *lives inside* `.specify/specs/085-sdd-temporary-goal-team/verification.md`, which `C-041`'s mechanical check forbids touching — the requirements do not carry the carve-out that `tasks.md` T041 has to disclose. [Consistency/Conflict, Req §FR-027, §FR-030, §A12 vs `C-041`, `tasks.md` T041]
- [ ] CHK018 Is `FR-017` ("MUST NOT 新增任何 `/speckit.*` 命令、技能入口模板或运行时服务") consistent with the new owner guideline and owner-declaration surface `FR-018` introduces? The prohibition enumerates commands, skill entry templates and services; it does not say whether a new `shared/guidelines/` document and its mirror count as an admissible addition. [Ambiguity, Req §FR-017, §FR-018]

## Acceptance Criteria Quality — can each criterion be decided from a record?

- [ ] CHK019 Does `SC-001` state a decidable wall-clock predicate, or only "有被记录的下降"? The criterion is jointly a diff (empty, decidable) and a magnitude (undecided), so it cannot be marked `pass` without a second, unrecorded judgement. [Measurability, Req §SC-001, §A13]
- [ ] CHK020 Is every one of `SC-001`…`SC-012` bound to a **record type** it can be read off, rather than to an action ("重跑", "检索", "对比")? `### Measurement Sources & Collection Methods` names files and commands for all twelve, but the criterion bodies themselves carry no record identity, so a reviewer cannot tell a stale record from a fresh one. [Measurability/Traceability, Req §SC-001–§SC-012]
- [ ] CHK021 Does `SC-006` ("差集为空") name the baseline referent unambiguously across `A9` (implementation-start slot) and `FR-014` (serial baseline of the same tree)? The two phrases can denote different runs. [Clarity, Req §SC-006, §A9, §FR-014]
- [ ] CHK022 Is the `**Path**: final` / `supporting` assignment justified anywhere, or is it an assertion? Twelve criteria carry a marker from the closed set, but no requirement explains why `SC-009`/`SC-010`/`SC-011`/`SC-012` are `supporting` while their stories are P1. [Traceability, Req §SC-009–§SC-012]
- [ ] CHK023 Is "至少一个阶段实际并发派发数大于一" (`SC-008`) measurable from a record whose shape is specified? The requirement names the quantity but not the record; `A17` fixes `requested=24` and gives clarify's effective 2, so the requirement does not say whether the *checklist*, *tasks* or *implement* stage is the one that must exceed 1. [Measurability/Coverage, Req §SC-008, §FR-028, §A17]
- [ ] CHK024 Can "工作树除运行前已存在的改动外无新增污染" (`SC-011`) be decided without a pre-run snapshot discipline being required? The Source names "运行前后快照对比" but no FR requires taking the pre-run snapshot, so the criterion is unfalsifiable if the snapshot is skipped. [Measurability/Gap, Req §SC-011]

## Coverage — scenario classes the requirement set does not enter

- [ ] CHK025 Are requirements defined for a **partial or interrupted parallel run** — a worker that dies mid-run, a pass whose list is written but whose exit code is lost — as distinct from the "整体崩在启动阶段" Edge Case? `FR-008` covers only the empty-vs-missing distinction. [Coverage/Exception Flow, Req §Edge Cases, §FR-008]
- [ ] CHK026 Are requirements defined for the case where the **marked serial set grows or empties**? `FR-011` requires the set size to be recorded; nothing says what happens when the serial pass collects zero tests, nor when a second test must be marked. [Coverage/Gap, Req §FR-011, `C-015`]
- [ ] CHK027 Are **recovery/rollback** requirements specified for the principle landing if a count guard or the byte budget fails after partial edits? `FR-022` orders a same-change update; no requirement states the recovery path when the batch cannot be completed. [Coverage/Recovery, Req §FR-022, `plan.md` R-4/R-6]
- [ ] CHK028 Are requirements defined for a **downstream project that already has its own parallel test setup** (its own `-n` in `addopts`), as distinct from "既有 constitution 已有测试原则"? The Edge Cases enter the constitution-coexistence case but not the configuration-coexistence case. [Coverage/Gap, Req §Edge Cases, §FR-004]
- [ ] CHK029 Is the **`SPECKIT_TEST_WORKERS` scope** specified — per-shell, per-CI-job, inherited by the runner's own child processes? `FR-003` fixes its precedence but not its lifetime, and `FR-005`'s nested guard depends on an inherited variable. [Coverage/Completeness, Req §FR-003, §FR-005, `STR-006`]
- [ ] CHK030 Is the reason-classification of a **named serial exception** closed? `FR-011`/`A7` require the reason to be "并行特有的（负载、共享状态、超时）" — an open parenthetical rather than an enumerated set, so two reviewers can classify the same test differently. [Clarity/Coverage, Req §FR-011, §A7]
