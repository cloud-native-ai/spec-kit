## Attribution defect (disclosed, not repaired)

The closure run **should not have been executed while the sandbox worktree existed**. Its recorded
`21 failed / 7533 passed / 271.72 s` is therefore **not a trustworthy closure measurement**: the extra
failures inflate the count and the extra copies enlarge the collection, and the run's own premise
(one clean tree, same selection as the baseline) was broken by the executor's process, not by the code.

Disposition options, for the driver (this is a decision, not a correction — the executor MUST NOT pick):

1. **Record `in-slot-rerun`** with this file as the trigger evidence, re-running the closure once on the
   cleaned tree. The slot model permits it: `in-slot-rerun` must follow `closure` and carries its trigger
   and evidence. Cost: one additional full-suite execution (≈4.5 min parallel pass + ≈35 s serial pass).
2. **Accept this record with the attribution attached** (this file's § Bookkeeping-level result), treating
   the 2 contaminated names as attributed-by-mechanism rather than attributed-by-re-run. Cheaper, but it
   leaves the closure slot's headline numbers describing a tree that no longer exists, and SC-001's
   wall-clock reading comes from a contaminated run.

This file does not pick. Both the contaminated numbers and the clean attribution are recorded above so
that either disposition is reviewable, and neither is silently smoothed away.
