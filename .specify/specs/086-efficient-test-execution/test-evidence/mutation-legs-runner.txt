## 5. The two legs whose surface is a *value*, not a heading (M-14, M-15)

The parametric case removes a heading-shaped carrier, which is the right probe for M-10…M-13. M-14 and
M-15 are about a byte-level property instead, so they were read directly rather than inferred:

**M-14 (hand-edited live instructions)** — the live file must be the generator's own output. Measured by
regenerating and asking git whether anything moved:

```
$ bash scripts/bash/generate-instructions.sh ; git status --porcelain -- .specify/instructions.md
exit 0
[no output — the tracked live file is byte-identical to a fresh generation]
$ md5 -q .specify/instructions.md    # before regenerate
7b62e28381adb19daae2df24aab9a80c
$ md5 -q .specify/instructions.md    # after regenerate
7b62e28381adb19daae2df24aab9a80c
```

A hand edit would make the two hashes differ or make the regeneration produce a diff; neither happens.
This is the proposition M-14 states, read on the tracked tree.

**M-15 (live version left behind)** — the pin that would catch it exists and now matches:

```
$ git show <merge-base>:.specify/memory/constitution.md | grep -m1 '^\*\*Version\*\*'
**Version**: 1.16.0 | **Ratified**: 2026-01-30 | **Last Amended**: 2026-11-05
$ grep -m1 '^\*\*Version\*\*' .specify/memory/constitution.md
**Version**: 1.17.0 | **Ratified**: 2026-01-30 | **Last Amended**: 2026-11-06
$ grep -n '1.17.0' tests/contract/test_fast_fail_discipline.py
1077:    assert m.group(1) == "1.17.0", f"C-5: live version is {m.group(1)}; expected 1.17.0"
```

The guard is an equality assertion against `1.17.0`, so leaving the live file at `1.16.0` — the exact
M-15 edit — makes that assertion fail. The leg is discriminating because the assertion is an equality,
not a `>=`.
