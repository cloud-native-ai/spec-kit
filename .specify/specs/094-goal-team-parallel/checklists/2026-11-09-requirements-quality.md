## 一、绑定 / 作用域 / 生命周期模型的可判定性

- [ ] CHK001 - 绑定记录的四个维度（`owner` / `owner_id` / `origin` / `lifecycle`）是否各自给出了**封闭取值域**，使「一条定义缺哪个维度就不可解释」可被判？[Clarity, Completeness, Req §FR-002, Req §FR-023] — **pass**：FR-002 给出 `owner` 封闭三值（`sdd-run` / `command-run` / `human`）与 `owner_id` 的取值锚（MUST 与状态脊 `run_id` 同名同义）、`origin` 封闭取值（`null` 或一个 spec 目录名）；FR-023 给出 `lifecycle` 的 goal 侧三值（`active` / `achieved` / `abandoned`）与 team 侧既有二值（`active` / `archived`），并显式写「每个维度 MUST 有封闭取值域与唯一 owner」。四个维度的取值域在需求内闭合。
- [ ] CHK002 - 「读写作用域不是声明维度、只能由 `owner` + 档案层级机械导出」这条排除命题，是否给出了导出函数的落点，使读者不会把它读成第五个可声明字段？[Clarity, Consistency, Req §FR-023, Req §FR-038] — **pass**：FR-023 末句明写「**读写作用域** MUST NOT 作为声明维度单独存在：它能且只能由 `owner` + [[STR-002]] 机械导出」；FR-038 给出该导出的具体内容（team 档案由 owner 身份独立可写；被任意 team 绑定的 goal 只有 `human` 可改写）。两处一为禁令、一为导出式，无第三读法。
- [ ] CHK003 - 「档案位置由 binding 决定，不由概念分类决定」（User Story 5 的核心命题）是否被写成一条**可检索的禁令**，而不是一个解释性陈述？[Measurability, Clarity, Req §FR-015] — **pass**：FR-015 逐字写「一个 goal 的归属 MUST 只由绑定记录回答；框架 MUST NOT 从目录位置推断归属，MUST NOT 保留任何『在 spec 下即属于 spec』的推断规则」；SC-009 的「把归属推断改成按目录位置时测试转红」给出变异判据。禁令与变异臂同时存在。
- [ ] CHK004 - `resolve-scope` 改后取值域的**成员集合**是否在需求正文被枚举，使「不得出现以目录位置命名的成员」有可判定的对象？[Completeness, Clarity, Req §FR-008, Req §FR-025] — **pass**：FR-008 逐字给出「`spec` 这一取值名 MUST 被删除……`global` / `auto` 保留取值名」，即改后域为 `{global, auto}` 两项；FR-025 给出该域的判定原则（表达档案层级与绑定维度、不得表达位置）并指向唯一 owner 文档。成员集合在需求内可列。
- [ ] CHK005 - 「终态 goal 拒绝新绑定」与「N teams : 1 goal 的一向身份引用」这两条既有全局约束，其**规范文本的 owner** 是否被点名，而不是在需求内被复述成第二个规范源？[Traceability, Consistency, Req §FR-026] — **pass**：FR-026 以「(a) 终态保留 (b) 一向身份引用 (c) 终态拒绝新绑定」三项列举后明写「这三条各自有既有 owner，本特性 MUST 引用而非复制其规范文本」；FR-024 点名概念 owner 为 `goal-definitions.md` 与 `create-team/references/conceptual-model.md`。复述禁令与 owner 指针同时在场。
- [ ] CHK006 - 迁移冲突判据「只比概念载荷、排除绑定行」是否给出了**载荷字段的封闭清单**，使其可被机器比较而无需读者解释「概念载荷」？[Clarity, Measurability, Req §FR-011] — **pass**：FR-011 逐字把载荷展开为「Objective、Success Criteria、Lifecycle status、Targets 的文本」四项，并明写「MUST NOT 包含后来新增的绑定行」，同时给出理由（否则迁移后档案与自身来源永久不等价）。清单封闭且排除项显式。
- [ ] CHK007 - 「`origin` 只记直接来源、不重建跨定义谱系」（A11）这条边界是否在需求正文（FR 级）留有落点，还是只活在一处 Assumption？[Gap, Completeness, Req §A11, Req §FR-009] — **fail**：`## Functional Requirements` 中没有任何一条 FR 承载「迁移 MUST NOT 重建跨定义的历史谱系」这条否定命题；FR-009 只要求「把来源 spec 记入 `origin`」。该边界只在 A11 出现，而 A11 恰处于那段**重复且互相冲突**的 Assumptions 块（见 CHK013/CHK014），其权威性本身待定。以 FR 编号检索不到这条约束，实现者可在迁移里重建谱系而不触犯任何 FR 句。

## 二、档案统一、迁移与 archive-not-delete

- [ ] CHK008 - 「goal 与 team 的唯一写入落点」这条命题的**判定形态**是否被写成结构不变量（写入路径数 = 0），而不是文档措辞？[Measurability, Completeness, Req §FR-007, Req §FR-013, Req §SC-002] — **pass**：FR-013 明写「MUST NOT 只以文档措辞断言」，要求以契约测试钉住「写 `.specify/specs/<spec>/goal|team/` 的代码路径数量为零」；SC-002 给出变异臂（任一写入改回旧路径时转红）。判定对象、判据与失败形态三者齐备。
- [ ] CHK009 - archive-not-delete 的**回执字段集**（来源 spec / 原 slug / 目标 slug / 关联目标档案 / 结果）是否闭合，使「无回执的删除」可被判为失败？[Completeness, Clarity, Req §FR-010] — **pass**：FR-010 逐字列出五项并写明「迁移失败 MUST 报告失败阶段，MUST NOT 留下无回执的删除」；Edge Cases 中断分支与 FR-010 续做要求互指。回执字段可枚举、失败形态可判。
- [ ] CHK010 - 中断迁移的**可续做语义**是否被写成可判定的阶段报告，使「第二次调用是续做还是重新搬一次」不产生两种读法？[Clarity, Measurability, Req §FR-010, Req §SC-011] — **pass**：Edge Cases 首条逐字要求「迁移 MUST 可判定地报告其阶段与实际状态（源归档目录名 + 目标是否已存在），再次调用 MUST 从该阶段续做而不是重新搬一次」；SC-011 给出变异臂「把第二次调用改成重新搬移或静默成功时测试转红」。阶段报告的字段与续做方向同时具名。
- [ ] CHK011 - 迁移与残余探测的**执行体与命令入口**是否各被声明为唯一（同一可执行体两个动作、`/speckit.goal migrate-archive` 唯一写入口、`/speckit.sanitize` 只读），使「不得新增第二个可执行体 / 第二个写入口」各有可判定对象？[Consistency, Clarity, Req §FR-012, Req §FR-030] — **pass**：FR-012 明写「探测的执行体归 FR-010 的迁移引擎（同一个可执行体的只读动作），MUST NOT 新增第二个可执行体」，RS-004 把两者绑到同一文件 `scripts/python/goal-utils.py`；FR-030 逐字写「goal 侧归 `/speckit.goal` 的 `migrate-archive` 模式……team 侧由同一动作按 [[STR-002]] 一并处理；`/speckit.sanitize` 只提供只读残余探测并列示读数」。执行体唯一、写入口唯一、只读面唯一。
- [ ] CHK012 - 迁移「不强制、先探测」这条范围前提（A5）是否与 FR-010「迁移 MUST 是 archive-not-delete」的**破坏性边界**自洽，即无人值守运行不得自动搬档案这一点在需求正文有名？[Consistency, Assumption, Req §A5, Req §FR-010] — **观察**：A5 明写「无人值守运行在未迁移仓库里 MUST NOT 自动搬动档案（那是无人值守的破坏性动作）」，与 FR-010 不冲突；但「迁移是被调用的、不是启动副作用」这条判据只落在 A5（Assumptions 块），FR-010 只描述迁移**执行时**的语义。记录点：A5、FR-030 的 `migrate-archive` 入口。
