## 3. Defect found in the owner document's normalization ORDER (agent-drafted, not user-ratified)
The document's steps 2 and 3 contradict its own Accepted-forms table:
- Accepted forms lists `/improve-skills` (Slash reference) as an accepted form meaning
  "the Skill behind that slash-command name".
- Step 2 says: "If the value contains a path separator (`/`) ... treat it as a path or
  directory reference and skip to step 5". A leading `/` IS a path separator, so
  `/improve-skills` leaves normalization as a PATH, and step 3 ("Strip one leading `skill:`
  label, then one leading `/` or `@`") is unreachable for every value that starts with `/`.
  Consequence: the slash form can never normalize to a bare name under the written order.
- `@/improve-skills` has no rule that strips `@` and then `/`; it becomes a path by step 2.
- The table's "Directory path" row ends in the directory itself, while step 2's path test
  admits `/`, `SKILL.md` or a trailing `/`; `skills/external/foo` only qualifies via the `/`.
- FR-030 requires the normalized result to be one of command-surface / skill id / failure.
  Step 5's outcome ("names go through the run-skills ladder; paths must sit inside the known
  locations") is a resolution procedure, not a third outcome, and step 3's expectation
  `^[A-Za-z0-9_-]+$` would reject a legitimate dotted skill name holding it to a hard failure.
