# Research: 070-subagent-task-teams

**Feature**: 070 — Task Decomposition & Team Coordination for Subagent-Driven SDD
**Created**: 2026-10-24
**Inputs**: `requirements.md`, `notes/clarify-decisions.md` (D1–D9), the Feature 070 brief, the driver skill source, and the 058/060/063/064/067/068 specifications.

This file records the Phase 0 decisions that the plan and the design contracts build on. It does not restate the requirements; every decision below resolves *how* a fixed requirement will be implemented without re-deciding *what* the requirement is.

- **Measured pre-change facts on this execution host** (2026-10-24):
  - `python3 --version` → 3.11.11; `pytest --version` → 8.4.2.
  - `python3 scripts/python/sync-mirrors.py --check --only skills/external/sdd-loop-driver` → `ok skills/external/ == .specify/skills/ (28 files)`, exit 0. The mirror baseline is clean before this feature.
  - Targeted existing driver tests (`test_decomposition_check.py`, `test_pre_analyze_check.py`, `test_overlap_check.py`, `test_sdd_loop_driver_gates.py`, `test_sdd_loop_driver_skill.py`) → 65 passed in 16.06 s.
  - The 067 baseline was measured on a different host class (macOS arm64, Python 3.14.6, pytest 9.1.1). Absolute durations are therefore not comparable; only name-level failure sets are portable.
- **Source survey**: the driver already carries a JSONL fence precedent (`<!-- test-budget:begin -->`), a parameterized runner (`scripts/stage-runner.sh`), a watcher with fixed exit codes, a line registry with the Ownership Manifest, and three deterministic gates. Feature 070 adds no fourth dispatch form: it composes the existing native and detached forms.

## R1 — The Work Package is the 067 part brief extended, not a second brief

**Decision**: define one WP record whose fields are the FR-001 schema, and for `implement` treat it as the 067 part brief plus WP identity, dependency, ownership, parallel-safety, and evidence fields. The ledger's `dispatch` event carries the 067 dispatch-log fields verbatim (`part_id` = `wp_id`, `task_ids[]`, `turns`, `test_delta`, `commit`, `outcome`, `duration_seconds`, `token_cost`).

**Why**: FR-025 and Assumption A11 preserve the 067 part discipline; a second brief or a second dispatch log would be a competing owner. One record with a stage-specific projection keeps the implement behavior attributable to 067 while giving the other stages the same bounded model.

**Rejected**: a separate `part-brief.md` writer for 070 (two formats drift); keeping the 067 free-form log alongside a new ledger (two ledgers, forbidden by FR-020 and D9.3).

**Consequence**: for a large `implement` stage that runs with 070 decomposition disabled, the 067 part discipline remains in force unchanged (see R13).

## R2 — The plan and ledger live in the existing line state spine

**Decision**: adopt D2.1 literally: one `wp-plan` fence per plan, one amendment fence per amendment, and one append-only `wp-ledger` JSONL fence inside the line state spine. The driver is the sole writer. Per-entry result, verdict, gate, and report artifacts live under the state directory, not in the spine.

**Why**: the spine is the only run ledger (058), the test-budget fence proves the pattern is workable, and concurrent branches cannot collide on a per-line file. A spec-local plan file would be a second source that the driver must reconcile on re-entry.

**Rejected**: a spec-local `work-packages.json` (re-entry ambiguity); a global JSONL ledger (violates the per-line spine model); a mutable aggregate index (Concurrent Development Safety).

## R3 — The decomposition gate is a new stdlib script, not an extension of `decomposition-check.py`

**Decision**: create `skills/external/sdd-loop-driver/scripts/wp-gate.py` with `--check plan|preflight|retry`, the D3 JSON/exit-code interface, and no third-party imports. `decomposition-check.py` keeps its Feature-level FR/task slicing gate.

**Why**: the names and scopes differ (feature slicing versus stage package graphs); extending the existing script would overload a gate already pinned by 063 contract tests. The repository convention for driver gates is a small stdlib-only script with a documented exit-code taxonomy.

**Rejected**: extending `decomposition-check.py` (semantic overload); implementing the gate in the line registry (064 owner, violates non-duplication); putting the checks in prompt text only (not deterministic).

**Consequence**: `wp-gate.py` also emits the deterministic `dispatch_layers` and `integration_order` derived from the graph, so the prompt-level scheduler (R4) does not re-derive ordering by intuition.

## R4 — Scheduling remains driver prompt logic; no runtime scheduler

**Decision**: the driver performs readiness selection, slot accounting, and dispatch. `wp-gate.py` computes plan properties (layers, order, write set, slot validity) but never dispatches. The algorithm is owned by `references/decomposition-model.md` and pinned by contract tests; a test-only simulator in `tests/fixtures/` models it for dry runs.

**Why**: Constitution Principle IX states that supervisor/orchestration constructs are prompt instructions, never runtime schedulers. A scheduler daemon or engine would breach the framework scope and add a failure surface the driver cannot inspect.

**Rejected**: `wp-schedule.py` (new runtime scheduler, Principle IX); a queue service (over-engineering); letting the LLM choose order freely (non-deterministic, violates FR-011's declared tie-break).

**Trade-off**: a prompt-level algorithm is proved by contract pins plus a deterministic simulator, not by executing an LLM. This limitation is recorded in the risks table and in the dry-run evidence scope.

## R5 — Stage-team preset plus a documentation-level adapter

**Decision**: add `skills/external/sdd-loop-driver/templates/stage-team-preset.md` per D1, and implement the adapter as a declared projection procedure in `references/decomposition-model.md`: it substitutes stage, line, plan hash, slot cap, pattern, and the package-to-seat mapping into a run-scoped plan fence. No `team.md`, no goal binding, no run report of its own.

**Why**: D1 already rejected a persisted team per stage; the remaining choice is where the projection lives. The driver skill must be self-contained at runtime, so the procedure lives in its references, not in the spec directory.

**Rejected**: direct `team.md` reuse (goal establishment and lifecycle cost); modifying `create-team`/`run-team` to accept a transient team (violates FR-008); a new team registry (violates the non-duplication rule).

## R6 — Dispatch reuses `run-agent` and `stage-runner.sh`

**Decision**: local topology dispatches one native host subagent per WP; remote topology launches one detached `stage-runner.sh` process per WP with unique labels and WP sentinels. Both forms are the existing forms; 070 adds only the label/sentinel naming rule and the per-package status/result collection rule.

**Why**: FR-010 and FR-027 forbid a new dispatch mechanism. The existing runner already provides the pid/status/log/heartbeat four-piece evidence and stream-json visibility.

**Rejected**: a batched multi-WP runner (new mechanism); using `qodercli` locally (violates the local topology rule); a shared FIFO/runner for several WPs (loses per-package verdicts).

## R7 — Verifier independence is structural, with a declared degraded fallback

**Decision**: one fresh-context verifier execution per WP, dispatched after settle, with a verdict JSON. The verifier's `execution_id` must differ from the executor's. On a host that cannot spawn a subagent, the driver performs the verification itself (it is never the executor) and records `verification_execution=driver-u4`; this is a recorded capability fallback, not a silent weakening.

**Why**: FR-016 forbids self-verification. The driver is structurally independent of the package executor, so driver verification preserves the independence property when a fresh subagent is unavailable. The fallback is explicit so evidence never implies a subagent that did not exist.

**Rejected**: accepting the executor's self-report (explicitly forbidden); treating a missing verdict as pass (forbidden); using the package's own tests as the only verdict.

## R8 — Integration is one execution per stage attempt; the stage gate stays last

**Decision**: after every package verifies, dispatch one integrator execution. It aggregates in the graph-derived integration order, detects missing/contradictory outputs, makes the single stage-closing commit, and emits the stage sentinel as its last non-empty line. The driver then runs the unchanged stage U4. Package sentinels are never accepted as stage sentinels.

**Why**: FR-014, FR-017, and FR-018 require aggregation before U4 and one deterministic integration. One integrator execution keeps the stage commit boundary single and auditable.

**Rejected**: per-package commits for non-implement stages (fragmented stage deliverable); driver-as-integrator always (loses the declared seat and the fresh-context assembly); promoting a package sentinel (explicitly forbidden).

**Consequence**: the decomposed stage does not execute the monolithic `/speckit.*` command; the package acceptance clauses and the integrator's assembly cover that command's artifact contract (R13).

## R9 — Retry is ledger-derived and delta-checked

**Decision**: count dispatch events per `(stage, stage_attempt, wp_id)`; allow attempt 2 only with a `retry_delta` changing scope, budget, or topology; reject attempt 3 as exhausted and escalate to the unchanged U5 path. `wp-gate.py --check retry` mechanically validates the delta.

**Why**: FR-013 and the 067 same-budget-rerun prohibition. A separate counter file would be a second ledger and would desync from the spine on re-entry.

**Rejected**: a counter file (second ledger); a free-form "reason" with no mechanical condition (unfalsifiable); consuming the stage retry budget for package retries (violates A4).

## R10 — Metrics are derived from the ledger, never from impressions

**Decision**: define wall-clock, critical path, parallelism efficiency, stage executions per canonical stage, retry counts, and manual interventions exactly as D7.2. `wp-report.py` derives the report from the ledger, writes Markdown and JSON, and writes the literal `not_evaluated` for any missing source. The benchmark anchor is the conservative upper bound (plan 70 min, review 37 min), requires at least three comparable samples, and is never mixed with a re-measured baseline.

**Why**: SC-001, SC-002, SC-007, and the 068 discipline forbid fabricated numbers. A single derivation script keeps the report and the spine consistent.

**Rejected**: absolute wall-clock promises (environment variance); counting a missing timestamp as zero (forbidden); deriving metrics from transcripts (raw dumps are forbidden).

## R11 — Opt-out is resolved once, recorded once, and inherited by the gate

**Decision**: U0 declares `decomposition`, `decomposition_stages`, and `decomposition_slot_cap`; the stage attempt may carry `decomposition_override`. Precedence is feature-off (hard) > stage-attempt override > stage map > built-in defaults. The resolved decision (`decomposed`, `single-package`, `disabled`, `fallback`) is written to the plan fence before dispatch.

**Why**: D8 fixes the names and precedence. Resolving once prevents the driver from re-reading a different layer later and silently flipping the mode.

**Rejected**: a per-package opt-out (no coherent stage model); environment-variable configuration (invisible in the spine); re-enabling after feature-level off (violates the hard opt-out).

## R12 — Tests are layered, red-first, and pinned to existing conventions

**Decision**: add unit tests for the two scripts, contract tests for each contract file, one integration dry-run file driven by a deterministic simulator fixture, a non-regression file for 058/063/064/067/068, and mutation drills that prove the tests go red when the gate/simulator is broken. Use pytest markers (`contract`, `integration`) and `scripts/bash/run-tests.sh` for the two full-suite slots.

**Why**: FR-028, FR-029, FR-030 and Constitution IV. The repository's existing driver tests use subprocess invocation, stdlib-only guards, and per-clause functions; 070 follows the same pattern.

**Rejected**: mocked-only tests with no script execution (a green check that cannot go red); a new test framework (no new dependency); snapshotting the whole spine (brittle and transcript-like).

**Limitation disclosed**: the scheduler is prompt-level (R4); the dry-run test proves the declared algorithm in a simulator and the contract tests pin the prompt-owner text. It does not prove an arbitrary LLM's adherence. The metric acceptance therefore remains `not_evaluated` unless a real benchmark run supplies spine timestamps.

## R13 — Decomposed stages honor the stage command's artifact contract without running its internals

**Decision**: each decomposition rule carries a closed required-output inventory and an acceptance clause set derived from the stage command's documented deliverables. Packages produce those deliverables directly; the integrator assembles them in the stage's required format; the unchanged stage U4 verifies the assembled result. If a required output or acceptance obligation cannot be represented, the stage falls back to the single-package path.

**Why**: FR-015 makes the driver the sole coordinator and D2.6 forbids a WP executor from invoking the stage command as a monolith. Bypassing the command's internals is acceptable only when its output contract is fully covered and independently verified; otherwise decomposition would weaken a gate.

**Rejected**: running `/speckit.*` inside each WP (duplicate, conflicting stage writes); ignoring the command contract and trusting package self-reports (forbidden); changing the stage command to expose parts (out of scope).

**Consequence for `implement`**: if 070 is off for a large implement stage, 067's part discipline still applies. The 070 single-package decision means one 070 package boundary, not the removal of the 067 part mechanism. This resolves the apparent tension between FR-005's single-package wording and FR-025's preservation clause: FR-025 governs the pre-existing part discipline.

## R14 — Attempt-scoped evidence paths (design refinement of D2.4)

**Decision**: result, verdict, gate, and report filenames carry the stage attempt and WP attempt:
`<state-dir>/wp/<line>-<stage>-<wp_id>-a<N>w<M>.result.json`,
`<state-dir>/wp/<line>-<stage>-<wp_id>-a<N>w<M>.verdict.json`,
`<state-dir>/wp/<line>-<stage>-a<N>-gate-<check>.json`,
`<state-dir>/reports/<line>-<stage>-a<N>-coordination.{md,json}`.

**Why**: D2.4's attempt-free names would let a U5 stage retry overwrite the evidence that an earlier ledger record points to, silently invalidating the retry history. The refinement preserves D2.4's directory and suffix so every documented reader still matches; it only adds the attempt dimensions.

**Rejected**: an archive subdirectory (second layout); overwriting with a note in the JSON (the earlier pointer still resolves to the wrong content); recording no verdict file for retries (loses evidence).

## R15 — Overlap is adjudicated against closed predecessor features

**Decision**: declare the full delivery surface in `feature-ref.md`. The deterministic overlap check reports 21 relations against 11 predecessor specs (15 `same-path`, 6 `nested-path`): the driver `SKILL.md`, the driver documentation page, and four new files under a predecessor's historical whole-directory declaration. Every predecessor's commits are already in the base history; 070 is the only live writer. Adjudicate the relations as sequential evolution: the edits are additive, predecessor primitives are reused read-only, and the non-regression suite preserves their pinned behavior. Record the raw JSON and the adjudication.

**Why**: FR-027 confines delivery to the driver skill and its docs page, which are shared with predecessor features. Hiding modified files from the declaration to obtain a literal `clear` would produce a green check that would not go red — the exact anti-pattern the Fast Fail discipline forbids.

**Rejected**: declaring only new files (under-declaration); a nested-path declaration of the whole skill directory (coarser, same result); waiting for a future feature (the delivery surface does not change).

## R16 — Mirror and two-hats obligations

**Decision**: all driver-source edits land under `skills/external/sdd-loop-driver/` and are projected to `.specify/skills/sdd-loop-driver/` by `sync-mirrors.py`. The spec directory, tests, and docs page are not mirrored. The mirror verification criterion is “no NEW drift on the touched pair”, measured against the clean 28-file baseline recorded in § 0.

**Why**: Principle XI's two-hats rule and the existing `MIRROR_PAIRS` configuration. Hand-editing the `.specify/` mirror is forbidden.

**Rejected**: editing the runtime mirror first (client-side instance fix); adding a new mirror pair (unnecessary; the pair exists).

## R18 — Stage required-output inventories (rationale; owner: `data-model.md` E13)

**Decision**: the closed per-stage required-output inventory and the package-shape guidance are owned by `data-model.md` E13 (`DecompositionRule`); that table is the sole authoritative copy. This section is the dated 2026-10-24 Phase 0 rationale for why an inventory exists and MUST NOT restate the rows.

**Why**: the rules in FR-002 need a concrete coverage baseline for `wp-gate --check plan` and for the integrator, and the per-stage shape guidance records what a sensible package boundary looks like. Keeping the inventory in one owner avoids the duplicated authored copies that Constitution XIV forbids; WP-15, the runtime owner document, and the task rows reference the owner instead of copying it.

**Consequence**: the plan's run-specific `required_outputs` field must cover the E13 inventory for its stage, or the gate rejects the plan (`orphan-output`); the `integrator_outputs` field names the outputs the integrator owns (at minimum clarify's write-back) so they are accounted for exactly once.

## R19 — Baseline and benchmark method

The measured baseline in `requirements.md` is the brief's dated record, not a re-measurement (A9). The conservative anchor is plan 70 minutes and review 37 minutes; a 20% reduction means ≤56 minutes and ≤29.6 minutes respectively, measured over the OR-04 interval (first package dispatch to stage U4 completion). The anchor is the dated whole-stage range's upper bound used as a conservative proxy; a re-measured baseline MUST use the OR-04 interval and replaces the anchor. A median claim requires at least three comparable samples on the same host class and topology; fewer samples, or a host-class mismatch, yields `not_evaluated`. This host (Linux x86_64, Python 3.11.11) is not the 067 baseline host, so absolute test durations are not used; the benchmark record must either re-measure the baseline on this host or record `not_evaluated` for SC-001. An all-`not_evaluated` benchmark blocks closure unless the user records an explicit waiver naming SC-001/SC-002 (FR-023).
