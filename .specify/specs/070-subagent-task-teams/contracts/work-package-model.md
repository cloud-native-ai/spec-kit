# Contract: Work Package Model and Ledger (WP-01…WP-18)

**Feature**: 070 — Task Decomposition & Team Coordination for Subagent-Driven SDD
**Owner of the design**: this file. Runtime projection: `skills/external/sdd-loop-driver/references/decomposition-model.md`; schema projection: `data-model.md` E1–E5.
**Scope guard**: no second brief format, no second ledger, no second registry, no stage-command change.

- **WP-01 (Work Package schema)**: Every Work Package MUST carry the fields of FR-001: `wp_id`, `stage`, `objective`, `inputs`, `outputs`, `owned_paths`, `read_only_paths`, `depends_on`, `parallel_safe`, `max_turns`, `acceptance`, `sentinel`, and `evidence`, plus the contract fields `kind`, `source_refs`, `intermediate_outputs`, `bounded_by`, `seat`, and `resources`. A package missing any required field MUST NOT be dispatched.
- **WP-02 (Kind and territory invariants)**: `kind=read-only` requires an empty `owned_paths`; `kind=write` requires a non-empty `owned_paths`; `parallel_safe=true` is legal only for `read-only`. A write package never declares `parallel_safe=true`.
- **WP-03 (Stable wp_id)**: `wp_id` is `<stage>-wp<NN>` for planned packages and `<parent>-a`, `<parent>-b`, … for split children. IDs are derived from the package's primary `source_refs` and its position in the DAG, never from dispatch timing. The sentinel is `WP-<WP_ID_UPPER>-DONE` (for example `WP-PLAN-WP03-DONE`), which renders the declared stage-plus-package sentinel without duplicating the stage segment.
- **WP-04 (Deterministic ID assignment and layers)**: The driver assigns provisional keys from `source_refs`, builds the DAG on those keys, computes topological layers, sorts each layer by provisional key lexicographically, assigns sequence numbers `01..NN` in layer order, and then rewrites `depends_on` to `wp_id`s. The same source artifacts and the same rule MUST yield the same ids and the same layers on replay.
- **WP-05 (Plan fence)**: The plan is written once per stage attempt inside `<!-- wp-plan:begin stage=<stage> stage_attempt=<n> -->` … `<!-- wp-plan:end -->` in the line state spine. The fence contains one UTF-8 JSON object. The driver is the sole writer; package executors never write the spine. The original plan fence is never edited.
- **WP-06 (Canonical plan_hash)**: `plan_hash` is `sha256:<hex>` over the canonical JSON of the effective plan (sorted keys, UTF-8, separators `,` and `:`, `ensure_ascii=false`) with `plan_hash`, `slot_cap_requested`, `slot_cap_ceiling`, and every timestamp key (`at`, any key ending in `_at`) removed. Replaying the same artifacts and rule MUST reproduce the same hash.
- **WP-07 (Amendments)**: An amendment is a separate `<!-- wp-plan-amendment:begin stage=<stage> stage_attempt=<n> seq=<n> -->` fence carrying `supersedes_plan_hash`, the changed package records, an optional addressable retry block (`wp_id`, `wp_attempt`, `retry_delta`), and the new effective `plan_hash`. Amendments apply in strictly increasing `seq` order; the latest effective hash wins.
- **WP-08 (Split retries)**: A split retry keeps the parent record with its attempt history, sets `superseded_by` to the child ids, adds the child packages with distinct outputs, and rewrites every dependent's `depends_on` from the parent to all children. The children inherit the parent's attempt count: their sole dispatch is the lineage's retry attempt, split depth is one (a child is never split again), and a child failure fails the stage gate without a further automatic retry. A superseded parent is never dispatched again; its evidence remains attributed to the parent.
- **WP-09 (Ledger fence)**: The ledger is one append-only JSONL fence `<!-- wp-ledger:begin -->` … `<!-- wp-ledger:end -->` in the same spine. Each line is one complete JSON object. The event set is `plan`, `dispatch`, `settle`, `verdict`, `retry`, `integrate`, `stage-close`, and `wp_failed`; no other run ledger may be created.
- **WP-10 (Ledger event fields)**: Events carry the fields fixed in `data-model.md` E4. The `plan` event is written with the gate verdict before the first dispatch and references the plan fence by `plan_hash`; a post-repair plan appends a second `plan` event with `supersedes_plan_hash` without creating a new stage attempt. A package that fails twice, or a split child that fails at all, appends `wp_failed` before U5. Unavailable quantities are the literal `not_evaluated`.
- **WP-11 (Attempt-scoped evidence files)**: Per-package evidence lives outside the spine and is attempt-scoped: `<state-dir>/wp/<line>-<stage>-<wp_id>-a<N>w<M>.result.json`, `<state-dir>/wp/<line>-<stage>-<wp_id>-a<N>w<M>.verdict.json`, `<state-dir>/wp/<line>-<stage>-a<N>-gate-<check>.json`, and `<state-dir>/reports/<line>-<stage>-a<N>-coordination.{md,json}`. These are per-entry evidence files, never a second ledger. A read-only package may write only its own evidence path under the state directory.
- **WP-12 (067 extension, not duplication)**: For `implement`, the WP record is the 067 part brief extended with WP identity, dependency, ownership, parallel-safety, and evidence. The `dispatch` event carries `part_id` (= `wp_id`), `task_ids[]`, `turns`, `test_delta{passed,failed,new_failures[]}`, `commit`, `outcome`, `duration_seconds`, and `token_cost`. There is one brief format and one dispatch log.
- **WP-13 (Single-package representation)**: A non-decomposed stage writes a plan fence with `decision` in `single-package|disabled|fallback`, the plan's `gate_verdict` per FN-08, exactly one package (`<stage>-wp01`, `kind=write` unless the stage is read-only, `parallel_safe=false`, `bounded_by={unit:"acceptance",count:1}`, `sentinel=<STAGE>-DONE`), and `integrator_outputs=[]`. The plan fence is the canonical decision record; the ledger `plan` event references it. The sole package is the stage execution itself; its sentinel is the stage sentinel, not a promoted package sentinel.
- **WP-14 (Canonical location and no second ledger)**: The plan and ledger MUST be fences in the existing line state spine. No spec-local plan file, no second JSONL stream, no mutable aggregate index, and no separate retry counter file may be introduced.
- **WP-15 (Stage-command opacity and output coverage)**: Package executors do not invoke the stage command as a monolith. Each executes its bounded slice from the stage authority artifacts and templates. The plan's `required_outputs` MUST cover the decomposition rule's required-output inventory (owned by `data-model.md` E13; this clause references it and does not restate it). The integrator assembles the stage deliverable in the stage's required format and owns the outputs listed in the plan's `integrator_outputs` (at minimum clarify's write-back); those outputs are excluded from package coverage but remain covered by the unchanged stage U4. An inventory item that cannot be represented forces the single-package fallback.
- **WP-16 (Replayability)**: The applied rule, `source_artifacts`, package list, edges, pattern, slot cap, gate verdict, and plan hash MUST be recorded before dispatch. Replanning the same stage artifacts with the same rule yields the same package set and hash; a changed artifact set may legitimately change them and the new hash records that fact.
- **WP-17 (Timestamp units)**: Ledger arithmetic timestamps (`started_at`, `ended_at`, `at`, `stage_u4_at`) are epoch seconds. Evidence timestamps (`verified_at`, `checked_at`) are ISO-8601. Mixed units are invalid.
- **WP-18 (Spine write authority)**: The driver writes the plan, amendment, and ledger fences. Stage executors keep writing their existing transport rows in `SPINE_WRITE_MODE=transport`; package executors never write a fence. A re-entry reads the spine and MUST NOT reconstruct a plan from session memory.
