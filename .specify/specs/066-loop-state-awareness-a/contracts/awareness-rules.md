# Contract — Awareness, Completion and Action Rules

**Owner**: `references/state-awareness.md` is the single prose owner of these rules; `scripts/loop-state.py` is the code side. Watch verdicts and numeric thresholds remain owned by `scripts/watch-target.sh` / `references/watch-model.md`; stall defaults and U4/spine write points remain owned by `references/stage-prompts.md`; the plan-owned artifact set remains owned by `references/efficiency-model.md` §3. Clauses are numbered `RUL-NN`.

## Verdict source

- **RUL-01**: When a watcher verdict is present (local `--once` or a probe with `watch_status=available` and a non-null `watch_verdict`), `loop_state` is that verdict verbatim and `verdict_source="watcher"`. The engine MUST NOT rewrite, downgrade or upgrade it. The snapshot's stricter stage-envelope attribution applies only to its own evidence and completion projection: a carrier whose line/run match but whose stage does not is `stale` for the snapshot and is reported, yet it never rewrites the watcher verdict.
- **RUL-02**: The derived map runs only when no watcher/probe verdict is present; it sets `verdict_source="derived"`, produces no watcher exit code, and never claims watcher semantics.

## Derived map (D1–D11)

- **RUL-03**: D1 maps `spine.state=stalled` to `STALLED` and `spine.state=reentry-required` to `REENTRY_REQUIRED` before any file-evidence rule.
- **RUL-04**: D2 yields `ANOMALY` when (an exit record exists OR the pid is dead) AND the last non-empty log line starts with `ANOMALY:`. It does not require an own status record.
- **RUL-05**: D3 yields `FAILED` on an exit record with `rc≠0`. D4 yields `DONE` on exit `rc=0`, complete artifacts, and either a required-and-present sentinel or an explicitly disabled sentinel. D5 yields `INCOMPLETE` on exit `rc=0` with a required-but-missing sentinel or incomplete artifacts. With a disabled sentinel, exit `rc=0` plus complete artifacts is D4, matching the watcher's `DONE` semantics.
- **RUL-06**: D6 handles no exit record plus a present sentinel (complete artifacts → `DONE`, incomplete → `INCOMPLETE`). D7 yields `DEAD` for no exit record and a pid record whose process is dead/zombie/reused.
- **RUL-07**: D8 yields `TIMEOUT` when a known deadline plus `effective.deadline_grace` has passed with no earlier terminal match, including a live process. D9 yields `NO_SIGNAL` when pid and exit record are both absent and the start grace has passed. D10 yields `RUNNING` for a live pid, or a fresh heartbeat with a pid that is not dead, with no earlier terminal match. D11 yields `UNKNOWN` for everything else.
- **RUL-08**: When the sentinel configuration is unknown, an exit `rc=0` cannot decide D4/D5/D6; the result falls through to D11 (`UNKNOWN`). When `start_anchor` or `start_grace` is unknown, D9 is skipped. `start_anchor` is `stage_started_at` when known, otherwise the earliest attributable carrier mtime; the snapshot invocation time is never used.

## Completion

- **RUL-09**: The completion table is evaluated in this order: not-dispatched → `not-applicable`; exit `rc≠0` → `incomplete`; required sentinel present + artifacts complete + (no exit or `rc=0`) → `complete`; sentinel present + artifacts incomplete → `incomplete`; sentinel required but missing → `incomplete`; sentinel disabled + exit `rc=0` + artifacts complete → `complete`; sentinel disabled + exit `rc=0` + artifacts incomplete → `incomplete`; sentinel disabled with no exit → `unknown`; unknown sentinel configuration or unevaluable artifacts → `unknown`.
- **RUL-10**: `completion` is independent of `loop_state`. A pseudo-completion (sentinel present, artifacts missing) keeps the watcher/derived `loop_state` and sets `completion=incomplete`; it never rewrites `DONE` to `INCOMPLETE` in `loop_state`.

## Spine consistency and registry precedence

- **RUL-11**: `spine.consistent` is `"true"` only when the final `loop_state` and `last_verdict` are both in the watcher verdict set and equal; `"false"` only when both are in the set and differ; `"unknown"` when `last_verdict` is missing/unknown or the final state is `STALLED`/`REENTRY_REQUIRED`/`UNKNOWN`. `stalled`/`retrying` without `last_verdict` is not `"false"`.
- **RUL-12**: The action table is A1–A10 in the slice order: not-dispatched → `none`; `UNKNOWN`/remote-unreachable/lifecycle-spine-violation/unattributable-stale-with-no-own-evidence → `stop`; retry-limit guard; same-line stale-run retry guard; running/unwatched/deadline-overrun-live → `watch`; complete + commit evidence → `verify`; complete + missing commit + non-implement → `resume`; complete artifacts + no positive evidence + valid salvage + non-implement → `resume`; pseudo-complete/other terminal/complete artifacts without salvage → `retry`; everything else → `stop`.
- **RUL-13**: The retry-limit guard stops only when `attempt` and `retry_limit` are both known and `attempt ≥ retry_limit`, and only when the candidate action would be `resume`/`retry`/`stop`. It never limits `watch`, `none` or `verify`. If either value is unknown, the guard is skipped and a resulting `retry` records `retry-limit-unknown`; no default limit or attempt is invented.
- **RUL-14**: A same-line `stale-run` drives `retry` with `isolation_required=true` only when the current attempt is not provably running and `completion≠complete`. A running current attempt keeps `watch`; a complete current attempt keeps `verify` or `resume` (including the complete-but-commit-missing case). In every preserved case the stale carrier remains in `stale_signals[]` and in the `stale-signal` finding. `foreign`/`unattributed` carriers never change the action and never produce a `resume` recommendation; when they are the only carriers and no own evidence exists, the evidence gap resolves to `stop` with `stale-signal-unattributable`.
- **RUL-15**: A live `TIMEOUT` (pid alive, or heartbeat fresh with a pid that is not dead) reaches the `deadline-overrun-live` form and action `watch`; it never recommends `stop`, kill or termination. A `stop` recommendation for a live process belongs to the later recovery slice's explicit-decision path.
- **RUL-16**: Valid salvage input is at least one non-empty `--salvage-evidence <ref>` or a spine `spine_salvage: accepted` record with evidence and time. Salvage is an input to A8, never a post-decision override. Without it, complete artifacts with no positive completion evidence resolve to `retry`. Salvage never converts a pseudo-completion to `resume` and never authorizes an implement code commit.
- **RUL-17**: Pseudo-completion (sentinel present, artifacts missing) resolves to `retry` and `completion=incomplete`; it is never `resume` and never `complete`.
- **RUL-18**: Interruption forms I1–I8 are annotations. They add evidence, detail and attribution, and none of them may set, override, downgrade or upgrade `loop_state`. Only RUL-01/RUL-02 produce `loop_state`.

## Interruption forms

- **RUL-19**: I1 `unwatched` fires when the stage is running (pid alive, or heartbeat fresh with a pid that is not dead) and the watchbeat is missing, non-own, or older than its `window` plus `effective.deadline_grace`. A fresh marker after a normal window expiry does not fire. A marker whose freshness is `unknown` (because `effective.deadline_grace` is unavailable) does not fire this form. If the state directory is unresolved, the marker is `missing` and the applicable reason is `state-dir-unknown`.
- **RUL-20**: I2 `dead-no-exit-record` fires only when a pid record exists, the process is dead/zombie/reused, no exit record exists and no sentinel is present. A sentinel routes the case to completion.
- **RUL-21**: I3 `deadline-overrun-live` fires when a known deadline plus `effective.deadline_grace` has passed and the pid is alive or the heartbeat is fresh with a pid that is not dead, with no terminal match; it only annotates. I4 `heartbeat-stalled` fires when the pid is alive, the heartbeat is present and stale (not unknown), and no terminal match exists; `loop_state` stays `RUNNING`.
- **RUL-22**: I5 `artifacts-without-completion` fires when artifacts are complete and the sentinel is missing, regardless of the exit record and its rc. It drives the completion verdict only.
- **RUL-23**: I6 `stale-signal` fires when `stale_signals[]` is non-empty. One finding is emitted per distinct attribution present, in the order `own`, `stale-run`, `foreign`, `unattributed`; a finding never hides another root cause. Legacy mode requires a readable Registry proving exactly one active line; without that proof, an envelope-less carrier is `unattributed` with reason `legacy-stale`.
- **RUL-24**: I7 `lifecycle-spine-violation` fires when a Registry entry file exists but the spine is missing/unreadable/invalid, or when the spine says running while no live process, no fresh heartbeat and no terminal evidence exist. The Registry-present/spine-missing evidence gap recommends `stop`; with a watcher/probe verdict the verdict is preserved and the gap is still reported. This is the interruption form only; the deterministic `check-spine` validator is out of slice.
- **RUL-25**: I8 `remote-unreachable` fires from a probe's additive `remote.unreachable=true` object. It never yields `DEAD` or a stage-failure verdict; the derived state is usually `UNKNOWN` and the action is `stop` with the remote reason.

## Dispatch and inputs

- **RUL-26**: The not-dispatched predicate is true only when no dispatch evidence exists: no machine segment with `spine_stage_started_at`/`spine_stage_deadline_epoch`, no readable legacy stage/checkpoint line, no Registry `stage` bound to stage runtime paths or a dispatch `last_event`, no attributable carriers and no watcher/probe verdict. Registration and its auto-generated `run_id` alone are not dispatch evidence. Not-dispatched precedes the derived map and yields `UNKNOWN`, `not-dispatched`, `completion=not-applicable`, action `none`.
- **RUL-27**: Registry-present/spine-missing is evaluated before the not-dispatched predicate. With no watcher/probe verdict it yields `UNKNOWN` + `stop` + `lifecycle-spine-violation`; with a watcher/probe verdict it preserves the verbatim verdict and still reports the form and `stop`. If the Registry/carriers cannot supply a stage envelope, `stage="unknown"`. Registry missing/unreadable/invalid with readable spine/carriers continues evaluation and preserves the status; it does not by itself force `UNKNOWN`.
- **RUL-28**: Effective values resolve explicit CLI → probe → spine machine field → stage map (sentinel only) → watcher `--help` (watcher thresholds only). A value with no source is `"unknown"`; a decision that depends on it reports `UNKNOWN` or skips the rule. Retry limit and attempt have no parsed owner default in this slice; absent input stays unknown.
- **RUL-29**: The watchbeat marker is `<state-dir>/watchbeat-<line>-<stage>`, written atomically by the driver at each U3 window start (`event=watch-window`) and return (`event=watch-return`) with `line=`, `run=`, `stage=`, `window=`, `at=`, `event=`. The snapshot only reads it; it never participates in completion or liveness. Freshness uses the marker's own `at` (or mtime if invalid) plus `window` and `effective.deadline_grace`.
- **RUL-30**: The stage artifact map has exactly the eight known stages, no ninth and no "all files" fallback. Completeness is file existence and non-empty content; a directory requires at least one non-empty `.md`. Commit evidence uses `spine_stage_base_commit` only; a missing base is `unknown`. `commit_required=false` is `not-applicable`; clarify is `conditional` on a `requirements.md` change; implement's commit scope is non-`.specify/` paths. The map cites `stage-prompts.md` § Independent Verification for the U4 artifact list and `efficiency-model.md` §3 for the six plan-owned paths; CMP-04 pins the map against both sources.
