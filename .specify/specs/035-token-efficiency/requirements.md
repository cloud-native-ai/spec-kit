# Requirements Specification: 大模型 Token 使用效率纪律(程序优先 + 摘要优先 + 消耗观察反馈)

**Requirement Branch**: `035-token-efficiency`  
**Created**: 2026-08-02  
**Status**: Draft  
**Input**: User description: "需要将大模型的 Token 使用效率放入到框架的考虑中,随着框架日益复杂、流程增多，Token 消耗也随之增加，因此需要在框架整体流程中进行 Token 优化。几个核心优化点是:1)能用固定程序处理的文本或数据，应优先由程序处理，而非依赖大语言模型。相较于将文本串发送给大语言模型进行判断，使用传统正则表达式判断文本串内容更高效且更节省 Token。2)需要禁止将本地数据文件的原文整体发送给大语言模型，这不但会造成上下文污染，也会极大消耗 Token。应尽可能向大语言模型发送摘要或部分文件内容。3)需要将 Token 消耗监控等功能记录下来，供后续优化。现有的 Feedback 机制可以很好地实现这一点，在 Feedback 时也可以评估当前 Token 消耗是否有优化空间。"

## Overview

随着框架命令、技能与流程数量持续增长,每次运行注入大模型上下文的内容量(以及由此产生的 Token 消耗与上下文污染)成为框架级质量属性。本需求把 **Token 使用效率**确立为框架的持久性纪律,分三条纪律落地,落地层级为**框架自身**(约定文档 + 创作模板 + 数据引擎 + 存量单元审计),下游项目经框架安装自然继承:

- **程序优先(Program-First)**:凡可用固定规则表达的文本/数据判断(模式匹配、结构校验、计数、去重、排序、比对等),MUST 交由确定性程序(脚本/引擎/正则)执行,而非把原文送入大模型判断;大模型保留给真正的语义级判断。与既有 Tool 复用门(Constitution 原则 XII)同向。
- **摘要优先(Summary-First)**:禁止把机器管理数据文件(反馈存量、证据 findings、记忆存量、历史库、运行工件、清单/索引等)的**原文整体**注入大模型上下文;例行流程 MUST 消费摘要、字段投影或定向节选,整读仅限明确定义的例外情形并遵循升级阶梯。
- **消耗观察(Consumption Observation)**:以现有 Feedback 机制为载体,在各命令/技能 wrap-up 的标准 feedback-step 中加入 Token 效率自评(本次运行是否存在可避免的 Token 消耗),带稳定标记落库、可检索、可聚合,供 improve-* 等消费层后续优化;精确计数不可得时采用定性/代理口径,不编造数值。

三条纪律共用一个单一事实源约定文档,经项目指令 ambient 引用与创作模板门槛双通道生效;对存量单元执行一次全量审计并整改 top 违规项。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 程序优先:确定性判断交还程序 (Priority: P1)

作为框架维护者,我把"可用固定规则表达的文本/数据处理"从大模型上下文内判断改为确定性程序执行:纪律写入单一事实源约定文档并经项目指令 ambient 生效,新单元创作模板带程序优先检查项,存量流程中由 LLM 代做的固定规则判断按审计清单整改为脚本/引擎执行——LLM 只接收判定结果或摘要。

**Why this priority**: 这是三条纪律中单位收益最高的一条:固定规则判断被 LLM 代做时,既消耗输入 Token 又引入不确定性;交还程序后结果确定、成本趋零。可独立交付并用单个整改点验证。

**Independent Test**: 选取审计清单中一个"LLM 代做固定规则判断"的存量热点,按纪律整改后重跑该流程:判断结论与整改前一致,注入 LLM 的相关内容量(行/字节代理指标)显著下降。

**Acceptance Scenarios**:

1. **Given** 纪律约定文档就绪, **When** 检查其内容, **Then** 含程序优先规范(固定规则判断 MUST 由确定性程序执行)及判定边界说明(何种判断属语义级、归大模型)。
2. **Given** 审计清单中一个由 LLM 在上下文内完成固定规则判断的存量违规项, **When** 按纪律整改, **Then** 该判断改由脚本/引擎完成,LLM 只接收判定结果(或摘要),流程输出结论与整改前一致。
3. **Given** 新技能/命令的创作流程与模板, **When** 创作新单元, **Then** 模板含程序优先检查项,含确定性文本/数据处理步骤的新单元 MUST 声明其由程序执行。
4. **Given** 一个无法用固定规则表达的语义级判断, **When** 单元执行, **Then** 允许由大模型判断,纪律不强制改写——防止过度应用损害质量。

### User Story 2 - 摘要优先:数据文件原文不整体入上下文 (Priority: P1)

作为框架维护者,我禁止例行流程把机器管理数据文件的原文整体注入大模型上下文:各数据引擎提供摘要/过滤/查询输出模式,消费方例行调用只拿摘要或定向节选;确需更多内容时按升级阶梯(摘要 → 定向节选 → 有界整读)逐级升级,整读限于明确定义的例外情形。

**Why this priority**: 原文整读是最大的单次 Token 消耗源,且直接造成上下文污染(无关内容挤占注意力)。与 US1 并列 P1,共同构成纪律的"硬约束"面。

**Independent Test**: 选取一个此前整读数据文件的例行流程,改为消费引擎摘要输出后重跑:流程决策不受影响,注入内容量下降,且运行全程无机器管理数据文件的原文整体注入。

**Acceptance Scenarios**:

1. **Given** 例行流程需要机器管理数据文件中的信息, **When** 流程执行, **Then** 注入大模型上下文的是摘要、字段投影或定向节选,原文整读零出现。
2. **Given** 摘要不足以支撑当前决策, **When** 升级访问, **Then** 按升级阶梯逐级进行(摘要 → 定向节选 → 有界整读),整读仅限例外情形:该文件本身是编辑目标(读后改)、文件低于小文件阈值、或记录升级理由。
3. **Given** 各机器管理数据的引擎(反馈、记忆、证据、历史等), **When** 消费方例行调用, **Then** 引擎提供摘要/过滤/查询输出模式,例行流程无需原文转储;缺失该模式的引擎列入审计整改清单。
4. **Given** 存量审计完成, **When** 查看违规清单, **Then** 每条含单元、所违反纪律、注入量代理指标(行/字节)、严重度与整改状态;top 违规项完成整改并记录前后注入量对比。

### User Story 3 - 消耗观察:Feedback 承载 Token 效率自评 (Priority: P2)

作为优化流程的执行者,我在每次命令/技能 wrap-up 的标准 feedback-step 中获得 Token 效率自评:本次运行是否存在可避免的 Token 消耗(原文转储、LLM 代做确定性工作、重复读取同一内容);有发现则带稳定标记记入反馈存量,可按标记检索聚合,重复出现的观察经证据 feedback 泳道以 recurrence 信号呈现,供 improve-* 消费——形成"观察 → 记录 → 后续优化"闭环。

**Why this priority**: 依赖既有 Feedback 机制(用户明示的载体),是纪律的"观测面":前两条纪律管当下,本条为后续优化持续供给证据。不阻塞前两条独立交付。

**Independent Test**: 对任一命令跑一次完整流程至 wrap-up,反馈条目含 Token 效率自评;用标记检索反馈存量能返回全部 Token 观察条目;干净运行不产生额外观察条目。

**Acceptance Scenarios**:

1. **Given** 一次命令/技能运行到 wrap-up, **When** 执行标准 feedback-step, **Then** 自评包含 Token 效率评估维度(是否存在可避免消耗及具体观察),有发现时以 [[STR-001]] 标记记入反馈点。
2. **Given** 运行干净、无可避免消耗, **When** 记录反馈, **Then** 不额外产生 Token 观察条目(防反馈灌水),沿用既有"无显著优化点"表述。
3. **Given** 反馈存量中已有多条 Token 观察, **When** 按 [[STR-001]] 标记检索, **Then** 反馈引擎返回全部相关条目;同一观察重复出现时经证据 feedback 泳道以 recurrence 信号呈现。
4. **Given** 精确 Token 计数在当前 AI 工具下不可得, **When** 记录自评, **Then** 采用定性描述或注入量代理指标(行/字节),编造的具体 Token 数值零出现。

### Edge Cases

- **过度应用**:把真正语义级的判断强行"程序化"会损害质量——纪律边界限定在"可用固定规则表达"的判断;存疑时允许 LLM 判断,并可作为 Token 观察记录供后续论证。
- **小文件**:对几十行的小文件强制摘要反而增加流程开销——纪律文档定义小文件阈值,低于阈值允许整读。
- **读后改约束**:编辑工具要求先读目标文件——编辑目标文件的整读属明确例外,不算违规。
- **摘要失真**:摘要遗漏关键细节导致错误决策——升级阶梯必须存在且可用,升级到整读时记录理由,不得因噎废食地禁止一切整读。
- **计数不可得**:八种受支持 AI 工具不统一暴露每次运行的 Token 计数——自评采用定性/代理口径(注入内容行/字节),MUST NOT 编造数值(与证据纪律"不编造"同向)。
- **反馈灌水**:每次运行都机械追加雷同的 Token 观察会稀释反馈存量——干净运行不加条目;重复观察依赖既有去重/recurrence 机制而非重复记录。
- **镜像漂移**:纪律文档、模板、引擎改动跨 canonical 与 `.specify/` 镜像双写——任何单侧修改即为缺陷,沿用现行 sync 引擎与 `diff -rq` 校验。
- **生成副本违规**:审计在 AUTO-GENERATED 副本中发现违规时,整改 MUST 落在 canonical 源,再经 sync 引擎扇出,不得直接改副本。
- **代理指标误导**:行/字节仅是 Token 的代理,不同语言/内容压缩率不同——代理指标只用于相对比较(同一流程前后对比),不用于跨流程绝对排名。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 框架 MUST 以单一事实源文档确立 Token 效率纪律(程序优先、摘要优先、消耗观察三部分,含判定边界、例外情形、升级阶梯与小文件阈值),经项目指令 ambient 引用生效;各命令/技能 MUST 仅引用不复制该纪律定义。
- **FR-002**: 程序优先——凡可用固定规则表达的文本/数据判断(模式匹配、结构校验、计数、去重、排序、比对等),框架流程 MUST 交由确定性程序执行,MUST NOT 将原文送入大模型进行该类判断;大模型保留给无法用固定规则表达的语义级判断;本纪律与既有 Tool 复用门(优先复用既有脚本/引擎/Tool 记录)协同,不新建重复能力。
- **FR-003**: 摘要优先——框架流程 MUST NOT 把机器管理数据文件(反馈存量、记忆存量、证据产物、历史库、运行工件、清单/索引等)的原文整体注入大模型上下文;例行访问 MUST 消费摘要、字段投影或定向节选;整读仅限例外情形:(a) 该文件是当前编辑目标,(b) 文件低于纪律文档定义的小文件阈值,(c) 沿升级阶梯(摘要 → 定向节选 → 有界整读)升级且记录理由。
- **FR-004**: 各机器管理数据的引擎 MUST 提供摘要/过滤/查询级输出模式,使例行消费无需原文转储;审计发现缺失该模式的引擎 MUST 列入整改清单并在本需求边界内补齐(top 违规项)或记入后续迭代(其余)。
- **FR-005**: 新单元创作门槛——技能/命令/代理的创作与改进流程模板 MUST 含 Token 效率检查项(确定性步骤是否交程序、数据访问是否摘要化),新单元未通过检查时 MUST 在创作流程内补正后再落库。
- **FR-006**: 存量审计——框架 MUST 对全部现有命令、技能与共享工作流(以运行时动态计数为准)执行一次两纪律合规审计,产出违规清单(单元、违规纪律、注入量代理指标、严重度、整改状态);按"触发频率 × 注入量"排序的 top 违规项 MUST 在本需求边界内整改并记录前后对比,其余 MUST 作为后续迭代待办留档。
- **FR-007**: 消耗观察——标准 feedback-step 约定 MUST 增加 Token 效率自评维度:wrap-up 时评估本次运行是否存在可避免的 Token 消耗(原文转储、LLM 代做确定性工作、重复读取),有发现则以 [[STR-001]] 稳定标记记入反馈点;干净运行 MUST NOT 追加空洞的 Token 观察条目;既有 `(unit_id, run_id)` 去重守卫照常适用。
- **FR-008**: Token 观察条目 MUST 可按 [[STR-001]] 标记检索与聚合(经现有反馈引擎),并可被证据 feedback 泳道消费(重复观察呈现 recurrence 信号),供 improve-* 等消费层后续优化;自评 MUST 采用定性描述或注入量代理指标,在精确 Token 计数不可得时 MUST NOT 编造具体数值。
- **FR-009**: 本需求全部落地工件(纪律文档、模板、引擎、技能/命令改动)MUST 遵循现行镜像模型:只改 canonical 源、经既有 sync 引擎扇出,以 `diff -rq` 校验镜像一致;生成副本(AUTO-GENERATED)MUST NOT 直接修改。

### Key Entities

- **Token 效率纪律(Token-Efficiency Discipline)**: 单一事实源约定文档,含程序优先/摘要优先/消耗观察三部分与判定边界、例外情形、升级阶梯、小文件阈值;经 ambient 引用与创作模板双通道生效。
- **违规清单(Violations Inventory)**: 存量审计产物;每条含单元、违规纪律、注入量代理指标(行/字节)、严重度(触发频率 × 注入量)、整改状态;top 项本期整改,其余留档。
- **Token 效率自评(Token-Efficiency Self-Assessment)**: feedback-step 的新增评估维度;有发现时以稳定标记落为反馈点,干净运行不落;定性/代理口径。
- **摘要访问模式(Summary Access Mode)**: 数据引擎面向例行消费的摘要/过滤/查询输出能力;是"摘要优先"纪律在引擎侧的支撑面。
- **升级阶梯(Escalation Ladder)**: 数据访问的逐级放宽路径(摘要 → 定向节选 → 有界整读),整读须满足例外情形或记录理由。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 纪律文档作为单一事实源存在,项目指令含其 ambient 引用;技能/命令/代理创作与改进模板 100% 携带 Token 效率检查项;全部落地工件镜像 `diff -rq` 校验通过。
- **SC-002**: 存量审计覆盖 100% 的现有命令、技能与共享工作流(以审计时点动态计数为准),产出违规清单;清单中 top 违规项(严重度排序前列,数量以清单实际为准)100% 完成整改,且每项整改附前后注入量代理指标对比。
- **SC-003**: 对 top 整改项抽样重跑:流程输出结论与整改前一致(功能零回退),注入大模型上下文的相关内容量较整改前下降 ≥ 50%(行/字节代理口径)。
- **SC-004**: 整改后代表性流程抽查(≥ 3 个流程各一次完整运行):机器管理数据文件的原文整体注入零出现;确定性固定规则判断由 LLM 在上下文内代做零出现(例外情形均有记录的升级理由)。
- **SC-005**: feedback-step 更新后,带 [[STR-001]] 标记的反馈点可经反馈引擎一次检索全部返回;抽查全部存量 Token 观察条目,编造的具体 Token 数值零出现;干净运行追加的空洞 Token 观察条目零出现。

### Measurement Sources & Collection Methods

- **SC-001 Source**: 纪律文档与项目指令静态扫描(引用存在性)+ 模板逐个核查单 + `diff -rq` 镜像校验输出。
- **SC-002 Source**: 审计违规清单存档 + 整改项前后注入量代理指标记录(verification 记录)。
- **SC-003 Source**: top 整改项的前后重跑演练记录:输出结论 diff 核对 + 注入内容行/字节测量对比。
- **SC-004 Source**: 代表性流程运行转录抽查记录(原文整体注入与 LLM 代做判断的人工核对)。
- **SC-005 Source**: 反馈引擎按标记检索的输出 + Token 观察条目逐条抽查记录。

## Assumptions

- **落地层级**:本需求落在框架自身(约定 + 模板 + 引擎 + 审计),下游项目经框架安装继承 `.specify/` 侧成果;不为下游项目单独立项(概念性输入的落地层级判定)。
- **观察载体为既有 Feedback 机制**:用户明示以现有 Feedback 机制承载 Token 消耗观察——本需求不新建独立监控子系统,不引入运行时拦截或计量组件。
- **精确 Token 计数不可得为常态**:八种受支持 AI 工具不统一暴露每次运行的 Token 用量;自评采用定性描述与注入量代理指标(行/字节),仅用于同一流程前后相对比较。
- **"数据文件"边界**:指机器管理的存量数据(反馈、记忆、证据、历史、运行工件、清单/索引、日志等),不含用户正在编辑的源码/文档文件;"禁止整体发送"针对注入大模型上下文,不限制程序侧(脚本/引擎)读取原文——程序读原文恰是纪律鼓励的方向。
- **小文件阈值默认值**:建议默认"≤ 100 行且 ≤ 10 KB"允许整读,最终值由纪律文档定稿并允许按场景覆盖;不作为澄清项。
- **是否升格为 Constitution 原则**:默认先以共享纪律文档 + ambient 引用落地;是否修宪(新增原则)由后续 `/speckit.constitution` 流程另行决断,不阻塞本需求。
- **存量计数为时点值**:命令/技能/共享工作流数量以审计运行时动态探测为准,不硬编码计数断言(既有测试基线纪律)。
- **术语对齐**:"程序优先(Program-First)""摘要优先(Summary-First)""升级阶梯(Escalation Ladder)"为本需求新引入术语,待词汇表收尾提案;"feedback-step""镜像""泳道""recurrence"沿用项目既有语义。
