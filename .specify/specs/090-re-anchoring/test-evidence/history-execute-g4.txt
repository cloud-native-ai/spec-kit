## The live-vs-dated split

The owner page § Renumber-Face splits the class into two legs. Leg 1 is path-addressed and is already applied
by the engine when it builds candidates: no entry below lives in `.specify/history/`, `.specify/archive/`,
`.specify/specs/.archive/`, a machine store, a `test-evidence/` segment or a date-named file. Leg 2 is
content-addressed: a live binding is correctable **iff the number it carries is this document's own identifier,
stale after a directory renumber** — "the reference is claimed as current and must point at the renumbered id".
A number that names a *different registry object* is not a renumbered id: the directory prefix was never its
value, so there is nothing for it to "follow".

requirement iterations (spec directory prefixes) and the feature registry (`features.md`). Old specs
(006…053 era) state the *owning feature* number in `**Feature ID**` / `**Related Feature**`; modern specs
(088 / 090 / 093) agree with their directory only because the two numbers happen to coincide. Rewriting, e.g.,
`specs/030-summarize-project/requirements.md:18` `Feature ID: 013` → `030` would make the file claim Feature 030
"History Command", contradicting its own `Feature Name: Skills Command` line and `features.md:22`, whose
Related-Specifications cell names spec 030 for Feature 013. That is falsification of a current,
registry-backed statement — the same refusal G5 recorded for dated specs. The 9 live entries are the opposite
case: the number is the spec's own former id, and the corpus itself (`092` plan rows C1 / C4) fixes exactly this
shape by moving it to the new directory number.
