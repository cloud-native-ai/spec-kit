## Data Protection & User-Data Rights

- [ ] CHK001 Are data-protection requirements for feedback entry content (agent free-text `## Review` / `## Optimization Points` that may carry sensitive project details) defined — e.g., redaction, retention, or an explicit statement that none is required? [Completeness, Gap, Req §Key Entities]
- [ ] CHK002 Is the red-line term "反馈为用户数据且完全可选" (FR-016) operationalized in requirements — i.e., what "完全可选" entitles the user to do (silence prompts / stop recording / delete recorded entries)? [Clarity, Ambiguity, Req §FR-016]
- [ ] CHK003 Are requirements consistent between the red line "completely optional" and Story 4 scenario 4 ("静默后……反馈记录不停止" — recording continues after muting), i.e., is the opt-out vs mute distinction documented? [Consistency, Req §FR-016 / Story 4]
- [ ] CHK004 Are requirements specified for user-controlled deletion or export of already-recorded entries (beyond the one-time legacy migration), given entries are declared user data? [Coverage, Gap]

## Zero-Transmission & External Isolation

- [ ] CHK005 Is the zero-network red line precisely scoped — "零自动传输" vs "手动投递允许" vs "无网络代码路径" — so SC-006's "网络传输次数为 0" unambiguously defines what counts as a transmission? [Clarity, Req §SC-006 / FR-010]
- [ ] CHK006 Is the external-probe exclusion (FR-020 "100% 排除") defined over derived artifacts as well as entry files — e.g., package MANIFEST rows, aggregate counts — so exclusion is objectively verifiable? [Measurability, Req §FR-020]
- [ ] CHK007 Are requirements consistent between FR-010 (模式二复用 package → 手动投递 → mark-submitted 语义) and FR-020 (外部条目 100% 排除) on which disposal/packaging actions external entries may participate in? [Consistency, Req §FR-010 / FR-020]
- [ ] CHK008 Are failure-mode requirements defined for the exclusion mechanism — what MUST happen if an external entry is detected in a to-be-uploaded package (block, warn, or silently drop)? [Coverage, Gap, Req §FR-020]
- [ ] CHK009 Is the standalone runtime-mode gate (FR-017) stated with an observable, testable assertion (no feedback artifacts created outside `.specify/` workspaces) rather than only a preserved-behavior clause? [Measurability, Req §FR-017]

## Destructive-Operation Safety (Migration & Cleanup)

- [ ] CHK010 Is the "无法判定是否已合入 → 倾向保留并重登记,而非误删" default binding as a requirement, or does it exist only as an open Edge Case question? [Ambiguity, Req §FR-014 / Edge Cases]
- [ ] CHK011 Are recovery/rollback requirements for the destructive migration (delete/re-register) specified — backup-before-delete, reversibility window — or is 包内留档 + 处置记录 the explicitly declared sole recovery means? [Coverage, Gap, Req §FR-014]
- [ ] CHK012 Is the cleanup scope constraint ("MUST 限定为已进入打包批次的条目,不得误清未打包条目") stated as a normative requirement with a defined failure state, or only as an Edge Case bullet? [Completeness, Req §FR-010 / Edge Cases]
- [ ] CHK013 Are retention/durability requirements for the packaged archive (the sole record after active-library cleanup) specified — storage location, lifetime, integrity verification? [Completeness, Gap, Req §FR-010]
- [ ] CHK014 Is FR-011 (处置状态 MUST NOT 改写条目正文) complemented by integrity requirements for the disposition metadata itself (e.g., append-only, tamper-evidence)? [Completeness, Req §FR-011]

## Integrity & Reference Stability

- [ ] CHK015 Are integrity requirements specified for historical entries when a Probe Object is renamed/deleted/re-classified — is the "按记录时点还是当前定义" resolution decided in requirements, or left as an open Edge Case? [Ambiguity, Req §FR-002 / Edge Cases]
- [ ] CHK016 Are dangling-reference semantics for external probes (target custom unit deleted/renamed — "不误报损坏,允许悬空标注") elevated into a requirement, or left open? [Completeness, Gap, Edge Case]
- [ ] CHK017 Is the internal/external identifier namespace collision policy (强制隔离 or 允许同名不同类别) decided in requirements, given FR-002 mandates project-wide unique IDs? [Ambiguity, Req §FR-002 / FR-018]
