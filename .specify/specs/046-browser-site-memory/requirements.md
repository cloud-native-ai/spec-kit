## Related Feature *(mandatory)*

**Feature ID**: 048  
**Feature Name**: Browser Utils Skill

## Overview

browser-utils 技能的整体升级,由三部分构成:

1. **能力三分层**:Tier 1 内置浏览器(agent 运行时原生浏览器工具)、Tier 2 脚本自动化(Playwright 驱动 Chromium)、Tier 3 MCP 连接器(browser-use MCP + Chrome 扩展)。分层判定纯能力导向,不绑定任何具体 agent 产品。
2. **脚本自动化双方向**:页面级方向(模拟真实用户操作:填表单、点按钮、读 DOM)与请求级方向(在页面上下文中直接发起底层网络请求,如 fetch 调用,自动继承会话)。请求级方向比页面级更高效、更稳定,但依赖对站点请求的既有认知。
3. **站点记忆机制**:对每个操作过的站点(domain 为 key)持久化操作记录与蒸馏产物,用一个简单状态机驱动"探索期 → 优化期 → 验证期 → sealed"的生命周期,使同一站点的重复自动化从"逐步摸索"进化为"固化流程直接执行"。

核心价值:任一阶段都完整完成用户任务,记忆只是副产品与加速器——探索期靠页面摸索完成,优化期靠页面+网络混合操作提效,验证期与 sealed 状态靠请求级固化流程高效完成。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 探索期:完成任务的同时完整留痕 (Priority: P1)

agent 首次操作一个陌生站点(如内部管控台)。用户给出目标(如"查询我的基线列表"),agent 通过页面级操作逐步探索完成:查看页面结构、填写表单、点击按钮、逐层导航。整个过程中,所有 DOM 操作(点击/填充/读取的目标与结果)与底层真实发出的网络请求(方法、URL、关键头、请求体模板、响应形态)被完整记录到该站点的记忆目录。

**Why this priority**: 这是记忆机制的数据源头,也是用户任务被完成的第一个场景;没有完整留痕,后续优化与固化都无从谈起。

**Independent Test**: 对一个从未操作过的站点执行一次真实任务,验证:(a) 用户目标被完整完成;(b) `site/<host>/` 下产出覆盖全部关键步骤的操作记录与网络请求记录,仅凭记录可复述完整任务流程。

**Acceptance Scenarios**:

1. **Given** 目标站点无记忆目录,**When** 用户发起一个需要多步页面交互的任务,**Then** 任务被完成,且站点状态为"探索期",记忆目录内含按时间序的 DOM 操作记录与网络请求记录
2. **Given** 探索过程中某一步骤失败重试,**When** 任务最终完成,**Then** 失败与重试步骤同样被记录(作为后续优化的避坑依据),而不是只保留成功路径
3. **Given** 任务中途无法完成,**When** 运行结束,**Then** 已完成部分的记录仍然保留,站点停留在探索期,下次运行可在既有记录基础上继续

---

### User Story 2 - 能力分层与双方向路由 (Priority: P1)

agent 调用技能时,先按可用能力判定 Tier(内置浏览器 → 脚本自动化 → MCP 连接器),再在脚本自动化内按任务性质与站点记忆选择方向:对无记忆的站点或需要真实交互探索的任务走页面级方向;对已有请求级固化步骤的站点走请求级方向;优化期任务走页面+网络混合方向。

**Why this priority**: 分层与方向选择是每次技能调用的入口决策,决定后续一切执行路径;分层的纯能力导向判定已在上一轮迭代落地,本需求将其与双方向路由、站点记忆贯通为统一入口。

**Independent Test**: 构造三种能力环境(有内置浏览器工具/仅脚本执行能力/有 browser-use MCP)与两种站点记忆状态(无记忆/已 sealed),验证入口路由各自落到正确的 Tier 与方向。

**Acceptance Scenarios**:

1. **Given** 无内置浏览器工具、无 MCP、有脚本执行能力,**When** 技能被调用,**Then** 路由到 Tier 2 脚本自动化
2. **Given** 目标站点已 sealed,**When** 用户发起该站点已固化的任务,**Then** 直接执行请求级固化流程,不做任何页面探测
3. **Given** 目标站点无记忆,**When** 用户发起任务,**Then** 走页面级方向并进入探索期留痕(与 User Story 1 衔接)

---

### User Story 3 - 优化期:从操作记录蒸馏请求级步骤 (Priority: P2)

第二次操作同一站点时,agent 分析探索期留痕:识别出完成任务所必需的真实网络请求序列,将其固化为请求级步骤(方法/URL/参数模板/动态令牌解析方式/预期响应特征),标注哪些步骤无法用请求替代(如复杂前端渲染、验证码)而保留页面级操作。随后以"请求级为主、页面级为辅"的混合方式高效完成用户任务,并把蒸馏产物写回站点记忆。

**Why this priority**: 这是效率跃升的关键一跳——把"摸索出的操作流程"转化为"可复用的请求配方";但它依赖探索期产物,故排在留痕之后。

**Independent Test**: 以一份探索期记录为输入,验证产出的请求级步骤集能够覆盖原任务的关键数据获取/提交动作,且混合执行能完整完成同一任务。

**Acceptance Scenarios**:

1. **Given** 站点处于探索期且记录完整,**When** 用户再次发起同类任务,**Then** 系统先蒸馏出请求级步骤集,再以混合方式完成任务,任务结果被用户目标验证
2. **Given** 探索期记录中存在无法用请求替代的步骤,**When** 蒸馏完成,**Then** 这些步骤被显式标注保留为页面级操作,步骤集为混合形态而非强行全请求化
3. **Given** 蒸馏产物已写入,**When** 查看站点记忆,**Then** 请求级步骤集包含每个请求的方法/URL/参数模板/动态字段解析方式与预期响应特征

---

### User Story 4 - 验证期与 sealed:状态机驱动的固化与回退 (Priority: P3)

第三次操作同一站点时进入验证期:端到端执行优化期产出的请求级步骤,验证其能独立(不依赖页面摸索)完成用户任务。验证通过 → 站点标记为 sealed,后续同类任务直接执行固化流程;验证失败 → 记录失败原因,站点回退到优化期,基于失败证据修订步骤集后再次进入验证。状态机的全部状态变更以确定性规则判定并持久化到站点记忆。

**Why this priority**: 它决定固化流程的可信度,是"越用越快"飞轮的闭环;但即便没有它,前三个故事已能交付完整任务能力。

**Independent Test**: 对同一站点连续执行:构造验证通过与验证失败(如请求模板过期)两种情形,分别验证 sealed 标记与回退到优化期的行为,以及 sealed 后再次执行零页面探测。

**Acceptance Scenarios**:

1. **Given** 站点处于验证期,**When** 请求级步骤端到端执行成功且结果符合预期响应特征,**Then** 站点状态置为 sealed 并记录验证证据
2. **Given** 站点处于验证期,**When** 执行失败,**Then** 失败原因被记录,状态回退到优化期,既有探索期记录与优化产物不丢失
3. **Given** 站点已 sealed,**When** 固化流程执行失败(站点接口漂移),**Then** 状态回退到优化期并提示需要重新蒸馏

---

### Edge Cases

- 同一 domain 下多个不同页面/路由的任务:记忆以 domain(host:port)为 key 建目录,目录内按页面/路由区分任务流,互不影响。
- 请求含动态令牌/签名(CSRF token、requestId 等):记录与蒸馏 MUST 标注动态字段的解析来源(页面变量/前置请求/cookie),验证期对动态字段解析失败按验证失败处理。
- 用户在站点尚未 sealed 时要求"直接用之前的方式跑":允许按当前状态对应的最佳方式执行,不强制走完状态机次数(状态由证据驱动,而非简单的计数)。
- 记忆目录被手工删除或损坏:视为无记忆站点,重新进入探索期;损坏文件不阻塞任务完成。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 技能 MUST 维持能力三分层(Tier 1 内置浏览器 / Tier 2 脚本自动化 / Tier 3 MCP 连接器),分层判定 MUST 纯能力导向(依据可用工具与 MCP 服务探测),MUST NOT 在分层判定中引用任何具体 agent 产品名;针对具体 agent 的定制信息由调用方在调用技能时自备。
- **FR-002**: 脚本自动化(Tier 2)MUST 区分两个方向并提供选择指引:页面级方向(模拟真实用户操作)与请求级方向(页面上下文中直接发起网络请求);对已有请求级固化步骤的站点 MUST 优先请求级方向。
- **FR-003**: 技能 MUST 以 domain(host:port)为 key 为每个操作过的站点建立记忆目录,位于技能 `site/` 目录下(如 `site/g.aliyun-inc.com/`);首次操作某站点时自动创建。技能安装后该目录落在调用方项目内,记忆数据归调用方所有并由调用方归档;spec-kit 框架仓 MUST 用 gitignore 排除 `skills/browser-utils/site/` 及其镜像,MUST 将其排除在 wheel 打包之外,镜像同步 MUST 跳过 `site/`(只同步技能本体)。
- **FR-004**: 探索期执行 MUST 完整记录:(a) 全部 DOM 操作(动作类型、目标、输入值、结果);(b) 底层真实网络请求(方法、URL、关键请求头、请求体模板、响应形态);记录 MUST 足以仅凭记录复述完整任务流程,且记录 MUST 包含失败与重试步骤。敏感字段(Cookie/Authorization/各类令牌)MUST 脱敏落盘——只记字段名与占位符,动态令牌只记其解析来源(页面变量/cookie 名/前置请求),MUST NOT 持久化凭证原值。
- **FR-005**: 技能 MUST 用一个简单状态机维护每个站点的状态:`exploration`(探索期)→ `optimization`(优化期)→ `validation`(验证期)→ `sealed`(固化);验证失败或 sealed 执行失败 MUST 回退到 `optimization`;状态 MUST 持久化在站点记忆目录内。
- **FR-006**: 无论站点处于哪个状态,执行 MUST 完整完成用户的任务目标——状态只改变完成方式(探索式 / 混合式 / 固化式),MUST NOT 出现"只记录不完成任务"或"只验证不完成任务"的运行。
- **FR-007**: 优化期 MUST 产出请求级步骤集:每个步骤含方法、URL、参数模板、动态字段(令牌/签名/requestId 等)解析方式、预期响应特征;无法用请求替代的步骤 MUST 显式标注并保留为页面级操作。
- **FR-008**: 验证期 MUST 端到端执行请求级步骤集并对照预期响应特征判定通过/失败;通过 MUST 将状态置为 sealed 并记录验证证据;失败 MUST 记录原因并回退状态。
- **FR-009**: 状态变更的判定(记录完整性、验证通过与否、漂移失败识别)MUST 遵循程序优先,由确定性程序完成;状态机文件与记录文件 MUST 为结构化、agent 中立的格式(三个 Tier 均可读写)。
- **FR-010**: sealed 站点再次执行已固化任务时 MUST 直接执行请求级固化流程,MUST NOT 做任何页面探测;执行失败 MUST 回退状态并提示重新蒸馏。

### Key Entities *(include if requirement involves data)*

- **站点记忆 (Site Memory)**: 以 domain 为 key 的目录(`site/<host>/`),内含状态机文件、探索期操作记录、优化期请求级步骤集、验证证据;随运行累积更新。
- **操作记录 (Operation Record)**: 一条 DOM 操作或网络请求的结构化记录——动作/方法、目标/URL、输入/请求体模板、结果/响应特征、成败与时间序。
- **请求级步骤集 (Request Recipe)**: 优化期蒸馏产物——有序的请求步骤列表,每步含参数模板与动态字段解析方式;混合形态时夹带显式标注的页面级步骤。
- **站点状态 (Site State)**: `exploration` / `optimization` / `validation` / `sealed` 四态之一,附状态变更历史(何时、因何证据变更)。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 对陌生站点首次执行多步交互任务,任务完成的同时,100% 的关键页面操作与底层网络请求在站点记忆中有对应记录(仅凭记录可复述任务流程)。
- **SC-002**: 同一站点第二次执行同类任务,完成所需的页面探测类步骤数较探索期减少至少 50%(混合执行提效可量化)。
- **SC-003**: 验证期对请求级步骤集的端到端验证给出明确的通过/失败判定与证据;sealed 站点重复执行固化任务的成功率在站点接口未漂移前提下达到 100%,且单次执行不包含任何页面探测步骤。
- **SC-004**: 全部状态变更 100% 由确定性程序判定并持久化,无"凭印象"改状态;任一状态回退后,既有记录与产物零丢失。
- **SC-005**: 三个 Tier 环境下,站点记忆的读写与状态机行为一致(同一结构化格式,跨 Tier 可继续生命周期)。

### Measurement Sources & Collection Methods

- **SC-001 Source**: 运行结束后对比任务步骤清单与 `site/<host>/` 记录条目;抽查式人工核对"仅凭记录复述流程"。
- **SC-002 Source**: 探索期与优化期两次运行的步骤计数(记录文件自带),差值比例。
- **SC-003 Source**: 验证期运行产生的验证证据条目;sealed 运行日志中页面探测步骤计数(应为 0)。
- **SC-004 Source**: 站点状态机文件的变更历史条目(每次变更必附证据引用);回退场景的重放测试。
- **SC-005 Source**: 三种能力环境下对同一站点记忆的读写一致性检查(格式校验程序)。

## Out of Scope

- 不修改 browser-extension、clone-website-ui 等其它技能(它们可消费本机制,但不在本需求内改造)。
- 不做跨站点的配方泛化/迁移学习(记忆严格按 domain 隔离)。
- 不引入云端同步或共享存储;站点记忆是纯本地文件。
- 不自动发起对写操作类请求(变更类调用仍遵循技能既有的确认要求)。

## Assumptions

- 站点记忆目录位于技能 `site/` 子目录;技能安装到调用方项目后(`.specify/skills/browser-utils/site/`),记忆由调用方项目归档(是否提交由调用方自决);spec-kit 框架源仓不保存(gitignore)也不分发(打包排除、镜像跳过)该数据。
- "第一次/第二次/第三次"是状态语义而非机械计数:状态变更由记录完整性与验证证据驱动,用户可要求停留在某一方式执行。
- 用户输入中"在探索期是通过不带摸索完成用户的要求"按"带着摸索(探索式)完成"理解。
- 上一轮迭代已落地的能力三分层(去 agent 名、Tier 顺序)视为本需求的既有基线,本需求在其上补双方向路由与站点记忆。
