# Requirements Specification: 框架资料卫生治理——残留冗余清理与关键资料正确性检查(Sanitize Command)

**Requirement Branch**: `045-sanitize-command`  
**Created**: 2026-08-20  
**Status**: Draft  
**Input**: User description: "创建一个新的命令speckit.sanitize,这个命令主要针对的是上面这种问题,针对框架中残留和冗余的资料进行清理. 同时也需要针对关键资料进行正确性检查,比如.specify目录,docs目录等,不用去关心用户的代码,脚本和测试用例."

## Related Feature *(mandatory)*

**Feature ID**: 047  
**Feature Name**: Framework Material Hygiene(框架资料卫生)

## Overview

框架自有资料——Parked Ideas(memory/todo/)、草稿(memory/draft/)、各类索引与存储、技能/代理镜像目录、兼容性符号链接、docs 树——随迭代不断累积,却缺少系统性的卫生机制。时间性声明材料在底层工作合入后悄然过期而无人复核:真实案例中,一份 2026-08-12 结转的 parked todo 声称五项能力"未落地",而提交记录显示其已于 2026-07-30 全部合入,该矛盾直到 2026-08-20 人工分析才被发现。同类问题不止于此:死引用(资料引用已不存在的文件/命令/技能)、索引与存储漂移、断链的兼容性符号链接、重命名后遗留的孤儿镜像目录,都在静默侵蚀资料可信度。

`/speckit.sanitize` 提供周期性的框架资料卫生治理:默认检查模式将分类发现报告(过期残留、冗余、死引用、索引不一致、链接失效、镜像漂移)持久化到指定运行工件区、发现携带 pending 状态,被检材料本体零修改;固定规则判定程序优先、语义判定只消费程序采集的证据摘要;呈现报告后提示用户是否进入清理,清理动作按确认门控两级判据执行——删除与移动/归档属破坏性桶,以清理计划的前置用户确认为前提,可逆修复自动执行,处置完成后更新发现状态并出具执行报告。治理对象限于框架自有资料,不评估、不修改用户的代码、脚本与测试用例。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 过期残留检测:报告持久化先行,被检材料零修改 (Priority: P1)

维护者运行 `/speckit.sanitize`(默认检查模式)。系统扫描框架自有资料中的时间性声明材料(parked ideas、drafts 等),采集确定性证据(相关路径的提交历史摘要、文件存在性),对声明与仓库现状矛盾的材料给出"过期残留"结论——例如一份 parked todo 声称"五项未落地",而提交证据显示早已全部合入;对内容已完整并入载体后残留的源材料给出"冗余"结论。发现报告持久化到指定运行工件区、每条发现携带 pending 状态,被检材料本体零修改;系统呈现报告摘要并提示用户是否进入清理,维护者据此决定后续动作。

**Why this priority**: 过期残留是本需求的直接动因,也是唯一需要"语义声明 vs 仓库证据"比对的能力;单独实现即可交付核心价值,是天然的 MVP。

**Independent Test**: 在复刻真实案例的夹具(parked todo 声称未落地 + 已合入的提交证据)上运行检查模式,断言该材料被检出为过期残留、发现携带提交级证据引用并以 pending 状态持久化落盘,且被检材料本体零变更。

**Acceptance Scenarios**:

1. **Given** 一份时间性声明材料声称某些工作"未落地/待办", **When** 提交记录或文件存在性证据表明该工作已合入, **Then** 该材料被标记为"过期残留",发现附提交哈希/路径等证据引用。
2. **Given** 检查模式运行, **When** 扫描与判定完成, **Then** 发现报告以 pending 状态持久化到指定运行工件区,呈现摘要并提示是否进入清理,全程不修改任何被检材料。
3. **Given** 一份材料的声明无法与仓库证据对照(证据不足), **When** 判定进行, **Then** 标记"证据不足"而非武断判过期,避免误报。

---

### User Story 2 - 关键资料正确性检查:死引用、索引一致性与镜像漂移 (Priority: P2)

系统对框架关键资料执行确定性正确性检查:资料内引用的文件/命令/技能/脚本是否可解析(死引用);索引与存储是否双向一致(feature 索引 ↔ 详情文件、feedback/evidence 索引 ↔ 条目文件);兼容性符号链接是否有效;源目录与已安装镜像目录是否漂移(含重命名后遗留的孤儿镜像)。全部判定由确定性程序完成,结论并入同一份发现报告。

**Why this priority**: 正确性问题静默侵蚀资料可信度,且四类判定全部可用固定规则表达(程序优先),实现成本低、收益稳定;复用 US1 确立的报告形态,故为 P2。

**Independent Test**: 构造含死引用、索引缺项、断链符号链接、孤儿镜像目录的夹具,运行检查模式,断言四类问题全部被检出且分类正确。

**Acceptance Scenarios**:

1. **Given** 一份资料引用了不存在的文件路径/命令名/技能目录, **When** 检查运行, **Then** 报告"死引用"发现,附引用出处与解析失败的目标。
2. **Given** 索引与存储不一致(索引有条目而无对应文件,或反之), **When** 检查运行, **Then** 报告"索引不一致"发现,两个方向均可检出。
3. **Given** 兼容性符号链接断链,或镜像目录存在源中已不存在的孤儿目录, **When** 检查运行, **Then** 报告相应发现,并指向既有修复命令作为处置建议。

---

### User Story 3 - 确认后清理:前置确认 + 状态更新 + 执行报告 (Priority: P3)

维护者审阅发现报告后确认清理计划。系统按计划执行处置:已合入材料的删除、被取代材料的归档(两者均属破坏性动作,以计划确认为执行前提)、可逆的引用修复(自动执行)。处置完成后对应发现的状态由 pending 更新为已处置,并呈现执行报告,逐项列明执行内容、变更工件与修改途径;任何删除与移动绝不发生在用户确认之前。

**Why this priority**: 检测与报告已交付主要价值;清理是价值收割步骤,受确认门控治理约束(删除/移动归档属破坏性桶),依赖前两个故事的产出,故为 P3。

**Independent Test**: 在夹具上走"检查 → 确认清理计划 → 执行"全流程,断言确认前零删除零移动、确认后处置正确落盘、发现状态由 pending 更新为已处置、执行报告三要素齐全。

**Acceptance Scenarios**:

1. **Given** 发现报告含删除/归档类处置建议, **When** 用户尚未确认清理计划, **Then** 不发生任何删除或移动。
2. **Given** 用户已确认清理计划, **When** 系统执行, **Then** 破坏性处置按计划执行,可逆修复自动完成,对应发现状态由 pending 更新为已处置,执行报告呈现执行内容/变更工件/修改途径三要素。
3. **Given** 执行中途某项处置失败, **When** 系统收尾, **Then** 如实报告失败点、原因与已产生的中间产物,不静默跳过。

---

### Edge Cases

- 声明与证据部分吻合(五项中三项已合入):发现按证据粒度呈现,不整体武断判定整份材料过期。
- 非 git 环境或无可比对提交记录:语义过期检测降级标记 unavailable,只输出确定性检查结论,不误报。
- 同一材料同时命中多类发现(既过期又含死引用):多分类并存,处置建议以可逆性最高影响者呈现。
- 客户项目资料结构不完整(如无 history/、无 evidence/):缺失的资料根视为空集,不作为发现、不报错。
- 资料引用了用户代码路径(如示例引用 src/ 下文件):引用检查只判定目标存在与否,不评估用户代码本身。
- 报告工件已存在且含未处置发现时再次运行检查:新发现并入报告,未处置发现保留其状态不丢失、不重复计为新发现。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: `/speckit.sanitize` MUST 默认以检查模式运行:完成全部扫描与判定后将发现报告持久化到指定运行工件区(发现初始携带 pending 状态),呈现摘要并提示用户是否进入清理;检查模式 MUST NOT 修改任何被检材料本体。
- **FR-002**: 扫描范围 MUST 覆盖框架自有资料根(运行时动态探测):memory 层(todo/draft/各索引与存储)、specs(含归档)、history、技能与代理镜像目录、兼容性符号链接、docs 树;缺失的根 MUST 视为空集而非错误。
- **FR-003**: 对时间性声明材料,系统 MUST 采集确定性证据(相关提交历史摘要、文件存在性),对声明与仓库现状矛盾者给出过期结论,每条过期发现 MUST 附证据引用;证据不足时 MUST 标记"证据不足",MUST NOT 判定过期。
- **FR-004**: 系统 MUST 检出冗余/被取代材料:内容已完整并入载体后的残留源材料、重复描述同一机制的多份资料。
- **FR-005**: 正确性检查 MUST 覆盖:死引用(资料内引用的文件/命令/技能/脚本不可解析)、索引↔存储双向一致性、兼容性符号链接有效性、源目录与镜像目录漂移(含孤儿镜像)。
- **FR-006**: 系统 MUST NOT 评估、修改或报告用户源代码、产品脚本与测试用例;发现的目标 MUST 限于框架自有资料(引用存在性检查只判定目标存在与否,不构成对用户代码的评估)。
- **FR-007**: 判定 MUST 遵循程序优先:存在性、一致性、链接有效性、引用解析等固定规则判定 MUST 由确定性程序完成;语义性过期/冗余判定仅消费程序采集的证据摘要;发现报告 MUST 以摘要形态产出(摘要优先)。
- **FR-008**: 清理执行 MUST 遵循确认门控两级判据:删除与移动/归档(破坏性桶)MUST 以清理计划的前置用户确认为执行前提;可逆修复(如引用修正)MUST 自动执行。
- **FR-009**: 清理完成后系统 MUST 呈现执行报告(执行内容/变更工件/修改途径);执行中途失败 MUST 如实报告失败点、原因与已产生的中间产物。
- **FR-010**: 属既有命令职责域的发现(docs 内容编纂收敛、符号链接/说明文件再生成、SDD 过程质量评审)MUST 以指向对应命令的建议呈现,MUST NOT 在本命令内重复实现其处置。
- **FR-011**: 每条发现 MUST 携带分类、严重度、证据引用与处置建议,处置建议 MUST 按确认门控两级判据标注可逆性。
- **FR-012**: 发现 MUST 携带生命周期状态(初始 pending);处置完成后系统 MUST 更新对应状态为已处置,使后续运行可区分存量未处置与新增发现;重复运行时既有未处置发现 MUST 保留状态并入,不重复计为新发现。

### Key Entities *(include if requirement involves data)*

- **Sanitize Finding(治理发现)**: 一条待处理项;属性:分类(过期残留/冗余/死引用/索引不一致/链接失效/镜像漂移)、目标路径、证据引用、严重度、处置建议(含可逆性标注)、生命周期状态(pending/已处置)。
- **Sanitize Report(发现报告)**: 一次检查运行的全部发现集合与范围摘要;持久化于指定运行工件区,是检查模式的唯一落盘产出(被检材料本体零修改);重复运行时增量并入。
- **Cleanup Plan(清理计划)**: 从发现报告导出的处置清单,作为破坏性动作前置确认的确认对象。
- **Material Root(资料根)**: 框架自有资料的一类根目录或清单项,运行时动态探测其存在性,缺失视为空集。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在复刻真实案例(材料声称"未落地"而提交证据显示已合入)的夹具上,检查模式检出该过期残留并附提交级证据引用。
- **SC-002**: 检查模式只写指定运行工件区;被检材料本体在运行前后无内容或元数据变更(可机械验证)。
- **SC-003**: 破坏性处置(删除/归档)100% 发生在用户确认清理计划之后;确认前删除/移动数为 0。
- **SC-004**: 固定规则类判定(死引用/索引一致性/链接有效性/镜像漂移)的结论全部来自确定性程序;语义判定仅覆盖过期/冗余两类且只消费证据摘要。
- **SC-005**: 对"证据不足"材料输出显式标记而非过期结论;抽检发现条目的证据引用全部可复核。

### Measurement Sources & Collection Methods

- **SC-001 Source**: 夹具测试(以真实案例构造材料与提交),断言发现分类与证据引用字段;本仓真实案例可作验收对照。
- **SC-002 Source**: 夹具测试:快照比对被检材料本体内容与元数据;断言检查模式的写入仅落在指定运行工件区。
- **SC-003 Source**: 契约测试与门控扫描(scan-confirmation-gates.py)对命令模板的机械检查;夹具全流程断言确认前后状态。
- **SC-004 Source**: 引擎契约测试(固定规则判定不依赖模型的结构断言)与运行产物字段。
- **SC-005 Source**: 夹具测试(证据不足场景断言显式标记)+ 发现条目证据引用的人工抽检记录。

## Out of Scope

- 用户源代码、产品脚本、测试用例的评估与修改(任何形式)。
- docs/ 内容编纂与结构收敛(/speckit.docs 职责;本命令只做引用存在性等正确性检查并建议移交)。
- 符号链接与说明文件的再生成、修复执行(/speckit.instructions 职责;本命令只检出并建议)。
- SDD 过程质量评审(/speckit.review)与实现前跨工件漂移分析(/speckit.analyze)。
- memory/history 内容的蒸馏与编纂(memory-record / /speckit.history 职责;本命令只判卫生状态,不改写内容)。
- 远程操作(推送、外部系统写入)与任何未经确认的自动删除。

## Assumptions

- 框架自有资料根可依既有 framework-map 清单枚举,运行时动态探测;本命令不维护第二份硬编码根清单。
- 语义过期/冗余判定由执行命令的 agent CLI 完成,证据采集由确定性脚本完成;非 git 环境语义检测降级标记 unavailable。
- 命令按既有 /speckit.* 命令解剖(命令模板 + 引擎脚本 + 文档接入)交付,镜像与命令副本经既有再生成机制同步。
- 发现报告持久化区沿用既有运行工件区模式(如 .specify/ 下按域归档),具体路径为规划层决策;报告工件不属于"被检材料",不参与卫生判定的自检(避免递归)。
- 触发模型为仅手动按需:独立命令、零环境挂点新增(宪法 IX 范围纪律);不做收尾挂点提醒或调度集成。
- "已合入即删除"为既有结转纪律;本命令检出的过期残留多数是该纪律的违例存量,删除处置与该纪律一致。
