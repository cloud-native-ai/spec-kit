## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一次代码评审自动把发现送进客户项目自己的通道 (Priority: P1)

客户项目的维护者跑完 `/speckit.review` 之后，本项目的反馈存储里出现**一条**指向那次代码评审记录的条目：它写着记录路径、这次评审的适用性取值、以及按严重度抄自汇总命令的条目计数。评审意见的正文仍然只存在 `code-review.md` 里，没有被搬运成第二条、第三条副本；这条条目也永远不出机器。

**Why this priority**: 这是用户诉求的字面内容。今天的代码评审发现只停在一个没人读的文件里，而 Dogfooding Loop B 已经声明"为你的产品建同样的循环"，却没有把评审发现接进去——缺口不在能力，在入口。

**Independent Test**: 在一个模拟客户项目夹具（根目录没有框架源目录）里武装客户通道，制造一个含代码 delta 的特性并运行一次 review，然后按 run 标识过滤查看外部条目，检查是否恰有一条本 run 的条目，且其内容与既有汇总命令的计数逐项相等。

**Acceptance Scenarios**:

1. **Given** 一个已武装客户通道的客户项目，**When** 代码段以适用性 [[STR-005]] 完成并写出记录，**Then** 存储中恰新增一条 `kind: external`（[[STR-002]]）条目，其单元为该项目声明的 `custom:` 单元，内容是记录路径 + 适用性取值 + 按严重度抄自汇总命令的计数。
2. **Given** 同一（单元、运行）对已被采集过一次，**When** 同一 run 被重复采集，**Then** 存储不新增第二条条目，且不产生错误或阻塞。
3. **Given** 一次评审里有若干 `blocking` 条目，**When** 采集执行，**Then** 采集照常完成且不改变合入门禁判决——采集是观察，不是判定。

### User Story 2 - 通道没准备好时如实说，绝不伪造 (Priority: P1)

同一次评审跑在一个**没有武装**客户通道的客户项目里时，存储里不会多出任何条目，运行也不中断：它会说清是哪一种"没采集"（没有声明过客户单元 / 声明了多个而本次没指定），并给出一次性的准备动作。读者因此永远不会把"没有条目"误读成"这次评审没发现问题"。

**Why this priority**: 这是本特性最危险的失败方式。引擎在没有对应探针对象时会拒绝记录（fail closed），若把该拒绝吞掉，采集就退化成静默死信——而"死信反馈"正是 Dogfooding 指南点名的反模式。宁可少采，不可假采。

**Independent Test**: 在一个未注入任何外部探针的客户项目夹具里跑一次 review，检查存储条目数不变、运行未被阻断、输出里出现具名披露 [[STR-004]]；再注入两个外部探针、不带显式单元参数跑一次，检查披露变为 [[STR-003]] 而不是随便挑一个。

**Acceptance Scenarios**:

1. **Given** 客户项目没有任何外部探针对象，**When** 一次 review 走完代码段，**Then** 不写任何客户条目，运行照常结束，输出以 [[STR-004]] 具名披露原因并给出一条一次性的准备指引。
2. **Given** 客户项目有两个以上外部探针对象且本次没有显式指定单元，**When** 采集判定，**Then** 不写任何客户条目，输出以 [[STR-003]] 具名披露，不猜测、不轮流、不选"最近使用"。
3. **Given** 客户项目带着显式单元参数运行，**When** 采集判定，**Then** 该显式指定优先于自动解析，且披露里写明采用的是显式指定。

### User Story 3 - 客户发现就地消化，框架发现照旧上送 (Priority: P1)

客户项目的维护者运行 `/speckit.feedback`，一次调用同时处理两侧：关于本项目自己单元的条目被就地消化（各自得到唯一的后续载体），关于框架的条目照旧进入打包路径，两侧各自呈报。全程没有任何数据自行离开这台机器。

**Why this priority**: 采集只解决"记下来"，不解决"被处理"。若消化环节不认客户侧条目，采集越成功，死信越多。

**Independent Test**: 在一个客户项目夹具里各造一条外部与一条框架单元条目，运行一次消化流程，检查外部条目被就地处置且被指派了载体、框架单元条目进入打包批次，且打包产物里不含外部条目。

**Acceptance Scenarios**:

1. **Given** 客户项目的存储里同时有外部与框架单元条目，**When** 运行一次消化流程，**Then** 两侧都被处理且分别呈报，任一侧非空都不会被静默丢弃。
2. **Given** 一批待打包条目里混有外部条目，**When** 生成打包产物，**Then** 外部条目被排除并在报告中给出排除计数，客户数据不外流。
3. **Given** 一条外部条目已被消化，**When** 查看它的处置结果，**Then** 它带着恰好一个后续载体（闭集见 FR-011），没有被指派两个载体。

### User Story 4 - 客户项目的改进循环复用同一套步骤 (Priority: P1)

客户项目的维护者对自己项目里的一件耐久工件（自定义技能、代理、命令或工具记录）运行一次改进命令：走的还是 why → what → how 那套步骤，主体判据、证伪要求、尝试上限、干预台账都没有第二套；唯一的不一样是它如实说明"这个主体的运行判定历史没有可用记录"，并改用客户通道里已经记下的观察作为起点。

**Why this priority**: 用户诉求的另一半是"改进"，而"持续的自我提升"若无闭环证据就只是一句口号。复用而不是新建，是这份规格最强的范围约束。

**Independent Test**: 在一个客户项目夹具里对一个满足执行主体判据的自定义工件运行改进循环，检查三段的产物、台账位置与"未评估"披露；再对一个没有唯一可编辑定义的模糊目标运行一次，检查它停在主体解析、未改动任何文件。

**Acceptance Scenarios**:

1. **Given** 一个满足执行主体五条判据的客户自定义工件，**When** 运行该循环，**Then** 三段（why / what / how）都执行，干预台账写在基线证据运行旁边，且报告给出"结果待定"而不是"已改进"。
2. **Given** 该主体在运行判定引擎里没有历史记录（引擎对 `custom:` 单元 fail closed），**When** 生成 why 摘要，**Then** 报告明写"运行判定历史未评估"并给出原因，改由客户通道条目与既有证据车道作为观察源，绝不伪造历史或缺省为"无问题"。
3. **Given** 一个目标无法解析到唯一可编辑定义，**When** 尝试运行循环，**Then** 停在主体解析，报告"无唯一所有者"并按既有失败表处置，不改动任何文件。

### User Story 5 - 循环是否真的有效可以被判定 (Priority: P2)

客户项目的维护者想知道"这套自我提升是不是在起作用"。答案来自四条已经存在的记录派生出来的数字（捕获、进入回路、闭环、重复），全部即读即建、不落任何汇总文件；分母为零时它说"未评估"，而不是给出一个漂亮的百分比。

**Why this priority**: 没有度量，"持续自我提升"不可证伪；但凭空造一套评分会比没有度量更糟，所以它排在可用性之后、且被严格限制在既有记录上。

**Independent Test**: 在一个客户项目夹具里造若干历史条目与一次 review 运行，运行消化路径，检查四条指标都能从既有记录复算；再把分母清零，检查输出是"未评估"且存储树无新增聚合文件。

**Acceptance Scenarios**:

1. **Given** 客户项目里已有若干外部条目与相应的评审记录，**When** 消化路径呈报度量，**Then** 四条指标各自给出可复算的分子与分母。
2. **Given** 任一分母为零，**When** 呈报该指标，**Then** 该指标显示为"未评估"（[[STR-006]]）并给出原因，不显示 0 或 100%。
3. **Given** 度量呈报完成，**When** 比较运行前后的存储树，**Then** 没有新增任何聚合或评分文件。

### User Story 6 - 两顶帽子各自干净：框架侧不被污染，客户侧不外流 (Priority: P2)

审计者要能回答两个问题而不必读全部日志：框架的反馈库里没有混进客户项目的代码缺陷；客户项目的反馈没有以任何形式流向框架。前者由既有分类义务守护，后者由打包侧的既有排除守护，两者在本特性里都不得被削弱。

**Why this priority**: 这是"扩散"这个动作最容易造成的伤害。上一个特性刚刚把"代码缺陷不得作为反馈条目投递"写成双表面义务，本特性如果为了给客户侧开道而放宽它，整个反馈机制的可信度一起归零。

**Independent Test**: 构造一次同时含代码缺陷与框架摩擦的客户项目评审，检查框架侧条目只有框架摩擦、客户侧条目只有指针形态的评审摘要；再对同一批数据跑打包，检查产物里既无客户条目也无代码缺陷正文。

**Acceptance Scenarios**:

1. **Given** 一次客户项目评审同时产生代码缺陷与框架摩擦，**When** 检查两侧条目，**Then** 框架侧只有框架摩擦、客户侧只有指针形态摘要，没有任何一条同时出现在两侧。
2. **Given** 客户项目存储里存在外部条目，**When** 生成打包产物，**Then** 产物内不含任何外部条目，报告的排除计数与实际排除数相等。
3. **Given** 一个框架项目（本仓）运行同一流程，**When** 检查存储，**Then** 没有新增任何外部条目——采集只发生在客户项目一侧。

---

### Edge Cases

- **客户项目把框架源 vendored 进自己的仓**（即它其实是一个框架分支）：帽子判定按既有 owner 判据得出"框架项目"，因此不采集；运行 MUST 明确说明本次未采集及其依据，不得因为"看起来像客户项目"而采集。
- **客户项目同时有 `feedback/` 目录**：帽子判据 MUST NOT 以该目录存在为据（既有规则不变）；一个有 `feedback/` 却没有根级框架源目录的项目仍是客户项目。
- **客户项目的探针注册表不可用**（未升级的 `.specify/` 运行时）：采集 MUST 判为未武装 [[STR-004]] 并 MUST NOT 记录无 `kind`/`slice` 的遗留条目——缺少外部分区的条目会被既有路由当框架条目处理，可能造成客户数据随包上送；一次性的准备指引指向重新初始化/升级 `.specify/`。
- **一次评审的适用性不是 [[STR-005]]**（无代码 delta 或环境不可评估）：没有记录可指向，采集不执行，MUST 披露"无对象可采集"（[[STR-009]]）而不是记一条空条目。
- **汇总命令以退出码 1 结束**（存在 `blocking` 条目，门禁拒绝）：采集照常执行——门禁判决与观察采集是两件事，采集 MUST NOT 因门禁拒绝而消失或改写计数。
- **汇总命令以退出码 2 结束**（输入不可解析）：采集 MUST 记为零条目并以 [[STR-010]] 具名披露"计数不可得"，MUST NOT 以 0 填充或凭印象报数。
- **反馈引擎以退出码 2 结束或被环境拒绝写盘**：采集失败 MUST 以 [[STR-010]] 具名披露，运行 MUST NOT 被阻断（反馈可选的红线优先）。
- **同一秒内重复采集**：引擎按（单元、运行）对幂等，MUST NOT 产生第二条条目。
- **客户单元从探针注册表里消失之后**：既有条目 MUST 保持可读、不被重写；消化路径 MUST 报告该单元的解析失败，而不是删除或重新归属它的条目。
- **客户项目里存在本特性落地之前产生的历史评审记录**：不回填，MUST NOT 为历史记录补造条目；度量口径 MUST 说明它只覆盖落地之后的运行。
- **内容审查把一条框架单元条目判定为"其实是本项目配置问题"**：既有单向精化规则不变（可向本项目移动、不可把外部条目移向框架）；移动后的归属 MUST 在报告中呈报。
- **客户项目里同时存在多个客户单元且本次显式指定了其中一个**：只有被指定的单元获得条目，其余单元 MUST NOT 因"也在场"而被一并采集。

## Requirements *(mandatory)*

### Functional Requirements

#### 客户身份与作用域

- **FR-001**: 「这是客户项目」的判定 MUST 继续由既有 owner 承担——`.specify/shared/definitions/dogfooding-definitions.md` § 2.1 的两顶帽子规则，判据是仓库根**是否拥有框架源目录**；本特性 MUST NOT 定义第二份判据、MUST NOT 以 `feedback/` 目录存在与否参与判定、MUST NOT 因某目录"看起来像"框架目录而放宽。

- **FR-002**: 「客户通道武装态」MUST 是一个显式声明的三值事实，而不是隐式推断，解析顺序封闭为：调用方显式指定的客户单元 > 存储中唯一的外部探针对象 > 其余情形。三值为：已武装 [[STR-007]]（恰有一个可用的外部探针对象，或调用方显式指定且该单元存在可用的外部探针对象——存在探针对象是「已武装」的必要条件，显式指定只消解歧义，MUST NOT 豁免探针对象检查）；未武装 [[STR-004]]（没有任何外部探针对象、显式指定的单元没有对应探针对象，或探针注册表不可用）；歧义 [[STR-003]]（存在多个外部探针对象且调用方未显式指定）。探针注册表不可用（未升级的 `.specify/` 运行时）时 MUST 判为未武装，并 MUST NOT 记录无 `kind`/`slice` 的遗留条目——该形态会被既有路由当框架条目处理，存在随包上送风险（见 Edge Cases）。武装态 MUST 在本次运行中解析一次并全程复用，MUST NOT 在运行中改变。

  外部探针对象的载体与命名归既有能力所有（`.specify/memory/feedback/probes/` 下的外部探针文件，由反馈技能的探针注入能力产出），本规格只引用其存在性，不另造登记面。

- **FR-003**: 客户发现的单元命名 MUST 采用既有的 `custom:<owner>/<name>` 形态并以 [[STR-001]] 作为单元类型；`<owner>` 与 `<name>` 由客户项目自定。客户发现 MUST NOT 使用 `/speckit.<command>` 或 `skill:<name>` 作为单元——这两个词族的单元在客户项目里要么不存在对应探针对象（记录会被引擎拒绝），要么被解析为框架内部单元（条目会被路由上送，即污染框架侧）。既有 Dogfooding Loop B 配方里以 `skill:<scenario-name>` 记录自家产品发现的写法 MUST 被改写为 `custom:` 形态并同批说明理由；改写 MUST NOT 削弱该配方的其余部分。

- **FR-004**: 一条客户条目 MUST 由既有三字段确定其作用域并保持单一归属：`kind` 为 [[STR-002]]、`slice` 为 [[STR-008]]、以及「一个单元 + 一次运行」的既有作用域语义。本特性 MUST NOT 新增第四个作用域字段、MUST NOT 新增条目标识族、MUST NOT 让一条条目同时属于两个单元或两次运行。

#### 采集（代码评审发现进入客户通道）

- **FR-005**: 代码段发现进入客户通道的入口 MUST 是代码段**非交互路径的第五步**——由确定性输入拼装一条客户条目——而不是新增命令、新增收尾步骤或让代理手写条目。该路径的步骤枚举由前序特性拥有（`.specify/specs/071-review-code-integration/requirements.md` 把非交互评审路径的步骤枚举封闭为四步；现行表述落在 `skills/internal/code-review/SKILL.md` § 非交互路径一节），本特性对其做**唯一一处**显式修订：四步 → 五步（基准解析、记录创建与轮转、意见落盘、回执与裁决、客户采集）。

  该修订的理由与代价必须一并记录：理由是采集所需的全部输入（记录路径、适用性取值、按严重度的计数）在第四步之后才齐备，把它放在同一条确定性路径上是唯一能让"发现必须进入客户通道"成为机械可核验事实的位置；代价是前序特性的一次闭合枚举被改写一次，故本特性 MUST NOT 再动它的任何其他闭合面（见 FR-025）。

- **FR-006**: 采集的触发条件 MUST 是两条同时成立的合取：本次运行所在仓为客户项目（FR-001），且代码段的适用性为 [[STR-005]]（存在记录可指向）。其余任何情形 MUST NOT 采集，且 MUST 按 FR-009 披露原因。采集 MUST 在一次合格运行中发生**恰好一次**——一次运行一条条目，MUST NOT 按意见条数、按文件数或按严重度各写一条。

- **FR-007**: 客户条目的内容 MUST 是**指针形态**，其字段集封闭为：代码段记录路径、本次适用性取值、按严重度的条目计数、本次运行的标识、以及该条目所属的客户单元。计数 MUST 逐项抄自既有的汇总命令输出（六项按严重度计数，含零值，与代码段技能既有的六级严重度词汇一一对应），MUST NOT 由人或代理另行清点或估算，MUST NOT 省略零项或合并级别。条目 MUST NOT 包含：评审意见正文、逐文件裁决清单、覆盖率回执的逐文件字段、变更文件总数或非代码文件数。把意见正文或逐文件清单抄进条目的行为 MUST 被判为违规——它同时违反"单一事实只留一处"与"摘要优先"，且体量会随代码库线性增长。

- **FR-008**: 采集 MUST 满足三条不变量：幂等（同一单元与同一运行至多一条条目，重复执行不新增、不报错）；非阻塞（采集失败 MUST NOT 阻断评审运行，MUST NOT 改变段裁决、合入门禁判决或状态转换）；不越权（采集 MUST NOT 修改代码段记录、MUST NOT 改写回执字段块，MUST NOT 触发任何传输）。

- **FR-009**: 采集未发生或计数不可得时 MUST 走"具名披露 + 零条目"，闭合取值为：未武装 → [[STR-004]]（含两个子情形：显式指定的单元没有对应探针对象；探针注册表不可用）；歧义 → [[STR-003]]；无对象可采集 → [[STR-009]]；计数不可得或引擎拒绝写盘 → [[STR-010]]。任一情形下 MUST NOT 写空条目、MUST NOT 以 0 填充、MUST NOT 以"本次无发现"表述替代原因。披露 MUST 出现在该次运行的面向人结论中，并 MUST 与该次运行的适用性取值同时可见。

#### 消化与后续载体

- **FR-010**: 客户条目的消化 MUST 复用反馈命令既有的就地消化路径，MUST NOT 新增第二条消费路径、第二套清单或第二套清理流程。打包路径 MUST 继续按既有规则排除 [[STR-002]] 条目并在报告中给出排除计数；本特性 MUST NOT 新增任何能绕过该排除的开关、参数或环境变量。

- **FR-011**: 一条客户条目被消化后 MUST 恰好被指派**一个**后续载体，取值封闭为三种，全部是既有机制：其一，`/speckit.todo` 的 Park 模式（自由漂浮的改进想法，默认落点）；其二，一个新的需求规格（当该发现约束本项目源码必须实现什么时）；其三，改进命令的一次主体循环（当发现落到一件满足执行主体判据的客户工件上时）。三者的边界与存放位置归各自既有 owner，本规格只规定"必须择一"，MUST NOT 新增第四种载体、MUST NOT 为一条条目指派两个载体。

- **FR-012**: 框架侧的目标闭集 MUST 原样不变：写入框架侧分区的观察仍然只能是框架自身摩擦，客户项目代码的缺陷 MUST NOT 作为框架侧条目投递（前序特性已经把这条分类义务写在命令模板与技能两个表面上）；反向同样成立——框架摩擦 MUST NOT 被登记到客户单元上。同一条观察 MUST NOT 同时出现在两侧。

- **FR-013**: 客户项目的消化呈报 MUST 至少包含三项既有事实：本次帽子与武装态（以及武装态是如何解析出来的）、两侧各自的条目数与处置结果、以及四条循环度量的读数（FR-021）。呈报 MUST NOT 改变既有消化路径的原子清理语义，也 MUST NOT 把度量计算并入清理动作。

#### 客户项目的改进循环

- **FR-014**: 客户项目的改进循环 MUST 复用既有自我提升技能的标准路径（`.specify/shared/workflow/self-improvement-workflow.md` 的 SI-0…SI-9），MUST NOT 新增客户专用改进流程、专用技能或专用台账。循环主体 MUST 通过执行主体判据（`.specify/shared/definitions/self-improvement-definitions.md` § Execution Subject 的五条）；判据本身 MUST NOT 被放宽或新增豁免。

- **FR-015**: why 段的观察源 MUST 按主体类型解析，且必须如实说明来源：`custom:` 主体在运行判定引擎里没有合法的持久化来源（该引擎的来源契约只接受命令与技能两种单元形态，对其它主体 fail closed 并返回"未持久化"与原因），因此客户主体的 why 段 MUST 以客户通道条目与既有证据车道为观察源，并 MUST 明写"运行判定历史未评估"及其原因。

  本特性 MUST NOT 发明一个来源字符串让写入成功，MUST NOT 伪造历史记录，MUST NOT 把"没有历史"表述为"过去运行都正常"。来源契约的加宽是其 owner 的动作，超出本特性范围。

- **FR-016**: how 段 MUST 继续按既有派发表路由到既有改进器（技能、代理、工具记录、团队），并在没有对应改进器时走既有的"降级为他者辅助提升"路径；本特性 MUST NOT 为客户主体新增改进器、MUST NOT 让命令自身直接改写主体。

- **FR-017**: 循环的既有约束 MUST 原样保留：每次派发前必须有一次已执行的证伪尝试；干预台账仍只有一份（基线证据运行旁的干预记录），MUST NOT 新增第二份台账或评分；尝试上限仍是硬上限，达到即停并要求人工介入；结果状态在可比运行的比较完成前 MUST 报为"待定"，MUST NOT 报为"已改进"。

- **FR-018**: 主体无法解析到唯一可编辑定义时，循环 MUST 停在主体解析（SI-0），报告"没有唯一所有者"，并把观察留给后续载体，MUST NOT 假设所有权、MUST NOT 改动任何文件。

#### 持续性与节奏

- **FR-019**: "持续" MUST 被定义为"每次合格运行都采集 + 既有非阻塞提示 + 显式触发"的组合，MUST NOT 被实现为调度器、常驻进程、定时器或后台任务。具体地：采集发生在每次满足 FR-006 的运行；提示继续由既有阈值协议产生并保持非阻塞（未被响应即视为跳过，不重复催促、不阻断收尾）；消化与改进循环仍由用户显式触发。MUST NOT 引入任何形式的周期性自启动。

- **FR-020**: 采集 MUST NOT 回填历史：本特性落地之前产生的评审记录 MUST NOT 被补造条目，MUST NOT 被批量重跑以生成条目。既有阈值协议与运行判定的组合规则 MUST 原样不变（两者同时为真才出现提示）；本特性 MUST NOT 改变提示的触发条件、出现位置或阻塞性。

#### 循环有效性度量

- **FR-021**: 「持续自我提升是否有效」MUST 由四条指标回答，每条 MUST 指明分子、分母与数据来源，且全部来自既有记录：其一，**捕获覆盖率** = 已采集的运行数 / 产生代码段记录的运行数；其二，**进入回路比例** = 已被指派载体的条目数 / 客户条目总数；其三，**闭环比例** = 已被证明确实处理完成的条目数 / 客户条目总数；其四，**重复发现率** = 其（文件、严重度）对在同一客户单元的历史条目里已出现过的条目数 / 客户条目总数。

  第三条 MUST 按「路由不等于完成」判定闭环——该判定的既有锚点是引擎的处置语义（`--action dispose` 的 `processed`/`ignored` 仅为本地元数据，不校验修复是否落地）与既有路由台账的行语义（`carried-by-spec-*` 表示被承接，不等于已完成；`open-unverified` 行 MUST 先复测再行动）：只有当被指派的 owner 文件确有变更证据时，条目才算闭环，处置标记本身 MUST NOT 被当作闭环证据。第四条 MUST 被标注为粗代理（它用位置加严重度近似同一问题），MUST NOT 被表述为缺陷复现率。

- **FR-022**: 度量 MUST 即读即建：每次呈报时从既有记录重新计算，MUST NOT 落盘为汇总文件、MUST NOT 进入任何既有存储的分区、MUST NOT 引入新的存储目录或索引。本特性 MUST NOT 新增评分体系、权重、总分或跨指标换算——四条指标彼此不合成单一数字。

- **FR-023**: 度量的诚实性 MUST 可机械判定：任一分母为零或缺数据时，该指标 MUST 报为"未评估"（[[STR-006]]）并给出原因，MUST NOT 报 0、MUST NOT 报 100%、MUST NOT 省略该行；粗代理指标 MUST 在呈报中带"代理"标注。度量 MUST NOT 影响任何判定——它不是门禁、不是状态转换条件、不是提示阈值。

#### 红线与不变量

- **FR-024**: 框架反馈的四条红线 MUST 原样保留并同样覆盖客户侧条目：目标仍是框架自身（客户侧条目的目标是本项目自身，见 FR-012 的闭集划分）；反馈仍是完全可选的用户数据（任一流程 MUST NOT 因未处理反馈而阻塞、反复催促或降级）；零自动传输（客户条目与框架条目一样，MUST NOT 被上传、推送或以任何方式发出，唯一合法传输路径仍是用户手动投递打包产物）；本地 workaround 价值不变。本特性 MUST NOT 新增任何网络调用或外部服务。

- **FR-025**: 前序特性的已完成契约 MUST NOT 被回退：代码段记录的形态与轮转、覆盖率回执的退出码字母表与字段块、过程报告代码段小节的封闭字段清单、评审单元收尾步骤集合、每次运行的三单元收尾普查——全部原样保留。本特性对它们的唯一修订是 FR-005 声明的步骤枚举。前序特性遗留的开放建议项保持开放，本特性 MUST NOT 实现它们、MUST NOT 依赖它们的结论（特别是：捕获计数取的是意见级计数，不是回执的文件级计数，因此不依赖回执对"非代码"与"未评审"的区分）。

#### 命令面与两顶帽子

- **FR-026**: 本特性 MUST NOT 新增 `/speckit.*` 命令，也不新增任何命令行子命令入口面（除 FR-005 的第五步之外）。既有入口的承载分工 MUST 是：评审命令承载采集（经其代码段，见 FR-005）并在其面向人结论里披露采集结果，并可经一个可选参数接收调用方显式指定的客户单元（该参数消解 FR-002 的歧义而不新增命令面，参数字面名归 plan 裁决）；反馈命令承载消化、载体指派与度量呈报；改进命令承载客户主体的循环。若实现时发现某入口确实无法承载，MUST NOT 就地新增命令，MUST 报告为需要裁定的缺口。

- **FR-027**: 编辑面 MUST 只有框架源（两顶帽子规则）：技能正文与技能侧参考文档、命令模板、共享 owner 文档、命令参考文档与契约测试。运行时投影（各工具命令副本、`.specify/` 下的镜像）MUST 由既有再生成与镜像同步机制产出，MUST NOT 手改。若实现触及探针注册面，MUST 先按既有顺序重编译再同步；MUST NOT 手改编译产物。

- **FR-028**: 随框架分发的表面 MUST 保持客户中立：新增文案 MUST NOT 引用本框架项目的具体规格键、特性编号或登记表条目（既有契约测试守护这条），MUST NOT 需要读者打开框架仓才能读懂。本特性 MUST NOT 删除、弱化或反转既有的负向断言（"客户项目自己的反馈不得被路由上送""帽子判据按框架源目录而非运行时镜像"两条为代表），新增断言 MUST 净增。

- **FR-029**: 客户侧行为 MUST 在**模拟客户项目**里被验证，而不是在框架仓自测：夹具是一个没有根级框架源目录、由框架安装出 `.specify/` 的项目；采集、武装态三值、打包排除、客户主体循环、度量即读即建五组行为各 MUST 有确定性检查覆盖。本特性 MUST NOT 重写历史记录、MUST NOT 回填既有特性、MUST NOT 新增依赖、外部服务或常驻进程。

### Key Entities

- **客户条目（client finding entry）**: 客户项目通道里的一条观察，复用既有反馈条目形态与一文一件布局；作用域由 `kind`（[[STR-002]]）、`slice`（[[STR-008]]）与「一个单元 + 一次运行」确定；内容为指针形态（记录路径、适用性取值、按严重度的计数、运行标识、所属单元）；永不随包、永不外发。
- **客户单元（client unit）**: 客户项目自定的耐久主体标识，形态 `custom:<owner>/<name>`，类型 [[STR-001]]；其在探针注册表中的外部探针对象是"通道已武装"的载体；它的可编辑定义在客户项目内部，不在框架侧。
- **武装态（armed state）**: 一次运行对"能否采集"的判定结果，三值封闭（已武装 [[STR-007]] / 未武装 [[STR-004]] / 歧义 [[STR-003]]）；解析一次、全程复用。
- **后续载体（carrier）**: 一条客户条目被指派的一个既有机（todo Park 模式 / 新需求规格 / 改进循环主体）；恰好一个；指派由消化决策做出并呈报。
- **循环度量（derived metrics view）**: 四条指标的即读即建视图（捕获、进入回路、闭环、重复），无落盘、无合成分数、零分母报"未评估"。
- **代码段记录（code-review record）**: 代码评审发现的唯一正文载体（前序特性所有）；本特性只指向它，不复制它。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在一个已武装的模拟客户项目里跑一次适用性为 [[STR-005]] 的代码段，按运行标识过滤外部条目的清单命令返回恰好一条本 run 的条目，且其六项按严重度计数（含零值）与既有汇总命令的输出逐项相等；同一 run 再采集一次，条目数不变。判定由确定性命令输出比对完成，不依赖人工阅读条目正文。

- **SC-002**: 在未武装的客户项目里跑同一流程，条目数不变、运行退出码为 0、输出含 [[STR-004]]；在有两个外部探针且无显式单元的客户项目里跑同一流程，条目数不变、输出含 [[STR-003]]；带显式单元参数时输出表明采用显式指定。三种情形的判定都只需检查退出码与具名披露，不需要阅读日志正文。

- **SC-003**: 在一个同时有 [[STR-002]] 与框架单元条目的客户项目里运行打包，打包产物内既无客户条目也无代码缺陷正文，报告中的排除计数与实际被排除条目数相等；在框架项目内重复同一流程，不产生任何 [[STR-002]] 条目。

- **SC-004**: 对一个满足执行主体判据的客户工件运行改进循环，三段产物与干预台账都落盘，报告给出"结果待定"且明写"运行判定历史未评估"；对一个无唯一可编辑定义的目标运行，运行停在主体解析、仓库文件零变更（以运行前后工作树状态比对判定）。

- **SC-005**: 四条指标可从既有记录复算：给定同一批记录，两次呈报得到相同读数；把任一分母置零后，该指标显示"未评估"（[[STR-006]]）；两次呈报前后存储树无新增聚合或评分文件（以路径集合比对判定）。

- **SC-006**: 五组客户侧行为的确定性检查全部存在且通过（采集、武装态三值、打包排除、客户主体循环、度量即读即建），每组各有一次记录在案的失败运行（红先行：命令行、退出码、失败计数）；既有的反馈路由与客户中立契约测试保持通过，断言只增不减。

- **SC-007**: 前序特性的闭合面未被削弱：代码段非交互路径的步骤枚举为五步（修订已声明）、评审单元的收尾步骤集合仍为既有六步、每次运行的收尾普查仍为三个单元、回执字段块与过程报告代码段小节的封闭清单逐字未变。判定按逐处文本与结构断言完成。

### Measurement Sources & Collection Methods

- **SC-001 Source**: 条目清单命令的 JSON 输出（按运行标识过滤外部条目）与汇总命令输出；两者比对一次，不做二次采集。
- **SC-002 Source**: 各次运行的退出码与面向人结论中的具名披露字面量；三种情形各一次运行。
- **SC-003 Source**: 打包产物的清单文件（其中所列条目标识）与打包报告的排除计数；两组运行各一次。
- **SC-004 Source**: 改进循环的收尾报告字段（主体身份、所有者、观察源、结果状态）与运行前后的工作树状态。
- **SC-005 Source**: 两次呈报的读数与运行前后存储树路径集合；单次运行的完整输出按既有的"执行时全量捕获"纪律归档到本特性的证据目录。
- **SC-006 Source**: 新增契约测试文件的收集计数与各组红先行运行记录（命令行、退出码、失败计数）；既有守护测试的运行结果。
- **SC-007 Source**: 三处闭合面的结构断言（步骤枚举、收尾步骤集合、三单元普查）与两处字段清单的逐字比对结果。
