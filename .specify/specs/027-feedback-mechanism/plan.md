## Summary

Introduce a distributed, **local-scope** feedback layer across the framework. At the wrap-up moment of a *qualifying* flow — the same lifecycle point where flows already prompt for a Git commit — the executing agent reflects on the just-completed run against the unit's declared purpose and records concrete, unit-scoped optimization points. The technical approach **reuses the proven memory-as-files pattern** (`memory-utils.py`): a new stdlib-only engine `feedback-utils.py` writes Markdown feedback entries plus a local `index.json` into `.specify/memory/feedback/`, tracks an accumulation count, and signals a single consolidated submission prompt at a defined threshold. The feedback step is embedded **by convention**: every skill carries a `## Feedback` section by default, and only *complex* commands (script-invoking / producer-consumer flows per FR-006) carry it. Trivial flows never trigger it, preserving execution efficiency. Local feedback stays strictly distinct from the global `/speckit.review` report.

## Technical Context

**Language/Version**: Python `>=3.8` (engine script, standard-library only — mirrors `memory-utils.py`); Markdown for templates/skills/commands
**Primary Dependencies**: None beyond the Python standard library for the engine; framework authoring surfaces are Markdown (skills `SKILL.md`, command templates under `templates/commands/`, `templates/skills-template.md`)
**Storage**: Files under `.specify/memory/feedback/` — one Markdown entry per qualifying run plus a per-store `index.json` (accumulation count + submission state). No database, no vector store.
**Testing**: `pytest` with existing markers `contract` and `integration` (`tests/contract/`, `tests/integration/`, `tests/unit/`)
**Target Platform**: Cross-platform CLI (Linux/macOS/Windows) distributed as `specify-cli`; scripts mirrored to `.specify/scripts/python/`
**Project Type**: single — code generator / framework (`templates/`, `scripts/`, `skills/`, `src/specify_cli/`)
**Performance Goals**: Zero feedback overhead on trivial/short flows (SC-004); at most one entry per qualifying unit per run (SC-005); engine write is a single-file append + index update
**Constraints**: Selective triggering is a hard constraint (all skills + complex commands only); feedback is agent self-reflection with **no** user-input step at wrap-up (FR-012); engine must be stdlib-only and idempotent per `(unit, run)`; nested invocations MUST NOT duplicate (FR-008)
**Scale/Scope**: 21 installed skills (all carry feedback) + 17 commands (13 complex → carry feedback, 4 simple → excluded); feedback entries accumulate across runs until the threshold prompt

## Phase 0: Research Review

All unknowns from Technical Context are resolvable internally; no external evaluation required.

- **Decision — Reuse the memory-as-files engine pattern.** `feedback-utils.py` mirrors `memory-utils.py`: stdlib-only, Markdown entries with YAML-ish frontmatter, a per-store `index.json`, and a strict `--source` boundary (`/speckit.<command>` | `skill:<name>`). *Rationale*: proven, dependency-free, observable; satisfies Principle VI (YAGNI) and keeps feedback in the same `.specify/memory/` neighborhood users already know.
- **Decision — Store format & threshold.** Entries live at `.specify/memory/feedback/<run-ts>-<unit-slug>.md`; `index.json` holds the entry list plus `count_since_submission`, `threshold` (default **10**), and `submitted_at`. The `status` action returns `should_prompt = count_since_submission >= threshold`. *Rationale*: FR-011 requires accumulation + a single consolidated threshold prompt; a count in the index makes the boundary deterministic (SC-007).
- **Decision — Idempotency / no duplication.** `record` is keyed by `(unit_id, run_id)`; a second call for the same pair is a no-op. *Rationale*: FR-008 / SC-005 (nested command→skill invocations must not double-count).
- **Decision — Command classification (FR-006).** A command is **complex** iff it (a) invokes scripts/CLI tools OR (b) produces an artifact consumed by another flow OR (c) consumes another flow's artifact. Applying this yields **13 complex** commands (the SDD-chain / script-invoking set) and **4 simple** (`agents`, `constitution`, `feature`, `team`). See `contracts/command-classification.md`. *Rationale*: matches the observed script-invocation set exactly and keeps feedback off self-contained authoring/registry commands, honoring FR-007.
- **Decision — Scope delineation vs `/speckit.review`.** `/speckit.review` remains the sole global, whole-project process report; local feedback entries carry `scope: local` and are bound to a single unit + run. *Rationale*: FR-005 / SC-006, Edge case "Overlap with global review".
- **Decision — Abort/failure handling.** On aborted/failed runs the wrap-up either skips feedback or records it with `partial: true` and a labeled review. *Rationale*: FR-009, Edge case "Aborted or failed flow".
