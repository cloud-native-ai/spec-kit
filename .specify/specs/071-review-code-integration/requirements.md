## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一次 review 同时得到过程结论与代码结论 (Priority: P1)

维护者在无人值守特性流程的末尾运行一次 `/speckit.review`，无需再单独调用任何别的命令，就同时拿到两类结论：这段 SDD 过程哪里卡住（过程评审），以及这个特性交付的代码差异有哪些可验证缺陷（代码评审）。两份结论各自成文、各自定级，互不冒充。

**Why this priority**: 这是用户诉求的字面内容，也是当前最大的入口缺口——代码评审技能已经存在却没有任何命令引用它，维护者跑完实现后拿不到代码 diff 的评审结论。

**Independent Test**: 在一个有已提交代码 delta 的特性上运行 `/speckit.review`，检查特性目录同时出现过程报告与代码段记录，且过程报告的代码段小节与绑定特性详情的评审记录条目都给出两段结论；再在一个无代码产出的特性上运行同一命令，检查代码段被如实记为不适用而不是静默消失。

**Acceptance Scenarios**:

1. **Given** 一个已提交代码 delta 的特性目录，**When** 运行 `/speckit.review`，**Then** 过程段先执行、代码段后执行，特性目录出现过程报告与代码段记录两份产物，过程报告的代码段小节与绑定特性详情的评审记录条目同时列出过程段的严重度计数与代码段的裁决。
2. **Given** 一次 review 运行，**When** 阅读过程报告，**Then** 过程报告只承载过程段的结论，代码段结论以「小节 + 裁决 + 指向代码段记录的路径」出现，不复制代码段的意见正文。
3. **Given** 过程段与代码段同时有结论，**When** 有人试图把两套严重度合成一个评分或一张表，**Then** 该行为被判为违反规格（两套词汇各自保留其 owner）。

### User Story 2 - 代码评审的对象与基准可判定、可复算 (Priority: P1)

评审人与后来的读者都能回答"到底审的是哪一段代码"：基准来自特性切片本身而不是某个硬编码的分支名；工作树里没有提交的改动不会被悄悄算进已评审范围；基准无法确定时明确记为不可评估，而不是猜一个。

**Why this priority**: 基线口径错误会让整份代码评审结论失去意义（审了不该审的、或漏审了真正的交付面），而且在无人值守场景里没人会在旁边纠正。

**Independent Test**: 对同一特性用不同显式基准各跑一次代码段，回执中的基准、目标提交标识与基准来源与实际 git 引用一致；在基准不可解析的构造场景下运行，得到不可评估结论与可复现命令，而不是一个猜测的基准。

**Acceptance Scenarios**:

1. **Given** 一个特性的 spec 目录已有首次提交，**When** 代码段解析基准与目标且调用方未显式指定，**Then** 基准取该首次提交的父提交、目标取运行开始时解析一次的 `HEAD`，回执记录的 base、head 与基准来源使 `git diff base..head` 可复算，且整次运行内 head 不再变化。
2. **Given** 工作树存在未提交改动，**When** 运行代码段，**Then** 这些改动不计入默认评审对象，报告显式披露"存在未评审的未提交范围"，且不得对未评审内容给出通过结论。
3. **Given** 显式基准与自动基准同时可用，**When** 运行代码段，**Then** 显式基准优先，报告记录实际采用的基准及来源。

### User Story 3 - 缺渲染器时不冒充已评审 (Priority: P2)

在没有 `delta` 的环境里，代码段仍然产出可信的结论：它改用纯文本读取全量 diff，并在记录里标注渲染模式；如果它没有把所有变更文件逐一看过并留下裁决，它给不出"通过"。

**Why this priority**: 现状是渲染器缺失即停，这让命令在多数无人值守环境里根本跑不完；但反过来"缺工具就裸看几眼然后说审过了"更糟。真正要守住的是**不冒充**，而不是**必须用某个工具**。

**Independent Test**: 在 `delta` 不在 PATH 的环境运行代码段，得到带文本渲染标记的记录与完整覆盖率回执；人为漏掉一个变更文件的裁决，回执命令以非零退出码报出缺口。

**Acceptance Scenarios**:

1. **Given** `delta` 不可用，**When** 运行代码段，**Then** 代码段完成并记录渲染模式为文本模式，且记录中不出现"已完成可视化评审"一类表述。
2. **Given** 变更文件集中有一个文件没有任何裁决，**When** 生成覆盖率回执，**Then** 回执命令以非零退出码报出缺口，代码段裁决不得为通过。
3. **Given** 变更文件集与回执文件集相等且每个文件都有裁决，**When** 生成回执，**Then** 回执以零退出码通过并给出计数。

### User Story 4 - 两套严重度各有其位，门禁关系单一可判定 (Priority: P2)

维护者知道一条 `blocking` 意见到底意味着什么：当前代码段记录含 `blocking` 条目时，特性不能从 Implemented 前进到 Ready for Review；过程段继续用它自己的 P0/P1/P2。两者之间没有换算表，只有一条被明确声明、写在状态机 owner 里的门禁关系。

**Why this priority**: 严重度混用是本次整合最容易产生的语义污染；把门禁关系钉在一个 owner 上，后续才不会被两处写法分裂。

**Independent Test**: 构造一次当前代码段记录含 `blocking` 条目的 review，检查特性状态转换被拒绝；再重跑一次代码段、产出一份 `blocking` 计数为 0 的新记录，检查同一转换通过。检查 owner 文档与命令模板里的门禁条件表述同源。

**Acceptance Scenarios**:

1. **Given** 当前代码段记录 [[STR-004]] 中存在至少一个 `blocking` 条目，**When** 尝试把特性推进到 Ready for Review，**Then** 转换被拒绝并给出阻塞依据。
2. **Given** 代码段只剩 `important` 及以下条目，**When** 尝试推进，**Then** 转换允许，且 `important` 条目被要求逐条回应。
3. **Given** 有人请求把代码段六级词汇重标为 P0/P1/P2，**When** 评审该变更，**Then** 该请求按规格被拒绝（词汇各自保留其 owner）。

### User Story 5 - review 与 feedback 的通道不再互相污染 (Priority: P2)

维护者跑完 review 后，反馈库里出现的是**框架自身的摩擦**（例如渲染器缺失、基准歧义、回执缺口），而不是这个特性代码里的缺陷；同时既有的建议登记义务与自省入口照旧工作，仍然没有任何自动传输。

**Why this priority**: 整合后两条通道会在同一次运行里同时活跃，污染风险从理论变成默认路径；而 feedback 的目标红线是机制层面的不变量，退回一次就很难再收回来。

**Independent Test**: 构造一次 review，其中代码段发现若干代码缺陷、同时暴露出一个环境摩擦，检查反馈条目只包含后者；检查建议编号登记与自省入口仍可用。

**Acceptance Scenarios**:

1. **Given** 一次 review 同时产生代码缺陷与框架摩擦，**When** 检查反馈条目，**Then** 只有框架摩擦进入反馈库，代码缺陷留在代码段记录里。
2. **Given** 一次 review 产出了建议编号，**When** 查看提交，**Then** 每个建议编号在同一提交内登记进项目登记表。
3. **Given** 一次 review 运行，**When** 检查收尾步骤，**Then** 命令的收尾步骤集合与整合前一致，没有新增步骤，也没有自动传输路径。

### Edge Cases

- **特性没有代码产出**（例如文档型 / 表达类特性）：代码段必须记为 [[STR-001]] 并写明依据——依据按 FR-003 的代码路径谓词判定（已提交 delta 中不含任何代码路径文件），过程段的读者基准评审结论不受影响。
- **特性尚未提交，代码只在工作树里**：默认对象为空，代码段记为 [[STR-001]] 并披露未提交范围；不得把工作树当作已提交切片来给结论。
- **特性首次提交缺失且主干基准不可解析**：记为 [[STR-002]]，附可复现命令，不猜基准。
- **仓库主干叫 `master` 而不是 `main`**，或仓库没有 `main`：命令不得依赖脚本的默认基准，trunk 识别按 FR-004 的封闭顺序（显式 `--trunk` > 可解析的 `refs/remotes/origin/HEAD` > `main` > `master` > [[STR-002]]），基准解析规则必须自足。
- **`delta` 存在但逐文件流程需要交互输入**：agent 路径必须能完全非交互走完；人类交互路径保留。渲染模式的选择规则见 FR-013（渲染器可用**且**标准输出为 TTY 才渲染）。
- **diff 规模超过体量守门阈值**：先提示拆分，再按模块聚焦；聚焦后覆盖率回执仍必须覆盖全部变更文件，未聚焦到的文件记为带理由的跳过（理由取自 FR-014 的闭合理由集）——该跳过不构成回执缺口，但按 FR-014 不得计为覆盖信用，因此聚焦审查后的段裁决不得为 [[STR-006]]，过程报告的代码段小节与特性详情评审记录条目必须单列跳过计数。
- **同一次 review 被重跑**：代码段记录按运行时间戳各自成文件，不覆盖上一份（落盘形态、时间戳格式与同秒冲突处置见 FR-010：上一份归档为同目录的归档件，[[STR-004]] 始终指向最近一次运行）；过程报告的重跑按既有产物链规则处理。
- **代码段记录含 `blocking` 条目但用户明确要求先合入**：只接受显式用户裁定的豁免（用户书写的豁免制品或用户本人的明确裁定；driver/编排者的确认不算），且必须写进过程报告的代码段小节与特性详情评审记录条目；代理不得自行降级。
- **review 在 `/speckit.implement` 之前运行**：过程段照既有前置要求处理，代码段对象可能为空，必须如实记为 [[STR-001]] 而不是给出 [[STR-006]]。
- **两段同时缺环境或缺对象**：两份结论都记为 [[STR-002]] 或 [[STR-001]]，过程报告的代码段小节与特性详情评审记录条目必须让读者一眼看出"这次没有评审结论"，不得呈现为 [[STR-006]]。
- **过程段中止或报错**：代码段照常执行，两段结论各自呈现；过程段自身记为不可评估并写明原因，命令不得因此把整体呈现为已完成评审（见 FR-002）。

## Requirements *(mandatory)*

### Functional Requirements

#### 编排形态（命令如何组合两段）

- **FR-001**: `/speckit.review` MUST 以固定顺序串行执行两段——过程段（委派 `review-sdd-process`）在前、代码段（委派 `code-review`）在后——且 MUST NOT 把两段的结论合并成单一严重度体系或单一评分。
- **FR-002**: 过程段 MUST 无条件执行，MUST NOT 被特性分类、命令参数或缺代码 delta 免除；两段 MUST 各自委派到既有技能，命令模板 MUST NOT 内联任一技能的方法论正文。过程段自身中止或报错 MUST NOT 抑制代码段执行——代码段的判定对象与过程段的前置条件无关；此时过程段自身记为「不可评估」并写明原因，两段结论各自独立呈现，命令 MUST NOT 因一段未完成而把整体呈现为已完成评审。该状态下代码段小节的载体不变：若过程段未能写出 `review.md`，命令 MUST 依据评审报告模板写出一份最小过程报告（只含代码段小节与中止原因），因此可核验载体仍是同一个 `review.md`，作者是命令而不是过程技能。
- **FR-003**: 命令 MUST 在代码段开跑前解析并记录代码段的适用性，取值封闭为三种：[[STR-005]]（存在本特性已提交的代码 delta 且其中至少含一个代码路径文件）；无代码产出或无已提交 delta 则记 [[STR-001]] 并写明依据；环境不满足则记 [[STR-002]] 并写明原因。这三种取值之外 MUST NOT 出现静默跳过。

  「什么算代码路径」的值域由唯一 owner 判定：`code-review` 技能的确定性脚本（`skills/internal/code-review/scripts/git-delta-review.sh`）拥有一个闭合的默认代码路径集，并接受显式覆盖参数（`--code-paths`）。本规格 MUST 引用该 owner 的判定结果，MUST NOT 在命令模板或本文件里另写第二份路径清单——两份清单必然漂移，而漂移的后果是同一仓库状态被两个评审人判成不同的适用性取值。

  变更集为空（base 与 head 指向同一提交、零变更文件）时 MUST 在覆盖率回执运行之前就判定为 [[STR-001]] 并写明依据「无已提交代码 delta」：空 delta MUST NOT 走到回执阶段被报成一次干净的评审。

#### 评审对象与 diff 基准

- **FR-004**: 代码段的评审对象 MUST 是本特性切片的已提交代码 delta，评审区间 MUST 记为 `base..head`。基准（base）解析顺序 MUST 为：调用方显式指定 > 本特性 `requirements.md` 首次提交的父提交 > 与仓库默认主干的合并基点；三者皆不可得时按 FR-006 处理。主干（trunk）识别顺序 MUST 为：显式 `--trunk` > 可解析的 `refs/remotes/origin/HEAD` > 存在的 `main` > 存在的 `master` > [[STR-002]]；MUST NOT 采用该顺序之外的猜测（例如取 `origin` 指向的任意远端、取最近活跃分支、取某个看起来像主干的提交）。目标（head）MUST 为：显式 `--head` > 运行开始时解析一次的 `HEAD`——该值在整次运行内 MUST NOT 再变，即使期间有新提交落地。

  评审区间 MAY 包含与本特性无关的提交（这是「head 固定在运行开始时」的直接后果，不是缺陷）；需要严格特性切片时 MUST 由调用方传显式 `--head`（该特性最后一个提交）。回执 MUST 记录 base 与 head 的提交标识以及基准来源（取自哪一档 trunk/首次提交），使区间可被 `git diff base..head` 复算。命令 MUST NOT 依赖脚本内置的分支名默认值。
- **FR-005**: 工作树未提交改动 MUST NOT 计入默认评审对象；存在未提交改动时 MUST 显式披露未评审范围，且 MUST NOT 对该范围给出任何通过结论。该披露按设计是**双载体**：既出现在过程报告的代码段小节（FR-011 的封闭清单含此字段），也出现在该次代码段记录 [[STR-004]] 内；两处承载同一句披露，不是两份判据。
- **FR-006**: 基准解析失败 MUST 记为 [[STR-002]] 并附可复现命令与失败原因；MUST NOT 退回猜测的基准，也 MUST NOT 以"看起来差不多的提交"代替。

#### 严重度与门禁关系

- **FR-007**: 两套严重度词汇 MUST 各自保留其 owner 与形态：过程段沿用 P0/P1/P2 且本特性 MUST NOT 改动其判定；代码段沿用六级词汇且 MUST NOT 被重标为 P0/P1/P2。本特性 MUST NOT 引入任何数值换算表、映射矩阵或统一评分。
- **FR-008**: 当前代码段记录 [[STR-004]] 中存在至少一个 `blocking` 条目时 MUST 阻断 `Implemented → Ready for Review` 状态转换；存在 `important` 条目时 MUST 允许转换但要求逐条回应；其余四级 MUST NOT 阻断。该门禁条件是**存在性判定**，只读当前记录（即 [[STR-004]] 所指的那一份），MUST NOT 累计归档件、MUST NOT 解释某条目为何被删除或被改写：后续运行写出的记录其 `blocking` 计数为 0 时，同一转换即不再被阻断。本特性 MUST NOT 定义「清除」这个动作，也 MUST NOT 定义「已清除」这个状态——转换只问当前记录里有没有 `blocking` 条目。

  该门禁条件的规范语句 MUST 由状态机 owner 承载——`templates/feature-details-template.md` § Canonical Status State Machine 的 `Implemented → Ready for Review` 行（该节自称权威转换表）——命令模板与技能 MUST 引用它而不是复制判据；特性集成协议里同一转换的摘要行 MUST 收敛为对该 owner 的引用，MUST NOT 保留第二份判据措辞。该门禁是**转换自身的属性**，不是某一个命令的属性：凡发起该转换的路径 MUST 引用同一 owner 判据，MUST NOT 各自另写一份。其中 `/speckit.checklist` 的同名转换行是**条件发起方**：只有当它在该特性的 `/speckit.implement` 之后运行时才发起该转换，此时 MUST 引用同一 owner 判据；在 implement 之前运行时不发起该转换，MUST NOT 因缺少代码段结论而报错或补造结论。owner 行 MUST 在同一行内同时承载「延迟项已解决或已豁免 + 评审证据已产出 + 代码段当前记录不含 `blocking` 条目」三项，且判定 MUST 直接读代码段的六级词汇，MUST NOT 先把它重标为 P0/P1/P2 再判定。
- **FR-009**: 门禁豁免 MUST 只来自显式用户裁定——用户书写的豁免制品，或用户本人在会话中的明确裁定；driver、编排者或任何代理的确认 MUST NOT 计为显式用户裁定。豁免事实 MUST 写入过程报告的代码段小节与特性详情的评审记录条目。代理 MUST NOT 自行把 `blocking` 降级、合并或在门禁判定中排除。无人值守运行的处置 MUST 为 halt-and-report，其门禁拒因 MUST 以 [[STR-010]] 作为具名字面量记录。

  上述处置的细节：当前记录含 `blocking` 条目且没有显式用户裁定时，命令 MUST 停在转换之前、如实报告阻塞，并把 [[STR-010]] 写入过程报告的代码段小节与回传结论；MUST NOT 以「无人反对」推定豁免，也 MUST NOT 静默地把状态留在 `Implemented` 却把本次运行报告为已完成。

#### 产物落点与形态

- **FR-010**: 过程报告 MUST 保持写入特性目录下的 `review.md`，结构由既有评审报告模板决定；代码段记录 MUST 写成特性目录内的独立文件 [[STR-004]]，两份产物 MUST NOT 相互覆盖，MUST NOT 共用同一份严重度汇总表。记录的存在性按适用性取值分工：仅当适用性为 [[STR-005]] 时 MUST 写出 [[STR-004]]；适用性为 [[STR-001]] 或 [[STR-002]] 时 MUST NOT 创建该文件（也不得写一份空记录），其结论与原因由过程报告的代码段小节（FR-011）承载。首次运行没有归档件，其归档路径 MUST 记为 [[STR-009]]。

  重跑语义：同一特性被重跑时，上一份代码段记录 MUST 先归档为同目录内的归档件（[[STR-004]] 去扩展名 + `-<运行时间戳>.md`），再写入新的 [[STR-004]]——因此 [[STR-004]] 恒指最近一次运行，历史运行一件一档、互不覆盖。运行时间戳格式 MUST 为 `YYYYMMDDTHHMMSSZ`（UTC，秒级分辨）；同一秒内出现归档冲突时 MUST 等到下一秒再落盘，或退出码 2 并写明原因，MUST NOT 覆盖既有归档件。过程报告 MUST 记录本次实际写入的路径以及本次产生的归档件路径（后者取 [[STR-009]] 或该次归档件的实际路径）。
- **FR-011**: 过程报告 MUST 含一个代码段小节，其内容封闭为：基准与目标的提交标识、基准来源（FR-004 解析出的档位）、渲染模式、覆盖率回执计数（变更 / 已评审 / 跳过 / 缺口）、段裁决（[[STR-006]]、[[STR-007]]、[[STR-001]]、[[STR-002]] 之一）、门禁裁决与其具名拒因（[[STR-010]] 这类字面量）、[[STR-001]] 或 [[STR-002]] 的原因、未评审的未提交范围披露（FR-005）、指向 [[STR-004]] 的路径与本次归档件路径（[[STR-009]] 或实际路径）；MUST NOT 复制代码段的意见正文，也 MUST NOT 逐条重列各严重度条目的计数（上述四项回执计数之外 MUST NOT 出现任何计数表）。

  该小节里的四项回执计数 MUST 逐项抄自该次回执的字段块——字段块是这组数值的唯一来源，小节 MUST NOT 独立计算或另行汇总；同一组计数出现在特性详情评审记录条目时同样 MUST 抄自字段块。三者的一致性 MUST 可由一条相等性断言核对，MUST NOT 依赖人工比对。
- **FR-012**: 代码段记录 [[STR-004]] MUST NOT 进入下游文档可用清单，MUST NOT 被当作 plan 与 tasks 的输入；它 MUST 被绑定特性详情 `## Latest Review` 条目中的评审记录行引用，使读者从特性侧可达。该载体 MUST 是既有的 `## Latest Review` 条目，MUST NOT 新增结构化字段或另造一份计数副本（计数按 FR-011 抄自回执字段块）。

#### 证据形态（"已读全 diff"）

- **FR-013**: 渲染器（`delta`）不可用 MUST NOT 阻断代码段；此时记录 MUST 标注渲染模式为 [[STR-003]]（文本模式），且 MUST NOT 出现任何声称做过渲染式可视化评审的表述。渲染模式的选择 MUST 是一条确定性规则，条件有且只有两个：渲染器可用**且**标准输出是交互终端（TTY）→ 渲染模式，记录标注 [[STR-008]]；其余一切情形 → 文本模式 [[STR-003]]。因此 agent / 非交互 / 重定向输出的调用即使渲染器存在也 MUST 取文本模式——本特性面向的主要调用形态正是这种。既有「渲染器缺失即停」条款 MUST 以「替代并说明理由」的形态改写，MUST NOT 以删除条款的方式弱化约束：技能正文 MUST 保留一条陈述「被替代的条款、其替代证据形态（覆盖率回执）与替代理由」的说明；同源措辞（Strict Requirements、Phase 0 环境确认步骤与 `references/` 内的说明）MUST 一并改写，MUST NOT 残留「缺失即停」的断言。
- **FR-014**: 适用性为 [[STR-005]] 且变更集非空时，代码段 MUST 产出一份覆盖率回执，其文件集 MUST 等于该次 delta 的变更文件集，逐文件带裁决（已评审 / 带理由跳过）；任一份文件无裁决或文件集不等时，代码段 MUST NOT 给出 [[STR-006]] 结论，且生成回执的确定性命令 MUST 以退出码 1 报出覆盖缺口。本条的三信号合取只适用于「适用性为 [[STR-005]] 且变更集非空」这一情形——空变更集在回执运行之前就按 FR-003 判为 [[STR-001]]，MUST NOT 走到这里被一个 0/0/0 的空回执报成干净评审。段裁决 MUST 由回执信号推导：跳过计数大于 0 时段裁决 MUST NOT 为 [[STR-006]]，只能为 [[STR-007]]（当前记录含 `blocking` 条目时）或 [[STR-002]]（其余情形）。

  回执命令的退出码字母表封闭为三种：`0` = 完整（文件集相等且逐文件均有裁决）、`1` = 覆盖缺口（有文件缺裁决、两文件集不等，或跳过了不被识别的理由）、`2` = 不可评估（base 或 head 不可解析、记录非法或仓库状态不可用）。MUST NOT 出现第四种退出码，也 MUST NOT 用 `1` 表示不可评估或反之。

  「带理由跳过」是合法裁决——不构成缺口、回执命令退出码仍为 0——但 MUST NOT 计为覆盖信用（裁决推导见上段）。跳过理由的取值封闭为五种：`non-code-file`、`generated`、`binary`、`out-of-scope-per-explicit-user-ruling`、`size-guard-focus-not-reviewed`；除此之外的理由（含自由文本）MUST NOT 被接受为合法跳过，MUST 按覆盖缺口处理（退出码 1）。回执 MUST 单列缺口计数与跳过计数，使上述判定可机械复核而不依赖人工阅读。

  回执 MUST 以代码段记录内的一段定界、机器可读字段块为载体（字段名=值逐行），由技能既有脚本产出并可被契约测试直接解析；MUST NOT 另建第二个产物文件。回执里的「覆盖率」恒指「已评审文件占变更文件集的比例」，MUST NOT 被读作测试覆盖率或编译覆盖率——本特性禁止复用的判定对象是后者（FR-027）。
- **FR-015**: "已读全 diff" 的唯一证据形态 MUST 是该覆盖率回执；MUST NOT 以"看过 diff 概览"、"读过变更文件列表"、"变更行数不大"替代，也 MUST NOT 以工具输出存在本身推定评审已完成。

#### feedback 流程优化与不变量

- **FR-016**: review 单元的收尾步骤集合 MUST 与整合前一致（运行判定、执行量化、反馈记录、阈值提示、token 反思、文档同步评估）；本特性 MUST NOT 新增收尾步骤，MUST NOT 在该链路上新增旁路或第二套记录。
- **FR-017**: 写入反馈库的观察 MUST 仅限框架自身摩擦（例如渲染器缺失、基准歧义、回执缺口、非交互路径不足）；代码段的代码缺陷 MUST NOT 作为反馈条目投递——它留在代码段记录里。
- **FR-018**: 嵌套执行时，每次运行的单元普查 MUST 为三个：命令单元 `/speckit.review`、被委派的过程技能单元 `skill:review-sdd-process`、被委派的代码技能单元 `skill:code-review`。命令与每一个被委派的技能 MUST 各自完成自己的收尾记录；命令 MUST NOT 抑制任何技能的收尾，也 MUST NOT 代为补记它的运行判定。本条 MUST NOT 被读作「本次运行只产生两条记录」——命令侧只多出自己那一条，两个被委派技能各自的记录既不合并也不省略。
- **FR-019**: 两段结论 MUST 同时出现在两个可核验载体上：该次运行的过程报告代码段小节（FR-011）与绑定特性详情的 `## Latest Review` 评审记录条目（FR-012），使读者只需打开过程报告一份文件就能知道代码段是否给出结论。「收尾摘要」（控制台与 handoff 的面向人输出）MAY 复述这两处内容，但它是呈现而不是制品：本特性 MUST NOT 把它当作第三份可核验载体，也 MUST NOT 为它设置独立的内容义务；其内容与上述两处不一致时，以上述两处为准。
- **FR-020**: 既有治理机制 MUST 原样保留：建议编号在同一提交内登记进项目登记表；全局建议的合法入口仍是反馈命令的自省步骤；零自动传输、反馈用户可选、单条条目归属单一单元的规则不变。本特性 MUST NOT 新增 intake 存储、第二套反馈聚合或任何上传路径。

#### code-review 技能自身的优化范围

- **FR-021**: 技能 MUST 提供一条完全非交互的评审路径，其步骤枚举封闭为四步，每步各由确定性子命令承担：基准解析、记录创建与轮转、意见落盘、回执与汇总裁决。MUST NOT 要求调用方应答交互提示、自造 TTY 或手写记录文件才能走完评审；该枚举 MUST NOT 被读作三步——第二次运行起「记录创建与轮转」是必经一步（见 FR-010），省掉它就会在无人值守路径上退化成代理代替脚本写记录。
- **FR-022**: 基准解析规则 MUST 由技能的确定性脚本实现并可由参数覆盖，MUST NOT 交由提示词现场判断；同一仓库状态 MUST 解析出同一基准。
- **FR-023**: 合入门禁判决 MUST 继续由技能的确定性脚本产出；整合后 MUST 只有一个判决来源，命令 MUST 复用该判决，MUST NOT 重算第二套判据。判决 MUST 以显式记录文件为输入（指向该次代码段的 [[STR-004]]），MUST NOT 依赖「目录内最新文件」一类的隐式选取——同一特性目录内同时存在 `review.md` 与 [[STR-004]]，隐式选取会把过程报告当作代码段记录、在没有 `blocking` 行时给出假通过。
- **FR-024**: 技能的交互式人类路径 MUST 保留：渲染模式的选择规则沿用 FR-013（本条不另写第二份规则），逐文件审查流程与既有严重度校验行为 MUST NOT 退化。
- **FR-025**: 技能与其姊妹评审技能的边界 MUST 在文档层面可判定：两者各自声明自己的判定对象与"由命令组合"的关系，MUST NOT 保留"两者互不相关"的表述（在该命令同时调用两者之后该表述为假）。
- **FR-026**: 技能新增的确定性能力（基准解析、覆盖率回执）MUST 落在该技能既有的脚本实体上；MUST NOT 新增引擎、常驻进程、外部服务或新依赖。

#### 测试与文档同步面

- **FR-027**: 既有契约断言 MUST NOT 被删除、弱化或使其语义漂移：表达类交付物的评审面仍按声明的读者基准判定，MUST NOT 复用代码评审的判定对象（编译、测试、覆盖率）。代码段 MUST 作为附加段存在——表达类特性无代码 delta 时记 [[STR-001]]，MUST NOT 反向替代或短路读者基准判定。

  恰好一个既有断言变更被授权：`tests/contract/test_review_p1_review_loop.py` 中 `test_c15_review_owns_the_ready_for_review_transition` 可在同一提交内被重写为「断言该转换行存在、断言该行引用状态机 owner 路径（`templates/feature-details-template.md` § Canonical Status State Machine）、断言被收敛掉的重复措辞已消失」，且 MUST 净增断言数——它必须保住原有主体（命令拥有该转换）并新增两条以上断言。其理由 MUST 在该特性详情的评审记录条目中声明。该授权是封闭的单点例外：其余任何既有断言 MUST NOT 被删除或弱化，MUST NOT 被援引为本条的类推依据。
- **FR-028**: 新增行为 MUST 有确定性契约测试覆盖，六项各成一组：命令模板的两段与固定顺序、代码段适用性的三种取值、状态机门禁条件、回执缺口的非零退出、基准解析规则、文档与模板的同构。

  红先行 MUST 是这六组每一组的义务：每组 MUST 在其守护的机制存在之前运行一次并记录失败（命令行、退出码、失败计数），该记录 MUST 可被复核；一组在被其守护的对象被破坏时不会变红的检查 MUST NOT 被计为覆盖，MUST 就地报告为缺口而不是记为绿。

  镜像判定 MUST 是相对判据：编辑前 MUST 先测量每个触碰对的漂移基线，编辑后 MUST 断言「无 NEW drift」；逐对基线表与生成器归属由 `plan.md` § Mirror Obligations 拥有，本条不复制该表，只规定判据形态。

  文档同步 MUST 覆盖命令参考页、两个技能的边界文案与状态机 owner 的门禁条件；框架源是唯一编辑面，运行时投影 MUST 经既有再生成与镜像同步脚本产出，MUST NOT 手改运行时副本。

### Key Entities

- **评审运行（review run）**: 一次命令调用，包含两个串行段、两份可核验产物（过程报告与代码段记录）与一个面向人的收尾摘要；其单元归属决定收尾记录的归属（单元普查见 FR-018）。
- **过程段（process segment）**: 判定对象是产生该特性的 SDD 过程与制品链，产出过程报告；严重度词汇 P0/P1/P2 由该段 owner 定义。
- **代码段（code segment）**: 判定对象是本特性切片的已提交代码 delta 中的可验证缺陷，产出代码段记录；严重度词汇为六级封闭集，由技能定义。
- **覆盖率回执（coverage receipt）**: 一次代码段的证据凭据，字段含基准与目标提交标识、基准来源、渲染模式、变更文件集与逐文件裁决、变更与删除行数、缺口计数与跳过计数；以代码段记录内的定界机器可读字段块为载体；是"已读全 diff"的唯一证据形态，也是四项回执计数的唯一数值来源（FR-011 的三处披露一律抄自它）。其中的「覆盖率」指已评审文件占变更文件集的比例，与测试覆盖率、编译覆盖率无关。
- **段裁决（segment verdict）**: 封闭取值为四个字面量——[[STR-006]]（通过）、[[STR-007]]（存在阻断条目）、[[STR-001]]（不适用）、[[STR-002]]（不可评估）；不接受第五个值，也不接受静默缺省。
- **特性切片区间（feature-slice range）**: `base..head`——base 由特性制品的首次提交推导（FR-004 的三档解析），head 在运行开始时解析一次并在该次运行内固定；区间 MAY 包含与本特性无关的提交，严格切片由调用方显式传 head。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在一个有已提交代码 delta 的特性上运行一次 `/speckit.review`，同一份过程报告内可同时读到过程段按严重度的计数与代码段裁决与回执计数，且绑定特性详情的评审记录条目引用同一份记录——判定只需打开那份过程报告，人工核对一次运行即可确认。
- **SC-002**: 代码段回执的文件集与该次 delta 的变更文件集相等；人为删去任一文件的裁决后重跑，回执命令以退出码 1 报出缺口（先红后绿可复现）；聚焦审查留下带理由跳过时，回执单列跳过计数且段裁决不是 [[STR-006]]；把跳过理由换成五种法定理由之外的值时，回执按缺口以退出码 1 报出——四者都由确定性检查报出，不依赖人工阅读。
- **SC-003**: 在渲染器不可用的环境运行同一特性，代码段仍产出回执与裁决，记录中出现文本模式标记 [[STR-003]]，且全文不出现下列任一禁用表述：`已完成可视化评审`、`rendered review complete`、`visual review performed`、`side-by-side review done`。该清单是闭合的：新增一类表述须先改本条，测试按这四条逐条检索而不是按「渲染」「review」等宽词匹配。
- **SC-004**: 当前代码段记录含至少一个 `blocking` 条目时，`Implemented → Ready for Review` 转换被拒绝并给出阻塞依据；随后重跑一次代码段、产出一份 `blocking` 计数为 0 的新记录后，同一转换通过——两次判定都只读当前记录。两次结果都由确定性检查报出，不依赖人工阅读。
- **SC-005**: 在一个无代码产出的特性上运行 review（按 FR-003 的代码路径谓词判定：已提交 delta 中不含任何代码路径文件），代码段记为 [[STR-001]] 且不创建 [[STR-004]]，既有读者基准评审结论保持不变，既有表达类评审面契约测试保持通过。
- **SC-006**: 新增的确定性契约测试覆盖 FR-028 列出的六项行为，且六组各有一次记录在案的失败运行（红先行：命令行、退出码、失败计数留痕）；全量套件按名称与 implement 起点基线逐条比对，新增失败数为零。
- **SC-007**: 把一条代码缺陷当作反馈条目投递的构造样例被判为违规（分类义务在命令模板与技能文案中可检出），而框架摩擦样例正常入账。

### Measurement Sources & Collection Methods

- **SC-001 Source**: 该次运行产出的过程报告与代码段记录（特性目录内），人工核对一次；计数取自报告内的段裁决与回执字段，不另行采集。特性详情一侧只需确认其评审记录条目引用同一份记录，不重复比对数值。
- **SC-002 Source**: 覆盖率回执命令的退出码与回执内容；先移除一条裁决制造缺口，再复原；把跳过理由替换为法定集之外的值再测一次；聚焦场景由同一回执的跳过计数与段裁决字段读取，不另行采集。
- **SC-003 Source**: 代码段记录正文，按 SC-003 的禁用表述清单逐条检索（四条各检索一次），在渲染器被移出 PATH 的环境中取得。

- **A1（脚手架偏离）**: 规格编号由项目既有脚手架脚本派生（脚本输出 `071-review-code-integration`），但该脚本的「创建并切换分支」动作被主动抑制——无人值守阶段规则禁止阶段子代理在工作区内切换分支，本线工作继续落在状态脊声明的分支上。规格目录与初始文件仍由该脚本产出，编号未手写。
