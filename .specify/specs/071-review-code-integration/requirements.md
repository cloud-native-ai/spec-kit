## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一次 review 同时得到过程结论与代码结论 (Priority: P1)

维护者在无人值守特性流程的末尾运行一次 `/speckit.review`，无需再单独调用任何别的命令，就同时拿到两类结论：这段 SDD 过程哪里卡住（过程评审），以及这个特性交付的代码差异有哪些可验证缺陷（代码评审）。两份结论各自成文、各自定级，互不冒充。

**Why this priority**: 这是用户诉求的字面内容，也是当前最大的入口缺口——代码评审技能已经存在却没有任何命令引用它，维护者跑完实现后拿不到代码 diff 的评审结论。

**Independent Test**: 在一个有已提交代码 delta 的特性上运行 `/speckit.review`，检查特性目录同时出现过程报告与代码段记录，且收尾摘要同时给出两段结论；再在一个无代码产出的特性上运行同一命令，检查代码段被如实记为不适用而不是静默消失。

**Acceptance Scenarios**:

1. **Given** 一个已提交代码 delta 的特性目录，**When** 运行 `/speckit.review`，**Then** 过程段先执行、代码段后执行，特性目录出现过程报告与代码段记录两份产物，收尾摘要同时列出过程段的严重度计数与代码段的裁决。
2. **Given** 一次 review 运行，**When** 阅读过程报告，**Then** 过程报告只承载过程段的结论，代码段结论以「小节 + 裁决 + 指向代码段记录的路径」出现，不复制代码段的意见正文。
3. **Given** 过程段与代码段同时有结论，**When** 有人试图把两套严重度合成一个评分或一张表，**Then** 该行为被判为违反规格（两套词汇各自保留其 owner）。

---

### User Story 2 - 代码评审的对象与基准可判定、可复算 (Priority: P1)

评审人与后来的读者都能回答"到底审的是哪一段代码"：基准来自特性切片本身而不是某个硬编码的分支名；工作树里没有提交的改动不会被悄悄算进已评审范围；基准无法确定时明确记为不可评估，而不是猜一个。

**Why this priority**: 基线口径错误会让整份代码评审结论失去意义（审了不该审的、或漏审了真正的交付面），而且在无人值守场景里没人会在旁边纠正。

**Independent Test**: 对同一特性用不同显式基准各跑一次代码段，回执中的基准与目标提交标识与实际 git 引用一致；在基准不可解析的构造场景下运行，得到不可评估结论与可复现命令，而不是一个猜测的基准。

**Acceptance Scenarios**:

1. **Given** 一个特性的 spec 目录已有首次提交，**When** 代码段解析基准且调用方未显式指定，**Then** 基准取该首次提交的父提交，回执记录的基线与目标可被 `git diff` 复算。
2. **Given** 工作树存在未提交改动，**When** 运行代码段，**Then** 这些改动不计入默认评审对象，报告显式披露"存在未评审的未提交范围"，且不得对未评审内容给出通过结论。
3. **Given** 显式基准与自动基准同时可用，**When** 运行代码段，**Then** 显式基准优先，报告记录实际采用的基准及来源。

---

### User Story 3 - 缺渲染器时不冒充已评审 (Priority: P2)

在没有 `delta` 的环境里，代码段仍然产出可信的结论：它改用纯文本读取全量 diff，并在记录里标注渲染模式；如果它没有把所有变更文件逐一看过并留下裁决，它给不出"通过"。

**Why this priority**: 现状是渲染器缺失即停，这让命令在多数无人值守环境里根本跑不完；但反过来"缺工具就裸看几眼然后说审过了"更糟。真正要守住的是**不冒充**，而不是**必须用某个工具**。

**Independent Test**: 在 `delta` 不在 PATH 的环境运行代码段，得到带文本渲染标记的记录与完整覆盖率回执；人为漏掉一个变更文件的裁决，回执命令以非零退出码报出缺口。

**Acceptance Scenarios**:

1. **Given** `delta` 不可用，**When** 运行代码段，**Then** 代码段完成并记录渲染模式为文本模式，且记录中不出现"已完成可视化评审"一类表述。
2. **Given** 变更文件集中有一个文件没有任何裁决，**When** 生成覆盖率回执，**Then** 回执命令以非零退出码报出缺口，代码段裁决不得为通过。
3. **Given** 变更文件集与回执文件集相等且每个文件都有裁决，**When** 生成回执，**Then** 回执以零退出码通过并给出计数。

---

### User Story 4 - 两套严重度各有其位，门禁关系单一可判定 (Priority: P2)

维护者知道一条 `blocking` 意见到底意味着什么：代码段存在未清除的 `blocking` 时，特性不能从 Implemented 前进到 Ready for Review；过程段继续用它自己的 P0/P1/P2。两者之间没有换算表，只有一条被明确声明、写在状态机 owner 里的门禁关系。

**Why this priority**: 严重度混用是本次整合最容易产生的语义污染；把门禁关系钉在一个 owner 上，后续才不会被两处写法分裂。

**Independent Test**: 构造一次代码段存在未清除 `blocking` 的 review，检查特性状态转换被拒绝；清除后转换通过。检查 owner 文档与命令模板里的门禁条件表述同源。

**Acceptance Scenarios**:

1. **Given** 代码段记录存在未清除的 `blocking` 条目，**When** 尝试把特性推进到 Ready for Review，**Then** 转换被拒绝并给出阻塞依据。
2. **Given** 代码段只剩 `important` 及以下条目，**When** 尝试推进，**Then** 转换允许，且 `important` 条目被要求逐条回应。
3. **Given** 有人请求把代码段六级词汇重标为 P0/P1/P2，**When** 评审该变更，**Then** 该请求按规格被拒绝（词汇各自保留其 owner）。

---

### User Story 5 - review 与 feedback 的通道不再互相污染 (Priority: P2)

维护者跑完 review 后，反馈库里出现的是**框架自身的摩擦**（例如渲染器缺失、基准歧义、回执缺口），而不是这个特性代码里的缺陷；同时既有的建议登记义务与自省入口照旧工作，仍然没有任何自动传输。

**Why this priority**: 整合后两条通道会在同一次运行里同时活跃，污染风险从理论变成默认路径；而 feedback 的目标红线是机制层面的不变量，退回一次就很难再收回来。

**Independent Test**: 构造一次 review，其中代码段发现若干代码缺陷、同时暴露出一个环境摩擦，检查反馈条目只包含后者；检查建议编号登记与自省入口仍可用。

**Acceptance Scenarios**:

1. **Given** 一次 review 同时产生代码缺陷与框架摩擦，**When** 检查反馈条目，**Then** 只有框架摩擦进入反馈库，代码缺陷留在代码段记录里。
2. **Given** 一次 review 产出了建议编号，**When** 查看提交，**Then** 每个建议编号在同一提交内登记进项目登记表。
3. **Given** 一次 review 运行，**When** 检查收尾步骤，**Then** 命令的收尾步骤集合与整合前一致，没有新增步骤，也没有自动传输路径。

---

### Edge Cases

- **特性没有代码产出**（例如文档型 / 表达类特性）：代码段必须记为不适用并写明依据，过程段的读者基准评审结论不受影响。
- **特性尚未提交，代码只在工作树里**：默认对象为空，代码段记为不适用并披露未提交范围；不得把工作树当作已提交切片来给结论。
- **特性首次提交缺失且主干基准不可解析**：记为不可评估，附可复现命令，不猜基准。
- **仓库主干叫 `master` 而不是 `main`**，或仓库没有 `main`：命令不得依赖脚本的默认基准，基准解析规则必须自足。
- **`delta` 存在但逐文件流程需要交互输入**：agent 路径必须能完全非交互走完；人类交互路径保留。
- **diff 规模超过体量守门阈值**：先提示拆分，再按模块聚焦；聚焦后覆盖率回执仍必须覆盖全部变更文件，未聚焦到的文件记为带理由的跳过——该跳过不构成回执缺口，但按 FR-014 不得计为覆盖信用，因此聚焦审查后的段裁决不得为「通过」，收尾摘要必须单列跳过计数。
- **同一次 review 被重跑**：代码段记录按运行时间戳各自成文件，不覆盖上一份（落盘形态见 FR-010：上一份归档为同目录的归档件，[[STR-004]] 始终指向最近一次运行）；过程报告的重跑按既有产物链规则处理。
- **代码段存在 `blocking` 但用户明确要求先合入**：只接受显式用户裁定的豁免，且必须写进评审报告与特性详情；代理不得自行降级。
- **review 在 `/speckit.implement` 之前运行**：过程段照既有前置要求处理，代码段对象可能为空，必须如实记为不适用而不是给出通过。
- **两段同时缺环境或缺对象**：两份结论都记为不可评估或不适用，收尾摘要必须让读者一眼看出"这次没有评审结论"，不得呈现为通过。
- **过程段中止或报错**：代码段照常执行，两段结论各自呈现；过程段自身记为不可评估并写明原因，命令不得因此把整体呈现为已完成评审（见 FR-002）。

## Requirements *(mandatory)*

### Functional Requirements

#### 编排形态（命令如何组合两段）

- **FR-001**: `/speckit.review` MUST 以固定顺序串行执行两段——过程段（委派 `review-sdd-process`）在前、代码段（委派 `code-review`）在后——且 MUST NOT 把两段的结论合并成单一严重度体系或单一评分。
- **FR-002**: 过程段 MUST 无条件执行，MUST NOT 被特性分类、命令参数或缺代码 delta 免除；两段 MUST 各自委派到既有技能，命令模板 MUST NOT 内联任一技能的方法论正文。过程段自身中止或报错 MUST NOT 抑制代码段执行——代码段的判定对象与过程段的前置条件无关；此时过程段自身记为「不可评估」并写明原因，两段结论各自独立呈现，命令 MUST NOT 因一段未完成而把整体呈现为已完成评审。
- **FR-003**: 命令 MUST 在代码段开跑前解析并记录代码段的适用性，取值封闭为三种：存在本特性已提交代码 delta 则运行；无代码产出或无已提交 delta 则记 [[STR-001]] 并写明依据；环境不满足则记 [[STR-002]] 并写明原因。这三种取值之外 MUST NOT 出现静默跳过。

#### 评审对象与 diff 基准

- **FR-004**: 代码段的评审对象 MUST 是本特性切片的已提交代码 delta；基准解析顺序 MUST 为：调用方显式指定 > 本特性 `requirements.md` 首次提交的父提交 > 与仓库默认主干的合并基点；三者皆不可得时按 FR-006 处理。命令 MUST NOT 依赖脚本内置的分支名默认值。
- **FR-005**: 工作树未提交改动 MUST NOT 计入默认评审对象；存在未提交改动时报告 MUST 显式披露未评审范围，且 MUST NOT 对该范围给出任何通过结论。
- **FR-006**: 基准解析失败 MUST 记为 [[STR-002]] 并附可复现命令与失败原因；MUST NOT 退回猜测的基准，也 MUST NOT 以"看起来差不多的提交"代替。

#### 严重度与门禁关系

- **FR-007**: 两套严重度词汇 MUST 各自保留其 owner 与形态：过程段沿用 P0/P1/P2 且本特性 MUST NOT 改动其判定；代码段沿用六级词汇且 MUST NOT 被重标为 P0/P1/P2。本特性 MUST NOT 引入任何数值换算表、映射矩阵或统一评分。
- **FR-008**: 代码段存在未清除的 `blocking` 条目时 MUST 阻断 `Implemented → Ready for Review` 状态转换；存在 `important` 条目时 MUST 允许转换但要求逐条回应；其余四级 MUST NOT 阻断。该门禁条件的规范语句 MUST 由状态机 owner 承载——`templates/feature-details-template.md` § Canonical Status State Machine 的 `Implemented → Ready for Review` 行（该节自称权威转换表）——命令模板与技能 MUST 引用它而不是复制判据；特性集成协议里同一转换的摘要行 MUST 收敛为对该 owner 的引用，MUST NOT 保留第二份判据措辞。该门禁是**转换自身的属性**，不是某一个命令的属性：凡发起该转换的路径（含 `/speckit.checklist` 的同名转换行）MUST 引用同一 owner 判据，MUST NOT 各自另写一份；owner 行 MUST 在同一行内同时承载「延迟项已解决或已豁免 + 评审证据已产出 + 代码段无未清除的 `blocking`」三项，且判定 MUST 直接读代码段的六级词汇，MUST NOT 先把它重标为 P0/P1/P2 再判定。
- **FR-009**: 门禁豁免 MUST 只来自显式用户裁定；豁免事实 MUST 写入评审报告与特性详情。代理 MUST NOT 自行把 `blocking` 降级、合并或在门禁判定中排除。

#### 产物落点与形态

- **FR-010**: 过程报告 MUST 保持写入特性目录下的 `review.md`，结构由既有评审报告模板决定；代码段记录 MUST 写成特性目录内的独立文件 [[STR-004]]，两份产物 MUST NOT 相互覆盖，MUST NOT 共用同一份严重度汇总表。同一特性被重跑时，上一份代码段记录 MUST 先归档为同目录内的归档件（[[STR-004]] 去扩展名 + `-<运行时间戳>.md`），再写入新的 [[STR-004]]——因此 [[STR-004]] 恒指最近一次运行，历史运行一件一档、互不覆盖；过程报告 MUST 记录本次实际写入的路径以及本次产生的归档件路径。
- **FR-011**: 过程报告 MUST 含一个代码段小节，只承载：基准与目标的提交标识、渲染模式、覆盖率回执计数（含缺口计数与跳过计数）、段裁决（取值见 Key Entities 的封闭集）、门禁裁决、[[STR-001]] 或 [[STR-002]] 的原因、指向 [[STR-004]] 的路径与本次归档件路径；MUST NOT 复制代码段的意见正文或逐条重复其计数。
- **FR-012**: 代码段记录 [[STR-004]] MUST NOT 进入下游文档可用清单，MUST NOT 被当作 plan 与 tasks 的输入；它 MUST 被特性详情的评审记录行引用，使读者从特性侧可达。

#### 证据形态（"已读全 diff"）

- **FR-013**: 渲染器（`delta`）不可用 MUST NOT 阻断代码段；此时记录 MUST 标注渲染模式为 [[STR-003]]（文本模式），且 MUST NOT 出现任何声称做过渲染式可视化评审的表述。渲染器可用时 MUST 默认使用渲染模式。既有「渲染器缺失即停」条款 MUST 以「替代并说明理由」的形态改写，MUST NOT 以删除条款的方式弱化约束：技能正文 MUST 保留一条陈述「被替代的条款、其替代证据形态（覆盖率回执）与替代理由」的说明；同源措辞（Strict Requirements、Phase 0 环境确认步骤与 `references/` 内的说明）MUST 一并改写，MUST NOT 残留「缺失即停」的断言。
- **FR-014**: 代码段 MUST 产出一份覆盖率回执，其文件集 MUST 等于该次 delta 的变更文件集，逐文件带裁决（已评审 / 带理由跳过）；任一份文件无裁决或文件集不等时，代码段 MUST NOT 给出通过结论，且生成回执的确定性命令 MUST 以非零退出码报出缺口。「带理由跳过」是合法裁决——不构成缺口、回执命令退出码为 0——但 MUST NOT 计为覆盖信用：跳过计数大于 0 时，段裁决 MUST NOT 为「通过」，只能为「存在未清除阻断」（有未清除 `blocking` 时）或「不可评估」（其余情形）；回执 MUST 单列跳过计数，使该判定可机械复核而不依赖人工阅读。回执 MUST 以代码段记录内的一段定界、机器可读字段块为载体（字段名=值逐行），由技能既有脚本产出并可被契约测试直接解析；MUST NOT 另建第二个产物文件。
- **FR-015**: "已读全 diff" 的唯一证据形态 MUST 是该覆盖率回执；MUST NOT 以"看过 diff 概览"、"读过变更文件列表"、"变更行数不大"替代，也 MUST NOT 以工具输出存在本身推定评审已完成。

#### feedback 流程优化与不变量

- **FR-016**: review 单元的收尾步骤集合 MUST 与整合前一致（运行判定、执行量化、反馈记录、阈值提示、token 反思、文档同步评估）；本特性 MUST NOT 新增收尾步骤，MUST NOT 在该链路上新增旁路或第二套记录。
- **FR-017**: 写入反馈库的观察 MUST 仅限框架自身摩擦（例如渲染器缺失、基准歧义、回执缺口、非交互路径不足）；代码段的代码缺陷 MUST NOT 作为反馈条目投递——它留在代码段记录里。
- **FR-018**: 嵌套执行时，命令与技能两个单元 MUST 各自完成自己的收尾记录；命令 MUST NOT 抑制技能的收尾，也 MUST NOT 代为补记它的运行判定。
- **FR-019**: 收尾摘要与特性详情 MUST 同时呈现两段结论（过程段按严重度的计数 + 代码段裁决与回执计数），使读者无需打开第二个文件即可知道代码段是否给出结论。
- **FR-020**: 既有治理机制 MUST 原样保留：建议编号在同一提交内登记进项目登记表；全局建议的合法入口仍是反馈命令的自省步骤；零自动传输、反馈用户可选、单条条目归属单一单元的规则不变。本特性 MUST NOT 新增 intake 存储、第二套反馈聚合或任何上传路径。

#### code-review 技能自身的优化范围

- **FR-021**: 技能 MUST 提供一条完全非交互的评审路径（回执 + 意见落盘 + 汇总裁决），MUST NOT 要求调用方应答交互提示才能走完评审。
- **FR-022**: 基准解析规则 MUST 由技能的确定性脚本实现并可由参数覆盖，MUST NOT 交由提示词现场判断；同一仓库状态 MUST 解析出同一基准。
- **FR-023**: 合入门禁判决 MUST 继续由技能的确定性脚本产出；整合后 MUST 只有一个判决来源，命令 MUST 复用该判决，MUST NOT 重算第二套判据。判决 MUST 以显式记录文件为输入（指向该次代码段的 [[STR-004]]），MUST NOT 依赖「目录内最新文件」一类的隐式选取——同一特性目录内同时存在 `review.md` 与 [[STR-004]]，隐式选取会把过程报告当作代码段记录、在没有 `blocking` 行时给出假通过。
- **FR-024**: 技能的交互式人类路径 MUST 保留：渲染器可用时默认渲染、逐文件审查流程与既有严重度校验行为 MUST NOT 退化。
- **FR-025**: 技能与其姊妹评审技能的边界 MUST 在文档层面可判定：两者各自声明自己的判定对象与"由命令组合"的关系，MUST NOT 保留"两者互不相关"的表述（在该命令同时调用两者之后该表述为假）。
- **FR-026**: 技能新增的确定性能力（基准解析、覆盖率回执）MUST 落在该技能既有的脚本实体上；MUST NOT 新增引擎、常驻进程、外部服务或新依赖。

#### 测试与文档同步面

- **FR-027**: 既有契约断言 MUST NOT 被删除、弱化或使其语义漂移：表达类交付物的评审面仍按声明的读者基准判定，MUST NOT 复用代码评审的判定对象（编译、测试、覆盖率）。代码段 MUST 作为附加段存在——表达类特性无代码 delta 时记 [[STR-001]]，MUST NOT 反向替代或短路读者基准判定。
- **FR-028**: 新增行为 MUST 有确定性契约测试覆盖：命令模板的两段与固定顺序、代码段适用性的三种取值、状态机门禁条件、回执缺口的非零退出、基准解析规则、文档与模板的同构。文档同步 MUST 覆盖命令参考页、两个技能的边界文案与状态机 owner 的门禁条件；框架源是唯一编辑面，运行时投影 MUST 经既有再生成与镜像同步脚本产出，MUST NOT 手改运行时副本。

### Key Entities

- **评审运行（review run）**: 一次命令调用，包含两个串行段、两份产物与一个收尾摘要；其单元归属决定收尾记录的归属。
- **过程段（process segment）**: 判定对象是产生该特性的 SDD 过程与制品链，产出过程报告；严重度词汇 P0/P1/P2 由该段 owner 定义。
- **代码段（code segment）**: 判定对象是本特性切片的已提交代码 delta 中的可验证缺陷，产出代码段记录；严重度词汇为六级封闭集，由技能定义。
- **覆盖率回执（coverage receipt）**: 一次代码段的证据凭据，字段含基准与目标提交标识、渲染模式、变更文件集与逐文件裁决、变更与删除行数、缺口计数与跳过计数；以代码段记录内的定界机器可读字段块为载体；是"已读全 diff"的唯一证据形态。
- **段裁决（segment verdict）**: 封闭取值——通过 / 存在未清除阻断 / 不适用 / 不可评估；不接受第五个值，也不接受静默缺省。
- **特性切片基准（feature-slice base）**: 由特性制品的首次提交推导出的 diff 基准，使代码评审对象与 SDD 特性切片对齐。

- Q: 代码段记录的文件命名与重跑语义如何定？FR-010 与 [[STR-004]] 把名字钉为 `code-review.md`，Edge Cases 又要求「重跑各自成文件、不覆盖上一份」，两者在字面上互斥。 → A: **稳定名 + 按运行归档**。[[STR-004]] 恒指最近一次运行；每次运行先把上一份归档为同目录内的「[[STR-004]] 去扩展名 + `-<运行时间戳>.md`」归档件，再写新的 [[STR-004]]。这样字面量保持稳定可引用（契约与文档不必解析时间戳）、历史运行一件一档不丢失、读者路径可预测；代价是每次运行产生两条路径，故 FR-010 与 FR-011 同时要求过程报告记录本次写入路径与归档路径。MUST NOT 直接覆盖上一份，也 MUST NOT 改成只写时间戳文件（那会让 [[STR-004]] 的字面量失效，破坏 Shared Strings 的逐字引用约定）。（FR-010、FR-011、Edge Cases「同一次 review 被重跑」）
- Q: 聚焦审查后「未聚焦到的文件记为带理由的跳过」在裁决语义上算覆盖还是算缺口？FR-014 只把「无裁决」「文件集不等」列为缺口，这样 50 个文件里只审 1 个、其余 49 个带理由跳过后回执仍会退出 0 并可能给出「通过」，与 FR-015 的「已读全 diff」相矛盾。 → A: **跳过是合法裁决但不是覆盖信用**。逐文件裁决仍是二值（已评审 / 带理由跳过），跳过不构成缺口、回执命令退出码为 0；但跳过计数大于 0 时段裁决 MUST NOT 为「通过」——有未清除 `blocking` 时为「存在未清除阻断」，否则为「不可评估」。回执因此必须单列跳过计数，使该判定可机械复核。这样既保住聚焦路径可用（不致让大 diff 永远无法完成评审），又守住「不冒充已读全」。MUST NOT 把跳过并入缺口计数（会让聚焦审查永远红），也 MUST NOT 把跳过计为已评审（那就是冒充）。（FR-014、FR-015、SC-002、Edge Cases「diff 规模超过体量守门阈值」、Key Entities 覆盖率回执）
- Q: 过程段中止或报错时，代码段是否仍执行？命令整体如何呈现？FR-001/FR-002 只规定顺序与「过程段无条件执行」，未规定失败传导。 → A: **不抑制、各自呈现**。过程段中止时代码段照常执行，两段结论各自独立；过程段自身记为「不可评估」并写明原因，收尾摘要不得因此把整体呈现为已完成评审。理由是两段的判定对象不同（过程 vs 代码 delta），且无人值守场景下一次运行应拿到尽可能多的信息；代价是可能出现「一段完成、一段未完成」的部分结论，故 Disclosure 是硬要求而非可选。（FR-002、Edge Cases「过程段中止或报错」）
- Q: 状态转换在何时判定？代码段「不适用」或「不可评估」是否阻断 `Implemented → Ready for Review`？FR-008 只写了 `blocking` 阻断、`important` 不阻断，未覆盖段裁决层面的无结论情形。 → A: **单一检查点、只由 `blocking` 阻断**。转换在两段完成且两份产物落盘之后判定一次（代码段结论是判据之一，故不得在代码段之前翻转状态）；只有「存在未清除阻断」阻止转换，「不适用」与「不可评估」不阻断但 MUST 在过程报告的代码段小节、收尾摘要与特性详情评审记录行同时披露。让「不适用」阻断会直接否掉表达类特性的合法路径（SC-005 与既有 c08 契约的前提）；让「不可评估」阻断则与 FR-006/FR-013 的「环境缺失不得导致不可完成」冲突。拒绝转换时状态保持 `Implemented`，拒因写入过程报告代码段小节与收尾摘要。该门禁是转换自身的属性，故两个发起方（`/speckit.review` 与 `/speckit.checklist` 的同名转换行）引用同一 owner 判据。（FR-008、SC-004）
- Q: 覆盖率回执的载体与封闭字段集如何定，才能被机械判定？Key Entities 只列字段名，未定载体形态与退出码边界。 → A: **记录内定界字段块 + 单一生成命令**。回执是代码段记录内一段定界、机器可读的「字段名=值」逐行块，由技能既有脚本的子命令生成（不新增产物文件、不新增引擎）；字段集封闭为基准与目标提交标识、渲染模式、变更文件集与逐文件裁决、变更与删除行数、缺口计数、跳过计数；退出码语义为「0 = 文件集相等且逐文件均有裁决（含带理由跳过），非零 = 存在缺口」。段裁决不由退出码单独推定，而由「缺口计数 = 0 且跳过计数 = 0 且无未清除 blocking」三者合取得出，因此「通过」不可被任一单独信号冒充。（FR-014、FR-015、FR-022、FR-026、Key Entities 覆盖率回执）
- Q: 复核结论——本批扫描覆盖了哪些区域，哪些点复核后判定无需新增澄清？ → A: 扫描覆盖 dispatch 指定的五个边界与四组冲突面，逐条对 owner 原文核验后**认定不需要新增裁决**的部分如下：(1) FR-008 对 owner 的引证逐字准确——`templates/feature-details-template.md` § Canonical Status State Machine 确实自述「the authoritative transition table cited by…」且确有 `Implemented → Ready for Review` 行（现状文本为「All deferred (`[~]`) tasks are resolved or explicitly waived, and review evidence has been produced.」，尚未含 `blocking` 门禁，故 FR-008 是对该行的扩写要求而非复述）；(2) Q3 声称的「两处措辞不一致」经核实成立——`.specify/shared/workflow/feature-integration.md` § Status State Machine 的同名转换行另有措辞「review.md committed AND every deferred item resolved or waived」，且该表由 063 新增，属既有事实重复，FR-008 的收敛要求因此有据；(3) FR-016–FR-020 与 063 既有治理逐条不冲突——`register.md` 已有 REC-063-01…10 指针行、`shared/workflow/feedback-step.md` 的自省步骤仍写明「review 推荐项的合法入口是 `/speckit.feedback` A3 自省」，零自动传输与 `scope: local` 未变，故 FR-020 只是保留而非改动；(4) FR-018 与 `(unit_id, run_id)` 语义兼容——`run-determination.py` 明写「the key is (unit_id, run_id)」，嵌套执行时命令单元与技能单元 unit_id 不同，共享 run_id 不会互相覆盖或去重（`feedback-step.md` § Dedup guard 按 (unit_id, run_id) 去重），故两单元各自记录可落地；(5) FR-027 与既有契约断言不冲突——`tests/contract/test_expression_gates_doc.py::test_c08_review_judges_reader_baseline_in_analyze_and_review` 断言的是 review 面须判定「读者基准」且「不得复用代码评审的编译/测试/覆盖率对象」，与代码段作为**附加段**并存，无漂移；(6) `flow-class-definitions.md` 台账已有 `skill:code-review` 行为判定行，本特性不改分类口径。另记录本趟扫描的**同趟修正**（exactly-one-reading 的局部修复，非裁决）：FR-011 补入「段裁决」与「跳过计数」字段（FR-019 与 Key Entities 已要求，原文漏列）；FR-013 补入「替代而非删除」的落地形态（Q5 已把该张力写成裁决，但当时未把绑定子句写进需求，属集成未完成）；FR-023 补入「判决以显式记录文件为输入」（同一目录内并存 `review.md` 会使目录内最新文件式的隐式选取把过程报告当代码段记录，产出假通过）。同作者委派门未触发：本份 requirements.md 由上一个独立阶段子代理撰写，属不同作者、跨会话，独立来源已提供该门所需的fresh context，故本趟为直接定向复核并在本节留痕。
