## User Scenarios & Testing *(mandatory)*

### User Story 1 - 对任一流程判定它属于执行还是表达，并得到两个人一致的答案 (Priority: P1)

框架维护者面对一个命令或技能，需要回答一个可复现的问题：它的交付物由机器执行后的行为验收，还是由人阅读后的理解与事实相符验收？答案必须来自唯一的所有者与一张逐流程台账，而不是每个命令文档里的自述；未登记的流程必须按明确的默认处理，且在消费点看得出「这是默认」。

**Why this priority**: 若分类不可复现、无所有者、无台账，它就只是文档里的一个形容词，后续所有「按类选门禁」的机制都建立在流沙上。这是整条轴的地基，也是本切片其余部分的共同前提。

**Independent Test**: 取全部流程单元，由两名独立判定者仅凭所有者判据分类，比对一致率与未分类数；再把一个新加的技能从台账里删掉，确认确定性检查能报出缺口。

**Acceptance Scenarios**:

1. **Given** 所有者文档已声明判据与台账，**When** 两名判定者独立分类同一批流程单元，**Then** 两人结论完全一致，且台账中不存在两类皆属或皆不属的单元。
2. **Given** 新增了一个技能但未登记类别，**When** 运行分类对账检查，**Then** 该技能被报为缺口（而不是被静默当作已分类），且运行任一流程时它在消费点显示为「未声明·按默认」。
3. **Given** 一份 OpenAPI 契约文件与一份 Markdown 架构文档同属某特性的交付物，**When** 判定两者所属流程的类别，**Then** 契约流程判为执行（其验收包含生成物可编译）、架构文档流程判为表达（其验收为读者理解与事实相符），判定理由指向 oracle 而非文件扩展名。

---

### User Story 2 - 文档型特性走完整 SDD，但面对的是文档型门禁，且门禁可测地更少更准 (Priority: P1)

文档型特性的作者仍然走 requirements → clarify → plan → tasks → checklist → analyze → implement → review 全阶段，但每一阶段的判定换成语义上真正能证伪文档的算子：读者与目的、证据等级与 as-of、结构/链接/构建、事实一致性、评审。代码型门禁不被原样搬运；同时给出可测的效率目标（门禁调用次数、人工确认次数、阶段墙钟时长），避免「加了分类、门禁反而更多」。

**Why this priority**: 这是本特性的用户价值所在——分类若不能换来文档型路径的实质改善，就只是命名。它与 US1 共享判据，但可以独立验收：只在文档型特性上跑一遍，就能看出门禁是否换对了算子、是否真的更少更准。

**Independent Test**: 选一个真实文档型特性，开工前冻结三项基线（门禁调用次数、人工确认次数、requirements→analyze 墙钟），收尾逐项对照；同时检查六面门禁是否都在，且 P0/P1 无新增。

**Acceptance Scenarios**:

1. **Given** 一个表达类特性开工，**When** 执行 requirements→review 全流程，**Then** 八个阶段一个不少，且每阶段的门禁算子来自文档型门禁集（读者/证据/结构/事实/评审），不存在整段照搬代码型门禁的阶段。
2. **Given** 同一表达类特性收尾，**When** 对照开工前冻结的三项基线，**Then** 门禁调用次数与人工确认次数各下降至少 30%、requirements→analyze 墙钟下降至少 25%，且 review 的 P0/P1 数不高于基线。
3. **Given** 一份文档的站点构建与链接检查全部通过，**When** 有人据此主张该文档内容正确，**Then** 该主张被拒绝：构建通过只算必要条件，事实正确性须由证据标注与评审证明。
4. **Given** 同一事实在三个文档里各写了一遍，**When** 运行事实一致性检查，**Then** 重复手写被判为缺陷并定位到三处，修复方向是改成对唯一所有者的引用。

### User Story 3 - 分类不能被当作跳过 analyze/review 的开关 (Priority: P2)

流水线使用者在赶工期时最容易产生的读法是「我们是表达类，所以可以轻一点」。框架必须把这条读法挡在机制层面：阶段的完整性与类别无关，任何以类别为由跳过、缩短或改判阶段的请求都被拒绝。升级兼容那一半（未刷新项目零变化、刷新后随框架到达）由 `069b` 承接，不在本切片。

**Why this priority**: 分类天然会被读成「轻通道」；若不先把防滥用写进需求，它会在第一次赶工期时变成绕过门禁的许可证。之所以排在 P2，是因为它是 P1 两条的防御面，不单独交付价值。

**Independent Test**: 构造一个「表达类 + 跳过 analyze」的请求，确认被拒绝；再核对阶段完整性判定是否读取类别（读取即为缺陷）。

**Acceptance Scenarios**:

1. **Given** 有人主张「本特性属表达类，可以不做 analyze/review」，**When** 该请求进入流程，**Then** 该主张被拒绝，analyze 与 review 仍执行。
2. **Given** 一个类别字段被篡改或缺失的流程，**When** 判定某阶段是否发生，**Then** 判据只取既有阶段记录，不取类别。

### Edge Cases

以下只列适用于本切片（分类本体、阶段关系、文档型门禁、首批成员）的边界。混合 oracle 的归属判定见 § Slice Scope 的 Out-of-Slice 表，由 `069b` 承接。

- **一个流程同时产出代码与文档**（如 implement）：按主交付物归类（口径见 SA-9），失败不可逆性只在主交付物并列时作 tie-break，不是第二判别量；其文档产物仍按文档型门禁检查，不因流程类别为执行而降级。
- **契约文件既可读又可编译**（OpenAPI 生成 SDK）：判为执行；其文档可读性要求仍以表达类门禁的读者面补强。
- **同一流程在 A 项目属表达、在 B 项目被当作执行**：框架拥有的流程类别不可被项目覆盖；项目只能为自己新增的流程声明类别——**声明机制不在本切片**（迁移与兼容归 `069b`），本切片不提供项目侧的声明面。
- **新增命令未登记分类**：确定性对账报缺口；运行时按默认类并显式标注，不静默。
- **分类台账与所有者判据冲突**：以判据为准，冲突本身记为缺陷并修复台账。
- **类中立共享技能被用来夹带门禁豁免**：类中立只免除「同类约束」，不免除任何门禁；一旦发现被用于绕过，该登记失效并回到按调用方类别归属。
- **表达类流程没有 wrap-up 面**（如 humanize）：类别读取点必须仍在主干流程内可执行，不得因缺少 wrap-up 而变成不可读——本切片的落点是委派技能的执行体（SA-8），不是命令模板的 wrap-up。
- **两份分类定义并存**（框架源与客户运行时各一份）：以所有者为准，副本必须由生成/刷新产生并带漂移检查；两份的分发机制（父编号 033–035）归 `069b`，本切片只固定「副本不是第二真源」。
- **分类被当作降级默认长期使用**：默认必须可见且计入缺口，不得因为「能跑」而永久停留在默认。

## Requirements *(mandatory)*

### Functional Requirements

#### A. 分类本体与判定（US1）

- **FR-001**: 框架 MUST 把「执行 / 表达」确立为贯穿流程的**一等分类**，取值分别为 `execution`（[[STR-001]]）与 `expression`（[[STR-002]]）；分类 MUST NOT 只以命令文档中的描述性标签存在，MUST 具有一份声明式定义与一张逐流程台账。台账的机器可读类别键 MUST 取带命名空间的 `flow_class`（[[STR-003]]），MUST NOT 以裸取值充当键名。`execution` 与既有 Agent 三层分类法中的 `Agent Execution` 同词异义，消歧 MUST 在所有者 § 命名空间 与 `.specify/memory/glossary.md` 两处显式声明。
- **FR-002**: 分类 MUST 回答且只回答一个问题：该流程**主交付物的验收由什么判定**——由「产物被机器执行/运行后观测到的行为」判定者为 `execution`（[[STR-001]]），由「人阅读后可理解并与外部事实相符」判定者为 `expression`（[[STR-002]]）。主交付物在多交付物下的判定口径见 SA-9：失败不可逆性 MUST NOT 构成第二个判别问题。台账每行 MUST 记录判定依据 `basis`，取值为 `behavior-oracle` / `reader-oracle` / `mixed-oracle`；`mixed-oracle` 行的归属裁决不在本切片（父编号 038 由 `069b` 承接）。
- **FR-003**: 分类判据 MUST NOT 依赖介质（文件扩展名、自然语言种类、是否含代码块、是否由脚本生成）。规范性示例：Markdown 架构文档属表达；须生成并编译 SDK 的 OpenAPI 契约属执行；站点构建通过不改变内容类别的判定。
- **FR-004**: 本分类轴 MUST 与既有复杂度轴（复杂/简单命令，owner：`.specify/shared/workflow/feedback-step.md`）显式声明为**正交**：前者选择门禁算子集，后者决定 wrap-up 面有无；两轴 MUST NOT 互相推导，MUST NOT 合并为一条。
- **FR-005**: 分类 MUST 有且只有一个已声明的所有者（定义 + 台账 + 边界例）；所有消费方 MUST 引用所有者，MUST NOT 复制分类数据；台账与判据冲突时 MUST 以判据为准并记该冲突为缺陷。
- **FR-006**: 判定 MUST 可复现：给定判据与流程描述，两名独立判定者 MUST 得到同一结论（一致率 100%）；不一致 MUST 判为判据缺陷并修正判据，MUST NOT 逐案裁定。「独立」MUST 指不同的人、不同的会话、判定时互不可见（结论分别落盘后比对）；不一致的处置顺序固定为「先修判据、再重判」，修正后 MUST 重新对全部样本判定一次。本条 MUST 可由固定 fixture（≥10 个流程单元，覆盖两类 / 未声明 / 类中立 / 混合 oracle）的机器比对核验（见 SC-001），两人演练为并列的人工证据。
- **FR-007**: 框架内全部流程单元（命令模板与技能）MUST 恰好归入两类之一；未分类数 MUST 为 0，缺口 MUST 由对照流程单元清单的确定性检查报出，MUST NOT 依赖人工阅读清点。
- **FR-008**: 每个流程单元 MUST 恰好属于一类；同时命中两类或两类皆不命中 MUST 判为缺陷。
- **FR-009**: 未声明类别的流程单元（含旧项目自建技能）MUST 按 `execution`（[[STR-001]]）处理，且 MUST 在消费点标注为「未声明·按默认」（[[STR-004]]），MUST NOT 呈现为已判定。「消费点」MUST 指**门禁读取点**，本切片的消费点 = 接线封闭集的入口（W1–W4，见 FR-015）；台账中其余单元尚未接线，其标注义务随接线扩面（`069b` 迁移与分发）。
- **FR-010**: 命令与其委托技能 MUST 同类；例外仅限显式登记的**类中立**共享技能（记忆、反馈、度量等载体），该清单 MUST 封闭，且类中立 MUST NOT 免除任何门禁。
- **FR-011**: 分类所有权 MUST 归框架；客户项目 MUST NOT 覆盖框架流程的类别，MAY 为自己新增流程按同一判据声明类别。客户侧**声明机制**不在本切片（迁移与兼容归 `069b`）；本切片只固定「两份分类定义并存时以所有者为准，副本由生成/刷新产生并带漂移检查」与「框架流程的类别不可被项目覆盖」。

#### B. 分类与阶段、门禁的关系（US1 / US3）

- **FR-012**: 分类 MUST NOT 改变 SDD 阶段集合：两类流程都 MUST 走 requirements → clarify → plan → tasks → checklist → analyze → implement → review（阶段名册的 owner 与引用方式见父 requirements §C 区第 1 条，父编号 018，由 `069b` 承接；本切片只固定「阶段集合不因分类改变」）；无待澄清项时跳过 clarify 属既有规则，不因分类而变。
- **FR-013**: 分类 MUST 只选择**门禁算子集**（用哪种检查证明同一不变量），MUST NOT 减少门禁数量、降低 P0/P1 定义或改变判定阈值。
- **FR-014**: 任何分类 MUST NOT 被用作跳过 analyze 或 review 的开关；两类流程的 analyze 与 review 调用率 MUST 均为 100%。**阶段完整性判定 MUST NOT 读取类别**——「这一阶段是否发生」由既有阶段记录判定，与类别无关；任何以「本流程属表达类」为由跳过、缩短或改判阶段的请求 MUST 被拒绝。
- **FR-015**: 门禁 MUST 在判定之前从唯一所有者读取类别；MUST NOT 依赖命令模板内嵌的标签副本。类别 MUST 在无 wrap-up 面的流程（如 humanize）中同样可读。本条的适用面是**门禁执行面**：本切片的执行面 = 接线封闭集的四个入口（W1–W4），其余单元的读取义务随接线扩面（`069b`）。`/speckit.humanize` 的读取位点在委派技能的 Stage 6 执行体（SA-8）：命令模板只给 owner 指针、不调用脚本，保持 Simple 形态。
- **FR-016**: 类别缺失、损坏或版本不兼容时 MUST 降级为默认类并在消费点标注，MUST NOT 中断流程，MUST NOT 静默切换门禁集。「版本不兼容」以**所有者台账的表头/列集合与解析器期望不符**为判据（不引入 version 字段；版本化属 `069b` 的落地口径）。两个降级标签互斥：所有者可解析但单元未登记 → `source: default` + [[STR-004]] 标记；所有者或引擎不可解析/缺席 → `owner-unavailable`（并保留默认类语义）。「降级不得被当作通过」适用于全部降级路径。
- **FR-017**: 类别变更 MUST 留可审计记录（流程、时间、依据判据、变更前后），且 MUST NOT 静默改变已发布流程的行为；行为改变 MUST 显式写入变更说明。

#### D. 文档型门禁（US2）

- **FR-018**: 表达类流程 MUST 具备一组文档型质量门禁，**本切片恰好六面**：需求清晰度、读者/目的/边界、证据分级与 as-of、结构/链接/构建、事实一致性、评审。六面是**封闭集**（SA-7）：新增面 MUST 由后续特性修订门禁 owner 与本条，MUST NOT 由消费方就地扩面；每面的机器名（face id）由门禁 owner 登记且与面一一对应。
- **FR-019**: 文档型交付物 MUST 声明目标读者与阅读场景；未声明 MUST 判为未完成（阻断），MUST NOT 仅记为警告。「文档型交付物」MUST 指表达类流程产出的、以人阅读验收的 Markdown 产物——规格产物（requirements / plan / tasks / data-model / research / quickstart / feature-ref / contracts / checklists）、技能 `SKILL.md`、命令模板、站点文档；检查器的扫描集合（S1 形式产物 / S2 显式文档）是可枚举子集，**不构成定义**。
- **FR-020**: 每条事实性断言 MUST 标注证据等级（实测 / 推断 / 引用）与 as-of；无标注的事实断言 MUST 不得进入交付，且证据 MUST 可复算（含命令、退出状态或可定位来源）。机械判定面是**三件套成组**：一条断言只要出现等级或 as-of 任一，等级、as-of、来源（`source`）三项 MUST 同时到位；`实测` / `推断` 的 `source` MUST 是可复算的命令或退出状态，`引用` 的 `source` MUST 是引文出处。逐句强制标注被明确排除（`research.md` R7）：未被标注的断言**不构成可援引的事实主张**——这是有意的判定边界，不是遗漏。本条的**对象**是文档断言；`shared/workflow/evidence-step.md` 的机制七态与 `shared/guidelines/single-run-evidence.md` 的运行记录留存 MUST NOT 被本条重定义、收窄或并入。
- **FR-021**: 结构/链接/构建检查通过 MUST 被视为必要条件而非充分条件；MUST NOT 被援引为内容正确性的证据。
- **FR-022**: 同一事实 MUST 只有一个所有者并以引用表达；同一事实在 ≥2 处手写 MUST 判为缺陷，其修复方向 MUST 是改为引用，MUST NOT 是把多处措辞改到一致；派生计数 MUST 由制品导出，MUST NOT 手打。机械检测有**下限**（归一化后完全相等且 ≥24 字符，或相似度 ≥0.90 且 ≥40 字符）：低于下限的真副本按设计不被机械报出——这是已声明的检测下限，不是判据放宽；人评审面仍按本条全量判定。
- **FR-023**: 表达类流程 MUST 保留人工评审门禁，评审 MUST 按声明的读者基准判定，MUST NOT 复用代码评审的判定对象，MUST NOT 由分类免除。评审判定者 MUST 是人工评审者或受其委托的评审代理；判定对象 MUST 是读者理解与事实相符（编译 / 测试 / 覆盖率 MUST NOT 作为该判定对象）。
- **FR-024**: 文档型门禁 MUST 在开工前冻结三项实测基线（门禁调用次数、人工确认次数、requirements→analyze 墙钟时长），收尾 MUST 逐项对照；基线缺失 MUST 判为不可验收。「开工前」MUST 指该特性 `requirements.md` 首次提交的时点（三项共用同一起点，记录 `frozen_commit`）；单阶段人工确认次数 MUST ≤3，超出即判该阶段门禁设计缺陷。
