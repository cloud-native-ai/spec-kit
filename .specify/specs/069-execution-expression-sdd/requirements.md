## Overview

为 Spec Kit 引入一条**贯穿全部流程的一等分类轴**——「执行（`execution`）」与「表达（`expression`）」——并在这条轴上重建文档型开发路径：文档不再是代码流程的附庸，也不再被要求套用为代码设计的门禁；它拥有与代码**同一套 SDD 阶段、同一套方法论骨架**，只在与验收对象直接相关的环节换成文档型的判定算子。

本特性要落三件事，三者互为支撑而非并列口号：

1. **分类本体**：定义「执行/表达」回答的唯一问题、判定判据、唯一所有者、逐流程台账、未声明默认，以及它与框架既有轴的关系。
2. **文档型 SDD**：为表达类流程定义一组文档型质量门禁（读者/目的/边界、证据分级与 as-of、结构/链接/构建、事实一致性、评审），保留全部 SDD 阶段，并把「更少但更准的门禁」写成可测目标。
3. **同构与其边界**：把「代码是以计算机语言写的文档、文档是以人类语言写的代码」落成可核对的阶段映射与一份不可同构边界清单，使它在需求、门禁与模板里可判定，而不停留在比喻。

**判定轴不是介质轴。** 本特性的核心判据是**验收 oracle（由什么判定交付物是否成立）**，而不是文件类型：一份 Markdown 架构文档按「读者理解 + 事实相符」验收，属表达；一份 OpenAPI 契约文件虽然也是文本，但其验收包含「生成的代码能编译通过」，属执行。这条判据同时给出了同构的落点与不可同构的边界。

### 与既有分类轴的关系（互不替代）

框架已有一条**复杂度轴**：命令是复杂命令，当且仅当它调用脚本/CLI 工具、产出被其他流程消费的制品、或消费其他流程的制品（owner：`.specify/shared/workflow/feedback-step.md` 开篇；其简单命令清单由该判据派生）。该轴决定**有没有 wrap-up 面**；本特性的执行/表达轴决定**门禁用哪套判定算子**。两轴正交，实测即可证：按复杂度轴，`/speckit.docs` 是复杂命令（`templates/commands/docs.md` 有 `## Wrap-up`），`/speckit.humanize` 是简单命令（同目录 `humanize.md` 无 `## Wrap-up`）；按本特性，两者同属表达类。因此**复杂度轴不得用于推导类别，类别也不得用于推导是否有 wrap-up 面**。

### Assumptions（本阶段裁决记录；clarify 可推翻）

**clarify 复核（2026-10-24）**：A1–A8 逐条复核，**无推翻项**。A6、A7 各补一条可核验条款（委托关系的机械核验 → FR-039；分发路径 → FR-035）；A1/A2/A3/A4/A5/A8 原文成立。复核结论落 § Clarifications Session 2026-10-24，本条不复述其内容。

- **A1 判据取验收 oracle，不取介质。** 依据：用户把「代码/文档」表述为同一物的两种写法，若按介质分类则同构命题自相矛盾；按 oracle 分类才能同时解释「文档属表达」与「可编译契约属执行」。
- **A2 未声明默认 = `execution`。** 依据：默认必须选**不削弱门禁**的一侧；默认表达会静默减少门禁，默认执行只会多付成本并产生「该归类而未归类」的可见压力。默认必须在消费点标注（FR-009），否则默认变成静默兜底。
- **A3 分类只换算子、不换阶段数与严重级。** 依据：用户明确要求保留 SDD 全阶段且不得降低 P0/P1；若分类能改阶段集合，它立刻成为绕过门禁的开关。
- **A4 表达类的人工评审不可省。** 依据：文档没有语义编译器（边界 (d)），机械检查只能证明结构、不能证明事实；因此评审是表达类的**必需门禁**而非可选步骤。
- **A5 表达类沿用既有读者基准。** 读者判定不复用代码评审对象，而复用 `.specify/shared/guidelines/user-facing-comprehension.md` 已定义的基准读者；本特性不新建第二套读者定义（Principle XIV）。
- **A6 分类覆盖命令与技能两类单元，且命令与其委托技能同类。** 依据：薄命令 + 技能承载是本仓既有形态；只给命令打标签会在委派边界处失去约束。类中立共享技能（记忆/反馈/度量载体）作为封闭例外单列。
- **A7 旧项目不迁移数据、只降级。** 依据：客户项目 `.specify/` 由 init/refresh 安装；要求客户手工维护分类数据的方案必然漂移，未刷新即按默认类运行。
- **A8 本特性不新建命令。** 表达类不是新命令集，而是既有命令在另一条轴上的归类；新增命令属后续特性。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 对任一流程判定它属于执行还是表达，并得到两个人一致的答案 (Priority: P1)

框架维护者面对一个命令或技能，需要回答一个可复现的问题：它的交付物由机器执行后的行为验收，还是由人阅读后的理解与事实相符验收？答案必须来自唯一的所有者与一张逐流程台账，而不是每个命令文档里的自述；未登记的流程必须按明确的默认处理，且在消费点看得出「这是默认」。

**Why this priority**: 若分类不可复现、无所有者、无台账，它就只是文档里的一个形容词，后续所有「按类选门禁」的机制都建立在流沙上。这是整条轴的地基。

**Independent Test**: 取全部流程单元，由两名独立判定者仅凭所有者判据分类，比对一致率与未分类数；再把一个新加的技能从台账里删掉，确认确定性检查能报出缺口。

**Acceptance Scenarios**:

1. **Given** 所有者文档已声明判据与台账，**When** 两名判定者独立分类同一批流程单元，**Then** 两人结论完全一致，且台账中不存在两类皆属或皆不属的单元。
2. **Given** 新增了一个技能但未登记类别，**When** 运行分类对账检查，**Then** 该技能被报为缺口（而不是被静默当作已分类），且运行任一流程时它在消费点显示为「未声明·按默认」。
3. **Given** 一份 OpenAPI 契约文件与一份 Markdown 架构文档同属某特性的交付物，**When** 判定两者所属流程的类别，**Then** 契约流程判为执行（其验收包含生成物可编译）、架构文档流程判为表达（其验收为读者理解与事实相符），判定理由指向 oracle 而非文件扩展名。

### User Story 2 - 文档型特性走完整 SDD，但面对的是文档型门禁，且门禁可测地更少更准 (Priority: P1)

文档型特性的作者仍然走 requirements → clarify → plan → tasks → checklist → analyze → implement → review 全阶段，但每一阶段的判定换成语义上真正能证伪文档的算子：读者与目的、证据等级与 as-of、结构/链接/构建、事实一致性、评审。代码型门禁不被原样搬运；同时给出可测的效率目标（门禁调用次数、人工确认次数、阶段墙钟时长），避免「加了分类、门禁反而更多」。

**Why this priority**: 这是本特性的用户价值所在——分类若不能换来文档型路径的实质改善，就只是命名。它与 US1 共享判据，但可以独立验收：只在文档型特性上跑一遍，就能看出门禁是否换对了算子、是否真的更少更准。

**Independent Test**: 选一个真实文档型特性，开工前冻结三项基线（门禁调用次数、人工确认次数、requirements→analyze 墙钟），收尾逐项对照；同时检查六面门禁是否都在，且 P0/P1 无新增。

**Acceptance Scenarios**:

1. **Given** 一个表达类特性开工，**When** 执行 requirements→review 全流程，**Then** 八个阶段一个不少，且每阶段的门禁算子来自文档型门禁集（读者/证据/结构/事实/评审），不存在整段照搬代码型门禁的阶段。
2. **Given** 同一表达类特性收尾，**When** 对照开工前冻结的三项基线，**Then** 门禁调用次数与人工确认次数各下降至少 30%、requirements→analyze 墙钟下降至少 25%，且 review 的 P0/P1 数不高于基线。
3. **Given** 一份文档的站点构建与链接检查全部通过，**When** 有人据此主张该文档内容正确，**Then** 该主张被拒绝：构建通过只算必要条件，事实正确性须由证据标注与评审证明。
4. **Given** 同一事实在三个文档里各写了一遍，**When** 运行事实一致性检查，**Then** 重复手写被判为缺陷并定位到三处，修复方向是改成对唯一所有者的引用。

### User Story 3 - 我能查到代码与文档在八个阶段上的对应关系，以及它们不可能同构的地方 (Priority: P2)

方法论读者要求「同构」是一个可核对的结构，而不是一句比喻：每个 SDD 阶段都有一行「代码型产物 ↔ 文档型产物」的对应，并标明这一行由哪条门禁强制、或只是已声明未强制；同时有一份不可同构边界清单，说明验收 oracle、验证算子、失败可见性、语义 oracle 四处为什么不能互换。

**Why this priority**: 没有边界的同构主张会立刻被误用——把「文档即代码」当作把测试、编译、覆盖率整套搬到文档上的许可证。它排在 US1/US2 之后，因为映射只有在分类与门禁成立后才有承载物。

**Independent Test**: 逐行检查映射表：每行是否有强制门禁或「未强制」标注；再逐条检查边界清单，确认每条边界都能在至少一处门禁设计中指出对应处理。

**Acceptance Scenarios**:

1. **Given** 同构映射表，**When** 逐行核对，**Then** 每一行都指向一条强制它的门禁，或被显式标注「已声明未强制」，不存在既无强制也无标注的行。
2. **Given** 边界清单，**When** 追问「文档为什么不能只靠构建通过验收」，**Then** 能从边界 (c)(d) 得到确定回答（陈旧事实仍能构建通过；文档无编译器），而不是从原则口号回答。

### User Story 4 - 升级后既有项目行为不变，且分类不能被当作跳过 analyze/review 的开关 (Priority: P2)

既有客户项目在未刷新时行为零变化；刷新后自动获得分类定义与默认行为，不需要手工维护任何分类数据。同时，任何把「我们是表达类」当作轻量通道、跳过 analyze 或 review 的用法都必须被机制挡住。

**Why this priority**: 分类天然会被读成「轻通道」；若不先把防滥用写进需求，它会在第一次赶工期时变成绕过门禁的许可证。兼容性则是框架分发的硬约束。

**Independent Test**: 在三个既有客户项目快照上运行刷新后的命令套件，按名字级基线比对新增失败；再构造一个「表达类 + 跳过 analyze」的请求，确认被拒绝。

**Acceptance Scenarios**:

1. **Given** 一个未刷新的旧项目，**When** 运行任一既有命令，**Then** 行为与分类引入前一致（名字级基线新增失败为 0）。
2. **Given** 一个已刷新的旧项目，**When** 查看任意流程的类别，**Then** 定义与默认行为随框架到达，项目侧无需复制或维护分类数据。
3. **Given** 有人主张「本特性属表达类，可以不做 analyze/review」，**When** 该请求进入流程，**Then** 该主张被拒绝，analyze 与 review 仍执行。

### Edge Cases

- **一份交付物同时有两种读者**（架构文档既被人读，又被脚本解析生成图或代码）：按其主要验收 oracle 归类；若两种 oracle 都是必需的，则该流程 MUST 两类门禁**叠加**而非择优，且叠加后不得减少任一侧门禁。**类别 MUST 取 `execution`**——这是唯一确定性取法，避免同一单元因判定者不同而落到两侧（FR-038、SC-012）。
- **一个流程同时产出代码与文档**（如 implement）：按主交付物与失败不可逆性归类；其文档产物仍按文档型门禁检查，不因流程类别为执行而降级。
- **契约文件既可读又可编译**（OpenAPI 生成 SDK）：判为执行；其文档可读性要求仍以表达类门禁的读者面补强。
- **同一流程在 A 项目属表达、在 B 项目被当作执行**：框架拥有的流程类别不可被项目覆盖；项目只能为自己新增的流程声明类别。
- **新增命令未登记分类**：确定性对账报缺口；运行时按默认类并显式标注，不静默。
- **分类台账与所有者判据冲突**：以判据为准，冲突本身记为缺陷并修复台账。
- **类中立共享技能被用来夹带门禁豁免**：类中立只免除「同类约束」，不免除任何门禁；一旦发现被用于绕过，该登记失效并回到按调用方类别归属。
- **表达类流程没有 wrap-up 面**（如 humanize）：类别读取点必须仍在主干流程内可执行，不得因缺少 wrap-up 而变成不可读。
- **两份分类定义并存**（框架源与客户运行时各一份）：以所有者为准，副本必须由生成/刷新产生并带漂移检查。
- **分类被当作降级默认长期使用**：默认必须可见且计入缺口，不得因为「能跑」而永久停留在默认。

## Requirements *(mandatory)*

### Functional Requirements

#### A. 分类本体与判定（US1）

- **FR-001**: 框架 MUST 把「执行 / 表达」确立为贯穿流程的**一等分类**，取值分别为 `execution`（[[STR-001]]）与 `expression`（[[STR-002]]）；分类 MUST NOT 只以命令文档中的描述性标签存在，MUST 具有一份声明式定义与一张逐流程台账。
- **FR-002**: 分类 MUST 回答且只回答一个问题：该流程**主交付物的验收由什么判定**——由「产物被机器执行/运行后观测到的行为」判定者为 `execution`（[[STR-001]]），由「人阅读后可理解并与外部事实相符」判定者为 `expression`（[[STR-002]]）。多交付物时「主交付物」MUST 取**验收时会被实际运行/观测其行为**的那个产物；两个产物都必须被验收时按 FR-038（混合 oracle 一律取 `execution`）处理。失败不可逆性 MUST NOT 构成第二个判别问题，只在主交付物并列时作 tie-break。台账每行 MUST 记录判定依据 `basis`，取值为 `behavior-oracle` / `reader-oracle` / `mixed-oracle`。
- **FR-003**: 分类判据 MUST NOT 依赖介质（文件扩展名、自然语言种类、是否含代码块、是否由脚本生成）。规范性示例：Markdown 架构文档属表达；须生成并编译 SDK 的 OpenAPI 契约属执行；站点构建通过不改变内容类别的判定。
- **FR-004**: 本分类轴 MUST 与既有复杂度轴（复杂/简单命令，owner：`.specify/shared/workflow/feedback-step.md`）显式声明为**正交**：前者选择门禁算子集，后者决定 wrap-up 面有无；两轴 MUST NOT 互相推导，MUST NOT 合并为一条。
- **FR-005**: 分类 MUST 有且只有一个已声明的所有者（定义 + 台账 + 边界例）；所有消费方 MUST 引用所有者，MUST NOT 复制分类数据；台账与判据冲突时 MUST 以判据为准并记该冲突为缺陷。
- **FR-006**: 判定 MUST 可复现：给定判据与流程描述，两名独立判定者 MUST 得到同一结论（一致率 100%）；不一致 MUST 判为判据缺陷并修正判据，MUST NOT 逐案裁定。「独立」MUST 指不同的人、不同的会话、判定时互不可见（结论分别落盘后比对）；不一致的处置顺序固定为「先修判据、再重判」，修正后 MUST 对全部样本重新判定一次。本条 MUST 可由固定 fixture（≥10 个流程单元，覆盖两类 / 未声明 / 类中立 / 混合 oracle）的机器比对核验，并 MUST 含一条变异断言（故意改错一个单元的类别 → 比对必须转红）；两人演练为**并列**的人工证据，未执行时记 `not-evaluated` + reason。
- **FR-007**: 框架内全部流程单元（命令模板与技能）MUST 恰好归入两类之一；未分类数 MUST 为 0，缺口 MUST 由对照流程单元清单的确定性检查报出，MUST NOT 依赖人工阅读清点。
- **FR-008**: 每个流程单元 MUST 恰好属于一类；同时命中两类或两类皆不命中 MUST 判为缺陷。
- **FR-009**: 未声明类别的流程单元（含旧项目自建技能）MUST 按 `execution`（[[STR-001]]）处理，且 MUST 在消费点标注为「未声明·按默认」（[[STR-004]]），MUST NOT 呈现为已判定。「消费点」MUST 指**门禁读取点**，即接线封闭集中**真正读取类别**的入口；只给 owner 指针的入口与沿用调用方结果的入口 MUST NOT 计入分母。分母也不是台账里全部流程单元的静态总数——未接线单元按默认类运行，其标注义务随接线扩面。
- **FR-010**: 命令与其委托技能 MUST 同类；例外仅限显式登记的**类中立**共享技能（记忆、反馈、度量等载体），该清单 MUST 封闭，且类中立 MUST NOT 免除任何门禁。
- **FR-011**: 分类所有权 MUST 归框架；客户项目 MUST NOT 覆盖框架流程的类别，MAY 为自己新增流程按同一判据声明类别。两份分类定义并存（框架源与客户运行时各一份）时 MUST 以所有者为准，副本 MUST 由生成/刷新产生并带漂移检查，MUST NOT 充当第二真源；「MAY 声明」是允许，不是框架会读取——客户侧**声明机制**落 FR-035 的分发面，本特性不新增项目侧存储或读取点。

#### B. 分类与阶段、门禁的关系（US1 / US4）

- **FR-012**: 分类 MUST NOT 改变 SDD 阶段集合：两类流程都 MUST 走 requirements → clarify → plan → tasks → checklist → analyze → implement → review（阶段名册的 owner 与引用方式见 FR-018）；无待澄清项时跳过 clarify 属既有规则，不因分类而变。
- **FR-013**: 分类 MUST 只选择**门禁算子集**（用哪种检查证明同一不变量），MUST NOT 减少门禁数量、降低 P0/P1 定义或改变判定阈值。
- **FR-014**: 任何分类 MUST NOT 被用作跳过 analyze 或 review 的开关；两类流程的 analyze 与 review 调用率 MUST 均为 100%。**阶段完整性判定 MUST NOT 读取类别**——「这一阶段是否发生」由既有阶段记录判定，与类别无关；任何以「本流程属表达类」为由跳过、缩短或改判阶段的请求 MUST 被拒绝。
- **FR-015**: 门禁 MUST 在判定之前从唯一所有者读取类别；MUST NOT 依赖命令模板内嵌的标签副本。类别 MUST 在无 wrap-up 面的流程（如 humanize）中同样可读。本条的适用面是**门禁执行面**（接线封闭集的入口集合）；其余单元（含尚未接线者）的读取义务随接线扩面，不因本条未接线而失效。`/speckit.humanize` 的读取位点在委派技能的执行体，命令模板只承载 owner 指针（见 FR-030）。
- **FR-016**: 类别缺失、损坏或版本不兼容时 MUST 降级为默认类并在消费点标注，MUST NOT 中断流程，MUST NOT 静默切换门禁集。「版本不兼容」以**所有者台账的表头/列集合与解析器期望不符**为判据（不引入 version 字段）。两个降级标签**互斥**：所有者可解析但单元未登记 → `source: default` + [[STR-004]] 标记；所有者或引擎不可解析/缺席 → `owner-unavailable`（并保留默认类语义）。「降级不得被当作通过」适用于**全部**降级路径。
- **FR-017**: 类别变更 MUST 留可审计记录（流程、时间、依据判据、变更前后），且 MUST NOT 静默改变已发布流程的行为；行为改变 MUST 显式写入变更说明。

#### C. 同构与其边界（US3）

- **FR-018**: 框架 MUST 声明一份**同构映射**：对八个 SDD 阶段各给出一行「代码型产物 ↔ 文档型产物」的对应（8 行 × 3 面列 = 24 格），并覆盖结构、流程、逻辑三个面（结构 = 实体/关系/边界；流程 = 阶段与门禁角色；逻辑 = 证据/契约/验收/版本/所有权）。阶段名册 MUST 引用既有阶段映射 owner（八阶段产物映射，由 `sdd-loop-driver` 的 `loop-state.py` 与同名 reference 章节共同承载，声明见 `.specify/specs/066-loop-state-awareness-a/requirements.md` FR-006），MUST NOT 新建第二份名册；名册变更时映射跟名册走，不另立版本。
- **FR-019**: 同构映射的每一行 MUST 标注它由哪条门禁强制执行，或被显式标注「已声明未强制」；既无强制又无标注的行 MUST 判为缺陷（口号行）。
- **FR-020**: 同构声明 MUST 附带**不可同构边界清单**，至少覆盖四类：(a) 验收 oracle（执行行为 vs 阅读理解）；(b) 验证算子（测试 vs 构建/链接/一致性检查）；(c) 失败可见性（运行期偏差 vs 构建通过而事实陈旧的静默失败）；(d) 语义 oracle 缺失（文档无编译器，意义只能由人判定）。
- **FR-021**: MUST NOT 以「文档即代码」为由把代码型门禁整套移植到文档型流程；跨类复用 MUST 指名所复用的不变量（契约、证据、所有权、版本等），MUST NOT 复用其判定算子本身。
- **FR-022**: 任何「同构」主张 MUST 落到一行可判定映射或一条边界；无法落地的表述 MUST NOT 进入需求、门禁或模板文本。

#### D. 文档型门禁（US2）

- **FR-023**: 表达类流程 MUST 具备一组文档型质量门禁，**恰好六面（封闭集）**：需求清晰度、读者/目的/边界、证据分级与 as-of、结构/链接/构建、事实一致性、评审。新增面 MUST 由后续特性修订门禁 owner（`shared/workflow/expression-gates.md`）与本条，MUST NOT 由消费方就地扩面；每面的机器名（face id）由门禁 owner 登记，且与面一一对应。六面是**表达类流程**的属性，不是单次命令调用的属性：每次调用只执行其调用点行登记的面，MUST NOT 被读成「一次命令调用必须跑满六面」。
- **FR-024**: 文档型交付物 MUST 声明目标读者与阅读场景；未声明 MUST 判为未完成（阻断），MUST NOT 仅记为警告。「文档型交付物」MUST 指表达类流程产出的、以人阅读验收的 Markdown 产物——规格产物（requirements / plan / tasks / data-model / research / quickstart / feature-ref / contracts / checklists）、技能 `SKILL.md`、命令模板、站点文档；检查器的扫描集合（S1 形式产物 / S2 显式文档）是可枚举子集，**不构成定义**。执行取样面当前只覆盖 S2（只给 `--spec-dir` 时 `reader` 面记 `not-applicable`），S1 形式产物的读者声明由评审面（FR-028）判定——这是已声明的执行面差异，不是判据放宽。
- **FR-025**: 每条事实性断言 MUST 标注证据等级（实测 / 推断 / 引用）与 as-of；无标注的事实断言 MUST 不得进入交付，且证据 MUST 可复算（含命令、退出状态或可定位来源）。机械判定面是**三件套成组**：一条断言只要出现等级或 as-of 任一项，等级、as-of、来源（`source`）三项 MUST 同时到位；`实测` / `推断` 的 `source` MUST 是可复算的命令或退出状态，`引用` 的 `source` MUST 是引文出处。逐句强制标注被明确排除：未被标注的断言**不构成可援引的事实主张**——这是有意的判定边界，不是遗漏。本条的**对象**是文档断言；`shared/workflow/evidence-step.md` 的机制七态与 `shared/guidelines/single-run-evidence.md` 的运行记录留存 MUST NOT 被本条重定义、收窄或并入。
- **FR-026**: 结构/链接/构建检查通过 MUST 被视为必要条件而非充分条件；MUST NOT 被援引为内容正确性的证据。
- **FR-027**: 同一事实 MUST 只有一个所有者并以引用表达；同一事实在 ≥2 处手写 MUST 判为缺陷，其修复方向 MUST 是改为引用，MUST NOT 是把多处措辞改到一致；派生计数 MUST 由制品导出，MUST NOT 手打。机械检测有**下限**（归一化后完全相等且 ≥24 字符，或相似度 ≥0.90 且 ≥40 字符）：低于下限的真副本按设计不被机械报出——这是已声明的检测下限，不是判据放宽；人评审面仍按本条全量判定。
- **FR-028**: 表达类流程 MUST 保留人工评审门禁，评审 MUST 按声明的读者基准判定，MUST NOT 复用代码评审的判定对象，MUST NOT 由分类免除。评审判定者 MUST 是人工评审者或受其委托的评审代理；判定对象 MUST 是读者理解与事实相符（编译 / 测试 / 覆盖率 MUST NOT 作为该判定对象）。
- **FR-029**: 文档型门禁 MUST 在开工前冻结三项实测基线（门禁调用次数、人工确认次数、requirements→analyze 墙钟时长），收尾 MUST 逐项对照；基线缺失 MUST 判为不可验收。「开工前」MUST 指该特性 `requirements.md` 首次提交的时点（三项共用同一起点，记录 `frozen_commit`）；单阶段人工确认次数 MUST ≤3，超出即判该阶段门禁设计缺陷。

#### E. 表达类首批成员与既有特性（US2 / US4）

- **FR-030**: `/speckit.docs` 与 `/speckit.humanize` MUST 登记为表达类首批成员；其既有门禁与行为 MUST NOT 被本特性削弱，只允许按 FR-023 补强。补强形态 MUST 保持两入口的既有复杂度类别：`/speckit.docs` 为 Complex（可在命令模板内 lookup）；`/speckit.humanize` 为 **Simple**——命令模板 MUST NOT 调用任何脚本，类别读取与门禁执行落在委派技能的执行体。
- **FR-031**: 本特性 MUST 引用而不重写 062（humanize，表达类首个实现）、067（循环效率加固）、068（执行量化反馈通道）的既有条款；三者规格 MUST 保持字节不变。
- **FR-032**: 表达类的效率度量 MUST 复用 068 已建立的记录/反馈通道（通道可用时），MUST NOT 新建统计系统、评分体系或计量台账。

#### F. 迁移与兼容（US4）

- **FR-033**: 未刷新的既有项目 MUST 维持原有行为；刷新指令后 MUST 自动获得分类定义与默认行为，MUST NOT 要求手工修改任何文件或数据。
- **FR-034**: 分类引入后，既有命令与技能的既有门禁、wrap-up 与既有测试 MUST 零新增失败，判据为名字级基线比对（不是失败条数比对）。
- **FR-035**: 分类定义与台账 MUST 随框架分发到客户项目；客户项目 MUST NOT 需要复制、维护或对齐第二份分类数据，副本只能由生成/刷新产生并带漂移检查。分发 MUST 走既有路径（`shared/` 框架源随包 + `specify init` 的复制步骤，实测见 `pyproject.toml` 的 `force-include` 与 `src/specify_cli/__init__.py` 的 shared 复制段），MUST NOT 新增分发机制；本特性 MUST NOT 新增客户项目侧的类别存储或读取点——项目自建流程按默认类运行，项目若在自己的知识空间记录其类别，框架不读取、不影响门禁。

#### G. 分类落地与度量口径（US1 / US2 / US4；clarify 2026-10-24 裁定）

- **FR-036**: 分类所有者 MUST 是 `shared/definitions/` 下按既有 `<域>-definitions.md` 命名惯例新建的一份定义文档（clarify 裁定：`flow-class-definitions.md`），并在开篇声明自己拥有判据、两个取值、边界例、逐流程台账、类中立清单、同构映射与不可同构边界。机器可读的类别键 MUST 取带命名空间的 `flow_class`（[[STR-003]]），MUST NOT 以裸 `execution` 充当键名；与 Agent Execution 的同词异义 MUST 在所有者条目与 `.specify/memory/glossary.md` 两处显式消歧。
- **FR-037**: 台账 MUST 是所有者文档内的一份声明式行集（每流程单元一行：单元标识、类别、依据判据、生效版本），MUST NOT 采用逐单元分散载体（命令模板元数据、技能 frontmatter）承载类别——分散载体即第二份副本。对账检查 MUST 解析该行集并与流程单元清单（命令模板与技能目录）比对，且 MUST 同时具备**反空真下限**（解析出的行数低于下限即判失败）与**覆盖率断言**（「零缺口因为表完整」MUST 可区分于「零缺口因为一行都没解析出来」）。
- **FR-038**: 同一流程的两种 oracle 都必需时，其类别 MUST 取 `execution`（[[STR-001]]）并**叠加**表达类门禁，MUST NOT 择优、MUST NOT 取 `expression`（[[STR-002]]）后省略执行侧门禁；该判定 MUST 只依据主交付物的消费方与失败可见性（失败是否只有人读才能发现），MUST NOT 依据交付物数量比例或文件类型占比。
- **FR-039**: FR-010 的「命令与其委托技能同类」MUST 由确定性检查核验：从命令模板中声明的委派技能路径解析出委托关系，再比对该技能在台账中的类别；MUST NOT 依赖人工维护的委托清单。类中立清单 MUST 封闭，其成员判据 MUST 是「交付物被两类流程共同消费且无类特定验收」；类中立 MUST NOT 免除任何门禁。
- **FR-040**: 六面文档型门禁的每一面 MUST 指向一个单一 owner 机制（读者面 → `user-facing-comprehension.md` 的基准读者；结构面 → `create-docs` 的确定性引擎；评审面 → 既有评审流程；需求清晰度面 → requirements 校验器与质量清单；事实一致性面的**判据** → `one-source-of-truth.md`）；本特性 MUST NOT 复制这些机制的判据正文，也 MUST NOT 因其已有 owner 而重复定义判据。事实一致性面本特性只新增**确定性检查器**、不新增判据；证据分级与 as-of 面属新增，MUST 在所有者文档内声明其与既有证据机制的**对象差异**（`evidence-step.md` 的证据状态词汇描述机制是否存在/被使用，本面描述事实断言的等级与时效；`single-run-evidence.md` 管一次昂贵执行的记录留存），MUST NOT 重定义或收窄它们的取值域。
- **FR-041**: FR-029 的三项基线 MUST 以同口径、同仪器在开工前落盘，仪器 MUST 限于既有提交时间戳、既有运行/反馈记录与 exec-quant 通道（FR-032），MUST NOT 新增采集器；前瞻可用运行不足 3 次时，未取得样本的判据 MUST 记为未评估（not-evaluated），MUST NOT 记为达成。

### 显式排除项（Out of Scope）

### Key Entities *(include if requirement involves data)*

- **Flow Unit（流程单元）**：被分类的最小对象，取值为命令模板或技能；属性含标识、类别、是否默认、依据判据、生效版本。
- **Class Assignment（分类登记）**：一条「流程单元 → 类别」的判定记录；带是否默认、判定理由与审计信息（何时、依据哪条判据）。
- **Classification Owner（分类所有者）**：唯一声明判据、取值、边界例与台账的文档；本文件不是它。clarify 裁定其落点为 `shared/definitions/flow-class-definitions.md`（遵循同目录 `<域>-definitions.md` 命名惯例），并且同构映射与其不可同构边界清单也归它——边界例即映射「为何到此为止」的理由，拆开必然各自漂移（FR-036 / FR-018）。
- **Gate Operator Set（门禁算子集）**：某一类别在某阶段用来证明同一不变量的检查算子集合；数量与严重级不随类别变化。
- **Isomorphism Row（同构映射行）**：一个 SDD 阶段的「代码型产物 ↔ 文档型产物」对应，附强制门禁或「已声明未强制」标注。
- **Non-Isomorphism Boundary（不可同构边界）**：四类不可互换的判定面（验收 oracle、验证算子、失败可见性、语义 oracle），每条须指出至少一处门禁处理。
- **Document-Form Gate（文档型门禁）**：六面文档质量检查中的一面，含判据、阻断级别与证据形式。
- **Reader Declaration（读者声明）**：文档型交付物的目标读者与阅读场景声明；缺失即未完成。
- **Evidence Annotation（证据标注）**：事实性断言上的等级（实测/推断/引用）与 as-of，附可复算来源。
- **Contract Clause（契约条款）**：文档中具唯一 ID、可被其他文档引用的规范单元；手写重复即事实漂移。
