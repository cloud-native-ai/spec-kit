# Run-Then-Report Contract — Requirements Quality Checklist

**Purpose**: Validate the quality, clarity, completeness and internal consistency of the requirements for Feature 062's 079 extension — `/speckit.humanize` becoming "run one instruction, then report on it": bare text parsed as an instruction, dispatch through the existing `run-agent` carrier, confirmation missing handled fail-closed, the five-section report, the source list, the legacy content mode, concurrency/nesting, and the wiring surface. Every item is a question about the requirement text, not about running the product.
**Created**: 2026-10-30
**Feature (Requirement Scope)**: `.specify/memory/features/062.md` (Feature 062 — Humanize Command / 动作输出人类友好化), extended by `079-humanize-run-output`
**Requirements (What)**: [../requirements.md](../requirements.md) — 30 FR / 10 SC / 4 user stories / 15 Shared Strings
**Specifications (How, context only)**: [../plan.md](../plan.md), [../data-model.md](../data-model.md), [../contracts/](../contracts/), [../quickstart.md](../quickstart.md), [../tasks.md](../tasks.md) — referenced only to expose gaps, ambiguities and conflicts in the requirements; never graded for their own quality.

**Note**: Generated by `/speckit.checklist` under `.specify/skills/internal/create-checklist/SKILL.md`. It is a requirements-quality instrument ("unit tests for requirements writing"): an item answerable only by executing the feature would be a defect here. Answering an item means judging the requirement text; a "no" becomes a finding against `requirements.md` (or against the named owner), not an implementation task.

## Notes

- **Intent defaults applied (unattended run, no interview)**: Depth = Standard · Audience = Reviewer · Focus = the two clusters that carry the feature's value — (a) the run-then-report chain (parse → dispatch → confirmation → five-section report → source list → output target), (b) the fail-closed and compatibility surface (concurrency/nesting, legacy content mode, wiring, measurability). The three intent questions were skipped because the stage directive already fixed scope (run-then-report contract surfaces), depth (skill default Standard) and audience (reviewer); no user-supplied items were incorporated.
- **Traceability**: 39/39 items (100%) carry at least one `[Req §…]` / `[tasks §…]` anchor; 30 of them additionally carry an explicit `[Gap]` / `[Ambiguity]` / `[Conflict]` / `[Assumption]` / `[Coverage]` marker, while 9 are plain clarity-or-measurability questions anchored to the requirement they judge — above the 80% floor either way. Every item is question-form; none opens with Verify/Test/Confirm/Check followed by implementation behaviour.
- **Same-author gap-finding limitation**: the skill's canonical method delegates gap-finding to fresh-context read-only subagents when the spec was written by the same agent. This line's execution constraint forbids dispatching subagents, so the gap-finding pass was single-context. Recorded here as a methodological limitation for `/speckit.analyze` (read-only, independent context) to re-check; it is not a claim of coverage.
- **Plan constraint respected**: no plan-owned artifact (`plan.md`, `data-model.md`, `contracts/`, `quickstart.md`, `feature-ref.md`) was read-for-edit or modified; this round adds one checklist file plus evidence only. Findings that would require a plan change are expressed as questions, not as edits.
