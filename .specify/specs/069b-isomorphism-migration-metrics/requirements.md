## Overview

本切片要把父特性里最容易被写成口号的一段变成可核对的结构：**同构**不是「文档即代码」的比喻，而是 8 行映射（每个 SDD 阶段一行）× 3 面列（结构 / 流程 / 逻辑）= 24 格的对应关系，每行必须指出它是被哪条门禁强制的，或显式标注「已声明未强制」；同时附一份**不可同构边界清单**，说明验收 oracle、验证算子、失败可见性与语义 oracle 四处为什么不能互换。

同一切片还要回答两个交付面的问题：**分类数据怎么到客户项目**（走既有 `shared/` 随包 + `specify init` 复制，不新增机制、不新增项目侧存储），以及**分类怎么落地、效率怎么量**（所有者与台账形态、混合 oracle 一律取 `execution`、命令↔委托技能的机械核验、六面门禁各自单一 owner、三项基线只用既有仪器）。

**判据不是介质轴，这一点在本切片同样是承重的。** 同构映射的「代码型产物 ↔ 文档型产物」是按**验收 oracle** 对齐，不是按文件扩展名对齐：一份 OpenAPI 契约虽然也是文本，但它与「代码」同格；一份 Markdown 架构文档与「代码」同格的是它的结构与论证链，不是它的文件类型。这条判据决定了映射行怎么写，也决定了边界清单为什么是四类而不是更多。

- **SA-12 样本事先落盘**：SC-002 的 3 个客户项目快照 MUST 在跑测前落盘（哪三个项目、哪个提交/刷新前状态），理由与父编号 004–006 的「过滤集合开工前冻结」同源（该三条 SC 归 069a）：事后回选会把「零回归」变成选样结果。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 我能查到代码与文档在八个阶段上的对应关系，以及它们不可能同构的地方 (Priority: P2)

方法论读者要求「同构」是一个可核对的结构，而不是一句比喻：每个 SDD 阶段都有一行「代码型产物 ↔ 文档型产物」的对应，并标明这一行由哪条门禁强制、或只是已声明未强制；同时有一份不可同构边界清单，说明验收 oracle、验证算子、失败可见性、语义 oracle 四处为什么不能互换。

**Why this priority**: 没有边界的同构主张会立刻被误用——把「文档即代码」当作把测试、编译、覆盖率整套搬到文档上的许可证。父规格把它定为 P2（映射只有在分类与门禁成立后才有承载物），该前提已由 069a 满足；**本切片沿用父标签 P2，不改标签**，切片内顺序由 FR 编号表达。

**Independent Test**: 逐行检查映射表：每行是否有强制门禁或「未强制」标注；再逐条检查边界清单，确认每条边界都能在至少一处门禁设计中指出对应处理；最后取一条「同构」主张，确认它能落到某个阶段 + 某个面，或落到某条边界。

**Acceptance Scenarios**:

1. **Given** 同构映射表（8 行 × 3 面列 = 24 格），**When** 逐行核对，**Then** 每一行都指向一条强制它的门禁，或被显式标注「已声明未强制」，不存在既无强制也无标注的行。
2. **Given** 边界清单，**When** 追问「文档为什么不能只靠构建通过验收」，**Then** 能从边界 (c)(d) 得到确定回答（陈旧事实仍能构建通过；文档无编译器），而不是从原则口号回答。
3. **Given** 一条关于「文档即代码」的表述，**When** 它既不落成映射行（阶段 + 面）也不落成边界，**Then** 该表述不得进入需求、门禁或模板文本。
4. **Given** 某一行实际没有任何门禁执行它，**When** 有人把它标成「被某条门禁强制」，**Then** 该标注判为失真并转红——标注必须反映实际，不能靠措辞补齐。

---

### User Story 2 - 升级后既有项目行为不变，且分类数据随既有分发路径到达 (Priority: P2)

既有客户项目在未刷新时行为零变化；刷新后自动获得分类定义与默认行为，不需要手工维护任何分类数据；框架源与客户运行时两份定义并存时以所有者为准，副本只能由生成/刷新产生并带漂移检查。

**Why this priority**: 兼容性是框架分发的硬约束，且分类天然会被读成「要我自己维护一份台账」。父规格把升级兼容与防滥用同列为 P2；**防滥用那一半（不得以「属表达类」跳过 analyze/review）已由 069a 交付**，本切片只承接兼容与分发这一半，标签沿用父 P2。

**Independent Test**: 在三个既有客户项目快照上运行刷新后的命令套件，按名字级基线比对新增失败；再检查一个刷新后的项目是否「零手工分类数据」也能得到正确类别与默认行为；再确认项目侧没有任何类别存储或读取点。

**Acceptance Scenarios**:

1. **Given** 一个未刷新的旧项目，**When** 运行任一既有命令，**Then** 行为与分类引入前一致（名字级基线新增失败为 0）。
2. **Given** 一个已刷新的旧项目，**When** 查看任意流程的类别，**Then** 定义与默认行为随框架到达，项目侧无需复制或维护分类数据。
3. **Given** 框架源与客户运行时各有一份分类定义，**When** 两份不一致，**Then** 以所有者为准，副本的漂移由检查报出（副本不是第二真源）。
4. **Given** 一个客户项目为自己的新流程记录了类别，**When** 框架运行该流程，**Then** 该记录不被读取，流程按默认类运行——本切片不新增项目侧的类别存储或读取点。

### User Story 3 - 分类的落地形态与度量仪器可被机械核对，而不是靠自述 (Priority: P2)

框架维护者要能验证三件事而不依赖任何人的声明：分类数据只有一份且形态可解析（「解析失败」不会被读成「零缺口」）；命令与技能的同类关系由命令模板里真实存在的委派路径推出，而不是靠人工维护的清单；三项效率基线用的仪器是既有通道，不是新采集器。

**Why this priority**: 这一条是本切片为可验收性组织的**切片内**故事（SA-9），不是新的父级故事——它承载的是父规格 User Story 1（分类可复现）与 User Story 2（门禁可测地更少更准）在落地层面的成立条件。若这一层不成立，前两个故事就只能靠自述结案。

**Independent Test**: 对台账做两次注入（删一行、破坏表形），确认对账检查各自转红且两红可区分；取一个混合 oracle 单元，确认它落 `execution` 且表达类门禁叠加；对六面 owner 做一次指针计数与判据正文 grep；核对三项基线的来源命令是否都在既有通道内。

**Acceptance Scenarios**:

1. **Given** 台账被删掉一行，**When** 运行对账检查，**Then** 转红并报「缺口」；**Given** 表形被破坏（解析出 0 行而清单非空），**When** 运行同一检查，**Then** 转红并报「解析失败」——两种红必须可区分，静默绿样本数为 0。
2. **Given** 一个混合 oracle 单元（既被人读又被脚本解析，或须生成并编译），**When** 两名判定者独立归类，**Then** 都落 `execution` 且叠加表达类门禁；**Given** 有人按「文档占比更高」改判 `expression`，**Then** 该改判被拒。
3. **Given** 一个命令模板与它声明的委派技能，**When** 运行同类检查，**Then** 委托关系由模板里的技能路径解析出、再与台账类别比对；人工维护的委托清单不作为核验依据。
4. **Given** 六面文档型门禁，**When** 核对 owner 指针，**Then** 每面各有 1 个 owner 指针（6/6），且判据正文在 owner 之外出现 0 次。
5. **Given** 前瞻可用运行不足 3 次，**When** 收尾对照三项基线，**Then** 未取得样本的判据记 `not-evaluated`，不记 0、不记达成。

### Edge Cases

以下只列适用于本切片（同构映射与边界、迁移与分发、落地口径与仪器）的边界；分类本体、阶段关系与六面门禁的边界归 069a。

- **一份交付物同时有两种读者**（架构文档既被人读，又被脚本解析生成图或代码）：按主交付物的消费方与失败可见性归类；两种 oracle 都必需时按 FR-011 一律取 `execution` 并叠加表达类门禁，不择优。
- **一个流程同时产出代码与文档**（如 implement）：按主交付物归类；其文档产物仍按文档型门禁检查，不因流程类别为执行而降级。
- **契约文件既可读又可编译**（OpenAPI 生成 SDK）：同类判定的落点是「它的验收包含生成物可编译」这一事实，不是文件扩展名；其文档可读性要求仍以表达类门禁的读者面补强。
- **「已声明未强制」被当成豁免**：该取值只表示「该行暂未被任何门禁强制」，标记本身不构成通过，也不构成新增未强制行的许可（SA-8）。
- **台账与判据冲突**：以判据为准，冲突本身记为缺陷并修复台账——台账是判据的投影，不是判据的来源。
- **两份分类定义并存**（框架源与客户运行时各一份）：以所有者为准；副本由生成/刷新产生并带漂移检查；分发机制不在本切片新增（FR-008）。
- **项目自建流程未声明类别**：按默认类运行；项目若在自己的知识空间记录其类别，框架不读取、不影响门禁（FR-008）。
- **未刷新项目「按默认类运行」但没有消费点标记**：这是 069a 的消费点标注条款的适用面，本切片只要求行为不变（FR-006）；把「未刷新即无标记」读成本切片缺陷属越权读法。
- **客户端对账没有可通过状态**（REC-069a-06）：不构成放宽判据的理由——两种注入仍须各自转红且可区分；形态取值归 plan（SA-11）。
- **样本不足**：前瞻运行不足 3 次时记 `not-evaluated`，不记达成；但「不足」不得成为不冻结基线的理由。

## Requirements *(mandatory)*

### Functional Requirements

#### C. 同构与其边界（US1）

- **FR-001**: 框架 MUST 声明一份**同构映射**：对八个 SDD 阶段各给出一行「代码型产物 ↔ 文档型产物」的对应（8 行 × 3 面列 = 24 格），并覆盖结构、流程、逻辑三个面（结构 = 实体 / 关系 / 边界；流程 = 阶段与门禁角色；逻辑 = 证据 / 契约 / 验收 / 版本 / 所有权）。阶段名册 MUST 引用既有阶段映射 owner（八阶段产物映射，由 `skills/external/sdd-loop-driver/scripts/loop-state.py` 与同名 reference 章节共同承载，声明见 `.specify/specs/066-loop-state-awareness-a/requirements.md` 的 FR 编号 006），MUST NOT 新建第二份名册；名册变更时映射跟名册走，不另立版本。映射与其边界清单的**唯一载体**是分类所有者 `shared/definitions/flow-class-definitions.md`（该文档已在 069a 版本里为这一节留了一行交接指针，本切片 MUST 把它换成实体章节并同步其 owns 列表），MUST NOT 出现第二份可执行副本或第二个所有者。
- **FR-002**: 同构映射的每一行 MUST 标注它由哪条门禁强制执行，或被显式标注「已声明未强制」；既无强制又无标注的行 MUST 判为缺陷（口号行）。标注 MUST 反映实际：被某条门禁实际执行的行 MUST NOT 标成「已声明未强制」，未被任何门禁执行的行 MUST NOT 标成有强制门禁——标注失真的行与未标注的行同等处理。
- **FR-003**: 同构声明 MUST 附带**不可同构边界清单**，至少覆盖四类：(a) 验收 oracle（执行行为 vs 阅读理解）；(b) 验证算子（测试 vs 构建 / 链接 / 一致性检查）；(c) 失败可见性（运行期偏差 vs 构建通过而事实陈旧的静默失败）；(d) 语义 oracle 缺失（文档无编译器，意义只能由人判定）。每条边界 MUST 能在至少一处门禁设计中指出对应处理；边界清单 MUST 与映射同属一个所有者文档（边界就是「映射到此为止」的理由），MUST NOT 拆成两份各自漂移。
- **FR-004**: MUST NOT 以「文档即代码」为由把代码型门禁整套移植到文档型流程；跨类复用 MUST 指名所复用的不变量（契约、证据、所有权、版本等），MUST NOT 复用其判定算子本身。
- **FR-005**: 任何「同构」主张 MUST 落到一行可判定映射或一条边界；无法落地的表述 MUST NOT 进入需求、门禁或模板文本。可判定性 MUST 按「该表述能否指向映射中的一行（阶段 + 面）或边界清单中的一条」判定，MUST NOT 按措辞风格判定。

#### F. 迁移与兼容（US2）

- **FR-006**: 未刷新的既有项目 MUST 维持原有行为；刷新指令后 MUST 自动获得分类定义与默认行为，MUST NOT 要求手工修改任何文件或数据。
- **FR-007**: 分类引入后，既有命令与技能的既有门禁、wrap-up 与既有测试 MUST 零新增失败，判据为**名字级基线比对**（按失败 nodeid 集合比对），MUST NOT 用失败条数比对——条数相同可以掩盖「修好一个、弄坏一个」。
- **FR-008**: 分类定义与台账 MUST 随框架分发到客户项目；客户项目 MUST NOT 需要复制、维护或对齐第二份分类数据，副本只能由生成/刷新产生并带漂移检查。分发 MUST 走既有路径（`shared/` 框架源随包 + `specify init` 的复制步骤；2026-10-24 实测见 `pyproject.toml` 的 `[tool.hatch.build.targets.wheel.force-include]` 中 `shared` 条目与 `src/specify_cli/__init__.py` 的 shared 复制段），MUST NOT 新增分发机制；本切片 MUST NOT 新增客户项目侧的类别存储或读取点——项目自建流程按默认类运行，项目若在自己的知识空间记录其类别，框架不读取、不影响门禁。

#### G. 分类落地与度量口径（US1 / US3）

- **FR-009**: 分类所有者 MUST 是 `shared/definitions/` 下按既有 `<域>-definitions.md` 命名惯例的**一份**定义文档（clarify 2026-10-24 裁定：`flow-class-definitions.md`；069a 已按此落盘），并在开篇声明自己拥有判据、两个取值、边界例、逐流程台账、类中立清单、同构映射与不可同构边界。机器可读的类别键 MUST 取带命名空间的 `flow_class`（[[STR-003]]），MUST NOT 以裸 `execution`（[[STR-001]]）充当键名；与 Agent Execution 的同词异义 MUST 在所有者条目与 `.specify/memory/glossary.md` 两处显式消歧。本切片只固定「映射与边界归该所有者」这一归属并闭合 069a 留下的交接行，MUST NOT 因本条新建第二个所有者或第二份映射。
- **FR-010**: 台账 MUST 是所有者文档内的一份**声明式行集**（每流程单元一行：单元标识、类别、依据判据、生效版本），MUST NOT 采用逐单元分散载体（命令模板元数据、技能 frontmatter）承载类别——分散载体即第二份副本。对账检查 MUST 解析该行集并与流程单元清单（命令模板与技能目录）比对，且 MUST 同时具备**反空真下限**（解析出的行数低于下限即判失败）与**覆盖率断言**（「零缺口因为表完整」MUST 可区分于「零缺口因为一行都没解析出来」）。列头逐字取 `flow_class`（[[STR-003]]），解析 MUST 按表头名而非列位置。**生效版本的承载形态** MUST 在所有者内声明一次（行级列，或「文档版本 + 逐行变更记录」，由 plan 择一），MUST NOT 逐单元分散；版本不兼容的判定沿用既有的「表头 / 列集合与解析器期望不符」判据（父编号 016，069a 承接），本切片 MUST NOT 引入与该判据冲突的第二个版本信号。
- **FR-011**: 同一流程的两种 oracle 都必需时，其类别 MUST 取 `execution`（[[STR-001]]）并**叠加**表达类门禁，MUST NOT 择优、MUST NOT 取 `expression`（[[STR-002]]）后省略执行侧门禁；该判定 MUST 只依据主交付物的消费方与失败可见性（失败是否只有人读才能发现），MUST NOT 依据交付物数量比例或文件类型占比。台账中 `basis: mixed-oracle` 的行 MUST 与本节一致（其 `flow_class` MUST 为 `execution`）；不一致 MUST 判为台账缺陷并修台账，MUST NOT 逐案裁定。
