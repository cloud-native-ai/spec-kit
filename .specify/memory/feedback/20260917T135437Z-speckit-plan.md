- ## 优化点
- ### 1. 我违反了模板自己的「summarize after, not before」,而且靠运气没出事
- `## Phase 1: Design Artifacts Summary` 表是在**任何 Phase 1 制品都还不存在时**写进 plan.md 的,带着具体计数(16/11/14/12/7 = 60 条款、9 实体、4 组校验、2 状态机、6 场景)。事后核验**全部吻合**——但这是**侥幸命中,不是纪律履行**。模板明文警告"pre-written counts routinely drift from the actual output and force a correction pass"。
- 根因是**顺序结构性冲突**:大纲第 4 步要求"填充模板",而摘要节位于同一文件的**底部**,自然的自上而下一遍写法必然把它写在制品之前。命令只说"Summarize after, not before",没有任何东西**强制**它。
- 两个可选修正:(a) 把该节留到 Phase 1 制品落盘后作为**独立一次编辑**填写(我本该这么做);(b) 把「计数已于落盘后机械核验」的戳记做成 plan 完整性门的一项——我本轮**手工加了**这个戳记(附实测命令与逐份数字),这是最便宜的修正,建议直接变成强制项。
- ### 2. Phase 1 制品之间没有交叉引用完整性检查
- `feature-ref.md` 把 38 条 FR 映射到 60 个契约条款,靠**手写 ID**(`discipline-doc C-9`、`surface-pointers C-10`……),这样的引用约有 90 处。**没有任何东西验证这些 C-N 存在**。一个悬空的 `C-N` 是静默的:它看起来权威,直到实现期有人照着去写测试才发现指错。
- 这与我在 clarify 轮记录的 FR 重编号风险是**同一类缺陷、上移一层**:plan 期引入了**第二个 ID 命名空间**(条款 ID)去交叉引用第一个(FR ID),而两者都没有机械校验。规格内部的 `FR-NNN` / `SC-NNN` / `[[STR-NNN]]` 我这轮用循环解析验证过零悬空——同样的循环应当延伸到跨制品。
- 建议 Post-Generation Quality Gate 增一项:`feature-ref.md` 中每个 `<contract> C-N` MUST 解析到该契约文件里一个真实条款;映射表中每个 `FR-NNN` MUST 存在于 `requirements.md`。这是纯文本解析,零新机制。
- ### 3. `AGENTS.md` 与 `update-feature-index.sh` 的矛盾已被**两次独立发现**,仍未修

- 两轮独立发现同一个活危险,正是 `ask-record-repeat.md` 描述的信号:"a rule stated in exactly one place is effectively absent"。这一条需要三层表面处理:改源头(`templates/instructions-template.md` 的 Feature Index 行)、并且**要么修脚本使其保留 7 列与既有散文、要么删掉它**——留着一个与文档说法相反的破坏性脚本,比没有脚本更糟。
- ### 4. 门控预算这个约束**没有 owner 文档**
- `shared/guidelines/confirmation-gates.md` 是门控治理的真源,但它 99 行里**没有一个字**提到预算(23 / cap 23.25 / 余量 0)。这个阈值今天只活在两个契约测试(`test_confirmation_gates_sweep.py:63-71`、`test_proactive_trigger_section.py:288-306`)、两份 Feature 索引散文(050、051)和本轮新增的词汇表条目里。
