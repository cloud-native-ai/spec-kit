## Optimization Points
- **四要素分析未在落盘前呈现(本轮实际穿过的合规缺口)。** 命令的 Goal-Based Create 分支 step 3 要求「创建前呈现」维度 / 判据覆盖 / 既有 Target / 可达成性,每项附理由。本轮我做了分析(维度=框架自身;判据覆盖=1 条;既有 Target=零,`targets --list` exit 0;可达成性=单团队可达成,故走单团队路径),但只把结论散在派生理由里,**没有作为一个具名小节在落盘前呈现**,team.md 先落了盘。分析是「建议非门禁」不等于可以不呈现——用户裁决单团队 vs 分解的前提是看见这四行。建议:命令模板把该小节写成落盘前的强制输出面(哪怕一行一项),而不是隐含在派生理由中。
- **跨命令的退出门悬空没有处置规则。** 用户在前一个命令(/speckit.goal)的退出门未显式确认时直接调起本命令。本轮按「队名沿用 slug」读作隐式确认并披露,但这是我现场裁的:命令模板与 create-mode.md 都没有规定「上游 goal 的退出门未确认时,基于它的 create 分支该怎么办」。风险是隐式确认把一个未经确认的定义固化成团队绑定。建议:分支 step 2 复述定义时增加一句「若该 goal 的定义在本会话内刚被修改且退出门未确认,MUST 显式点出」。
