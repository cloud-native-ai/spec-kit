## Review
modify 模式：把 goal draw-two-layer-structure 判据 1 的技能枚举由六个改为七个（加入 draw-drawio），经 goal-utils.py criteria 落盘，exit 0、validate 通过、判据 2/3 与 Objective/Targets/status/created 逐字未动、History 留痕三条前值。触发原因是 /speckit.team modify 把团队结构扩到七技能后，authored goal 与团队结构出现矛盾，而 goal.md 在该团队 territory.forbidden 内、improve-team 不得写。本次暴露一个真实的引擎能力缺口：无 objective 修改动作，导致 Objective 的五引擎枚举无法同步修正。

## Optimization Points
- `goal-utils.py` 缺 `objective` 修改动作：action 集为 {create,validate,check-statement,list,status,criteria,migrate,targets}，源码亦无 `set_objective`。Objective 一经 create 即**经引擎不可变**，而本命令明令「never hand-write a definition file」——于是「修正 objective 措辞」这件事当前**无合法路径**。本次即撞上：判据 1 可经 `criteria` 改为七个技能，Objective 里 `draw-{d3js,echarts,excalidraw,mermaid,plantuml}` 的五引擎枚举却无法改，导致同一份 authored 文件内判据说七技能、Objective 说五引擎。建议补 `objective` 动作，语义照 `set_criteria`（替换 + History 留痕前值 + bump updated + 终态只读）。
- 判据里硬编码「数量 + 成员枚举」（`六个绘图技能（draw-diagram 与 draw-{…}）`）对套件成员变更脆弱：本会话内这是第二处因加引擎而失效的枚举（另一处是 team.md 的 description/co_targets）。可考虑支持**目录指代形**（如「全部 `skills/draw-*` 绘图技能，以目录为准」），使判据的主体可被程序解析且无需随成员变更重写；代价是 scope 变为动态，需在概念文档里明确这是特性而非缺陷。
- 验证引擎承诺的副作用时 MUST 断言文件内容，不能断言**过滤后的 diff**：本次为核对「History 是否留痕前值」而用 `git diff | grep -E '^[+-]' | grep -v '^[+-][+-]'`，该过滤把新增的 History 行（以 `+- ` 开头）一并滤掉，差点据此误报引擎未留痕。是 `--stat` 的插入行数(2)与可见 `+` 行数(1)不符才暴露了过滤错误。教训：过滤器会制造假阴性，凡「引擎应当写下 X」类断言直接读文件。
