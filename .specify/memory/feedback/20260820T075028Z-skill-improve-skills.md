## Review
Second improve-skills run of the session, targeting create-pages after the user specified a three-stage model: local doc library -> Hugo-rendered site -> pages service (local/aoneci/github), with the library scoped to the docs directory unless explicitly widened. Three user decisions steered it: unify on the mount renderer, leave github as a structure-only stub, and treat aoneci (not 'gitlab') as the name of the internal platform. Delivered: scaffold.sh renamed to scaffold-ci.sh and slimmed 325->125 lines into a stage-3 CI adapter that writes exactly one file; the aoneci pipeline rewired from a repository-root dist/ to <docs>/public built by running Hugo inside the docs directory; the staging-copy renderer, its build script, .hugo-content staging and root .gitignore append all retired; SKILL.md restructured 216->189 lines around the three stages with an explicit target table and honest per-target status; design-rationale.md and verification.md rewritten per stage; the ci-templates registry and github contract updated. Two latent defects were found by actually building: front-matter-less pages rendered empty titles (fixed by porting the retired renderer's title fallback into a partial and wiring it through baseof/list/index, verified before/after) and three deprecated Hugo keys (two fixed, the excludeFiles one recorded with its migration blocker). Verified: shape gate exit 0, mirrors byte-equal, scaffold-ci.sh exercised across all six branches including an unknown-platform rejection of 'gitlab', a real Hugo build in a fresh project and on this repo's own docs, 49/50 docs+pages tests green, and a clean-HEAD failure-set diff whose single delta reproduces on clean HEAD with the same gitignored scratch dirs.

## Optimization Points
- ## Optimization Points
- **Add a "retire the superseded implementation" step to Step 4's unification branch.** When a loop consolidates two implementations of the same capability into one, the surviving implementation may lack fixes the retired one had. This run unified two Hugo renderers; the retired staging renderer shipped a `title.html` partial that the surviving mount renderer never had, so plain consolidation would have silently regressed every page title to `<title>· Site</title>` and blanked every list/nav link. It was caught only because Step 6's "reference code is executed" rule forced a real build. Make it explicit: before deleting the losing implementation, diff its feature set against the winner's and port anything the winner lacks — a consolidation is a *superset*, not a survivor.
- **Extend the Step 5 rename checklist with the "vocabulary the previous loop introduced" sweep.** The prior loop in this same session introduced a "mode A / mode B" framing into `SKILL.md`, a spec-contract revision note, and a feature-history cell. This loop replaced that framing with three stages, and the stale vocabulary survived in the two *non-skill* artifacts until a dedicated grep found it. The checklist tracks pointers to renamed *files*; it should also track renamed *concepts* — grep the terms the previous loop coined across `.specify/specs/**` and `.specify/memory/**`, not just paths.
- **Deterministic-output validation must check the file, not just the exit code.** `scaffold-ci.sh` reported `{"created": [...]}` with exit 0 while writing a YAML file with no trailing newline (command substitution strips it). Exit status and the JSON summary both looked clean; only `od -c` on the artifact and a `yaml.safe_load` round-trip exposed it. Step 6 should require, for any script that writes a file, one assertion on the written artifact's content (parse it, or byte-check its boundaries) rather than accepting the script's own success report.
- **Record third-party deprecation findings with their migration blocker.** The real build surfaced three Hugo deprecations; two were one-line fixes, and the third (`module.mounts.excludeFiles` → `files`) could not be migrated because the `index.md` remap depends on the exclusion semantics and verifying the replacement needs current upstream docs. Writing "expected today, still functions, migration needs X verified" into the troubleshooting table is the honest outcome, and the playbook should name that pattern so a future loop neither silently ignores the warning nor blind-migrates it.
- **token-efficiency**: scaffolder validation was run with `--action mounts` in the previous loop and with a full `--action scaffold` JSON dump in this one; both piped the entire machine payload into context when a projected field would do. This run improved on it (`python3 -c` projections over `json.load`), and that projection idiom — not raw invocation — should be the documented default for validating a JSON-emitting script.
