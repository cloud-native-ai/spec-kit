## Optimization Points
- Outline 步骤 1 无条件运行 `create-new-plan.sh`,而该脚本第 54 行是无守卫的 `cp "$TEMPLATE" "$IMPL_PLAN"`。本次 `plan.md` 已被另一流程手工预置了一段「Pre-seeded Constraints」设计输入并明确要求 `/speckit.plan` 保留,若照步骤 1 执行会直接覆盖销毁。命令的 Outline 与 AGENTS.md 记载的「In-place amend ≠ re-scaffold」教训相互矛盾。建议:步骤 1 改为条件化——`plan.md` 不存在时才 scaffold,已存在时跳过并走原地填充路径;或在脚本内加 `--force` 守卫。
- Phase 0 的「Codebase exploration pass」只要求探查代码触点,没有要求**执行**被依赖的外部能力。本次真正决定设计成败的四条事实(R 档可满足性、ID 字面量文法、引擎已自带 0% 与甘特降级、`coverage` 恒产要求)全部来自实际跑一遍被调技能脚本链,靠读文档只能得到前两条的错误版本(文档未提 ID 文法约束,也未提 `coverage` 为空会触发 CG-COVERAGE FAIL)。建议:当规格依赖一个既有可执行能力(技能/脚本/引擎)时,Phase 0 MUST 包含一次对该能力的最小真实调用,并把观测到的退出码/字段作为设计依据落进 research.md。
- Post-Generation Quality Gate 第 4 条要求 quickstart/contracts 里的 CLI 示例经真实执行或契约测试钉住,但没有要求**记录**验证结果。本次执行验证产出了可复用的判据(如"四步退出码全为 0""越界 ID 报 exit 3 并打印约束原文"),这些是后续 `/speckit.tasks` 写验收任务的直接素材。建议:该门禁增加一句——把每条已验证示例的预期输出/退出码写在示例旁,使验证结论随文件流转而不是留在会话里。
- Feature Integration 只说「Advance status Draft → Planned」,未涵盖本次这种**演进规格挂到已 Implemented Feature**的常见情形。此时推进的是"需求状态"而非"Feature 状态",Principle VII 的 no-status-regression 门禁禁止把 027 退回 Planned。命令若照字面执行会产生状态回退。建议:在该节显式区分「需求状态」与「Feature 状态」两个轴,并写明 Implemented Feature 上追加演进规格时只更新 Last Updated 与 Feature 明细的 Review 段。
