## Optimization Points
- **既有 serial 团队的房形带一处断引用,而 create 路径没有程序步骤会检出它。** `.specify/teams/draw-two-layer-structure/team.md` 给 `agent-team-supervisor-template` 标 `lifecycle: persistent`,但该 agent 只解析为 `skills/create-team/templates/agents/` 下的临时模板,`.specify/agents/{templates,instances}/` 里没有它的持久定义。`create-mode.md` 的 schema notes 写着「unresolved members are surfaced as broken references」,但整条 create 流程没有任何一步真做这个解析核对——本次是我自写脚本逐席试三个候选路径才发现,照房形抄就会把断引用复制下去。建议:落盘前加一步程序可判定的成员解析核对(逐 `members[].agent` 试 `.specify/agents/{instances,templates}/<slug>.agent.md` 与 `skills/create-team/templates/agents/<slug>.md`,并断言 `lifecycle` 与解析结果一致)。
- **粒度纪律要求的程序计数没有工具化,且不排噪声就会把判定建在错数上。** `patterns.md:202` 明确要求「`find <dir> -type f | wc -l` 一类程序步骤,不是 LLM 估读」,但没有任何脚本产出这个计数,本次手拼了 5 条 find/grep 才拿到 25 / 34 / 18 / 13687 / 13232。其中 `find skills -type f` 直接给 13687,而 `skills/draw-mermaid/server/` 一个 vendored 子树独占 13232——不排噪声,stage 粒度会按 13687 判,结论完全失真。建议:给一个 stage 规模计数脚本(接 `--dir` 与 `--exclude`,输出计数 + 构成 top-N),把「排 vendored 噪声」变成程序默认。
- **门控预算余量为 0 这一机械上限只在词汇表里可达,create 路径不会主动读它。** 本团队写面(`templates/commands/` + `skills/`)与 `scan-confirmation-gates.py` 的 SCAN_DIRS 完全重合,实测 total 已等于钉死值 23(余量 0),任何新增 BLOCKING_PATTERNS 命中会同时打爆两个契约测试。本次是因为 glossary 协议的「约束侧读取」条款我才去查并实跑扫描器;不读词汇表的调用者会让团队带着一个必炸的写面落盘。建议:create-mode 派生 territory 时加一步「写面 ∩ 已知机械上限」核对,主动拉入词汇表里 type=ceiling 的条目。
- **两个自称「本节为唯一真源」的纪律节不是标题,无法被定位。** `Stage granularity discipline`(`patterns.md:202`)与 `Substance floor`(`:252`)都是加粗段落而非 `###` 标题,但 `SKILL.md:71` 与 `create-mode.md:15` 都以 `§ Serial Chain → <节名>` 的形式点名它们并标注「落盘 team.md 前必做」。按标题扫描查这两节会得到「悬空引用」的假象——本次就发生了,多花一轮 grep 才否证自己的怀疑。建议把这两节升为 `###` 标题,使被点名的真源可被机械定位。
- token-efficiency — 为取房形读了既有 team.md 的 frontmatter 全量(约 105 行)加正文 70 行;frontmatter 那段是 schema 实例、必要,但正文 70 行里我只需要 stage 行的字段形状,定点抽取(`grep -n '"stage_id"\|"quality_gate"'`)即可替代整段读。
