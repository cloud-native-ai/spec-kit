## Optimization Points
- **`goal-utils.py` 没有 `boundary` 动作**：Boundaries 只能在 `create` 时经 `--boundary` 设定，事后无法经引擎修改（动作集只有 create/validate/check-statement/list/status/objective/criteria/migrate/targets/run-checks）。而 Boundaries 与判据、Target 一样会与后续理解冲突——本次就撞上：Boundaries 排除「依据标注进行的任何差异化处理」，而同一 goal 的 T-002 要求按标注施加结构规则（internal 配合 .specify / external 零依赖），团队 S2b 正在执行后者。要改只有两条路：手改 authored 定义文件（违反「never hand-write a definition file」），或给引擎补动作。建议补 `boundary <slug> --set/--add/--clear`，与 `criteria` 同构（整集替换 + History 记前值 + `--clear` 归入破坏性写入需明示批准）。
- **create-team 的席位模板不在宿主 agent 注册面内，导致按房形建出的团队只能 virtual 派发。** `.qoder/agents/` 只安装了 `.specify/agents/{templates,instances}/` 里的 2 个（skill-verifier、structure-adjuster）；`skills/create-team/templates/agents/` 下的 4 个 orchestration/stage 模板不在安装面内。后果：任何按 create-mode 房形建出的团队，其 team-supervisor / stage-executor / stage-evaluator 三席在 Qoder CLI 下都拿不到隔离与并行，而 stage 批规模是按原生并行估的——设计与运行时错配，且 create 路径上没有任何一步会提示。建议：落盘前加一步派发模态核对（逐 `members[].agent` 判 native / virtual），把模态写进 `## Static Structure`，并让粒度纪律按 virtual 保守估批规模（真源 `.specify/shared/definitions/subagent-definitions.md`「virtual 任务要保持小」）。
- **write∩forbidden 的排除式解法在 shipped 校验器下不可见**（对方团队 `session-driven-self-improvement` 的 non_path `type: cross-goal-write` 条目已持有并已记入 feedback，本条只引用不复述）：`build-summary-input.py` 的 `_write_intersections` 只比 write×write、从不减 forbidden，故 create-mode schema 允许的 forbidden-write 排除解法在同 `goal_slug` 下仍会报 overlap。本次沿用该 idiom 时无从自检，只能靠读对方团队的记录得知。
- token-efficiency — 本轮为覆写 `team.md` 被迫整篇重读 227 行（Write 工具的 staleness guard 要求先 Read 全文，`limit` 形式的部分读不算），而改动虽多仍是定点的；若改用逐条 Edit 可省掉整篇重读。另一处：上一轮为取房形读了既有 team.md 的 frontmatter 全量约 105 行，其中真正需要的只是 territory/members/config 的字段形状。
