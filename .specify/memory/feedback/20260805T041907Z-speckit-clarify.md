## Optimization Points
- ## Optimization Points
- **A capability-addition argument is a third clarify shape the command does not model, and it inverts the question/integrate order.** Session #1 was decision resolution, #2 was conformance against an authority, #3 was "add this capability". The command has exactly one rule for it — "integrate user-provided decisions first, then queue the residuals" — which is right but far too thin: a capability addition is not a decision, it is a *design brief* with implicit forks. Here the brief ("record the teams, build a coordination mechanism") silently contained four independent design decisions (scope representation, coordination authority, persistence home, trigger point), none stated by the user and none discoverable from the taxonomy. The taxonomy's categories (Feature Linkage, Domain & Data Model, Interaction & UX Flow…) do not prompt for "what representation makes this mechanically checkable" or "what authority does the mechanism have over user artifacts", which were the two questions that actually mattered. **Proposed fix**: add a Mode A sub-procedure for capability additions — before queueing, (a) search the repo for an existing mechanism that solves the same problem at a different scope, (b) enumerate the decisions the brief leaves implicit, (c) ask only those, and (d) record the rejected alternatives alongside each choice so the plan does not re-open them.
- **Searching for prior art before asking changed both the questions and the answers — and nothing in the command asks for it.** The brief said "coordination mechanism", which invites inventing a "coverage area" concept from scratch. Grepping `skills/create-team/SKILL.md` first found Territory Division: Write Scope / Read Scope / Forbidden, a *zero write overlap* invariant, a Forbidden Write List, and optional worktree isolation — the same problem already solved one level down, at member level. That reframed the whole design as "lift the existing discipline one level" instead of "design a new one", and it produced the constraint that mattered most: territory exists **only** in the parallel pattern, so a team-level field is unavoidable and cannot be derived from members. Had I asked first, I would have offered options built on invented vocabulary. **Proposed fix**: make "search for the same problem already solved at another scope" an explicit pre-step for capability additions, and require the chosen design to state why it is not reusing what was found.
- **Two decisions were only answerable because a *previous* session's decision constrained them — the command has no notion of accumulated constraints.** "Roster as a `goal.md` field" is superficially the most natural reading of "record at the goal level", and I could only rule it out because FR-007 (definition never rewritten by a derived flow) and the concept authority's one-way binding were already fixed. Same for the persistence home: last session's `goal.md` + `summary/` two-way split made "add an authored `coordination.md`" a decision to *reopen a settled split*, not a free choice. I surfaced both as option descriptions, but only because I happened to hold three sessions of context. A fresh run would not. **Proposed fix**: the Coverage Scan should load prior `## Clarifications` sessions as *binding constraints*, and every new option should be checked against them, with any option that contradicts one labelled as such in the prompt.
- **[token-efficiency] Existence-checking cross-references is not enough, and I only know that because it failed last session.** I re-ran the semantic cross-reference check (print each reference next to the *text it points at*) on the four new-group references and all four were right — but the cheap version (does `FR-0NN` exist?) passed last session while two references were pointing at the wrong requirement. The expensive-looking check is ~15 lines of script and catches a class of error that no amount of re-reading reliably catches. **Proposed fix**: fold it into the Validation step as a standard check rather than something I remember to do — for each `FR-\d+`/`SC-\d+` reference outside `## Clarifications`, emit the referring line and the referenced requirement's first clause for verification.
- **[token-efficiency] Three sessions in, the spec has tripled in scope and nothing in the command watches the artifact's size or coherence budget.** 28 FR at draft → 27 → 32 → 42, and 5 user stories across seven FR groups. Every addition was justified and none is redundant, but the command happily accepts unbounded growth in a single requirement slice with no signal that the slice may have stopped being one slice. I recorded a size flag for the plan myself; the command should prompt it. **Proposed fix**: at wrap-up, when the target artifact's requirement count grows beyond a threshold or gains a self-contained FR group whose dependencies are limited to a subset of stories, emit an advisory suggesting the plan evaluate a phase or requirement split. Advisory only — never block, and never split automatically.
