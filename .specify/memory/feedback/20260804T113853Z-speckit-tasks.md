## Optimization Points
- Scope Revision Protocol 只在 `/speckit.clarify` 的命令文档里,但本次触发它的是一句**普通用户消息**(既非 `/speckit.clarify` 也非 `/speckit.plan` 的 `$ARGUMENTS`)。协议因此存在"无人认领"的空档:如果不主动去 clarify 文档里找它,默认路径会是"直接改 tasks.md"或"新建一个规格",两者都会丢历史。建议把该协议提到 `.specify/shared/workflow/` 成为独立的共享约定,并在 requirements/plan/tasks 三个命令的 Handoffs 里各指一次,使"用户在下游改范围"这一常态有明确入口。
- 协议第 3 步"residual-reference sweep"只要求 grep 被弃用术语,但未要求**同时校验新术语的采纳面**。本次弃用路径 `.specify/teams/<slug>/summary/` 清零之后,我另做了一次"新路径在 9 个工件中是否都已出现"的正向核对,才发现 quickstart 与 feature-ref 起初仍是旧口径。建议该步改为双向:弃用项零命中 **且** 新项在所有相关工件中均已出现。
- 协议未提示 Shared Strings 的**值变更**是最高风险的一类修订:`[[STR-001]]` 的引用点不会因为值变了而报错,任何漏改都会静默指向旧路径。本次靠"STR 定义数 = 1 且引用数 > 0"的机械核对兜住。建议协议显式列出"若修订改变了某个 Shared String 的值,MUST 逐个引用点复核语义仍成立"。
- 任务 ID 策略在协议中缺失。本次选择**不重排** T001-T101、把修订增量放在 T102+(US6 阶段),以保持既有引用稳定;但这使阶段顺序(Phase 8 US6)与 ID 顺序(T104-T120 在 T087-T101 之后)不一致,阅读时需要说明。建议协议给出明确取舍:小修订追加 ID 段并在 Notes 说明,大修订才整体重排。
- 本次最有价值的一步是把新设计**先跑一遍再写进契约**:双索引把 N 个团队装进同一个数据库,实测发现两个团队各自的 `TI-0001` 会因 `entity_ids` 全局主键而撞号(exit 3),必须加团队前缀;而"每团队 ID 团队内唯一"是极自然的直觉,纯推理几乎必然踩中,并且要到实现期才暴露。建议在协议的"regenerate downstream"一步补一句:若修订改变了数据的**聚合基数**(1:1 → 1:N),MUST 用最小样本真实跑一次装载/合并,再据结果写契约。
- token-efficiency: 本次全程未重读自己刚写的工件,改动一律用带足上下文的 Edit 精准替换;校验用两段 Python 一次性输出 FR 连续性/SC 配对/STR 定义与引用数/任务格式/blockedBy 完整性,而非逐节人读。一处真实失误值得记:把 `grep -c`(无命中时 exit 1)串在 `&&` 链中间,导致后续的 blockedBy 校验与残留扫描**根本没执行**,而末尾 `|| echo "ZERO HITS"` 还打印了误导性的"clean"。已重跑并纠正。教训:校验命令必须各自独立执行(用 `;` 而非 `&&`),或显式 `|| true`,否则"看起来通过"可能只是短路。
