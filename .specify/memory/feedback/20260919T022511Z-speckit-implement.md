## Optimization Points
- **The Completion Gate re-validation step does not say what to do when a gate's own cited premise has decayed.** Step 8 says "re-validate every gate item against the current tree (running its stated check)", which this run did — but three gates and two DoD rows cited premises that upstream edits had already invalidated: `BASE_SHA` was orphaned by the rebase (so `git diff BASE..HEAD` swept in upstream commits and two gates blamed another unit's files on this feature), and DoD-3/DoD-4 pinned preserved content by line number that this feature's own earlier insertions had shifted (`interview-pattern.md:125-126` → `:122-123`; `confirmation-gates.md`'s five criteria sections → all +2). Both times the right move was the same and neither is written down: re-freeze or re-cite, **measure that the new form is stricter rather than looser**, and annotate the row with the falsified premise instead of quietly substituting a different check. Adding that as one named move would turn an improvisation into a documented step — and would stop the failure mode where an executor "fixes" a gate by weakening it.
- **Step 9 walks into a vocabulary collision it does not mention.** The Pre-Status-Flip Gate's item 3 requires "every `SC-NNN` has a status row", and `templates/feature-details-template.md:70` states the `Planned → Implemented` condition as `SC-NNN_status=pass|deferred`. But `templates/verification-log-template.md:22-26` **owns** that vocabulary with five values and explicitly names this exact narrowing as the anti-pattern ("a DoD row reading 'record `pass` or `deferred`' silently forbids `partial`"). `/speckit.implement` is the only command that writes both files, so it is the only one that can hit this — and this run hit it with four honest `partial` rows. Step 9 should name the owner document and state which one wins, so the executor is not left choosing between misclassifying a criterion and overriding a state machine.
- **The "3 consecutive failed re-validations" escalation counter has no defined lifetime.** Step 8 tracks consecutive gate rejections and escalates at 3, but nothing says whether that count is per-session, per-run, or persisted. This feature ran in two sessions separated by a rebase and a scope change; the second session inherited an unknown counter value. Either persist it beside the gate results in `verification.md` or state that it resets per session — an unwritten counter is unenforceable, which is the same defect shape this feature's own blind-check lesson describes.
