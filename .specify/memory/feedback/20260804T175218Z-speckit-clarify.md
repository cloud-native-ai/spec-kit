## Optimization Points
- ## Optimization Points
- **A user-supplied authority document is a distinct clarify mode the command does not model.** The input was not a decision or a question — it was "check the spec against this file". That is a *conformance pass*: enumerate the authority's constraints, compare each against the spec, and classify every difference as already-aligned / conflict / gap. The command's Coverage Scan only knows its own fixed taxonomy (Feature Linkage, Functional Scope, Domain & Data Model, …), which does not help here at all; I had to invent the comparison procedure. Crucially, most findings should **not** become questions: of 9 differences, 6 had no optional space because the authority already ruled on them (outcome-not-tasklist, per-goal singularity, unrestricted object, criteria authority, no structural link, and the composition/hierarchy conflicts) and were integrated directly. Only 3 warranted asking — one because the authority and spec genuinely disagreed and dropping either side loses capability, one because *how much of the property this requirement owns* is a scope call, one because "single source of truth" had become ambiguous between two levels. **Proposed fix**: add a Mode A sub-procedure "conformance against a supplied authority" with the classify-then-triage rule — direct-integrate anything the authority already decided, ask only where the authority is silent, where honoring it costs capability, or where its direction of precedence is unclear.
- **The command never asks which artifact wins when the spec and an external authority disagree, yet that is the first thing that must be settled.** I had to raise it myself (it became the third question). Until it is answered, every conflict has two opposite valid resolutions — edit the spec, or edit the authority. Here "the definition file is a read-only input" made all nine findings resolve in one direction and turned a potentially sprawling negotiation into a mechanical pass. **Proposed fix**: when `$ARGUMENTS` names an external document as a standard to conform to, make "direction of precedence" the first question, before enumerating findings.
- **The removal-and-renumber problem I flagged last run recurred immediately, and prose numbering maps are already showing strain.** This session deleted one more FR, producing a *second* `旧→新` map; the two prior Clarifications entries now both need map-chaining to read correctly, and I had to hand-fix six stale FR cross-references scattered across Overview, Assumptions and Edge Cases (`FR-023`→`FR-022`, `FR-024`→`FR-023`, `FR-027`→`FR-026`, …). Nothing verified I caught them all except my own grep. **Proposed fix**: pair the renumbering clause with a mechanical rewrite — a script that, given a `旧→新` map, rewrites every `FR-\d+`/`SC-\d+` reference outside the Clarifications section and reports any that resolve to a deleted ID. Prose maps document the change; they do not perform it.
- **[token-efficiency] Self-reported counts in prose remain the most reliable place for me to be wrong, and the fix is always a script.** My first draft of this session's log claimed "13 concept points, 2 conflicts + 4 gaps" and the SC-013 baseline repeated it; recounting programmatically gave **17 / 3 / 6**. The composition conflict was uncounted and two gaps were named in the prose while excluded from the total — and the error had already propagated into an acceptance-criterion baseline, i.e. into something a later run would have measured against. Recounting also revealed SC-013's six conformance dimensions did not cover three of the FRs it was supposed to guard, so it was widened to eight. This is the third occurrence of this exact class (036's invariance-group count, last run's STR consumed-by lists, now this). **Proposed fix**: the Validation step should forbid narrative counts that are not produced by the run's own script output — either emit the number from a command, or do not state a number.
- **[token-efficiency] Reading the whole 274-line spec was avoidable on the second pass.** I re-read the full artifact at the start of this session even though the previous session had just rewritten it and the edit targets were locatable by grep. A cheaper pattern for a conformance pass: read the (99-line) authority in full, then pull only the spec sections each constraint touches via targeted grep with context. The edit-target exception justifies reading regions I modify, not the entire file up front.
