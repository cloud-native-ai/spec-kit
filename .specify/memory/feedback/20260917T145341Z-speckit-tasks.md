- **无权威副本**:每份都是快照,彼此按定义不一致,没有任何东西告诉新一轮哪份是起点、自己该放哪。
- **GATE 命令硬编码了这个路径**:我写的 GATE-1 是 `comm -13 .specify/specs/051-.../baseline-failed.txt …`。若约定位置变了,门禁就静默失效。
- 这正是本特性(051)要处理的那类问题的**框架侧同型实例**:一个被三处独立重新发明的约定,没有真源文档。建议要么写进 tasks 模板/一份共享 workflow 文档(含确切路径与再冻结时机),要么明确它不是约定。
- ### 2. plan 阶段的"逐条免责声明"保护了执行要求,却放过了**假前提**
- quickstart.md 场景 5c 的"以本仓为安装源执行 `specify init`"是**假前提**,而它躲过了 plan 阶段的 Post-Generation Quality Gate——因为该门的执行核验要求针对的是"可执行 CLI 示例",而 5c 被我自己标注为"agent 驱动、非 shell 管线",于是逐条免责声明生效、不要求实跑。**免责声明免掉了执行义务,却没有免掉前提真实性。**
- 结果是:假前提要到 tasks 阶段做环境探测时才被撞到,靠的是 Environment Prerequisites 规则 4 的跨制品漂移检查——一条**下游**规则偶然兜住了**上游**的漏洞。若本轮没有触发那次探测,它会在 implement 期以"演练跑了但验证的是 0.0.22 的模板"的形式暴露,那时更难归因。
- 建议:plan 阶段质量门的逐条免责声明,除声明"此例无法执行"外,MUST 同时**列出该例依赖的前提**(此处即"已安装 CLI 反映本工作树"),使下一阶段知道该重新探测什么。免责一个例子不等于为它的前提作保。
