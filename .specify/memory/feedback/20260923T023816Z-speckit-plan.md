## Optimization Points
- 模板的 Phase 1 摘要规则说了"先落盘后回填、预写计数会漂移",但**没有要求把印出来的派生命令实跑一遍**。本轮同一根因出现 **3 次**:① plan.md 印 `grep -c '^## 场景'` = 9,实跑得 10(该模式同时匹配 `## 场景覆盖表`);② feature-ref.md 印 `grep -cE '^\| FR-[0-9]{3} \|'` = 78,实跑得 85(主映射表与"未覆盖"表各含一次那 7 条 FR);③ quickstart 场景数因补演练而变 12,连带使 ① 的订正值再次过期。三处都是"印了一个派生命令或数字却没有实跑它"。建议在 `## Phase 1: Design Artifacts Summary` 的 ACTION REQUIRED 注释里加一句:**凡印出的派生命令 MUST 实跑并把真实输出贴上,计数取该输出而非作者的记忆**;命令若含正则,MUST 说明它会不会匹配到非目标行(本轮两处都是模式过宽)。
- Post-Generation Quality Gate 的 execution-verify 规则把作用域写成"`quickstart.md` 或 `contracts/` 里的可执行示例",**不覆盖 plan.md 自己印的命令**。但 plan.md 的 Phase 1 摘要表与 Mirror Obligations 的 Verify 列承载完全同类风险——BASELINE DRIFT 注释本身就警告"一个预写的退出码会发运一条没人度量过的判据"。建议把该规则的作用域从两份制品扩到**本命令产出的全部制品**(含 plan.md 的摘要表与 Verify 列)。
- 质量门点名了"省略了必需步骤的场景是错的",但**没有点名"开出了一条不可能执行的步骤"的场景**。本轮 quickstart 场景 8 开出 `--action cleanup` 清理一条未打包的演练条目,而该 action 实测要求 `--package`(`feedback-utils.py:1389` 抛 FeedbackError)、`dispose` 又只翻元数据不删文件——照它执行会把演练条目**永久留在真实存据**,从而伪化该文件基线总表第 18 行的 `count: 0`,让下一个执行者撞上一条他自己没造成的基线冲突。建议给该规则补一句:**多步场景的 teardown 与 setup 同等对待,MUST 实跑**;凡清理步骤涉及引擎 action,MUST 先核该 action 的参数前置条件。
