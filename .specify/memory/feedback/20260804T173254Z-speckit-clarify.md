## Optimization Points
- ## Optimization Points
- **A `[NEEDS CLARIFICATION]` marker about an external, verifiable fact must be resolved by verification BEFORE it enters the question queue — the command has no rule for this.** The Question Generation loop assumes every question goes to the user. Here the draft's only marker was the host CLI's `/goal` contract, which the user could not answer either; it needed an official-docs fetch (`docs.qoder.com/llms.txt` → `/cli/goal.md`). Fetching first changed the whole shape of the run: the docs showed `/goal set` accepts inline text only with no file-or-identity option, which is what made "drop the CLI integration" a sensible option at all — and it revealed the draft's FR-017 was asserting a capability the host CLI does not have. Had I asked the user first, the likely answer would have been to design against a guessed option. **Proposed rule** for the Coverage Scan step: classify each candidate question as *decision* (goes to the user) or *fact* (resolve by verification — docs, repo, execution — and present the finding as context to the decision question). Only decisions belong in the max-5 queue.
- **The Feature Linkage integration rule covers bind-to-existing but not create-new, so following it literally produces a dangling binding.** Mode A says only "Feature linkage → Update `Related Feature` with `Feature ID` and `Feature Name`". When the answer is "new Feature", writing just those two fields leaves the spec pointing at a Feature that has no index row and no detail file — an inconsistency `/speckit.analyze` would then flag, created by the command that was supposed to resolve the section. I had to infer the rest of the obligation myself (allocate the next ID from the index, add the `features.md` row, write `features/<ID>.md`, and add the reverse cross-reference in the neighbouring Feature I had just argued against binding to). **Proposed fix**: state the create-branch obligation explicitly in the Mode A integration rules — allocate next ID, register row + detail as Draft, add the reverse cross-reference — or explicitly hand it off to `/speckit.feature` and say so.
- **Deleting requirements is an unhandled interaction between two existing rules.** An accepted answer can remove FRs/user stories (here: 3 FRs and 1 story). That forces renumbering to keep IDs contiguous, which makes the FR numbers inside *earlier* Clarifications entries stale — but the append-only invariant forbids rewriting those rows. The command gives no ruling, so two runs would diverge (one renumbers and breaks history, another leaves gaps and fails the contiguity check). I resolved it by renumbering forward and appending an explicit numbering map to the new session entry. **Proposed fix**: add a "Removal & renumbering" clause to the shared integration rules mandating exactly that — renumber downstream, never touch prior entries, and emit a `旧→新` map in the new session entry.
- **[token-efficiency] The Validation step is entirely qualitative, so its exit gate is not reproducible — and improvising a deterministic check found defects two prior LLM re-reads had missed.** The rules list "no lingering vague placeholders", "markdown structure valid", "terminology consistent" — all LLM re-reads of the whole artifact, which is both expensive and unreliable. Per Program-First I scripted the checks instead (FR/SC contiguity + duplicates, SC↔Source 1:1 pairing, live-marker count, `[[STR-nnn]]` resolution both ways, Clarifications `- Q:` row-count monotonicity, residual sweep for dropped-design terms). Computing the Shared Strings consumed-by lists mechanically immediately exposed **three pre-existing inaccuracies** in the `STR-001` row (it named FR-007, FR-026/027/028, SC-008 and SC-011 as consumers when none of them cite the string) — inaccuracies that survived two hand-written "mechanical re-validation" passes in the checklist. **Proposed fix**: ship these as a small validator script invoked by the Validation step, so the gate is a verdict rather than a re-read. Two cheap wins in the same spirit: the marker check must match `[NEEDS CLARIFICATION:` (with the colon), since a prose mention of the token in a resolution note otherwise counts as a live marker; and the residual sweep must expect hits inside historical Clarifications entries rather than demanding a global zero.
- **[token-efficiency] Discovering an external doc page cost ~54 KB of fetched index.** `WebFetch` on the docs index returned 53.8 KB (auto-persisted to a temp file), from which I needed exactly one URL. I recovered by grepping the persisted file instead of re-reading it, then fetching the single page — but the cheaper first move is a targeted `WebSearch`/direct-URL guess, falling back to the index only if that fails. Worth a line in the docs-verification guidance: prefer a targeted fetch over an index dump when the page name is predictable.
