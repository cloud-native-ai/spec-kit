## Review
在 /speckit.team run 的前置步骤中，为读取 goal 判据而调用 goal-utils.py criteria <slug>（未带 --criterion），该 action 实为 setter，导致三条 Success Criteria 被整体替换为空。经 History 的 append-only 留痕机械提取原文并用引擎写回，已核实恢复值与事故前逐字节相同；未手改 goal.md。

## Optimization Points
- `goal-utils.py criteria <slug>` 在**不带 `--criterion`** 时会把该 goal 的全部 Success Criteria **替换为空**（`## Success Criteria` 变成 `None provided.`）。命令名与输出形态（打印 `slug:` / `criteria:`）看起来像只读查询，实际是破坏性 setter——`--help` 的一行说明是「replace criteria, recording the prior value」。本次因此误删 `draw-two-layer-structure` 的三条判据，靠 History 的 append-only 留痕才完整恢复。
- 建议：`criteria` 与 `status` 这类 setter 在**缺少必要入参**时应**报错退出**（exit≠0）而非静默以空值覆盖；或要求显式 `--clear` 才允许清空。当前行为等于把「查看」与「清空」共用一个入口。
- 建议：`/speckit.goal` 的命令文档与 `goal-utils.py --help` 应显式标注哪些 action 是读、哪些是写（`list` / `validate` / `check-statement` / `targets --list` 为读；`status` / `criteria` / `targets --add|--set` / `create` / `migrate` 为写）。
- 可恢复性做对了一点：`criteria` 变更前把旧值**逐字**追加进 `## History`，使误操作可无损回滚。这个 append-only 留痕设计值得保留，并建议在所有 setter 上统一落实。
- 代理侧教训（本条为自省）：对任何 `*-utils.py` 引擎，MUST NOT 凭 action 名推断读写性；调用前先 `--help` 确认，或改用明确只读的入口（读判据用 `list --json` 的 `criteria_count` 或直接读 `goal.md`）。
