## Optimization Points
- 1. **手改 `features.md` 的长单元格需要「行拆列→断言→整表校验」的固定流程,substring 替换链会把文件改崩。** 本轮给 053 行的 Last Updated 单元格追加一段 tasks 记录时,一个先嵌入含 `|` 的文本、再用两步字符串修补的链条把整张 53 行的表压成了 1 行(HEAD 未含该损坏,恢复零损失;事后每一步的 `replace` 单独看都无害,坏在跨步用 `row.split` 的旧变量去替换已改写的文件)。修法不是更小心,而是把流程钉死:一次性 `split('|')[1:-1]` → 断言恰 7 列且每列不含 `|` → 重组 → **写前**跑整表校验(行数/每行管道数/ID 连续),失败立即 `git checkout -- <file>` 重来而非继续修补。恢复之所以便宜,只因为先把上一轮成果提交了——这一步顺手救了这次事故,值得作为默认纪律写进命令。
- 2. **让 tasks.md 提前踩自己特性要修的坑,能暴露只有自举才会现形的约束。** 本轮 T018 行内用反引号引用 blockedBy 标记字面量,被**当前**的 `validate-tasks.py`(尚不区分提及/引用,而这正是 FR-009 要机械化加守卫的规则)判为悬空引用报 ERROR;同理,T045 计划写入的 `[green:]` 认领在 T019 修好分类器之前会让步骤 5 的 `parallel-safe` 假报警。处置:命令的生成规范里,涉及"本 spec 会改变校验器语义"的步骤时,应**先**让行避开该形态(引用改用坐标)、把踩坑点编成显式串行任务,而不是靠事后解释 WARN。
- 3. **自查脚本也是被测物:跑在已知坏例上之前,别相信它的清白。** 校验故事标签的临时脚本按冒号截断 Phase 名后再判断是否故事阶段,把 Phase 3–7 全部误标 NON-STORY(文件本身是对的)。本轮 Note 段已把它列为第四个形态陷阱;可推广:凡为「验证刚写出的制品」临时写的检查,先在一个故意做坏的最小样本上跑一遍,再拿它的绿当证据。
