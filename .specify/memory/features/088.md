## Overview

框架已合入大量并发与异步流程：team 并行派发、外部子代理、阶段执行器、嵌套 SDD 运行、主从监视结构。并发度越大，用户在长跑中越难知道「现在到底在做什么」——会话可能几十分钟没有任何输出，而这段沉默与卡死、跑飞、等待输入完全无法区分。

现状的缺口不是「没有记录」，而是**没有节奏、也没有确定的可见面**：磁盘上已有运行记录与逐条状态文件，外部派发已有 `.live.log` 三元组，进展汇报纪律也已存在——但它以 15 分钟的交互档为缺省，且没有规定「team 必须有一个人负责汇报」「主从结构的主流程必须汇报子流程」这两件事。

本 Feature 把现状可见性变成**框架级义务**，复用既有 owner 而不再造一层：Progress Reporting 继续拥有节奏纪律与四要素内容下限；Subagent Definitions 的 External Dispatch Visibility Contract 继续拥有可见载体；team 存储、agent Template 存储与 line registry 继续拥有被汇报的状态。新增的只有一份 owner 文档、一个 reporter Template、roster 上的一个席位义务、主从结构的一项汇报义务、一个有界摘要入口与一个确定性守卫。

2. **双档周期与唯一缺省值**：长跑档缺省 30 秒，交互档沿用既有 progress-reporting 缺省；两档由「本次运行是否存在活的汇报接收方（reporter 席位或主从结构主流程）」这一条声明性条件选择，同一运行内不竞争。
3. **reporter 的 agent Template**：发布在框架 agent Template 源目录（`agents/`，`specify init` 安装到 `.specify/agents/templates/`），能力面足以读状态、写自身流工件，不含派发／授权／重试／终止权。

5. **主从汇报义务与 `coaching-skills` 修订**：主从结构按周期汇报每个被派发子流程的身份／状态／最后活动龄期，按既有阈值表区分「慢」与「停滞」，显著状态变化越周期上报；`skills/external/coaching-skills` 的 `## Dispatch Payload` 闭集必须增补汇报字段（保持闭集不变量，不做「任意字段」放宽）。
6. **当前态摘要入口 + 确定性守卫**：一个 `speckit.*` 瘦命令 + 一个确定性脚本，共用同一读状态路径；摘要按声明的上限截断并报出省略条数、对陈旧条目显示龄期、无运行时报「无正在运行」并以声明退出码退出。
7. **效率维度（第二轮修订）**：状态行与摘要对每个已列单元携带**一个**有界效率元素（单元标识 + 耗时，记录携带时加 token 与调用次数），每项按记录所载 provenance 标注，缺测显式渲染「未评估」而非 `0` 或省略；元素是既有行/摘要的内容，受既有条目上限约束，不新增行、不新增第三可见面（FR-023、A17）。

## Implementation Notes

- **两顶帽子**：owner 文档、Template、席位义务与守卫须落在框架源（`shared/`、`agents/`、`skills/`、`scripts/`、`templates/`），并同步到本仓 `.specify/` 运行时镜像；只改 `.specify/` 不会到下游项目。
- **不新增机制**：无定时器、无守护进程、无第三方依赖、无新持久化存储、无第二注册表／状态脊／账本；节奏由运行中的流程在自身步骤之间执行，与既有 progress-reporting 的机制口径一致。
- **状态来源只读**：摘要与守卫的**机器可读来源**是 line registry（owner：`skills/external/sdd-loop-driver/scripts/line-registry.py`；条目按其引擎的解析顺序落在 `$SPECIFY_LINE_REGISTRY_DIR` → `$XDG_STATE_HOME/spec-kit/lines` → `~/.local/state/spec-kit/lines`）；`.specify/state/` 的状态脊仅供人读，不用于回填 registry 已携带的字段。不新建「流程状态注册表」。
- **载体记录不新增工件**：每条汇报的接收载体记在发出方**既有**的运行记录里（team run report / 派发记录 / 监视记录），不为汇报新造落盘工件。
- **停滞数值不复制**：数值阈值归既有 team pattern 的阈值表；owner 文档引用而不再定义一套。
- **执行类**：本线 `flow_class=execution`，验收以运行时可观察行为为准（到点无行、子流程从汇报中消失、摘要无界、席位缺失而守卫仍绿）。
- **效率元素的边界（第二轮修订）**：效率信息只落在本特性已拥有的两个面上（周期状态行、当前态摘要），作为每个已列单元的一个元素；不新增第三面、不新增测量专用周期。`not_evaluated` 必须显式，缺测不得填 `0` 或均值（与 run-determination 的「测量而非印象」同向）。
- **measure 不是 watcher（第二轮修订）**：`/speckit.measure` 调用即读、读毕即退，与摘要入口同形；它不轮询、不常驻、不导指标。既有引擎的 `list-records` 与 `aggregate` 语义不变，`aggregated/` 层仍属 feedback 的收包汇总通道，不被本特性挪用。
- **趋势是读取期比较（第二轮修订）**：趋势＝调用方选定的两个窗口在读取时比较，不落盘基线序列（落盘即第二存储），也不下「太慢」阈值裁决（阈值 owner 不属本特性）。

## Future Evolution Suggestions

- 若后续引入 web/dashboard 渲染面，应作为摘要入口的**消费者**接入，而非第二套状态源。
- 若更多技能实现自身的主从结构，可把「主从汇报义务」的接入点收敛为一个共享的派发载荷片段，避免逐技能重述字段。
- 停滞阈值若需按场景差异化，应在既有阈值表内扩展维度，而不是引入第二个阈值 owner。
- 效率若需按场景差异化（例如按模型／配置分组），应在既有权重的 `config_id` 快照维度上展开读取，而不是新增采集字段或第二份记录。
- 若 measure 的固定窗口选择成为常用动作，可考虑把常用窗口作为命令输入侧的命名预设（读取期映射，仍不落盘基线）。
