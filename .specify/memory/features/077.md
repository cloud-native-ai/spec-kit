# Feature Detail: 项目文档的 SDD 接入（特性级类别与文档型阶段门禁）

**Feature ID**: 077
**Name**: 项目文档的 SDD 接入（特性级类别与文档型阶段门禁）
**Description**: 把项目文档的开发接入 SDD 阶段链：在 `requirements.md` 声明特性线类别（`flow_class`），七个阶段命令按类切换门禁算子；表达类的 plan 产出可核对的文档结构（章节树 / 基准读者 / 证据清单 / 事实 owner 清单），implement 按结构落文并过四面门禁；`sdd-loop-driver` 携带类别、按类校验门禁证据，并把两槽位测试预算在表达类下换成两个文档门禁槽位
**Status**: Draft
**Created**: 2026-10-30
**Last Updated**: 2026-10-30（requirements：`.specify/specs/077-doc-sdd-integration/requirements.md` + 质量清单 + 三份门禁证据落盘；绑定新建 Feature 077）

## Overview

框架已有「执行 / 表达」分类轴（Feature 069，`Implemented`）：判据、唯一所有者、79 行逐流程台账、六面文档型门禁与八阶段算子表都在位，`/speckit.docs`、`/speckit.humanize` 两个入口也已接线。但这条轴**只到流程单元为止**：

- 台账回答的是「这个命令 / 技能属于哪类」，没有任何位置回答「**这条特性线**属于哪类」；特性索引与详情都没有该字段。
- 七个阶段命令（requirements / clarify / plan / tasks / checklist / analyze / implement）对 `flow_class` 零命中——**表达类特性线跑的还是代码型门禁**，八阶段一个不少，但每阶段仍在要测试与覆盖率。
- `sdd-loop-driver` 同样零命中：阶段提示词不带类别，U4 只校验哨兵与产物，两槽位测试预算按代码型设计。文档型线即便手工声明了类别，也无人据此放行或拦截。

069 的规格把这件事明确划到后续特性（其 Out of Scope：「不新建表达类专用命令集……属后续特性」）。本特性承接的正是**接线**而非再定义：把「类别可查」变成「类别被真正读取并改变门禁算子集」，并把用户对「项目文档要像代码一样有严密结构与逻辑」的要求落成能红能绿的判定。

三件事互为支撑：

1. **特性级类别**：一条特性线在 `requirements.md` 头部声明类，经既有引擎解析（同形记录、同退出码语义、未声明按默认并可见标注），索引与详情不复述。
2. **阶段命令按类切换**：七个模板在门禁判定前读一次类别，执行门禁 owner 的阶段算子行；执行类零行为变化，降级可见且不得当通过。
3. **文档结构与逻辑硬约束 + 驱动接入**：plan 产出四项结构、implement 过四面门禁；驱动携带类别、校验门禁证据、把两槽位换成两个文档门禁槽位。

## Latest Review

- **2026-10-30 requirements**: `/speckit.requirements` 落 `requirements.md`（25 FR / 8 SC / 4 用户故事 / 2 Shared Strings）与 `checklists/requirements.md`；三条确定性门禁实跑——`validate-requirements.py` `status: ok`（五项全 pass，239 行 / 33 定义行 / 0 error 0 warning）、`pre-analyze-check.py --stage requirements` `decision=pass`（errors=0 / advisories=0 / fr=25 / sc=8）、`decomposition-check.py --mode plan` `decision=proceed`（fr_count=25 ≤ 30）。绑定新建 Feature 077，并对 069 / 069a / 069b / 058 / 067 / 062 / 074 / 076 做 reuse-first 复核。三条裁决记录在规格 § Assumptions：声明位置（requirements 头部字段）、声明单位（特性线，多切片各自声明）、接线面（七个模板，纠正派发文本「六个」与枚举七个的计数不一致）。

## Key Changes

1. **类别载体**：`requirements.md` 头部一行类别字段（`**Flow Class**`，封闭取值 `execution` / `expression`）；特性索引与详情至多留指针，第二处声明即缺陷。
2. **解析入口**：复用唯一读取引擎 `scripts/python/flow-class-check.py --action lookup`，新增特性线键族，返回与单元同形的记录；不新增第二份分类数据文件、不新增第二条读取路径。
3. **七阶段接线**：`requirements` / `clarify` / `plan` / `tasks` / `checklist` / `analyze` / `implement` 七个模板在门禁判定前读一次类别，执行门禁 owner 的阶段算子行；模板只带调用与 owner 指针，不带算子表副本。
4. **文档结构硬约束**：表达类 plan 产 `## Document Structure`（章节树 / 基准读者与阅读场景 / 证据清单 / 事实 owner 清单）；implement 两向比对章节、逐断言证据三件套、事实唯一 owner，四面门禁 blocking。
5. **驱动类别感知**：阶段提示词携带类别（本地与远端同规）；U4 对表达类校验门禁证据；两槽位测试预算换成两个文档门禁槽位（时点不变，不得静默跳过或记 0）。
6. **不变量**：八阶段集合、门禁数量、P0/P1 定义、analyze/review 100% 调用率一律不动；不新增命令、不引入运行时。

## Implementation Notes

- **现状锚点（2026-10-30 实测）**：`flow-class-check.py --action check` = 79 单元 / 0 finding（27 命令 + 52 技能）；`lookup --unit-id "/speckit.implement"` = `execution` / `mixed-oracle` / `source: ledger`；`lookup --unit-id "feature:077"` = `invalid unit id` + exit 2（特性的键族是新增对象，不是既有别名）。`isomorphism` = 8 阶段 / 6 面 / 0 finding；`faces` = 6 面 / 0 finding。
- **声明位置为什么是 requirements 而不是索引或详情**：requirements 是链上第一个阶段，也是第一个做门禁判定的阶段；绑定时点（clarify）晚于它，若声明落在 Feature 详情，第一个阶段必然在错误门禁集下运行再翻转——正是要禁的静默切换。其次，七个阶段命令与驱动都以 spec 目录为输入，声明与产物同目录零额外查找；而在 76 行手维护宽表上加列会让每行出现空值，把「未声明」变成默认态。
- **声明单位是特性线，不是 Feature 编号**：多切片特性的切片可以有不同类别（069a 交付引擎、069b 交付映射文档即此类），注册表汇总成一个取值必然错一半；类别按线解析也顺带封住「进程级全局值跨线泄漏」这一并发缺陷。
- **与 069 的关系是承接不是复制**：069 交付「类别存在且可查」「映射存在且可核」；本特性交付「命令与驱动按类别执行」。069 与两个切片均 `Implemented`，其状态与正文 MUST NOT 被本特性改写。
- **对 058 / 067 的边界**：`sdd-loop-driver` 的载体归 058，两槽位测试预算的时点与审计口径归 067（规格实存、索引未登记，属既有缺口，不在本特性范围）。本特性只在它们的 owner 文件中增加**类别分支**，`execution` 分支逐字不变。

## Future Evolution Suggestions

- 类别声明从「作者写一行」升级为「作者写 + 机器给出建议」的辅助模式（本特性明确排除自动推断模型）。
- 文档结构产物的章节树与既有 `create-docs` 基准结构对齐，让「计划结构」与「站点结构」共用一套节名。
- 表达类三项基线（门禁调用次数、人工确认次数、requirements→analyze 墙钟）在试点线上积累后，回看 069 的下降目标是否达成。
- 项目侧自建流程的类别声明面（069 显式推迟、本特性亦未建）——届时需与特性线声明共用同一判据。
