# Feature Detail: 驱动子代理的任务拆解与配合机制（Task Decomposition & Team Coordination for Subagent-Driven SDD）

**Feature ID**: 070
**Name**: 驱动子代理的任务拆解与配合机制（Task Decomposition & Team Coordination for Subagent-Driven SDD）
**Description**: 在无人值守 SDD 驱动的阶段边界增加一等的工作拆解与配合层——把阶段拆成有界工作包并用确定性门校验，映射到既有团队席位与协作模式，按依赖图派发、独立验证、确定性集成；阶段哨兵、U4 与全部质量门不变，改进以相对基线的墙钟时间、返工率、并行效率与人工干预数度量。
**Status**: Draft
**Created**: 2026-10-24
**Last Updated**: 2026-10-24 (clarify: nine decomposition/coordination decisions landed in `requirements.md` Clarifications and `notes/clarify-decisions.md`; 30 FRs unchanged)

## Overview

Feature 058 的无人值守循环在阶段边界是串行且整体的：一个子代理执行整个阶段，驱动等待，然后一次性校验。2026-10-24 的测量记录显示，成本集中在最长的 `plan` 与 `review` 阶段，以及 review 之后的单体修复（064 的 review 后修复为 156 分钟）；同时每个规范阶段被重复执行（063 达 2.6 次/阶段，064 为 1.4 次/阶段）。本特性不增加另一个 watcher，而是引入工作拆解与配合层：阶段被拆成有界工作包（输入、输出、写属、依赖、预算、验收证据），经确定性门校验后按依赖图派发；只读包可并行，写包在行工作区内串行；每个包由独立验证者核验，驱动在阶段 U4 之前完成聚合与确定性集成。

边界是严格的：驱动仍是唯一协调者，阶段命令不透明，阶段哨兵 + U4 + checklist/analyze/review 门不变，Feature 064 的线路登记/归属/worktree/集成语义是既有原语而非本特性范围，Feature 067 的 implement part brief 与测试经济学被扩展而非替换。首片只允许只读包并行；并行写包需要 Feature 064 的后续扩展，明确不在本特性。

## Key Changes

1. **工作包模型（Work Package）**：定义有界、可独立验证的包单元，字段覆盖 id、阶段、目标、输入、输出、写属/只读路径、依赖、并行安全、预算、验收与证据；implement 的包是既有 067 part brief 的扩展，不引入第二种 brief 格式。
2. **确定性拆解门**：DAG 无环、阶段必需输出全覆盖且无孤儿、并发写属不相交且落在行 Ownership Manifest 内、包大小有界、模式与图兼容；任一项失败即阻断派发，只能拆分、串行化或单包回退。
3. **阶段团队 preset + 薄适配器**：复用 create-team 的 Role × Stage × Type 席位与 parallel/serial/iteration/continuous 模式词汇，新增 schema 兼容的席位 preset 与驱动侧薄适配器；不持久化每阶段 team.md，不修改 create-team/run-team。
4. **按图派发与失败隔离**：依赖满足才派发；只读包可在声明的槽位上限内并行；写包串行；单包失败/预算耗尽不影响无关包；每包至多一次重试且必须改变范围、预算或拓扑；第二次失败升级到既有 U5 阶段重试。
5. **独立验证与确定性集成**：每包由非执行子代理验证并留证据指针；驱动检测缺失/矛盾输出后按 DAG 顺序集成；冲突即停止，不得把部分集成提交成完整阶段产物；阶段哨兵与 U4 仍是最终权威。
6. **可观测与度量**：状态脊记录包台账（派发顺序、起止、尝试、预算、裁决、证据、输出路径），阶段报告给出关键路径、墙钟、并行效率、返工率；验收按相对基线与零门回归，未测指标记 `not_evaluated`。

## Implementation Notes

- 首片阶段范围：`plan` / `implement` / `review` 在门通过时默认拆解；`analyze` / `clarify` 仅在显式启用时使用只读调查包；`requirements` / `tasks` / `checklist` 保持单子代理。
- 并行写包在本特性首片明确排除；只读包并行必须声明端口/临时目录/缓存隔离或只读共享资源，槽位数不得超过该行剩余并发额度（064 的并发上限为唯一 owner）。
- 重试语义：每包至多一次自动重试，重试必须改变范围（更小的包）、预算（附派发级证据）或派发拓扑；相同预算的原地重跑禁止。第二次失败先判阶段门失败，再进入既有 U5（默认两次阶段重试）。
- 团队复用裁定：采用 schema 兼容的 stage-team preset + 驱动侧薄适配器，而不是每阶段持久化 `.specify/teams/<slug>/team.md`；后者需要 goal 建立与绑定、每次运行报告与 summary 刷新，生命周期远超一个阶段。
- 度量定义：阶段墙钟 = 首个包派发到阶段 U4 完成；关键路径 = 时长加权的最长 DAG 路径；并行效率 = 各包时长之和 ÷（墙钟 × 最大并发包数）；返工率 = 阶段派发尝试数 ÷ 规范阶段数；人工干预 = 每次运行的 continue/retry/status 类用户消息数。
- 交付面：sdd-loop-driver 技能源（SKILL、references、templates、scripts）、其 docs 页、以及本特性规格与证据；不新增运行时服务、守护进程、外部依赖、模型 API，或第二套注册表/账本。
- 证据来源缺口：简报命名的原始证据文件（macOS 家目录 digest、`/private/tmp` 状态脊、桌面/CLI 会话转录）在本执行环境不可达；基线按简报的 2026-10-24 dated record 采用，未重新测量，已在规格 A9 与 `## Measured Baseline` 披露，后续复测必须替换该记录而不是混用来源。
- 绑定与脚手架偏离：本 Feature 在 requirements 阶段先行绑定（默认协议为 clarify 时绑定）；分支 `070-subagent-task-teams` 已存在，故跳过脚手架脚本的 `git checkout -b`，规格目录以同一模板手工落盘；两项均记录在规格 Clarifications。

### Canonical Status State Machine (single source of truth)

This is the authoritative transition table cited by `/speckit.feature`, `/speckit.plan`, `/speckit.tasks`, and `/speckit.implement`. Those commands MUST NOT paraphrase the rules — they MUST point at this section.

| From | To | Owner Command | Trigger / Definition of Done |
|------|------|----------------|------------------------------|
| (n/a) | Draft | `/speckit.feature` | Feature row first added to `.specify/memory/features.md`. |
| Draft | Planned | `/speckit.plan` | `plan.md`, `data-model.md`, `contracts/`, and `quickstart.md` exist for the requirement bound to this feature; Constitution Check has no unjustified Fail rows. |
| Planned | Implemented | `/speckit.implement` | `tasks.md` has zero `[ ]` rows (all tasks are `[X]` closed or `[~]` deferred) AND `verification.md` records a `SC-NNN_status=` row for every Success Criterion in `requirements.md`, drawn from the status vocabulary owned by `.specify/templates/verification-log-template.md` (MUST NOT be narrowed to a subset of it — an honest `partial` is a legal status, not a DoD failure). |
| Implemented | Ready for Review | `/speckit.review` (or human) | All deferred (`[~]`) tasks are resolved or explicitly waived, and review evidence has been produced. |
| Ready for Review | Completed | Human / governance | Final acceptance. |

**Critical contract**: `/speckit.plan` MUST land status `Planned` (not `Implemented`). `/speckit.implement` MUST advance `Planned → Implemented` only when the DoD above is satisfied; if any task is `[~]` deferred, append a ` (deferred: T<comma-list>)` suffix to the `Last Updated` cell in `features.md` so the deferral is visible at the index level.

**Extension slice rule**: when a later requirement plans an extension of a Feature whose status is already `Implemented`, the status is NOT regressed (`Implemented → Planned` is not a legal transition). Instead: keep the status, record the extension's planning in the Feature detail (Latest Review / Key Changes) and in the `features.md` Last Updated cell, and let the extension's own `/speckit.implement` run re-assert `Implemented` with updated evidence when it closes.
