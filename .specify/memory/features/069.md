**Feature ID**: 069  
**Name**: 执行/表达二元分类与文档型 SDD 同构（Execution/Expression Classes & Document-Form SDD）  
**Description**: 引入贯穿全部流程的一等分类轴「执行（execution）/ 表达（expression）」，以验收 oracle 而非介质为判据，并在该轴上重建文档型 SDD 路径——同一套八阶段与方法论骨架，只换门禁算子集；同构主张落成可核对的阶段映射与一份不可同构边界清单

## Overview

框架今天只有一条分类轴（复杂度轴：复杂/简单命令，决定有没有 wrap-up 面），没有一条回答「这个流程的交付物由什么验收」的轴。结果是文档型工作被迫套用为代码设计的门禁：Markdown 架构文档要过构建与结构检查，而这些检查通过并不证明内容正确；与此同时，真正的文档型判据（读者是否读懂、事实是否与外部相符、同一事实是否只有一处）散落在 `user-facing-comprehension.md`、`one-source-of-truth.md`、`create-docs` / `improve-docs` 里，没有被组织成一组门禁。本 Feature 把「执行 / 表达」立为一等分类轴，用它选择**门禁算子集**（不改变阶段、不改变严重级、不减少门禁），再把「代码是以计算机语言写的文档、文档是以人类语言写的代码」落成 8 行 × 3 面的可核对映射与四类不可同构边界，使同构可判定而不是比喻。

## Key Changes

1. **分类本体**：判据 = 主交付物的验收 oracle（机器执行后的行为 vs 人阅读后的理解与事实相符），不取介质；两类取值 `execution` / `expression`，机器键 `flow_class`；默认 `execution`，未声明者在消费点标注「未声明·按默认」。
2. **唯一所有者 + 逐流程台账**：`shared/definitions/flow-class-definitions.md` 同时拥有判据、取值、边界例、台账与类中立清单；台账是所有者内的手写声明式行集，对账检查解析它与命令/技能清单比对，带反空真下限与覆盖率断言。
3. **门禁不变量**：分类只换算子集——八阶段不变、门禁数量不降、P0/P1 定义不动、analyze 与 review 调用率 100%、人工评审不可省；阶段完整性判定**不读取类别**，从机制上封死「属表达类所以跳过」。
4. **文档型门禁六面**：需求清晰度、读者/目的/边界、证据分级与 as-of、结构/链接/构建、事实一致性、评审；每面指向单一 owner，本特性只补新增面（证据等级与 as-of、事实一致性检查器），不复制既有判据。
5. **同构与边界**：8 阶段 × 3 面（结构/流程/逻辑）的映射，行级标注强制门禁或「已声明未强制」；四类不可同构边界（验收 oracle / 验证算子 / 失败可见性 / 语义 oracle）各须在至少一处门禁设计中被指认处理。
6. **兼容与分发**：分类数据随既有 `shared/` + `specify init` 路径到达客户项目，不新增项目侧存储或读取点；未刷新项目行为不变；本特性不新建命令。

## Implementation Notes

- **分类与同构同文档**（clarify 裁定）：`flow-class-definitions.md` 一份文件承载判据/取值/边界例/台账/类中立清单/同构映射/不可同构边界。理由是「边界例」就是映射为何到此为止的理由，拆到两份文件会各自漂移；命名遵循同目录 `<域>-definitions.md` 惯例（现有 10 份：agent / contract-clause / derivation / dogfooding / framework-map / goal / probe / self-improvement / subagent / tool）。
- **词义消歧**（同词异义，非冲突）：`execution` 与既有 **Agent Execution**（Agent 三层分类法第三层）同名不同义。消歧义务落在两处——所有者条目的 § 命名空间 小节与 `.specify/memory/glossary.md`；机器侧以带命名空间的 `flow_class` 承载，不以裸 `execution` 作键。`expression` 与 `flow_class` 在本仓作标识符零占用（2026-10-24 实测；`expression` 仅作为普通英文词出现在散文里）。
- **台账的形态先例**：复杂度轴已有一份同样是「手写声明式表 + 由契约测试派生」的实例——`.specify/specs/027-feedback-mechanism/contracts/command-classification.md` 与 `tests/contract/test_feedback_command_classification.py`（含 `MIN_COMMANDS` 下限与「表完整」vs「没解析出行」的区分）。本特性的对账检查照该形态做，不引入第二套机制。
- **委托关系是机械事实**：命令模板里以 `.specify/skills/<layer>/<name>/SKILL.md` 形式声明「Load and follow 哪个技能」，检查器据此解析命令↔技能配对，再与台账比对同类，不依赖人工维护的委托清单（FR-039）。
- **六面门禁的既有 owner**：读者面 = `shared/guidelines/user-facing-comprehension.md` § 基准读者与覆盖协议（A5 不新建第二套读者定义）；结构/链接/构建面 = `create-docs` 的 `scripts/docs-utils.py`（`--action validate` 管保留名与结构、`--action fix-links` 管链接、站点脚手架存在时由 `improve-docs` § Verify 跑 Hugo 构建）；需求清晰度面 = `validate-requirements.py` + 质量清单；事实一致性判据 = `shared/guidelines/one-source-of-truth.md`（本特性只加检查器）；评审面 = 既有评审流程。
- **新增面的对象差异**：证据分级（实测 / 推断 / 引用）与 as-of 是本特性新增的**文档断言**属性，与 `shared/workflow/evidence-step.md` 的七态证据词汇（机制存在/接线/被使用，描述机制而非断言）、`shared/guidelines/single-run-evidence.md`（一次昂贵执行的记录留存）对象不同，MUST NOT 互相重定义或收窄取值域；as-of 的既有先例是 glossary「易变测量值」条对基线值的要求。
