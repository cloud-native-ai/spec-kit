# Feature Detail: Interview Mode

**Feature ID**: 042  
**Name**: Interview Mode  
**Description**: Promote interview-style elicitation from a single agent's workflow into a framework-wide design pattern (`shared/patterns/interview-pattern.md`), usable from commands, skills, and agent/team definitions, plus `/speckit.interview` as the standalone entry.  
**Status**: Implemented  
**Created**: 2026-08-06  
**Last Updated**: 2026-08-06

## Overview

The framework had **interview behavior without an interview pattern**. Multi-round user questioning existed in at least six places, each having independently invented its own rules: `/speckit.clarify` (a capped sequential loop over a fixed taxonomy), `shared/workflow/interview-walkthrough.md` (the Requirements Analyst's field-proven multi-day walkthrough), `summarize-project` (four sequential confirmation gates), `create-skills` (one question per round until frontmatter is complete), `study-project` (≤3 questions per round across analysis phases), and `/speckit.goal` create (a fixed three-item elicitation). None of them referenced the others, and nothing named the shared mechanics.

The cost of that gap is not stylistic. Each site re-decided the load-bearing questions — whether the agent may ask the user for a fact it could look up, whether answers are written through before the next round, whether one round may ask a question whose prerequisite is still open, and *who* decides the session is finished. Sites that got those wrong produce the two characteristic failures: interrogating the user for discoverable facts, and declaring a converged artifact that encodes decisions nobody was asked about.

This Feature names the mode once, with an explicit boundary against the neighbours it is confused with, so that a new command, skill, or team member can claim it by declaring four things instead of reinventing it.

## Latest Review

Not yet reviewed. Delivered directly (registered Feature + implement, no spec→plan→tasks track) at the user's direction after a research pass over the reference `grilling` / `grill-me` skills and a full survey of the project's ~20 commands, 26 skills, and 7 role agents.

## Key Changes

1. **`shared/patterns/interview-pattern.md`** — the generic pattern, in the house style of `reconcile-pattern.md`: applicability judgment (tacit information + branching decisions + a converging target artifact + a live user), the core model (design tree / dependency DAG, decision records, isolation planning, frontier, round, write-through), the `I0–I6` loop with retraction propagation and the exit gate, the four-part **self-contained open-question format** (ID + plain-language title + mandatory `**Context**` blockquote + an open question, no options and no recommendation) with its comprehension rules, the fact-vs-decision split, ledger/decision-record schema and resumability rules, the embedding contract, the adoption map, and the anti-pattern list.
2. **Boundary section** — a table separating interview from **reconcile**, **iteration loop**, **continuous loop**, and a **one-shot confirmation gate**, keyed on two axes: where the information comes from, and what ends the loop. Includes the nesting rule (an interview *feeds* a reconcile or a plan; it never substitutes for one) and a near-synonym list (frontier ≠ tolerance band; user-confirmed stability ≠ quality threshold ≠ one-time approval; interview ledger ≠ audit log ≠ STATE.md).
3. **`/speckit.interview`** — the standalone, **unbounded** entry: resolves the target artifact (argument → current phase artifact → new record), probes writability before asking anything, resolves and resumes the ledger, runs the loop, and exits only on the user's confirmation. Carries the standard Glossary / Feedback / Documentation steps. Delegates all graph computation to the engine (item 6).
4. **Two standalone run modes** (added after the initial delivery): **Special Interview (专题访谈)** requires one concrete target (file / directory / concept), keeps the design tree bounded to it, and each round **edits that target in place then echoes the change back** so the user sees decisions as recorded text; **Informal Interview (漫谈访谈)** may start from a bare topic, spans the whole space, and each round **consolidates and organizes** — reconciling answers against each other, grouping by area, splitting or adding artifacts as the shape emerges. Both run the pattern's round **unchanged** (whole frontier, open questions, then wait): the modes differ in *what converges* and *what the write does*, never in the question unit. Mode resolves before the first question (explicit argument → resumed ledger header → concrete target implies Special / broad topic implies Informal → ask once); switching requires an explicit user request recorded as a header amendment.
   - **Reverted design note**: the modes were first drafted as a per-answer vs per-batch **write unit**, which would have had Special ask one question at a time. That contradicted the pattern's own `Round` rule (and the `grilling` loop it derives from), where asking the whole askable frontier per round is the point and drip-feeding is an anti-pattern. The write-unit generalization was reverted from `interview-pattern.md` — the pattern is unchanged by this Feature's second pass — and the distinction was moved to scope + write behaviour, which needs no pattern change at all.
5. **Structured decision records + retraction propagation** (third pass): the design tree was previously a *mental* model, so nothing could answer "what depended on this?" — a changed answer silently left descendants derived from a dead premise, and independent questions were never planned as such, so one revision could invalidate a whole session. Now: each decision is a **persisted record** with a stable **ID**, its **`dependsOn`** premises (a DAG — one decision may rest on several), and the **artifact span** it wrote; `I1` additionally **plans branch isolation** and orders branches so the **most-depended-on premises are asked first**; `I5` **surfaces conflicts** with already-settled decisions instead of silently overwriting them; and a new **`I6` retraction step** walks the transitive descendants, classifies each as still-valid / needs-confirmation / invalidated, rolls back the invalidated spans, re-opens those decisions in dependency order, and records the retraction. Questions now carry their ID and name the decisions they build on (see the format in item 7) so the user has a handle to retract by. Retracted records are superseded, never deleted (↩︎ + `Superseded by`); IDs are never reused; the exit gate additionally requires no unresolved conflicts and no stale descendants, and a retraction *at* the gate reopens the loop.
6. **`interview-utils.py` — the DAG made executable** (fourth pass): the decision graph was specified as prose, which meant every run re-derived reachability and ordering by reasoning — unreliable for exactly the operations that must be exact. `scripts/python/interview-utils.py` (stdlib-only, `<TOOL:.specify/memory/tools/interview-utils.py.md>`) now owns them: `init` / `add` / `answer` / `defer` maintain the graph, `frontier` returns the askable round, `order` gives the topological order **tie-broken by descendant count** (the `I1` deep-premise-first rule), `descendants` walks transitively, `retract` propagates, `conflicts` narrows candidates, `status` reports exit-gate readiness, `render` regenerates the markdown table. State is a JSON sidecar beside the ledger (`interview-log.md` → `interview-log.dag.json`) so the markdown stays human-readable while the graph stays queryable. The **division of labour is strict**: the engine computes (frontier, ordering, cycle rejection, descendant walks, span rollback lists, gate readiness); the model judges (which decisions exist, question wording, whether two decisions truly conflict, whether a descendant survives a premise change). Two deliberate boundaries: `retract` is **dry-run by default** and **never edits the target artifact** — it reports the spans, and the caller rolls them back, because only the caller knows how to edit that artifact; and `conflicts` returns **candidates, not verdicts**. Cycles are refused at insertion (a retraction walk over a cycle would not terminate) and answering a decision with an unsettled premise is refused — the "never ask a blocked question" rule made mechanical. This is Feature 042's first executable surface; Principle IX still holds because the engine does deterministic graph/text processing while all interaction stays in the prompt layer.
7. **Self-contained question format + comprehension rules** (fifth pass): the format was a one-liner carrying a bare `(rests on: D1, D3)`, which asked the user to decode the agent's own shorthand — and an unexplained abbreviation in a question buys a confidently wrong answer, which then propagates through the whole DAG. A question now carries its decision ID, a plain-language title, and a mandatory **`**Context**` paragraph rendered as a markdown blockquote (`> `)** — why the question arises now, which earlier decisions it builds on (**named in words**, not merely cited as `D3`), and what the answer will change in the target artifact; the quote block keeps background and question as visually distinct blocks. Five comprehension rules bind: plain language in the user's vocabulary; no unexplained abbreviations or jargon (glossed inline on first use *in each question*, since a question may be read in isolation days later — decision IDs are the sole permitted short form, and even those get named); special terms annotated at point of use using the glossary's canonical wording; never assume shared context; one decision per question (an "and" hides two). The glossary step now runs **both ways** — inbound correction of the user's terms, outbound canonical wording in questions — and three anti-patterns were added (context-free questions, jargon/bare abbreviations, compound questions). **Superseded in part**: this pass also copied clarify's options table and recommended answer, which item 8 removed.
8. **Open questions — no options, no recommendation** (sixth pass, a correction): the format inherited `/speckit.clarify`'s closed shape (options table + a **Recommended** pick), which is wrong for interviewing. The two flows differ in **whether the answer space is already known**: clarify *澄清* operates on a space bounded by the artifact and its taxonomy, so proposing options and a recommendation is correct and fast; interview *采访* exists precisely because the space is **unknown**, so presetting it destroys what the mode is for. An option menu asserts the agent already knows the possibilities and makes the user pick the closest one instead of saying what was on their mind — the good answer is frequently the option nobody listed. A recommendation is the subtler failure: the user finds it plausible, agrees, and the artifact records the agent's opinion under the user's name, which is the fabrication rule broken by another route. Questions are now **open** ("What should happen when a message fails?", never "Should we retry 3 times?" — ask *what*, not *whether*), with examples offered only on request as explicitly non-exhaustive illustrations, never renumbered into a menu. Structured choice widgets are therefore avoided for frontier questions specifically — see the host-tool split below. Consequently `/speckit.clarify` was **reclassified from "bounded instance" to "sibling flow"** — it borrows only the context discipline and the fact/decision split, keeps its closed format deliberately, and escalates here when the space turns out to be unknown rather than merely ambiguous; `/speckit.goal` create became a **partial instance** (open objective/criteria elicitation, mechanical identity field). Three anti-patterns added: presetting the answer space, recommending an answer, asking "whether" instead of "what".
   - **Host interactive tools — capability fit, not tool preference**: the governing rule is that a host tool is used when it presents a given prompt **more clearly than plain text**, and **not used** when none fits, in which case the prompt is markdown or plain text. Fit is judged by the **prompt's shape** against what the tool offers, deliberately **not hard-coded to any tool name** — a future free-text prompt, open form, or diff surface should be judged the same way, per host and per prompt. Applied here: choice widgets (this CLI's `AskUserQuestion`: 2–4 preset options plus an "Other" escape) fit the loop's genuinely closed prompts — run-mode selection at `I0`, conflict resolution at `I5`, retraction triage at `I6`, deferral, the exit-gate confirmation — while **frontier questions stay markdown**, because their space is unknown and a widget would anchor the user even with the escape available (the escape reads as the awkward path). Rules: options must be the true complete space (not a sample), never mark one recommended, **never bend a prompt to fit a tool** by inventing options (the **widget-driven questioning** anti-pattern), and degrade cleanly to plain text without ever skipping, batching away, or self-answering a question. The tool is a presentation layer, never an authority over what is asked.
9. **Existing walkthrough demoted to an instance** — `shared/workflow/interview-walkthrough.md` keeps all of its field-proven requirements-domain content (interview units, decision cards, L1/L2/L3 verification levels, delivery-loop coupling, lessons) and now declares the pattern as the authority for shared mechanics. Its own "open main question first, never preset the answer space" rule is where the open-question requirement was already field-proven.
10. **Five integration points**, each a declarative pointer rather than a copy: `/speckit.clarify` (sibling flow + named escalation when the space proves unbounded), `/speckit.plan` (interview rather than fabricate an underdetermined design), `/speckit.goal` create (open elicitation protocol), `create-team` (eliciting a missing or too-vague goal), `requirements-analyst` (pattern as mechanics authority above its domain instance).
11. **Registration** — pattern registered in the two `shared/` contract tests; command registered in the feedback-classification (15→16) and docs-step (14→15) contract tests and the post-init optional-command hint; engine registered as a Tool record + Resource Registry row; `docs/reference/commands/interview.md` and the quickstart tables added.

## Implementation Notes

- **The ledger goes nearest the artifact**, not into a new central store: `.specify/specs/<feature>/interview-log.md` in a feature context, else `.specify/memory/session/`. This reuses the existing walkthrough-ledger convention and the memory-as-files layer instead of adding a third state location.
- **Prompt layer + one deterministic engine** (Constitution IX): all interaction stays in the prompt layer; the only code is `interview-utils.py`, which does graph computation (reachability, topological order, cycle detection) — precisely the class of fixed-rule work Principle XII says must not be left to the model. No runtime platform, no service, no new storage system: the store is a JSON file beside a markdown ledger, and the remaining judgments the mode needs (does the target exist, is it writable) stay shell probes the host already runs.
- **Reference forms differ by host type** and are pinned by contract tests: command templates cite `shared/patterns/…` (install-time rewriting upgrades them), skills must cite `.specify/shared/patterns/…`. `create-team/SKILL.md` uses the installed-absolute form for exactly this reason.
- **`_CANONICAL_COMMANDS` in `tests/integration/test_ai_tools_command_coverage.py` was deliberately left alone** — it is a fallback set used only when `templates/commands/` is absent, and it is already a stale subset (missing docs/goal/team/todo/history). Adding one name to a stale list would imply a currency it does not have; the live path globs the directory.
- **The feature index count was corrected in passing**: the header claimed 38 features against 41 actual rows. It now reads 42 with the new row.
- **Bad fits are named explicitly in the pattern**, not left to judgment: `/speckit.analyze`, `/speckit.review`, `/speckit.implement`, `/speckit.history`, `/speckit.feature`. Read-only diagnosis, mechanical execution, and automated distillation have no tacit information to elicit, and an adoption map without an exclusion list is how a pattern sprawls.

## Future Evolution Suggestions

- **Retrofit the pre-existing narrower loops** (`summarize-project`'s four gates, `create-skills`' one-question-per-round, `study-project`'s ≤3-per-round) to cite the pattern when each is next revised. They are conformant today; the citation is what keeps them from drifting apart again.
- **A team-level interview seat**: `create-team` currently gains only goal elicitation. A stakeholder-facing member that runs the pattern inside a team's cycle (interview → hand decisions to implementing roles → verify) is the delivery-loop coupling already field-proven in `interview-walkthrough.md`, generalized beyond requirements.
- **Structured-question-tool adaptation**: the pattern specifies a text format with the host's structured question tool as the preferred path. If the tool surface stabilizes across the supported CLIs, the format could become a declared adapter rather than a fallback.
- **Measure the fact/decision split**: the command's Feedback step reflects on whether the user was asked for something lookupable. If that signal recurs in the feedback store, it is the highest-value candidate for a mechanical check.
