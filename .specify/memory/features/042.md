# Feature Detail: Interview Mode

**Feature ID**: 042  
**Name**: Interview Mode  
**Description**: Promote interview-style elicitation from a single agent's workflow into a framework-wide design pattern (`shared/patterns/interview-pattern.md`), usable from commands, skills, and agent/team definitions, plus `/speckit.interview` as the standalone entry.  
**Status**: Implemented  
**Created**: 2026-08-06  
**Last Updated**: 2026-08-06

## Overview

The framework had **interview behavior without an interview pattern**. Multi-round user questioning existed in at least six places, each having independently invented its own rules: `/speckit.clarify` (a capped sequential loop over a fixed taxonomy), `shared/workflow/interview-walkthrough.md` (the Requirements Analyst's field-proven multi-day walkthrough), `summarize-project` (four sequential confirmation gates), `create-skills` (one question per round until frontmatter is complete), `study-project` (≤3 questions per round across analysis phases), and `/speckit.goal` create (a fixed three-item elicitation). None of them referenced the others, and nothing named the shared mechanics.

The cost of that gap is not stylistic. Each site re-decided the load-bearing questions — whether the agent may ask the user for a fact it could look up, whether answers are written through before the next round, whether one round may ask a question whose prerequisite is still open, and *who* decides the session is finished. Sites that got those wrong produce the two characteristic failures: interrogating the user for discoverable facts, and declaring a converged artifact that encodes decisions nobody was asked about.

This Feature names the mode once, with an explicit boundary against the neighbours it is confused with, so that a new command, skill, or team member can claim it by declaring four things instead of reinventing it.

## Latest Review

Not yet reviewed. Delivered directly (registered Feature + implement, no spec→plan→tasks track) at the user's direction after a research pass over the reference `grilling` / `grill-me` skills and a full survey of the project's ~20 commands, 26 skills, and 7 role agents.

## Key Changes

1. **`shared/patterns/interview-pattern.md`** — the generic pattern, in the house style of `reconcile-pattern.md`: applicability judgment (tacit information + branching decisions + a converging target artifact + a live user), the core model (design tree / frontier / round / write-through), the `I0–I5` loop with the exit gate, the question-format contract (`❓ **Q<n>** — **<title>**` + a mandatory `➡️` recommended answer), the fact-vs-decision split, ledger placement and resumability rules, the embedding contract, the adoption map, and eight anti-patterns.
2. **Boundary section** — a table separating interview from **reconcile**, **iteration loop**, **continuous loop**, and a **one-shot confirmation gate**, keyed on two axes: where the information comes from, and what ends the loop. Includes the nesting rule (an interview *feeds* a reconcile or a plan; it never substitutes for one) and a near-synonym list (frontier ≠ tolerance band; user-confirmed stability ≠ quality threshold ≠ one-time approval; interview ledger ≠ audit log ≠ STATE.md).
3. **`/speckit.interview`** — the standalone, **unbounded** entry: resolves the target artifact (argument → current phase artifact → new record), probes writability before asking anything, resolves and resumes the ledger, runs the loop, and exits only on the user's confirmation. Carries the standard Glossary / Feedback / Documentation steps. No new engine.
4. **Existing walkthrough demoted to an instance** — `shared/workflow/interview-walkthrough.md` keeps all of its field-proven requirements-domain content (interview units, decision cards, L1/L2/L3 verification levels, delivery-loop coupling, lessons) and now declares the pattern as the authority for shared mechanics.
5. **Five integration points**, each a declarative pointer rather than a copy: `/speckit.clarify` (bounded instance + named escalation when the space branches past its cap), `/speckit.plan` (interview rather than fabricate an underdetermined design), `/speckit.goal` create (question protocol), `create-team` (eliciting a missing or too-vague goal), `requirements-analyst` (pattern as mechanics authority above its domain instance).
6. **Registration** — pattern registered in the two `shared/` contract tests; command registered in the feedback-classification (15→16) and docs-step (14→15) contract tests and the post-init optional-command hint; `docs/reference/commands/interview.md` and the quickstart tables added.

## Implementation Notes

- **The ledger goes nearest the artifact**, not into a new central store: `.specify/specs/<feature>/interview-log.md` in a feature context, else `.specify/memory/session/`. This reuses the existing walkthrough-ledger convention and the memory-as-files layer instead of adding a third state location.
- **The pattern is prompt/doc-only** (Constitution IX): no Python engine, no new storage format. The ledger is a markdown table, and every deterministic judgment the mode needs (does the target exist, is it writable) is a shell probe the host already runs.
- **Reference forms differ by host type** and are pinned by contract tests: command templates cite `shared/patterns/…` (install-time rewriting upgrades them), skills must cite `.specify/shared/patterns/…`. `create-team/SKILL.md` uses the installed-absolute form for exactly this reason.
- **`_CANONICAL_COMMANDS` in `tests/integration/test_ai_tools_command_coverage.py` was deliberately left alone** — it is a fallback set used only when `templates/commands/` is absent, and it is already a stale subset (missing docs/goal/team/todo/history). Adding one name to a stale list would imply a currency it does not have; the live path globs the directory.
- **The feature index count was corrected in passing**: the header claimed 38 features against 41 actual rows. It now reads 42 with the new row.
- **Bad fits are named explicitly in the pattern**, not left to judgment: `/speckit.analyze`, `/speckit.review`, `/speckit.implement`, `/speckit.history`, `/speckit.feature`. Read-only diagnosis, mechanical execution, and automated distillation have no tacit information to elicit, and an adoption map without an exclusion list is how a pattern sprawls.

## Future Evolution Suggestions

- **Retrofit the pre-existing narrower loops** (`summarize-project`'s four gates, `create-skills`' one-question-per-round, `study-project`'s ≤3-per-round) to cite the pattern when each is next revised. They are conformant today; the citation is what keeps them from drifting apart again.
- **A team-level interview seat**: `create-team` currently gains only goal elicitation. A stakeholder-facing member that runs the pattern inside a team's cycle (interview → hand decisions to implementing roles → verify) is the delivery-loop coupling already field-proven in `interview-walkthrough.md`, generalized beyond requirements.
- **Structured-question-tool adaptation**: the pattern specifies a text format with the host's structured question tool as the preferred path. If the tool surface stabilizes across the supported CLIs, the format could become a declared adapter rather than a fallback.
- **Measure the fact/decision split**: the command's Feedback step reflects on whether the user was asked for something lookupable. If that signal recurs in the feedback store, it is the highest-value candidate for a mechanical check.
