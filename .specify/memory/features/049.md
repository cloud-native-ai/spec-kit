# Feature Detail: Derivation Command

**Feature ID**: 049  
**Name**: Derivation Command  
**Description**: 推导式架构生成:`/speckit.derive` 强制联网核实权威来源,提取其思维方式为可复用的思维算子,在可校验的完整性规则下构建推导链,逐步推导出每个元素都可溯源的完整架构;前提耗尽处记为未决问题而非静默填空。  
**Status**: Implemented  
**Created**: 2026-09-05  
**Last Updated**: 2026-09-05

## Overview

本 Feature 承载 `/speckit.derive` 命令及其推导模型。动因来自一个真实场景:用户 handed-in 一份 REST/Web 架构经典文献清单,诉求不是「读懂或整理这些文献」,而是「学习它们的思维方式,构建可用于推导的思维链路,通过逐步逻辑推导形成完整架构」。那份清单里恰好含一个死链和一篇社区改标题的文章——不联网核实,这两个缺陷会静默污染整条推导链,产出一个看起来是推导出来、实则建立在误引之上的架构。

因此本命令的方法论核心是**重放推理方法而非收集结论**:从来源中抽取的是「如何从前提走到结论」的推理形状(带命名槽位、可跨领域复用的思维算子),而不是来源主张了什么。与之配套的三道防线是:溯源等级门控(只有 primary / authoritative-secondary 能锚定推导步骤)、禁用空洞论证(best practice / 业界通用 一类字面量被程序扫描拒绝)、以及每个架构元素强制回指推导步骤(缺 `derived-from` 即硬失败)。

## Implementation Notes

- **两个 ID 命名空间独立**:Feature ID = 049,requirement key / spec 目录 = 048-derive-command(偏移恒为 −2,与 047→045、048→046 一致)
- **`update-feature-index.sh` 是破坏性脚本**:整体重写 features.md、输出 6 列(缺 Spec Path)、以目录 slug 与桩文本覆盖手写散文、重置全部 Status,而 `test_c3` 仍然通过(静默损坏)。本 Feature 的索引行与表头计数一律手工编辑
- **确认门控预算零余量**:扫描器 total 23 / 上限 23.25,新增文件里任何一个 BLOCKING 匹配都会同时打爆两个契约测试。derive 的产物(新文件 + 追加)可逆,按 046 判据本就应自动执行 + 执行报告,故设计为零门控
- **禁用节标题**:`shared/**` 与 `templates/**` 内不得出现 `## Resolving a disagreement`、`## 判定边界` 等(子串级扫描),故用 `## Contradiction Handling` 与 `## Script / Prompt Boundary`
- **shipped-surface 中性**:`templates/` 与 `shared/` 内禁止出现 `Feature 0NN` / `requirement 0NN` / `.specify/specs/0NN-`;特性归属只写进本文件、Tool 记录、docs 与 spec 目录
- **语料不得入分发文件**:用户的 REST 清单是示例输入,不是框架内容。锚文件与模板只用槽位化合成示例,避免随包分发一份会腐烂的语料
- **基线**:全套件 50F(名字级,`baseline-failed.txt`);门控 total 23;probe 72 internal,`--reconcile` 既有 2 条错误(`skill:git-fleet`、`skill:git-server-init`),改动后错误集必须仍是这 2 条
- **契约赢了实现(本特性最重要的一次纠偏)**:引擎先按口头规格落地并通过 44 项端到端驱动;随后独立撰写的 `contracts/derive-engine.md` 暴露出两者接口**实质性分歧**——契约要求固定信封(`ok`/`action`/`workspaceRoot`/`generatedAt`/`errors[]`/`warnings[]`/`semanticChecksPending[]`/`notes[]`/`payload{}`)、`--slug` 而非 `--topic`、camelCase payload、`--force` 留 `.bak`、`online`/`degraded` 标志、投影元数据(`librarySize`/`fullReadAllowed`)、`duplicateIds`/`duplicateForms` 计数、原子写(`.part` + `os.replace`)、以及**单一传输缝 `_http_get`**(这是「任何测试不得触网」可被机械断言的前提)。**判定:契约更严也更好,且 camelCase 与本仓 `sanitize-utils.py` 房式一致(`semanticCandidates`/`evidencePack`),故重写引擎去符合契约,而不是弱化契约去迁就实现。** 若当时让测试直接对着实现写,会得到一套全绿、而契约沦为装饰的结果——这正是 Principle IV 要防的
- **实现期暴露并修正的四处契约/规格缺陷**:① FR-005(每个 `unverified` 来源须记入 `## Unverifiable Sources`)原先**没有任何 error code 归属**,A2 的映射集只有 `premise-grade-ineligible` → 补 `unverified-source-unrecorded` 并写进契约 A2 行;② C7 的「少于 2 行」下限**不可满足**(记录形态是单行 `- derivation: <value>` 字段)→ 契约表与 C-13 同步修订为仅保留 40 码点下限,并写明恢复条件;③ STR-001 的 *Value (verbatim)* 单元格携带中文标签前缀,导致三方漂移守卫(锚 / 引擎常量 / requirements)解析不出同一集合 → 前缀移入 *Consumed by* 列,值列保持逐字;④ `--anchor` 过滤器接受裸式与限定式(查询),而 `moves-add` 的 `anchor` **必须**限定式(写入)——二者判据不同,因为 `moves-add` 不携带 topic、无从限定,写进库的裸形式会在下一次 `validate` 触发 `anchor-form` 违例
