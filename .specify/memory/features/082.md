# Feature Detail: 元技能治理：机制/策略分离与技能引用归一化（Meta-Skill Governance: Mechanism–Policy Separation & Skill Reference Grammar）

**Feature ID**: 082
**Name**: 元技能治理：机制/策略分离与技能引用归一化（Meta-Skill Governance: Mechanism–Policy Separation & Skill Reference Grammar）
**Description**: 把「机制/能力」与「策略/职责」的归档边界立为一等原则，并让它经由**元技能与元命令的作者与改进流程**生效（**能力一：机制/策略分离**）；机制侧（判定规则、算法、步骤顺序、可复用方法）归档到技能资产，策略侧（配置、输入、输出、路径与落点）归档到具体运行环境；一个命令或技能必须同时具备两层信息才能执行，策略缺失或含糊时以统一形态向用户索取、并在任何副作用之前停下。**能力二：技能引用文法与归一化**（2026-11-05 scope update）——框架条目「怎么命名一个技能」收成一份唯一 owner 文档 `shared/definitions/skill-reference-definitions.md`：封闭的接受形式集合、确定性归一化顺序、消歧规则与四类失败语义归它所有；五个元技能只声明自己的参数并以路径引用；归一化结果恰为**命令面／技能标识／失败**三值之一的封闭判定，由一份固定 fixture 逐项复算。两个能力共享同一元技能范围判据（C1 谓词），各有独立 owner，互不复制。
**Status**: Implemented
**Created**: 2026-11-05

## Overview

技能与命令今天解决的是**技能内部**的归档问题：`create-skills` 已有存储位置选项、`${SKILL_HOME}` / `${SKILL_WORKDIR}` 路径约定与「不放进正文的内容」清单，`improve-skills` 已有「`SKILL.md` 是一份契约」「把确定性逻辑落成脚本」两条相邻规则——它们判的是「该放 `SKILL.md` 还是 `references/`／`scripts/`」。没有任何一条规则判**技能与运行环境之间**的边界，于是两类内容可以互相住进对方的地盘：可复用的判定逻辑散落在某个用户目录的运行说明里，或者某个运行环境的绝对路径被固化进技能正文、下次换环境就静默出错。本特性补的就是这条外部边界，并把「缺了策略就停下问」立成执行期义务。

交付面是**元层**，不是存量技能。用户原话开头是「优化所有的命令和技能」，末句又明确「针对元技能和命令……而不是针对当前项目中加载的这些技能」；规格按末句执行（§ Assumptions A7）：原则落进 `create-skills`、`improve-skills`、`merge-skills` 这些用来**操作其他技能**的流程，对成员表之外的既有技能正文零回溯改造。不回溯的做法之所以可行，是因为 `improve-skills` 是存量技能进入本条原则的唯一通道——它是「对账通道」，而不是一次性改写。

**第二能力（2026-11-05 scope update）**：把同一个技能交给元技能处理时，使用者手里的写法五花八门——`improve-skills`、`/improve-skills`、`@improve-skills`、`skill:improve-skills`、规范 `SKILL.md` 路径、技能目录。今天这五种写法由每个元技能各自解释，「`/` 是不是要我直接调用它」「`/speckit.skills` 是命令还是技能」「dev 层与安装层同名算一个还是两个」的答案取决于读到的是哪一份正文。本能力把「怎么命名一个技能」收成一份 owner 文档，五个元技能只声明自己的参数，并让归一化结果成为**命令面／技能标识／失败**的封闭判定。它与能力一同属元技能治理：前者决定「内容归哪一侧」，后者决定「操作对象是谁」——后者不成立时，前者判定的对象都可能选错。

五条用户故事（细节与 SC 归规格制品，此处只记索引）：

- **US1（P1）** 新建技能时强制区分两层，误置当场被拦下：`create-skills` 的收尾校验新增一条可定位的判定（点名文件与位置），两类误置各自给出改正方向，正确分层的技能不误报。
- **US2（P1）** 改进技能时先与运行环境对账：`improve-skills` 把被引用的运行环境文件与技能正文看成同一份契约，「策略来源不明」作为**候选**改进项提出，而不是把现存硬编码当成默认策略继承。
- **US3（P2）** 消费侧：策略缺失时以统一形态提示而不是猜：在任何副作用之前停下，点名缺的是哪一项、为何此刻需要、用户可以怎么提供；区分「策略缺失」与「环境错误」。
- **US4（P2）** 元层成员裁定是封闭、可复算的：一条谓词（「产出改变另一命令或技能的定义/行为」）+ 封闭成员表 + 排除理由，第三方按同一谓词独立判定得到同一结论。
- **US5（P1，第二能力）** 元技能用一份确定的文法识别「这次操作的是哪个技能」：六种写法归一为同一个技能标识、`/speckit.*` 报告为命令面、四类失败各自关闭，且五个元技能对同一输入给出同一个归一化结果。

关键裁决（详见规格 § Assumptions A1–A11、§ Constraints C1–C11 与 § Clarifications § Session 2026-11-05）：

## Key Changes

1. **一等原则 + 唯一 owner**：新增 `shared/definitions/mechanism-policy-definitions.md`，承载双向边界测试（换掉运行环境这段文字要不要改）、两类误置症状（机制误置／策略误置）、归档规则，以及与 `directory-governance` / `dogfooding-definitions` 的引用关系（不复述其内容）。
2. **执行期双输入与统一提示**：两层信息必须同时具备才可执行；策略缺失或含糊时以一条统一形态索取，三要件（缺哪一项／为何此刻需要／用户可照做的提供方式），且必须在任何副作用之前停下。
3. **元层封闭集**：一条谓词 + 封闭成员表 + 排除理由，可被第三方按同一谓词复算。
4. **作者侧落点**：`create-skills` 既有收尾校验与 `improve-skills` 既有调研/候选清单各新增一条同源判定，按「一行判定 + 指向 owner 的路径」形态落地。
5. **零回溯与不新增机器**：成员表之外的既有技能正文逐字节不变（基线 `3ffeb26e`），不新增命令、校验器、环境变量、目录根或第二套门禁。
6. **技能引用文法与归一化（2026-11-05 scope update，第二能力）**：新增唯一 owner `shared/definitions/skill-reference-definitions.md`，拥有封闭的接受形式集合（bare name、`/name`、`@name`、`skill:name`、规范 `SKILL.md` 路径、技能目录路径）、确定性归一化顺序、消歧规则（前导 `/` 只标记命令面而非调用指令；归一化后命中 `/speckit.*` 报为命令面并指向该命令、不得解析成技能；同层镜像命中算一处、两层不同命中才失败；元技能工作项不得被重分类）与四类失败语义；五个消费方（`run-skills` / `create-skills` / `improve-skills` / `merge-skills` / `coaching-skills`）只声明自己的参数并以路径引用 owner、MUST NOT 复制文法；`create-skills` 只「命名」不「解析」的特例在接线处写明。归一化结果是**命令面／技能标识／失败**三值之一的封闭判定（FR-030），由 ≥ 12 行 fixture 逐项复算（SC-006…SC-009）。`.specify/` 下的 owner 与技能镜像都是生成物，由 `sync-mirrors.py` 再生成、不手改、不作为源提交。
