# Feature Detail: 机制/策略分离（Mechanism–Policy Separation）

**Feature ID**: 082
**Name**: 机制/策略分离（Mechanism–Policy Separation）
**Description**: 把「机制/能力」与「策略/职责」的归档边界立为一等原则，并让它经由**元技能与元命令的作者与改进流程**生效：机制侧（判定规则、算法、步骤顺序、可复用方法）归档到技能资产，策略侧（配置、输入、输出、路径与落点）归档到具体运行环境；一个命令或技能必须同时具备两层信息才能执行，策略缺失或含糊时以统一形态向用户索取、并在任何副作用之前停下。
**Status**: Draft
**Created**: 2026-11-05
**Last Updated**: 2026-11-05

## Overview

技能与命令今天解决的是**技能内部**的归档问题：`create-skills` 已有存储位置选项、`${SKILL_HOME}` / `${SKILL_WORKDIR}` 路径约定与「不放进正文的内容」清单，`improve-skills` 已有「`SKILL.md` 是一份契约」「把确定性逻辑落成脚本」两条相邻规则——它们判的是「该放 `SKILL.md` 还是 `references/`／`scripts/`」。没有任何一条规则判**技能与运行环境之间**的边界，于是两类内容可以互相住进对方的地盘：可复用的判定逻辑散落在某个用户目录的运行说明里，或者某个运行环境的绝对路径被固化进技能正文、下次换环境就静默出错。本特性补的就是这条外部边界，并把「缺了策略就停下问」立成执行期义务。

交付面是**元层**，不是存量技能。用户原话开头是「优化所有的命令和技能」，末句又明确「针对元技能和命令……而不是针对当前项目中加载的这些技能」；规格按末句执行（§ Assumptions A7）：原则落进 `create-skills`、`improve-skills`、`merge-skills` 这些用来**操作其他技能**的流程，对成员表之外的既有技能正文零回溯改造。不回溯的做法之所以可行，是因为 `improve-skills` 是存量技能进入本条原则的唯一通道——它是「对账通道」，而不是一次性改写。

四条用户故事（细节与 SC 归规格制品，此处只记索引）：

- **US1（P1）** 新建技能时强制区分两层，误置当场被拦下：`create-skills` 的收尾校验新增一条可定位的判定（点名文件与位置），两类误置各自给出改正方向，正确分层的技能不误报。
- **US2（P1）** 改进技能时先与运行环境对账：`improve-skills` 把被引用的运行环境文件与技能正文看成同一份契约，「策略来源不明」作为**候选**改进项提出，而不是把现存硬编码当成默认策略继承。
- **US3（P2）** 消费侧：策略缺失时以统一形态提示而不是猜：在任何副作用之前停下，点名缺的是哪一项、为何此刻需要、用户可以怎么提供；区分「策略缺失」与「环境错误」。
- **US4（P2）** 元层成员裁定是封闭、可复算的：一条谓词（「产出改变另一命令或技能的定义/行为」）+ 封闭成员表 + 排除理由，第三方按同一谓词独立判定得到同一结论。

关键裁决（详见规格 § Assumptions A1–A10 与 § Clarifications § Session 2026-11-05）：

- **Flow Class = `execution`**（行为判据 oracle）：验收对象是 owner 文档的可判定性、元流程的拦截行为与守护测试的红绿，都可机器判；原则正文虽以 Markdown 呈现，但介质不参与判定。`flow-class-check.py --action lookup --unit-id "spec:082-mechanism-policy-separation"` → `execution` / `source: declaration` / exit 0。
- **新建 Feature 082**：复核 013／023／032／036／040／047／050／051／052／053／069／077／078／079／081 无归属，且无「反复吸收同类工作」的兄弟规格前例（绑定前例判定为 create）。
- **C1 谓词逐字保留、全表复算无翻转**：`create-skills`／`improve-skills`／`merge-skills` 纳入；`coaching-skills` 的产出是观察与计划、不改写受训技能，按逐字谓词排除并写理由；`run-skills` 同按排除处置；`/speckit.skills` 只作命令面接线位。
- **原则的名字沿用既有 canonical 词根**：`机制修复 (Mechanism Fix)` / `问题修复 (Problem Fix)` 已把「机制」锚在流程载体上；`Mechanism–Policy Separation` 与二者同族，不新造第三套名字（[[STR-003]]）。本特性拥有的是一条**相反方向的归档边界**，与 Dogfooding owner 的「机制 vs 问题」不是同一事实（C2）。
- **不新增机器**：不新增 `/speckit.*` 命令、不新增校验器、不新增环境变量、不新增目录根、不新增第二套门禁；消费侧提示形态只在 owner 的一个章节定义一次，作者侧判定挂在元技能既有校验步骤。

## Key Changes

1. **一等原则 + 唯一 owner**：新增 `shared/definitions/mechanism-policy-definitions.md`，承载双向边界测试（换掉运行环境这段文字要不要改）、两类误置症状（机制误置／策略误置）、归档规则，以及与 `directory-governance` / `dogfooding-definitions` 的引用关系（不复述其内容）。
2. **执行期双输入与统一提示**：两层信息必须同时具备才可执行；策略缺失或含糊时以一条统一形态索取，三要件（缺哪一项／为何此刻需要／用户可照做的提供方式），且必须在任何副作用之前停下。
3. **元层封闭集**：一条谓词 + 封闭成员表 + 排除理由，可被第三方按同一谓词复算。
4. **作者侧落点**：`create-skills` 既有收尾校验与 `improve-skills` 既有调研/候选清单各新增一条同源判定，按「一行判定 + 指向 owner 的路径」形态落地。
5. **零回溯与不新增机器**：成员表之外的既有技能正文逐字节不变（基线 `3ffeb26e`），不新增命令、校验器、环境变量、目录根或第二套门禁。

## Implementation Notes

- **Two Hats**：本特性改的是框架源（`shared/definitions/`、`skills/external/{create-skills,improve-skills,merge-skills}`、`templates/`）；`.specify/` 下的同名文件是生成镜像，修复方式是重生成（`sync-mirrors.py` / `regen-command-copies.py` 的 `--check` 必须 exit 0），不是手改。
- **本阶段（clarify）只写规格与注册表**：owner 文档、元技能正文与命令模板的落地属 plan／implement 义务（§ Assumptions A9）。
- **不新增第三个路径占位符**：运行环境侧落点由既有 `${SKILL_HOME}` / `${SKILL_WORKDIR}` 约定承载（A3、C3）；`references/` 随技能分发，属机制侧。
- **字节边界**：消费侧提示与作者侧判定都以指针形态接入，复制 owner 的判据表或词表即违反 FR-015。
- **单一所有者状态**：`glossary.md` 与 `features.md` 是单一所有者注册表，本阶段只按本特性需要写 `features.md`；词汇表登记在 plan 阶段声明（见 § Clarifications）。
