# Feature Detail: 机器可判定的制品命题(Machine-Decidable Artifact Propositions)

**Feature ID**: 053  
**Name**: 机器可判定的制品命题(Machine-Decidable Artifact Propositions)  
**Description**: 把制品对**自己**或对**兄弟制品**做出的结构性断言(编号连续、引用可解析、计数正确、某条款由哪一行任务转绿、某判据的主体是否被覆盖)从「代理阅读后声明」改为「程序判定后输出」。动机是本仓最贵的一类缺陷形态:检查跑完给出了绿,但那个绿不是关于它被写来判定的那个命题的——一份声称「107/107 条款已覆盖」的 tasks.md 会把一个结构性不可满足的验收条件送进 implement,而没有任何东西会发现。五处缺口同题:① `requirements.md` 无确定性检查器(同型先例 `validate-tasks.py` 已存在于 tasks 侧);② 条款→任务的绿点归属对结构检查器不可见,需在 tasks 模板定义行内归属声明面并给检查器增 WARN 级「绿点跨阶段」检查;③ 机器覆盖核算,其前置缺口是契约条款语法当前**无 owner**;④ goal 判据主体的「目录指代形」,当前靠成员枚举、脆弱且不可程序指代;⑤ `goal-utils.py` 增 `run-checks` action,一次输出团队 run 前置五项检查的机读 verdict。跨切面约束:每个新检查都 MUST 有逆样本(快速失败纪律对机器给出的绿同样成立)、门控预算整数余量为 0 故新增措辞须零命中、`templates/` 保持项目中立、新检查器走 Program-First 的既有归属声明形态。  
**Status**: Draft  
**Created**: 2026-09-23  
**Last Updated**: 2026-09-24

## Overview

本 Feature 处理的是**证据资格**问题,不是新增功能面。框架今天已把大量结构性命题写成 MUST 并要求代理核验,但核验手段是「读一遍然后声明」——于是错前提可以静默进入下游,而下游把那个声明当证据引用。

判据边界很窄:只做**可机械判定的结构命题**,不做语义正确性判断(某条 FR 写得好不好、某个故事是否真的独立可测仍归 `/speckit.analyze` 与 `/speckit.clarify`)。因此本 Feature 不与任何既有 Feature 争夺语义评审的所有权,它只把已经写成 MUST 的那些命题接上一个会红的程序。

五处缺口来自同一轮 `/speckit.feedback consume` 的自省报告,其中 5 项被路由为「需要新能力而非小编辑」,经 `.specify/memory/feedback/backlog.md` 以 **carried-by-spec-053** 状态移交至此。

## Key Changes

1. **`requirements.md` 侧**:新增一个与 `validate-tasks.py` 同形的确定性检查器,检查面为 FR/SC 编号连续且按**文档出现序**、`FR-\d+` / `SC-\d+` / `[[STR-\d+]]` 三类引用可解析、活动标记计数只数「带冒号且未被反引号包裹」的实例。`/speckit.requirements` 在写完规格后调用它,报任一 ERROR 即**停止**且 MUST 原样呈现输出。
2. **偿还一笔既有债务**:`shared/constants/clarify-taxonomy.md` 里 2026-09-23 刚加入的过渡期 awk 抽取式与「Until that validator ships」一句 MUST 被移除,该处文档序不变量改为指向新检查器——留一份过渡副本就是留第二份真相。
3. **`tasks.md` 侧**:模板定义行内归属声明面 `[green: <contract>#<clause>]`,`validate-tasks.py` 增两项 WARN 级检查(绿点跨阶段、同条款同区间被两行认领)与一项 ERROR 级检查(悬空归属)。归属声明与既有行形态检查**正交**,且围栏代码块内的形态 MUST NOT 被当作真实声明。
4. **覆盖核算**:先给契约**条款语法**指定唯一 owner(实测 110 份契约只有 31 份有机器可抽取形态,当前无任何 owner),再以**集合差**表达核算结果并印出未覆盖集;既有 spec 取**冻结名字级基线**判据,只阻断新增未覆盖项。
5. **`goal-utils.py` 侧**:增 `run-checks` action 一次输出五项检查的机读 verdict,退出码沿用该二进制既有的 `EXIT_*` 四码原义并为 `blocked` 取空闲码 5;`shared/definitions/goal-definitions.md` 定义可由程序解析的**判据主体指代形**,使主体集合在解析那一刻被导出而非取自判据文本里的成员枚举。

## Implementation Notes

- **量化词辖域已固定**(FR-003 尾部):**形态类**要求(docstring 体例、机读输出键集)只辖本特性**新增**的检查器;既有 `validate-tasks.py` MUST NOT 因本特性被要求迁移其 JSON 形态,只受 FR-046 的钉子扩充义务与 FR-017/FR-018 的新增检查项约束。**安全类**要求(FR-005 只读性)普遍适用于全部检查器。这一不对称是刻意的:只读性是安全不变量,不是形态约定。
- **门控预算是硬约束,只能靠措辞回避**:`scan-confirmation-gates.py` total 为 **23**,cap = 93 × 0.25 = 23.25,**整数余量 0**,且该上限由三处不同形态的断言钉住。故 MUST NOT 放宽被扫描文档集、调高上限或修改任何基线数据。新建在 `shared/definitions/` 下的 owner 文档从第一稿起就在扫描面内(`SCAN_DIRS` 含 `shared`)。
- **钉子的形态已被既有先例决定**:检查项集合的钉子 MUST 以**标签集**表达而非计数,退出码表 MUST 单独被钉——仓内唯一先例 `EXPECTED_CHECKS` 正是这个形态。计数形态的钉子会在新增一项检查时打破一个与语义无关的数字。
- **每个新检查都 MUST 有逆样本**,断言「某集合为空」的检查 MUST 配反空真哨兵,守卫负面命题的检查 MUST 有一次变异演练(弄坏→变红→精确复原→恢复绿)且演练临时产物残留计数为 0。这是 `fast-fail.md` § 判据同样覆盖机器给出的绿 的直接适用,不是本特性的额外要求。
- **自定位陷阱**:本仓同时是框架源与自己的客户运行时,「向上找最近含 `.specify/` 的祖先」式自定位在本仓**自匹配**。新检查器 MUST 只在自身已解析路径含字面 `.specify` 组件时才允许自定位,且 MUST 为**否定情形**配断言——该缺陷的表现是工作区状态被写进框架仓,而不是一个失败的测试。

## Future Evolution Suggestions

- **退出码表缺 owner(本 Feature 范围外,已实测)**:`scripts/python/` 下 `derive-utils.py` / `goal-utils.py` / `interview-utils.py` / `trigger-utils.py` 四个脚本各自重复定义同一张 `EXIT_OK=0 / [EXIT_USAGE=1] / EXIT_INPUT_ERROR=2 / EXIT_NOT_FOUND=3 / EXIT_INVALID=4` 表,而 `shared/`、`templates/`、`docs/` 三处对该表的命中数均为 **0**——即无任何 owner 文档。`skills/create-team/scripts/build-summary-input.py` 另有第五套(`3=NO_MATERIAL / 4=SERIALIZED`),与四脚本的 3/4 语义相左。本 Feature 只在 FR-033 局部回避了冲突,未解决无 owner 本身。
- **79 份无条款形态的 `.md` 契约**:本 Feature 以冻结名字级基线把这笔欠账留档可见,但收敛机制不在范围内。若要让覆盖率真正趋近 100%,需要一个独立的迁移特性(定义最小可解析子集并逐批改造),其规模由 FR-023 实测的 79 份给出。
- **`Consumed by` 列的反向检查**:本轮实测该列有 7 处「点名了却未引用」,而模板的引用公约只保证**正向**可解析(`[[STR-NNN]]` → 表内一行)。反向(表内点名 → 该处确有引用)在全仓无任何守卫,本 Feature 的 US1 检查器是它最自然的落点,但未纳入 FR 以免扩大范围。
- **`命题 (Proposition)` 实体的唯一判定者关系**:Key Entities 声明「一个命题恰有一个判定者」,但无 FR 强制该唯一性;两个判定者对同一命题给出不同 verdict 时的裁决顺序亦无记录。
