# Feature Detail: Shared Reference Directory

**Feature ID**: 029  
**Name**: Shared Reference Directory  
**Description**: Reclassify `sdd-workflow` from a (non-invocable) skill into a dedicated shared reference directory (`shared/workflow` → `.specify/shared/workflow`) copied wholesale at init like templates/scripts, retained across re-init, with a `.specify/` path-rewrite rule; remove it from the skills registry/count/symlinks and rewrite ~100 references, with a zero-`sdd-workflow`-reference acceptance gate.  
**Status**: Implemented  
**Created**: 2026-07-14  
**Last Updated**: 2026-07-14

## Overview

`sdd-workflow` was shipped as a "skill" but self-declares "This skill is NOT invoked directly" — it is really a passive bundle of shared SDD protocol/reference documents (input protocol, feature integration, agent configuration, clarify taxonomy, DfX catalog, ignore patterns, tool definitions, checklist methodology, requirements guidelines, feedback step) that `/speckit.*` commands load on demand to avoid duplicating common logic. Packaging it as a skill has real costs: it appears in the invocable skill list (mis-invocation risk), pollutes the skills registry and namespace, is symlinked into every tool's skills directory, and confuses maintainers about whether it is a skill or a document library.

This feature moves those documents out of `skills/` into a first-class **shared reference directory** — source `shared/workflow`, installed `.specify/shared/workflow` — copied wholesale at `init` exactly like the existing `templates/`/`scripts/` core assets, retained across re-init, and reached via a `.specify/` path-rewrite rule. `sdd-workflow` is removed from the skills registry/count and all skills symlinks, and the ~100 existing references are rewritten to the new location. The acceptance gate is a repository-wide `sdd-workflow` search returning zero live matches (no runtime dead links).

## Key Changes

1. Remove `sdd-workflow` as a skill: delete its source skill directory and ensure absence from the installed skills dir and all compatibility skills symlinks.
2. Remove `sdd-workflow` from the skills registry table, the skill count, and any skill-discovery listing.
3. Relocate the ten shared protocol documents to `shared/workflow` (installed `.specify/shared/workflow`), preserving content.
4. Copy `shared/` at init like other core assets; add `.specify/shared` to the retained core-asset list; add a `shared/ → .specify/shared/` path-rewrite rule.
5. Rewrite ~100 references — command templates to root-relative `shared/workflow/...`, skills to installed absolute `.specify/shared/workflow/...`, no mixing.
6. Update user-facing docs to describe the shared reference directory rather than a skill.
7. Ensure packaging/release logic bundles `shared/`; final acceptance gate: zero live `sdd-workflow` references.

## Implementation Notes

- Reference-rewrite volume is large but mechanical; the real risk is a missed reference causing a runtime dead link — hence the zero-`sdd-workflow`-reference grep gate (historical/archival content such as `docs/history/`, this spec, and the proposal are excluded).
- Two reference forms by convention: command templates use root-relative paths (rewritten with the `.specify/` prefix at install), skills use hard-coded installed absolute paths. Do not mix the two.
- The installed `.specify/` mirror is regenerated from source; source changes must fully propagate so no `sdd-workflow` remnants survive regeneration.
- Concrete CLI/packaging touchpoints (init copy block, `_CORE_SPECIFY_ASSETS`, `_rewrite_paths`, `pyproject.toml` wheel force-include, release enumeration) are to be settled during `/speckit.plan`.

## Future Evolution Suggestions

- Introduce additional shared reference families under `shared/` (beyond `workflow/`) as more cross-command protocols emerge.
- Add a CI check that fails on any new `skills/sdd-workflow` reference or on pseudo-skills (skills whose body declares they are not invocable).
