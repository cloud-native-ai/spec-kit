# Feature Detail: Harness 三重结构（markdown + yaml + script）

**Feature ID**: 084
**Name**: Harness 三重结构（markdown + yaml + script）
**Description**: 把「涉及 harness 的流程」的载体从 `markdown + script` 两层升级为 `markdown + yaml + script` 三层：markdown 继续拥有「为什么 + 怎么读」（义务、判定顺序、边界叙事），新增的 yaml 声明层（`shared/declarations/`，一文一件、路径即身份）拥有**机器读得到的取值**（阈值、封闭集、有序算子表、映射、记录 schema），script 保留确定性执行与判决并**只从声明层读取值**、不再写第二份内联常量。范围不靠流程清单定义，而靠两条合取判据（D1 资产面 ∧ D2 机器面）加一条机械候选屏幕 S 在树上重算；每个候选单元要么被一条事实声明覆盖（三层齐备才 `complete`），要么持有一条封闭三值理由（`no-machine-fact`／`no-harness-asset`／`by-owner-decree`）且锚点可解析的排除记录。判定引擎 `scripts/python/harness-triple-check.py`（`coverage`／`verify`／`lookup`，stdlib-only、只读、无模型判断）挂在既有门宿主上，不新增门禁阶段。迁移分三批且每批独立可验收；兼容期不得变成永久态。非目标 N1–N7。
**Status**: Planned

## Overview

用户原话给出的是这次改造的全部命题：「在所有涉及到 harness 的流程中，需要使用 markdown + yaml + script 的三重结构来实现，之前主要使用 markdown + script 的两层结构。」本仓今天的常态正是那个两层结构：一条事实（一个阈值、一个封闭集、一张映射表、一个记录 schema）被**散文 owner 写一遍、某个引擎的元组常量再写一遍**，两处各有测试守着各自那一份，于是它们可以长期不一致而两边都是绿的。`shared/guidelines/better-harness.md` § 证据纪律 第 2 条就是标本：七态枚举在那里全文重列一遍，`evidence-utils.py` 有同内容的常量，`evidence-discipline.md` 才是定义 owner —— 三面重复、又被机器消费。

第二类失效比重复更贵：**假绿**。声明文件存在、目录长得对、校验器退出 0，都可以与「没有任何引擎真的读它」同时成立。所以本特性的判据不是「有没有 yaml 文件」，而是三层合取：(a) 每条事实有且仅有一份通过 schema 与子集校验的声明；(b) markdown 载体含指向该事实的指针、不再规范性重述其值（机械读数 = 既有 `doc-consistency-check.py` 的 `duplicate` 面对该事实零命中）；(c) `consumers` 中至少一个引擎的读取点在源码中可定位。缺 (c) 即使 (a)(b) 全绿也判 `pending` 并报 `third-layer-missing`。

第三类问题是范围：如果「涉及 harness 的流程」靠枚举，这份清单本身会成为第二份分类数据，与 `flow-class-definitions.md` 的逐流程台账和 `framework-map.md` 打架。因此本特性把界写成可判定：候选集由屏幕 S 在树上重算（载体文本里出现指向框架内确定性引擎的路径即入候选），处置由两条合取判据给出，两句都不是清单。

关键裁决（详见规格 § Assumptions A1–A10 与 § Clarifications § Session 2026-11-05）：

- **Flow Class = `execution`**（basis `behavior-oracle`）：主交付物是一组机器读取的声明文件加一个确定性校验引擎，缺陷最先在机器面暴露。`flow-class-check.py --action lookup --unit-id "spec:084-harness-triple-structure"` → `execution` / `source: declaration` / exit 0。
- **归 yaml 的判据 = 机器消费 ∧ 跨面**（A2，clarify **收窄** (i)）：机器消费 = 存在一个确定性引擎，其**判决结果随该取值改变而改变**；仅被测试钉住、无判决消费者的字面量不算。
- **范围 = 资产面 ∧ 机器面 + 候选屏幕 S，不新造流程清单**（A3，clarify ratified，附一处事实订正：台账实测 80 行，原写 79）。
- **A8 拆成两条、结论相反**（clarify 的核心裁定）：081 已验收契约里的 `Path` 取值域 `{final, supporting}` **不越界**（成员、散文、拒绝消息、退出码、既有测试断言全不动，只把取值集移入声明层并留指针）⇒ 保留 in-scope；六个检查项标签集 **越界**（它的唯一消费者是 `test_c01_c02_docstring_enumerates_exactly_the_pinned_labels` 的提取断言，迁出必须改写 081 验收测试）⇒ 不迁，记 N7 并给可解析锚点。
- **不重构既有子集解析器**（A5，bounded）：仓内先例是 `execution-config.py:136 parse_yaml_subset()` 与 `gate-check.py:48 parse_gate()`，`pyproject.toml` 无任何 YAML 库；本特性把子集**写下来**（FR-008），不趁手重构（N4）。
- **绑定新建 Feature 084**：复核 081／069／053／055 后无归属（依据 `.specify/shared/workflow/feature-integration.md` § Feature Binding Rules；`shared/declarations/` 树内零命中）。

## Key Changes

1. **新增 yaml 声明层** `shared/declarations/`（框架源，经既有 `sync-mirrors.py` 的 `shared → .specify/shared` 映射投影）：`contract.yaml` 拥有全部机器读取取值（五类 fact kind、二值完整性状态、三值排除理由、三退出码、子集标识、必填键集、门禁调用点），`facts/<fact-slug>.yaml` 一文一件持有事实，`exclusions/<reason>.yaml` 按理由一词一文件持有排除记录。
2. **新增判定引擎** `scripts/python/harness-triple-check.py`（`coverage`／`verify`／`lookup`；stdlib-only、只读、无模型判断），失败只发射六个封闭原因（`third-layer-missing`／`declaration-outside-subset`／`duplicated-fact-literal`／`exclusion-anchor-unresolvable`／`unclassified-candidate`／`declaration-absent`），逐字模板由规格 § Shared Strings 拥有。
3. **范围与覆盖判据**：候选屏幕 S 在树上重算（`templates/commands/*.md`、`skills/{external,internal}/*/SKILL.md`、`shared/workflow/*.md` 中出现 `scripts/python/<name>.py` 或 `skills/<layer>/<name>/scripts/<file>` 即入候选），处置由 D1 资产面 ∧ D2 机器面给出；单元处置**由声明反投影派生**，禁建聚合 ledger。
4. **三批迁移**：批 1 已跨面重复的封闭集与阈值（漂移已存在）→ 批 2 被门禁消费的映射与有序算子表（决定放行与误杀）→ 批 3 记录 schema（只影响证据形态）；每批独立可验收，关闭时 in-scope 集合内 `pending` 必须为 0。
5. **既有 owner 文档改为指针 + 判据保留**：`better-harness.md` § 证据纪律 第 2 条（七态）、`flow-class-definitions.md`（类别／basis／flow_type 取值、台账列）、`feedback-step.md`（提示阈值）、`expression-gates.md`（阶段算子表与六面）、`acceptance-hardening.md` § Closure Verdict（`Path` 取值二值，A8(a)）；`shared/definitions/framework-map.md` 同变更登记新目录含义。
6. **分发与兼容**：`specify init` 把声明层带到客户项目；旧项目缺目录的引擎降级为「未接线」并显式标注，MUST NOT 抛异常、MUST NOT 被读作通过；兼容期不得变成永久态（声明存在 ⇒ 内联值删除，不得双读）。

## Implementation Notes

- **三层的职责边界是判据，不是排版**：markdown 拥有「为什么 + 怎么读」，yaml 拥有「机器读得到的取值」，script 拥有「确定性执行与判决」；script MUST NOT 把 yaml 拥有的值再写成一份内联常量（FR-001、FR-007 (c)）。
- **判据纪律的自我适用**：本特性要求别人分层，自己的目标锚点 `better-harness.md` 也必须分层（A7）——五维表**不迁**（无引擎读取，继续是维度名 owner），七态枚举**必须迁**（三面重复且被机器消费）。这条示范是复核者最容易反驳、也最该先看的地方。
- **并发安全**：一条事实一个文件（两个并行分支新增两条事实 = 两个不同路径）；排除记录按理由分文件（至多三份，近静态），但其冲突面必须在双写者测试里被承认（新增单元只追加一行，不重排既有行）。
- **不重判既有门禁的判据**：`harness-triple-check.py` 只判声明完整性；重复字面量复用 `doc-consistency-check.py --faces duplicate` 的 `duplicate-fact`，不新建扫描器、不新增门禁阶段、不改既有退出码契约（FR-010、N5）。
- **非目标 N7 是边界样本，不是豁免口袋**：`validate-requirements.py` 的六个检查项标签集**不迁**，因为它没有判决型消费者、且迁出会迫使改写 081 的验收测试；该单元本身仍因 `Path` 取值域而 in-scope，故不写第二条单元级处置记录。
- **`lookup` 是消费入口**：`--action lookup --unit-id <unit>` 输出该单元的处置与事实摘要，让下游流程不必读原始声明，也让「派生索引即读即建」落到实处。

## Future Evolution Suggestions

- **把 `--action coverage` 接成 requirements／plan 阶段的 advisory**：解析既有 manifest 而不必读原始文件，让「新命令只写 markdown + 脚本」在提交前就被点名。
- **`execution-config.py` 的内联子集解析器并入共享读取入口**（N4 登记项）：需要一次独立的解析器重构，不在本特性内做。
- **声明层 schema 版本化**：`contract.yaml` 加入版本键后，客户项目的旧声明可以在升级时被显式判定为「需迁移」，而不是「未接线」。
- **把三批迁移的 `pending` 计数固化**：批 1／2／3 的 `pending` 计数随时间下降的曲线，是这条纪律是否还活着的唯一客观信号。
