# 通用绘图原则（所有图表通用）

> **适用范围**：本文件是**图表类型无关**的核心绘图原则，适用于类图/组件图/部署图/时序图/架构图等**所有** PlantUML 图表——不只大图。大图特有的美化技术栈见 [large-diagram-playbook.md](large-diagram-playbook.md)。
> **说明**：以下均为抽象原则；文中代码为**通用示意**（用占位名如「服务 A / 主机节点 / 子系统」），不针对任何具体系统——套用时按你的领域替换。

---

## 四步执行顺序（先「对」与「达意」，再「好看」）

任何一张图，按此顺序推进，前两步定「画什么、如何达意」，后两步定「画得好看」：

1. **UML 语义正确性** — 选对图类型、用对元素种类与关系类型、补齐构造型/接口（本文 §1）。
2. **视觉语义正确性** — 位置/数量/颜色/文字量本身即在传达信息，按人类第一眼理解规划（本文 §2）。
3. **基本布局与结构** — 分组、分层/分带、主次结构成形。
4. **对齐 · 着色 · 精简文字与线条** — 收尾美化（大图见 playbook 五步技术栈）。

> **纯绘图技巧有天花板**：当反复调布局/连线仍无实质提升，瓶颈通常在**建模（步骤1）或达意（步骤2）**，而非美化。务必先把 1、2 做对。

---

## §1 UML 语义先行（步骤 1）

绘图前先做语义分析（见 [howto/00-semantic-analysis.md](../howto/00-semantic-analysis.md)），确保 UML 定义层面最优：

1. **选对图类型**（[howto/01-choose-diagram-type.md](../howto/01-choose-diagram-type.md)）：逻辑结构/依赖→类图/组件图；物理运行时拓扑→部署图；交互时序→时序图；等等。选错类型，后续全歪。
2. **用对元素种类**（最常见错误）：不要一律 `rectangle`/`component`。按类型用其原生元素——部署图用 `node`/`artifact`/`database`/`cloud`；组件图用 `component`/`interface`/`package`；类图用 `class`/`interface`/`enum`……**元素种类本身就是语义**，混用即丢失语义、也让引擎无法正确布局。
3. **区分关系类型**：不要所有边都用同一种线。按语义选——实线关联/通信路径、虚线依赖/控制信号、`«deploy»`/`«manifest»`/`«include»` 等构造型依赖、泛化/实现/聚合/组合各有记号。
4. **构造型与多重性**：用 `«stereotype»` 表达种类/角色/部署方式，用多重性（`1..*`、`«×N»`）表达数量关系，让模型自解释。
5. **补齐缺失构造**：为对外契约加 `interface` 棒棒糖 `()` 与端口——只加提升保真度且不增杂乱的部分。

---

## §2 视觉语义（人类视角，步骤 2）

UML 语义保证「正确」，读者的**第一眼理解**还依赖**视觉语义**——位置、数量、颜色、文字量本身在传达信息。UML 正确后、动手绘图前，先按人类视角规划：

1. **角色即位置**：按元素在系统中的角色决定空间位置，而非任由引擎摆放。中心/枢纽放**中心偏上**、从属/边缘沿**边/底部依次**；入口在一侧、汇聚在另一侧（Hub/Edge/Entry/Sink）。
2. **一对多（1:N）关系的表达**：当「一类 vs 另一类」的数量关系重要时（如 1 主控 : N 从属实例、1 网关 : N 后端），要让 1:N 被看见——但**表达法有讲究**：
   - **「一」**：详绘为**单个具体元素**（完整内部结构），作为该类的代表。
   - **「多」**：**不要画 N 份同级副本**。多个兄弟盒子会打乱对齐、撑乱结构、无谓增宽画布。改用**单一代表元素 + 多重性标注**表达「多」，手段按强弱：
     1. `collections`（原生**堆叠多框形**，UML 惯用"多实例"字形）——注意：在**部署图**中 `collections` **无法嵌套子元素**，只适合无内部结构的"多"。
     2. **堆叠阴影 motif**：给单个元素加 `Shadowing`（局部 `<style>` 类）制造"一叠 N 个"的观感，且能保留内部详绘——需要展示内部结构时的首选。
     3. **`«×N»` / "×N" 标签 + legend 一行**说明（"N 个同构对等，图示其一"）——最轻量。
   - **判据**：读者应看出"这是 N 个同构实例"，而画布上只有**一个**（堆叠/标注的）盒子——不因 N 而增加对齐负担。这与 [large-diagram-playbook.md](large-diagram-playbook.md) §1 的「×N 折叠」同源：折叠是呈现压缩、不是信息删除。
3. **关联即同色**：同一逻辑子系统用**同一色相族**（深浅随嵌套层级变化），让读者**前注意（pre-attentive）**地把相关元素归为一组。语义关键边用深色粗线，确保在色块上仍醒目。**色相承载语义，而非装饰。**
4. **分组即框选（容器分组）**：同类/同组元素除同色外，再用一个**共同的框架元素**框选，形成色彩之外的第二重分组信号（容器边界是比颜色更强的分组线索，尤其利于大图分区）。两档用法：
   - **宏观逻辑分区**用**可见命名框**——把一个逻辑子系统装进具名 `frame`（如 `frame "子系统 A"`），让分区一眼分明。
   - **同类细分组**用**不可见框**——透明边/背景的 frame（`<<invis>>` + `<style> .invis { LineColor transparent; BackGroundColor transparent; FontColor transparent; LineThickness 0 }`），把「多个对等副本」「一群同类外部元素」等无需标题的同类项**框选对齐但不增可见盒子/连线**。这是「同类共用一个副元素框选，副元素可不可见」的落地。
   - 注意：分组框是**容器**（与浮动 `note` 不同，不会被引擎甩到页边），但仍是嵌套层级——勿过度嵌套撑大画布；分区应服务于「角色即位置」（如枢纽框居上、从属框在下）。
5. **文字即负担**：密集文字既拥挤、又在渲染不佳时给读者压力。能用图元/形状/颜色/图标传达的，就不用文字——见 §3。

## §3 元素标签最小化规则（去重优先）

**图元的文字标签只承载「最小可识别身份」**——认出「这是什么」所需的最短名称（含必要区分词，如带限定的「订单查询服务」而非泛化的「服务」）。一切说明性/限定性信息（职责、协议、端口、部署方式、组成、约束）都不进标签，按优先级消解：

- **① 去重 → 直接删除**：若信息已由相邻图元表达——`interface` 棒棒糖（协议/端口）、`«stereotype»`（种类/部署）、嵌套容器（归属）、legend（通道/术语语义）——则从标签删除。**零成本，且消除冗余。**
  - 例：`component "服务 A\n<协议·鉴权等描述>"` → `component "服务 A"`（协议已由下方的 `interface` 承载）。
- **② 无处可依 → 外移**：确需保留又不在别处的描述，移入 **legend（单一细节仓，首选）**；仅当描述为某元素独有且 legend 不合适时，才用该元素的**一个** `note`（慎用——嵌套簇/大图中浮动 note 易被引擎甩到边缘、引长连线）。
  - 例：`node "主机节点 «device»\n<运行时组成等描述>"` → `node "主机节点" «device»` +（若为同类共有）legend 一行统一说明。
- **判据**：读者用「短名(图元) + 形状/颜色(种类) + 接口(契约) + stereotype(部署) + legend(语义)」应能**重建全部信息**，而画布上每个盒子只剩一个短名。
- **可选增强**：用 OpenIconic `<&icon>` 给短名加一个种类图标（`<&cog>`服务、`<&hard-drive>`存储、`<&box>`制品、`<&person>`actor…），以符号代替/强化文字——注意这是**冗余编码**，在小尺寸下收益有限且略增宽度，按需采用。

---

> 大图（节点多、渲染尺寸大）在以上通用原则之上，还需要「×N 折叠 / 弱化管线突出语义色 / 字号层级 / 正交路由+隐藏边控宽高比 / legend 细节仓」等专项技术，以及连线治理、隐藏脚手架的能与不能——详见 [large-diagram-playbook.md](large-diagram-playbook.md)。
