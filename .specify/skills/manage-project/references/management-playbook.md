# 项目管理操作手册 (Management Playbook)

`manage-project` 技能的细则参考：管理文档结构、更新模式规则、分解深度、估计默认与假设标注、状态推断、里程碑跟踪、图集拆分、三图一致性清单、范围与粒度控制、管理循环与概念映射、集成扩展点。工作流主框架见 [../SKILL.md](../SKILL.md)；图表语法与渲染以 draw-plantuml 技能的操作指南为准。

## 1. 管理文档结构（单一事实源）

默认位置 `.specify/project/project.md`，章节骨架固定如下（初始化模式按此创建；更新模式不得打乱既有章节顺序）：

````markdown
# <项目名> 项目管理文档

## 项目背景
<背景、目标、干系人、范围 —— 纯 Markdown 文本，人工可自由补充>

## 项目里程碑
<「里程碑 | 锚定 | 状态」跟踪表格>

```plantuml
@startgantt
' 仅含里程碑条目的紧凑视图：[名称] happens <日期> / happens at [工作项]'s end
@endgantt
```

## 主要工作

```plantuml
@startwbs
' 单一分解树：阶段 → 任务 →（可选）子任务
@endwbs
```

## 进度追踪

```plantuml
@startgantt
' 三态进度 + 百分比 + 当前日期参照线 + 里程碑菱形 + 依赖
@endgantt
```

## 迭代记录

<!-- 敏捷循环日志：每迭代一行，登记五环节锚点与结论；来源(source)当前恒为 local -->

| 迭代 | 周期 | 需求 | 特性 | 任务/负责人 | 测试用例 | 评估 |
|------|------|------|------|-------------|----------|------|
| 1 | <起> ~ <止> | <锚点> | <Feature ID/锚点> | <锚点；负责人> | <锚点/结果> | <结论；下一轮输入> |

## 元信息
- 最后更新：YYYY-MM-DD
- 本次变更摘要：<一句话>
- 估计假设：<逐条显式标注，无则写「无」>
````

- **图表即文本**：PlantUML 源码块是权威形态；若渲染了配图，图片放在同目录并以相对路径引用在源码块之后，源码块永不删除。
- **背景节归属**：`## 项目背景` 内的人工叙述属于用户；技能只在初始化时起草、在材料出现明显更新（目标/范围变更）时提议修订，不静默改写。

## 2. 更新模式规则（重复运行）

- **只增量，不重建**：定位到受影响的表格行 / 源码行，做最小 diff 修改（状态翻转、百分比刷新、新增/移除条目）；未变化的行保持逐字节稳定。
- **人工编辑优先**：用户手工调整过的命名、说明、排序视为权威；技能后续更新沿用该措辞，冲突时提问而非覆盖。
- **变更留痕**：每次运行刷新 `## 元信息`（最后更新日期 + 本次变更摘要一句话）；里程碑达成时更新跟踪表格状态列，不删除历史里程碑行。
- **迭代只追加**：`## 迭代记录` 每轮迭代新增一行；历史迭代行不改写（如需修正在评估列追加备注）。
- **结构漂移修复**：若文档缺失某固定章节，补齐该章节骨架，其余内容不动。

## 3. 工作分解深度规则

- **默认三级**：阶段（phase）→ 任务（task）→ 子任务（sub-task，可选）。至少覆盖 阶段 → 任务 两级。
- **叶子即工作包**：叶子节点是可分配、可估算的最小单位；粒度以"一句话能说清交付物"为准。
- **命名规范**：业务语言动词短语（如"完成镜像构建流水线"），不用内部代号；同一工作项在 WBS、甘特图、里程碑视图、叙述中**逐字一致**。
- **数量控制**：单图节点 ≤15 时一图呈现；超出按 §6 拆分图集。

## 4. 时间信息的估计默认与假设标注

材料缺少日期/工期时的处理顺序：

1. **有锚点用锚点**：git 标签、发布日期、规格创建日期、迭代周期都可作为锚点。
2. **相对排期**：只知先后顺序时，用相对依赖排期（B 在 A 结束后开始），不给绝对日期。
3. **必须估计时**：按同类任务的常规工期给默认值，并在管理文档 `## 元信息` 中**逐条显式标注**为估计假设（assumptions），格式：「假设：<工作项> 工期估计为 N 天（材料未提供）」。
4. **猜测会误导时**：转为最多一轮澄清提问（≤4 问），不静默落笔。

## 5. 进度状态推断与里程碑跟踪

| 材料信号 | 推断状态 | 备注 |
|----------|----------|------|
| 任务清单勾选完成 / 规格状态 Implemented / 已发布 | completed | 百分比 100 |
| 进行中分支、部分完成清单、规格状态 Planned/进行中 | in-progress | 必须给出百分比及依据 |
| 未启动、无痕迹 | not-started | 百分比 0 |

- 推断依据写入文档叙述或图注；无依据的状态不标注。
- **退化情形**：项目未开始（全部 not-started）或全部完成（全部 completed）时图表仍须正常渲染，叙述中显式说明整体状态。
- **当前日期参照**：项目进行期（同时存在 completed 与 not-started/in-progress）时，进度甘特图必须标出当前日期参照线。
- **里程碑跟踪表**：`## 项目里程碑` 节的表格列固定为「里程碑 | 锚定（日期或关联工作项） | 状态（achieved / pending / at-risk）」；表格行与里程碑视图中的 `happens` 条目一一对应、同名同锚定。at-risk 判定须有材料依据（如依赖项延期），无依据不标注。

## 6. 大项目图集拆分

- **触发**：WBS 节点 >15，或甘特条目 >20，或单图宽高比严重失衡。
- **结构**：1 张概览图（只到阶段层）+ 每阶段 1 张下钻子图；概览图标注「▶ 见 图N」交叉引用。每张子图是文档内独立的 PlantUML 源码块。
- **一致性**：图集内命名、配色、编号、字号跨图一致；每张子图自足（不读其他图也能看懂该阶段）。
- 拆分技术（方向、配色、图注外置）遵循 draw-plantuml 的图集与大图指南。

## 7. 三图一致性自检清单（落盘前必过）

- [ ] 每个带时间信息的 WBS 叶子工作项在进度甘特图中有且仅有一个同名条目
- [ ] 甘特图中没有 WBS 里不存在的孤儿条目
- [ ] 里程碑视图、里程碑跟踪表、进度甘特图三处里程碑同名、同锚定、同状态
- [ ] 里程碑视图的全部 `happens` 条目已逐条复制进进度甘特图（生成时保证，非事后修补）
- [ ] 进度甘特图的 `today` 以 `today is N days after start` 相对项目起点显式定位（不依赖渲染环境时钟）
- [ ] 三态（completed / in-progress / not-started）在图与叙述中口径一致
- [ ] 迭代记录最新行五个环节（需求/特性/任务/测试用例/评估）均有锚点或显式「无」
- [ ] 所有估计性时间/状态都已在 `## 元信息` 假设区显式标注
- [ ] 每个 PlantUML 源码块都通过 draw-plantuml 渲染校验

**标准渲染校验命令**（在管理文档所在目录执行；按源码块顺序命名，避免每次手写提取逻辑）：

```bash
python3 - <<'EOF'
import re, pathlib
text = pathlib.Path("project.md").read_text()
blocks = re.findall(r"```plantuml\n(.*?)```", text, re.S)
names = ["milestones", "wbs", "gantt"]  # 与文档中源码块顺序一致；图集拆分时按需扩展
for name, src in zip(names, blocks):
    pathlib.Path(f"{name}.puml").write_text(src)
    print(name, "->", len(src.splitlines()), "lines")
EOF
# 逐个渲染校验（render-plantuml.sh 路径以 draw-plantuml 技能安装位置为准）
for f in milestones wbs gantt; do <draw-plantuml>/scripts/render-plantuml.sh $f.puml . $f; done
```

## 8. 管理范围与受众粒度

- **周期限定**：用户给出管理周期（如"本季度"）时，甘特时间轴与叙述只覆盖该范围；范围外工作省略，或在图中以弱化样式呈现并注明。
- **粒度限定**：高管受众默认只展开到阶段层（任务层以汇总行表示）；技术受众展开到任务/子任务层。
- 无论粒度如何，阶段级结构必须完整呈现，三图一致性清单仍然全量适用。

## 9. 文档落盘检查单

- [ ] 四要素章节齐全：项目背景 / 项目里程碑 / 主要工作 / 进度追踪
- [ ] `## 迭代记录` 节存在且最新迭代行五环节完整（锚点或显式「无」）
- [ ] 每图配一段简要说明（图讲了什么、读者应关注什么）
- [ ] 元信息齐全：最后更新日期、本次变更摘要、估计假设（assumptions）
- [ ] PlantUML 源码嵌入文档且通过渲染校验；配图（若有）相对路径引用、源码保留
- [ ] 默认输出位置 `.specify/project/`（或用户指定位置），目录内自包含

## 10. 管理循环与概念映射

- **循环定义**：需求 (Requirement) → 特性 (Feature) → 任务 (Task，含人力分配) → 测试用例 (Testcase) → 评估 (Evaluation) → 下一轮迭代。一轮迭代 = 该链路完整走一遍；短迭代允许环节从简，但**评估环节不可省略**——没有评估结论的迭代无法驱动下一轮。
- **锚点而非副本**：每个环节在迭代记录中只登记锚点（文件路径、Feature ID、测试结果摘要）与一行结论；禁止把 requirements/tasks/用例内容复制进管理文档（双源漂移）。spec-kit 项目映射表见 SKILL.md「管理循环」节；非 spec-kit 项目用等价材料回退。
- **人力分配**：负责人登记在迭代记录「任务/负责人」列，并同步到工作项记录（Step 2）与甘特任务行（若适合展示）；材料无负责人信息时留空，不臆造分配。
- **测试用例**：登记用例来源锚点与通过状态（如 `tests/contract/xxx.py 27 passed`、`verification.md SC-001..004 pass`）；用例明细留在源工件中维护。
- **评估**：结论一行内可读（如「评审 0P0/3P1；反馈 2 条入库；下一轮聚焦 X」）；改进项显式标注为下一轮迭代的需求输入。
- **迭代与图表联动**：每轮迭代结束时以更新模式刷新四要素图表（新任务入 WBS/甘特、达成里程碑翻状态），保证"迭代记录说的"与"图表画的"一致。

## 11. 集成扩展点（预留，不实现）

- **来源约定**：迭代记录每个环节隐含一个来源 (source)，当前恒为 `local`（本地工件锚点）。文档结构、四要素章节与图表约定对来源不敏感。
- **未来扩展方向**（仅当用户明确要求时启动）：
  - 需求/特性/任务 ↔ 外部项目管理系统（如 Jira：登记 issue key 作为环节锚点）；
  - 测试用例/评估 ↔ CI/CD 流水线（登记流水线运行 ID 与结果）；
  - 任务/进度 ↔ 代码托管平台（登记 PR/commit 作为完成证据）。
- **接入方式**：替换对应环节的来源适配、在迭代记录中登记外部 ID，其余一切不变——不改文档骨架、不改图表约定、不引入新章节。
- **红线**：在用户明确要求接入之前，本技能不得引入任何外部系统调用、凭据存储或自动同步逻辑。
