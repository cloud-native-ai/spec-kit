# 经典案例：访谈驱动的全站页面走查与 OpenAPI 契约重构

> 通用流程已抽象为框架文档 `shared/workflow/interview-walkthrough.md`（随框架安装到目标项目）；本文件保留该案例的完整细节，仅供本项目内部参考，不随框架分发。

> **案例类型**：人机协作工程实践 / 访谈式需求走查
> **项目**：xuanji-ui（璇玑智能运维平台前端，41 页 / 9 大业务域）+ xuanji-api（OpenAPI 契约子模块）
> **周期**：2026-07-15 ～ 2026-07-21（7 天，含收尾合入）
> **核心记录来源**：`xuanji-ui/docs/ui/_redesign-log.md`（走查总账）、`xuanji-ui/submodule-edits.md`（子模块台账）、各页 `docs/ui/**/*.md`（页面文档）

---

## 一、案例背景

xuanji-ui 前端存在大量 mock 数据、手写 httpClient 调用与「页面 ↔ 后端契约」脱节的问题。本次实践的目标：

1. 以「与前端页面同步」为准则，**重构 `src/services` 全部函数与数据结构**；
2. 建立目标架构：**页面（src/pages）→ Service 层（src/services）→ OpenAPI 生成客户端（openapi-fetch）→ 后台服务**；
3. OpenAPI 有缺口时同步补契约，使契约成为唯一事实源。

难点在于：41 个页面的重构需求分散在用户（领域专家）脑中，没有现成的需求文档。因此采用了 **「逐页访谈 + 即时落库 + 即时实现」** 的工作形式——AI 打开真实页面截图提问，用户逐页给出决策，AI 当场实现并双门禁验证。

## 二、访谈流程与形式

### 2.1 总体流程

```
Phase 0（一次性基建）
  └─ 更新 api 子模块 → build.sh 生成 openapi-fetch 客户端 → tsconfig/CRACO 别名接入 → 编译门禁

每页三阶段循环（41 页逐页）
  ├─ 阶段 1【访谈】 浏览器打开真实页面 + 截图/快照
  │     └─ 开放式提问：「这个页面需要做哪些修改？」
  │     └─ 用户口述决策 → 覆写页面文档的「重构需求」+「交互元素定义」
  ├─ 阶段 2【实现】 Service 封装（函数 + models）对接生成客户端
  │     └─ 补全「交互元素 → Service → 端点」映射表 + frontmatter services/apis
  │     └─ 同步改页面/hooks 调用点 → tsc + dev 双门禁
  └─ 阶段 3【补契约】 OpenAPI 有缺口 → git-submodule-edit 在 api 子模块补
        paths/schemas（原子 commit + 台账记账）→ 重生成客户端 → 回阶段 2

收尾（走查完成后）
  ├─ 全域兜底扫描：手写 httpClient 残留分类（A 类就绪可迁移 / B 类路径错位）
  ├─ 跨页面/框架级优化意见汇总
  └─ 子模块 11 个原子 commit push → MR 合入 master → 父仓 gitlink bump + LANDED 记账
```

### 2.2 访谈形式要点

| 要素 | 做法 |
|------|------|
| **访谈粒度** | 一次只谈**当前打开的一个页面**，杜绝跨页发散 |
| **提问方式** | 开放式主问题（"这个页面需要做哪些修改？"）+ 针对导航结构/具体控件的跟进追问 |
| **现场感** | 用 browser-utils 打开真实运行页面（HashRouter URL），配合截图/快照，让用户"看着页面说需求"而非凭记忆描述 |
| **决策记录** | 每条用户决策以「用户决策：……」显式落库到该页 md，**覆写**旧的「重构需求」节，仅保留本轮问答 |
| **进度可视** | 总账表格（41 行）：状态图例 ⬜/🔄/✅/⏭ + 走查时间 + 意见摘要，每页完成即回写 |
| **即谈即做** | 访谈结论不积压：当场进入阶段 2/3 实现，门禁通过后才标 ✅ |
| **默认约定先行** | 走查约定（目标架构、URL 规则、工具、落库策略）在文档头部一次性声明，减少每页重复沟通 |

### 2.3 用户决策的典型形态（访谈产出示例）

- **保持现状**：Agent 页「保留当前表格形态，待后端真实数据就绪再重构」（标 To Do）；
- **立即接入**：Sandbox 页「现在就接真实接口」；
- **补契约再接入**：交互分析页「现在补 OpenAPI 并接入」；
- **裁剪**：Pod/Sandbox 查询页「先删除，后需要再加回」；
- **重新设计**：发布件管理域「参考 DevOps 设计图整体重新设计 + 改名 + 路由迁移」；
- **对齐数据基准**：资源管理域「MySQL 基础表 asiops_* 严格对齐，去臆造字段」；
- **附件输入**：值班管理页用户直接给出参考设计（阿里云 Apsara 排班管理）。

> 这组形态说明开放式提问能自然覆盖「保持 / 接入 / 补契约 / 删除 / 重设计 / 对齐基准」全部决策空间，AI 无需预设选项。

## 三、成果数据

- **41/41 页**走查完成（首页 1 + 域概览 8 + 子页 32），零遗漏；
- **8 大业务域 Service 全量迁移**到 openapi-fetch 生成客户端；
- **11 个原子 OpenAPI commit**（新增约 20+ 端点、30+ schema）合入 xuanji-api master（merge 4b9e2007 → 主干 91c51746）；
- 每页均通过 **tsc --noEmit + dev 编译双门禁**；
- 沉淀三层文档资产：总账 `_redesign-log.md`、41 份页面 md（frontmatter 含 services/apis 映射）、子模块台账 `submodule-edits.md`；
- 附带产出：路径错位清单（6 处）、死代码清理建议、框架级优化意见（契约驱动 / 数据基准 / 子模块治理）。

## 四、遇到的问题

| # | 问题 | 影响 | 处置 |
|---|------|------|------|
| 1 | **外部进程周期性把 api 子模块 checkout 回 origin/master**，导致生成的 api-types 被重置 | 发生 2 次，生成客户端类型丢失、编译报错，需现场排障 | 切回 pd-openapi-supplements 分支 + 重生成恢复；根因未消除，列入待办 |
| 2 | **手写 httpClient 与契约路径错位**（如 `/Common/api-cost`、`/ProblemDiagnosis/diagnose` 等 6 处契约中不存在的端点） | 页面调用注定 404，历史欠账隐蔽 | 兜底扫描统一暴露，分 A（就绪可迁移）/B（待后端确认或连页面清理）两类给出建议，不在本轮硬修 |
| 3 | **契约与真实数据基准脱节**：早期 schema 存在臆造字段（product.status、node.role 等） | 前端列展示与真实库表不符 | 访谈中用户拍板「以 MySQL 基础表为准」，Stage 3 重塑 3 个 schema 并同步页面列 |
| 4 | **子模块多分支演进管理复杂**：走查中途分支从 info-query-search-intent 更名为 pd-openapi-supplements 累积分支；父仓 gitlink 长期 pending | 台账出现多条 "(pending，父仓 gitlink 暂 staged 未提交)"，锁步关系需人工修正备注 | 收尾时一次性 push + MR 合入 + gitlink 单指针线性 bump 至 91c51746，LANDED 记账闭环 |
| 5 | **部分页面依赖后端未就绪**（如 Agent 页真实数据、告警大盘真实链接） | 无法当场端到端验证 | 显式标记 To Do 并落库，Service/契约先行就绪，避免访谈节奏被阻塞 |
| 6 | **故障检测域一次性重设计范围大**（事件模型 + 工作流规则 + 四页联动） | 单页访谈粒度被突破，只能做编译级验证 | 用户决策「一次性设计保统一，仅编译验证」，明确降级验证标准并记录 |

## 五、可优化的地方

### 流程层面

1. **契约缺口预扫描前置**：路径错位是收尾兜底扫描才集中暴露的；若在 Phase 0 就做一次「手写调用 vs 契约端点」diff，访谈时可携带缺口清单逐页确认，减少返工。
2. **验证标准分级显式化**：目前「双门禁」只保证编译级正确；对已接真实接口的页面，可增加 Prism/mock 契约重放或最小 E2E，形成「编译 / 契约 / 端到端」三级验证标签（本案例中 releasedAt nullable 问题正是 Prism 重放发现的，值得推广为常规动作）。
3. **访谈决策模板化**：用户决策形态已收敛为 6 类（保持/接入/补契约/删除/重设计/对齐基准），可做成决策卡片供访谈时快速勾选 + 补充说明，降低记录歧义。
4. **大域重设计单独立项**：像故障检测这种跨 4 页的一次性重设计，应从逐页走查流程中拆出，走独立的 spec → plan → implement 流程，避免走查粒度约定被突破。

### 工程层面

5. **消除子模块外部干扰的根因**：外部进程 checkout 子模块到 master 的问题只做了恢复未做根治；应排查定时任务/IDE 插件来源，或在生成产物中加校验哨兵（如生成头注释校验分支）快速发现漂移。
6. **gitlink 锁步自动化**：台账多次出现「Parent Commit 修正」备注，说明 record-bump 脚本运行时机与实际 bump 提交不同步；建议把「gitlink bump + 台账行」封装为同一原子提交的脚本。
7. **原子 commit 及早推送**：11 个 commit 在本地累积 4 天才 push + MR，窗口内被外部干扰击中 2 次；改为「每 2-3 个 commit 即 push 远端分支」可缩小风险敞口。
8. **死代码同步清理**：访谈决定下线的页面（实例运维/云资源等）其 service/hooks 未即时清理，收尾才提建议；可在「删除」类决策的 DoD 中直接包含调用链清理。

### 文档层面

9. **截图与文档同步刷新**：页面重构后部分 `_screenshots` 未同步更新，文档截图可能滞后于实现；可在每页 ✅ 前加「截图刷新」检查项。
10. **意见摘要结构化**：总账「意见摘要」列信息密度极高但为自由文本；可拆为「决策类型 / 契约变更 / 验证级别」三个子列，便于后续统计与检索。

## 六、可复用的经验（案例结论）

1. **「看着真实页面访谈」是低成本高保真的需求获取方式**——比让用户凭空写需求文档快得多，且决策直接绑定具体控件。
2. **单页粒度 + 开放式提问 + 覆写式落库**三者组合，保证了 41 页走查不发散、不积压、可追溯。
3. **访谈-实现-验证同回路**（阶段 1→2→3→回 2）让每条口头决策在当天变成可编译代码，用户信任感与决策质量随之提升。
4. **契约唯一事实源 + 原子 commit + 台账记账**使跨仓库（父仓 + 子模块）协作全程可审计，收尾合入一次成功。
5. **兜底扫描作为收尾必选动作**，能把访谈覆盖不到的历史欠账（路径错位、死代码）显式化为下一迭代输入，而不是默默遗留。
